# Muntin architecture

Muntin owns the application model. Transports adapt to `App.handle(Request) -> Response`; they do not define application semantics.

This file is the current state: the thesis, the invariants, the [current architecture](#current-architecture) and a [revisit index](#revisit-index). Why each part is as it is (reasons, rejected candidates, measurements, revisit conditions) is in the [decision records](history/architecture-decisions.md), one record per decision. Milestone tags below, such as (M3-015), name the item; the links name a specific record. Public API and user-visible semantics: `docs/DX.md`. Product scope: `docs/SPEC.md`.

## Architectural thesis

Muntin's leverage should come from application-level developer experience and compile-time/type-system guarantees. Networking machinery is replaceable infrastructure behind `App.handle`; where that ends is in [Flare policy](#flare-policy).

The architectural fulcrum is the boundary between the **Muntin-owned application model** and **transport/backend adapters**.

```text
Application code
      |
      v
+--------------------------------+
| Muntin public API              |
| App / Request / Response       |
| routes / handlers              |
| extraction / errors (M2)       |
| state / headers / JSON (M3)    |
| middleware functions (M3)      |
+---------------+----------------+
                |
         narrow backend seam
                |
       +--------+---------+
       |                  |
       v                  v
 in-memory            Flare adapter
 reference            (M1+)
 backend                   |
                           v
                 HTTP/TLS/QUIC/reactor
```

## Invariants

### A1. Muntin owns the public application API

Public application code imports Muntin-owned concepts. Third-party transport-library types must not appear in normal handler signatures, routing APIs, middleware contracts, application-state contracts, or canonical examples.

### A2. Dependency direction points inward

Muntin core/application modules do not import Flare. Backend adapters depend on Muntin's backend/application contract.

```text
muntin core  <-  in-memory backend
muntin core  <-  flare adapter
```

Never invert this relationship merely because an adapter has a convenient abstraction.

### A3. Replaceability is executable

Transport independence is not a diagram claim. An in-memory/reference path exercises the same application-dispatch seam as transport adapters.

A refactor that makes the in-memory path bypass real routing/dispatch is an architecture regression even if tests stay green.

### A4. The backend seam stays narrow

Do not invent a universal networking abstraction. The seam should expose only what Muntin needs to accept an application request, dispatch it, and produce an application response/lifecycle result.

Do not pre-abstract executor, reactor, poller, wakeup, TLS session, QUIC stream, socket option, or backend-specific cancellation machinery into public contracts.

### A5. Protocol mechanics stay outside core

Wire parsing, sockets, TLS, HTTP/2 flow control, HTTP/3, QUIC, platform event loops, connection pools, and protocol negotiation belong to networking backends/runtimes.

### A6. Async evolution must remain survivable

Do not publish a framework-specific executor/future/task model just to fill a temporary language/runtime gap. The Muntin application model should be able to adopt future Mojo async/runtime primitives with minimal application-level breakage.

### A7. Evidence before abstraction

Add an abstraction when a current requirement, two real implementations, or a strong external constraint justifies it. A hypothetical future backend is not enough.

The in-memory backend exists to prove the seam and provide deterministic tests, not to force every networking feature into a lowest-common-denominator interface.

### A8. DX is an architectural input

`docs/DX.md` is not decoration after implementation. Public API examples constrain internal design. If internal convenience would make ordinary application code materially more verbose, reconsider the internal abstraction first.

If the desired API is impossible in the current Mojo toolchain, preserve the intended semantic property and document the proven language limitation.

## Logical components

The exact package layout must follow the supported stable Mojo toolchain, but logical dependencies should resemble:

```text
muntin/
  application core
  request/response model
  routing/handler adaptation
  backend contract

muntin/testing/
  in-memory backend / TestClient

muntin/adapters/flare/
  Flare conversion and server integration
```

Filesystem names may change. Dependency direction may not.

### Backend seam

- The only seam is `App.handle`, in two overloads that answer alike: `handle(self, request: Request) -> Response`, which borrows, and `handle(self, var request: Request) -> Response`, which takes the request (M3-064, decided by [M3-063](history/architecture-decisions.md#request-context-decision-m3-063); which one a call picks: `docs/DX.md` section 11). A backend builds a Muntin `Request`, calls `handle`, and converts the `Response` back; `TestClient` and the Flare adapter hand their request over. Middleware runs inside `handle` (request handling, below), so every backend runs it without knowing of it. There is no backend trait until a second network backend exists (A7).
- `TestClient[origin: Origin[mut=False]]` holds a `Pointer[App, origin]`: it borrows the `App` immutably, so `TestClient(app)` copies nothing, and `App.handle` takes `self` read-only. `TestClient.get(target)`, `.head(target)`, `.post(target, body)`, `.put(target, body)`, `.patch(target, body)` and `.delete(target)` (`head` and `delete` with an empty body; `body` text, or a `List[UInt8]` moved in, M3-040) send no header fields; `headers=` (keyword-only, defaulted, moved in) sends the given fields unchanged (M3-011). The client builds `Request(method, target, body, headers^)` and calls `App.handle`, nothing else.
- `Request(method, target, body, headers^)` (body and headers defaulted) splits `target` at its first `?` into `path` (all that routes match) and `query` (raw, undecoded, `""` when absent). Both backends pass the raw target, so the split is the same for both, and a typed route's value is decoded once, by Muntin (request handling, below); a backend that decoded the target first would decode values twice. `Request` and `Response` own their data: `String` method, target parts and fields, and the body as `List[UInt8]` (M3-040, decided by [M3-040](history/architecture-decisions.md#binary-request-and-response-bodies-decision-m3-040)), the bytes the backend received or will send, its one representation; `text()` reads it as strict UTF-8 and raises otherwise. A backend copies body bytes both ways unchanged; no backend type or buffer lifetime reaches application code.
- `HEAD` (M3-027, decided by [M3-026](history/architecture-decisions.md#head-decision-m3-026)): `App.handle` answers a `HEAD` request through the matching `GET` route, body included, and never removes a body: a typed handler receives the `GET`'s arguments, a raw handler the `HEAD` request (DX asks it to answer as for the `GET`). Keeping the content off the wire is each network backend's obligation: it sends the response's status and fields with no content, and declares a `Content-Length` equal to the byte length of the body it would have sent for the `GET` (`App.handle`'s, or its own answer where it answers without `App.handle`), none for a status that never carries content (1xx, 204, 205, 304). Here the in-memory response (with its body) and the wire response (without) differ. `TestClient.head` is an in-memory caller of `App.handle` with no wire, not a network backend: it returns that in-memory response unchanged, body and fields, and removes no body, declares no `Content-Length` and applies no status rule ([TestClient HEAD decision (M3-036)](history/architecture-decisions.md#testclient-head-decision-m3-036)).
- `scripts/check_boundaries.sh` fails if `src/muntin` imports or mentions Flare or socket modules (A2). `scripts/check_unsafe.sh` confines unsafe operations to `_handler_storage.mojo` and `rebind_var` to one helper in `app.mojo` (below).
- One `App` is never called concurrently: `server.serve(app)` serves it on one reactor thread, and `server.serve[make](workers=n)` ([M3-049](history/architecture-decisions.md#multi-worker-serving-decision-m3-049)) gives each worker thread its own `App`, built by `make` on that thread, with its own `State` values; `make` is a `thin` function, so it captures nothing a second worker could reach, and Mojo 1.1.0 has no module-level `var`. Flare's own multi-worker `serve` is not used: it needs a `Copyable` handler, `App` is move-only and `Server`'s handler is not `Copyable`. That bounds JSON parse memory (one parse at a time per `App`, so one per worker), and since each `App` also stays on the thread that serves it (this adapter's, not the seam's: "Flare policy"), keeps interior mutability in a `State` value single-threaded; a concurrent backend, one that calls an `App` from several threads in turn, a `Copyable` `App` or a `make` that can capture reopens them (revisit index). Two workers share a value only through what Muntin does not check: an unsafe pointer from an address, `_get_global` or a C call in `make`. The cost is head-of-line blocking ([M3-046](history/architecture-decisions.md#head-of-line-blocking-decision-m3-046)): Flare v0.12.0 runs each handler inline on its reactor, so a running handler holds every connection and stream of the process, and a long one makes Flare's idle timer close waiting connections with their requests unread (`docs/DX.md` section 1). With workers, a connection opened while one worker's handler runs is accepted and served by another (the held worker does not poll), but the connections the held worker already has, every stream of one h2c connection among them, still wait; `adapters/flare/test_server.mojo` pins both, for `Server`, its workers and Flare alone.

### Registration surface

`App.get`, `App.post`, `App.put`, `App.patch` and `App.delete` have eight overloads each: one per request-slot arity (0 to 3), stateless and stateful (M3-015; slot arity 3: [M3-022](history/architecture-decisions.md#several-route-values-decision-m3-022)). `put` and `patch` are copies of `post` and take its shapes under its rules, `delete` a copy of `get` ([M3-020](history/architecture-decisions.md#http-methods-decision-m3-020)): `_rule` sends `GET` and `DELETE` to `_get_rule` and `POST`, `PUT` and `PATCH` to `_post_rule`, which hands a bodyless shape (every slot absent, a route value or `Headers`; `_bodyless`) to `_get_rule` ([M3-048](history/architecture-decisions.md#bodyless-typed-post-put-and-patch-handlers-decision-m3-048)), and a message that names a method names the registration's. A request slot is a handler parameter that comes from the request. The stateful family takes a fixed leading `State[S]`, which is not a slot, and the state as the registration's second argument, so the argument count separates the families and no two overloads of a method accept the same handler. Every slot is a generic `var A` whose kind is decided at compile time from its type alone: an `Int` or `String` route value or an `Optional` of either, bare or in a `Param` (which has its value type's kind, M3-050), a body (a `FromBody` or a `FromBytes`, possibly move-only, or a `WithHeaders[B2]` carrier), the raw `Request`, the request `Headers` (on `get` and `delete`, and on a bodyless `post`, `put` or `patch` handler), or, rejected by the rules, a `State` or a type of no kind. Every handler type is `thin raises E` with `E: Deinitable` inferred (`Never` for a non-raising handler, `Error` for `raises`, the application's `T` for `raises T`). The result `R` is generic and accepted only through `where (R == String or R == StaticString or conforms_to(R, ToResponse))` on every overload, which the compiler checks by identity at the call site.

| Method | Stateless (`app.m[route](handler)`) | Stateful (`app.m[route](handler, state)`) | Results |
|---|---|---|---|
| `get`, `delete` | `def()`, `def(V)`, `def(Headers)`, `def(V, Headers)`, `def(V, V)`, `def(V, V, Headers)` | `def(State[S])`, `def(State[S], V)`, `def(State[S], Headers)`, `def(State[S], V, Headers)`, `def(State[S], V, V)`, `def(State[S], V, V, Headers)` | `String`, `StaticString`, or `R: ToResponse` |
| `post`, `put`, `patch` | `def(B)`, `def(V, B)`, `def(V, V, B)` | `def(State[S], B)`, `def(State[S], V, B)`, `def(State[S], V, V, B)` | same |
| `get`, `delete` (and a bodyless `post`, `put`, `patch`); `post`, `put`, `patch` | `def(P)`, `def(P, Headers)`; `def(P, B)` | `def(State[S], P)`, `def(State[S], P, Headers)`; `def(State[S], P, B)` | same |
| `get`, `post`, `put`, `patch`, `delete` | raw `def(Request)` | raw `def(State[S], Request)` | `Response` only |

`V` is a route value: an `Int` or a `String` (M3-018), an `Optional[Int]` or `Optional[String]` (M3-025), which binds a query placeholder only, or an application type conforming to `FromRouteValue` (M3-055), bare or as a `Param[name, T]` around one of them (M3-050); two in one shape may be of any of these types (M3-022), both bare or both `Param`s. `P` is a route-value record, a struct conforming to `RouteValues` that carries every route value of its route as fields (M3-062, below); it takes the shapes of one bare `V` and no `V` beside it. `B` is a body: a `FromBody` text conversion, a `FromBytes` bytes conversion (M3-041) or a `WithHeaders[B2]` carrier around a `FromBody` or a `FromBytes` (M3-042).

Within the existing slot arities (0 to 3), a new shape is a slot kind, or a rule in `_get_rule` or `_post_rule` with its message in `_check`, not a new overload; raising the maximum slot arity adds overloads to every method ("Arity budget", below). Because `_post_rule` hands every bodyless shape to `_get_rule`, a new slot kind also says whether it is bodyless, and a change to `get`'s rules or messages changes bodyless `post`, `put` and `patch` handlers too.

- **Route literals** are compile-time strings checked at the registration call: a leading `/`, static or `{name}` segments, an optional query part of `{key}` items joined by `&` (keys visible ASCII, none of `{}=&?#`). The placeholder count must equal the handler's route-value count (zero, one or two, or a route-value record's field count); raw routes declare none. An optional value binds a `{key}` item ([Optional query values decision (M3-024)](history/architecture-decisions.md#optional-query-values-decision-m3-024)): one alone needs exactly one query placeholder and no path placeholder, and of two values, one at a position below the literal's path count, where it would bind a path segment, is rejected. A literal's query keys must differ (`route declares a query parameter twice`, reported after every other rule); path names are not compared, so `/x/{a}/{a}` registers. Binding is positional (the path placeholders left to right, then the query placeholders left to right, then the body or the `Headers`). Mojo 1.1.0 cannot reflect handler parameter names, so a name is compared only as written in a `Param[name, T]` ([Named route values decision (M3-050)](history/architecture-decisions.md#named-route-values-decision-m3-050)): a `Param`'s name must equal the placeholder at its position (`_placeholder_name`, `_misnamed`), so two `Param`s whose names are in the other order than the literal's are a compile error, and of two route values both or neither are `Param`s; `Param` is opt-in, and two bare values of one type declared in the other order still receive each other's values (the accepted cost of M3-022). The variable's own name is never compared: `pid: Param["uid", Int]` binds `{uid}`, and a lone bare value is not checked (`test_variable_names_are_not_compared` in `tests/test_named_values.mojo`). `_slot` converts a `Param`'s `T` as a bare slot and wraps it (`_NamedValue._wrap`), with no second rebind. Literals are stored and split as runtime `String`s per request.
- **Route-value records** ([M3-061](history/architecture-decisions.md#route-value-records-decision-m3-061)): a `RouteValues` struct is a slot kind (`_RECORD`) carrying several route values in one slot, so three or more values add no overload. Its rules read the literal's placeholder names once (`_placeholder_names`), so a record's build time grows little with its field count (measured in pull request #123, one route on Mojo 1.1.0 in the cloud container: about 8 s with 2 fields, 6 s with 30, 9 s with 60, against 28 s and 158 s at 30 and 60 fields when each check re-read the literal; 50 three-field record routes about 7 s against 5 s for 50 one-`Int` routes, 200 about 15 s against 8 s, and 200 ten-field record routes about 23 s). `_rule` checks it before the family rules, in this order: a `State` among the request slots beside a record (a forgotten state argument or a second `State`, the family's `State` message), a record anywhere but the first slot (two records included), a bare value beside it, then its own rules through `std.reflection` (`_record_fault`: a field; each field a bare route value, not a `Param`, a record or a route value that is also a body; one field per placeholder; each placeholder named once; field `i` named after placeholder `i`; an `Optional` field only at a query placeholder), each with a message built as `_misnamed_message` is (`_record_message`, naming the field and placeholder). The family rules then see the record as one `String` value on one placeholder, so it takes the shapes of one bare value and every existing message is unchanged. `_slot` builds it with `_build_record` (Storage and ownership, below), converting field `i` as a bare slot of its type at `args[at + i]`; `_route` marks each query key an `Optional` field binds. The record's `__init__` never runs: Mojo 1.1.0 reflects fields, not initializers, so a record with its own `__init__` cannot be refused (the record's documented first limit; `test_init_is_never_called`). `tests/test_route_records.mojo`, `tests/route_records_api_fail`, and the record routes in `adapters/flare/test_localhost_roundtrip.mojo`.
- **Disjointness** (M2-005): a slot is an `Int`, `String`, `Optional[Int]` or `Optional[String]` route value by exact type equality, or a `FromRouteValue` route value by conformance (M3-055), never a body (so `StaticString`, `StringSlice`, an application type that does not conform and an `Optional` of any other type are no route value, and a `String` last on `post`, `put` or `patch` is a bodyless handler's route value, M3-048); an ordinary body is an application type conforming to exactly one of `FromBody` and `FromBytes` ([M3-041](history/architecture-decisions.md#typed-binary-request-bodies-decision-m3-041)). A type conforming to both has two conversions and is a kind of its own (`_TWO_BODIES`), and so is a `WithHeaders[B]` whose `B` conforms to both (the carrier reports how many of the two its `B` conforms to through the private `_HeaderCarrier._conversions`; a carrier converts as a bare body of its `B` does, so accepting it would pick a conversion silently): a body wherever the rules look for one (so `get` reports `takes no request body` and a body before the last slot `takes one request body`), and in the body position `the request body's type conforms to both FromBody and FromBytes; a body type conforms to one of them`. `List[UInt8]` is no body (`tests/body_bytes_api_fail/bytes_body_parameter.mojo`): an application declares its own `FromBytes` type. A `FromBytes` type whose `max_bytes` is negative, bare or carried (the carrier reports its `B`'s limit through the private `_HeaderCarrier._max_bytes`), is a body kind of its own too (`_NEGATIVE_LIMIT`, [M3-043](history/architecture-decisions.md#typed-binary-request-body-size-limits-decision-m3-043)), a body for every other rule, and in the body position `the request body's max_bytes is negative; a FromBytes type's max_bytes is a byte count, 0 or more` (`tests/bytes_limit_api_fail`). `Json[T]` is a body or a result like any other, so JSON adds no shape. A `FromRouteValue` type that is also a `FromBody` or a `FromBytes` is a kind of its own (`_VALUE_AND_BODY`, also through a `Param`), which `_rule` rejects before the family rules wherever it is, so `_kind`'s order never picks one of its two conversions ([M3-054](history/architecture-decisions.md#application-route-value-types-decision-m3-054)); a `WithHeaders[B]` around one is that kind too (the private `_HeaderCarrier._carries_route_value`), and one whose `B` is a `FromRouteValue` but no body fails the carrier's `_FromBodyOrBytes` bound where it is declared. In the same way a `RouteValues` record that is also a `FromRouteValue`, a `FromBody` or a `FromBytes` is a kind of its own (`_AMBIGUOUS_RECORD`), bare, in a `Param` or in a `WithHeaders[B]` (`_HeaderCarrier._carries_record`), rejected right after `_VALUE_AND_BODY` (M3-061).
- **Header carrier in the body slot** (M3-013): the body kind is `FromBody`, `FromBytes` (M3-041) or the private `_HeaderCarrier`, so `WithHeaders[B]` is a body without being a `FromBody` or a `FromBytes`, and the body-type rule keeps its message (since M3-041 it names `FromBody or FromBytes`). A carrier's `B` is bounded by the private `_FromBodyOrBytes`, the parent trait both `FromBody` and `FromBytes` refine (M3-042), so an ordinary type that is neither is rejected where the handler is declared, with the bound's name in the compiler's text (`tests/with_headers_api_fail/carrier_of_int.mojo`, `tests/bytes_headers_api_fail/carrier_of_bytes_list.mojo`). The bound is a private marker, not a closed set: a type conformed to it directly passes the declaration, has no conversion, and `_kind` gives the carrier no kind at registration (`carrier_of_bound_only.mojo`), so `_kind` is the final check. Neither trait therefore names every type a `post` (`put`, `patch`) body slot accepts (the accepted cost). `get` (`delete`) takes no body; its typed handlers read fields through a `Headers` slot (below).
- **`Headers` slot on `get` and `delete`** (M3-016, M3-020): `Headers` is a slot kind by exact type equality, not a trait, so no application type is one. On `get` and `delete` it is accepted once, as the last slot, after at most two route values, with the placeholder rules of the route values it follows; any other of their shapes with a `Headers` slot is `a get handler takes one Headers, as its last parameter` (`a delete handler ...` on `delete`), checked after the `State`, `Request`, body and no-kind rules so their messages win. The route sets `_Route.headers`, which marks a route whose handler receives the fields (a carrier or a `Headers` slot). On `post`, `put` and `patch` a shape with a body takes no `Headers` slot (its last position is the body), and `_post_rule` reports a `Headers` before the body as a type of no kind; a bodyless shape takes `Headers` as `get` does, under `_get_rule` and its messages ([M3-048](history/architecture-decisions.md#bodyless-typed-post-put-and-patch-handlers-decision-m3-048)).
- **One injected slot** (M3-001): a handler takes state exactly when its registration passes a second argument, a `State[S]`; it is then the first parameter, and the rest is one stateless shape. Argument count separates the two families. The slot is registration-bound; M3-012 keeps request header fields out of it (they travel in the body slot or, on `get`, `delete` and bodyless handlers, the `Headers` slot, above). A second injected kind, request-scoped injection included, needs its own decision, because a second injected kind doubles the stateful family (M3-014).
- **Rules guard the adapter** (M3-015): one ordered rule function (`_rule`) holds every registration rule except the result's. `_check` states each rule as a compile-time assert with Muntin's message, and `_admits`, the same rules as one Bool, guards the adapter's instantiation: without the guard Mojo 1.1.0 reports the adapter's own failure before the rule's message (`tests/registration_api_fail/slot_misuse_names_the_rule.mojo`). If the Bool ever rejects a shape the asserts accept, the guard's `else` aborts at registration instead of leaving the route unregistered. Rules that had a message before M3-015 keep it; new ones name the method. A `String` route value (M3-019) has its own one-value placeholder messages, so every `Int` message stays byte-identical, and the no-kind messages on `get` and before the `post` body name both route-value types. Two route values (M3-022) have one placeholder message per family whatever their types; three are reported before the placeholder count. At slot arity 3 each family's order extends rule by rule across the slots, so every arity-1 and arity-2 result is unchanged except the two retired `at most one` codes: on `get`, a `State`, a `Request`, a body, a no-kind slot, a `Headers` not last, three route values, then the placeholder count; on `post`, each rule over both slots before the last (a `Request`, a `State`, a body, a `Headers` or no-kind slot), then the placeholder count, then the last slot's body rules; since [M3-048](history/architecture-decisions.md#bodyless-typed-post-put-and-patch-handlers-decision-m3-048) a bodyless `post` shape (only route values and a `Headers`) is handed to `get`'s order before any of them. An optional value (M3-025) has one placeholder message per family, checked where the one-value count is, and a path-position message checked right after the two-value count; the two no-kind messages name `Optional`, and every other message is unchanged. The names rules (M3-050: of two values both or neither `Param`s, then each `Param`'s name at its position) run in `_rule` after the family rule accepts a shape, so no family rule's message changes; the distinct-query-keys rule runs last, only for a shape every other rule accepts. A route-value record's rules (M3-061, above) run before the family rules and hand them one value on one placeholder, so they change no other shape's message.
- **Route conflicts** ([M3-053](history/architecture-decisions.md#route-conflict-decision-m3-053)): every registration goes through `App._add`, which aborts at that call with `_conflict`'s message when an earlier route of the same method overlaps the new one (same segment count; at each position equal static text, or a placeholder facing a placeholder or a non-empty static segment, as `_match` matches) and is not more specific than it (`_covers`: it matches every path the new one does, and not the reverse). So identical paths (placeholder names and the query aside), a more general route first and two routes neither of which covers the other abort, raw and typed alike, and every pair of overlapping routes in an `App` is ordered most specific first. It is a run-time check because each call sees only its own literal and an `App`'s type does not record its routes. `_add` asks the `App`'s `_RouteIndex`, which gives `_conflict`'s answer without comparing every pair: a route without a placeholder conflicts with an earlier one only when their shapes (placeholders written `{}`) are equal, found in a `Dict`, and only earlier routes with a placeholder, each split when it was registered, are compared one by one, whatever the new route's method or kind. With `S` routes without a placeholder and `P` with one, building an `App` therefore costs about `S + P²` plus one comparison per later route for each earlier route with a placeholder (`S×P` when they come after them), not only `P²` (measured in pull request #95: 1,000 static routes about 1 ms, 1,000 routes with a placeholder about 12 ms, 1,000 `GET` routes with a placeholder then 1,000 static `POST` routes about 16 ms, against 0.2 to 0.7 ms before M3-053). `tests/test_route_conflicts.mojo` checks the index against `_conflict` on random registration sequences. `tests/route_conflict_abort` (built and run by `check.sh`, must abort with the expected text), `tests/test_route_conflicts.mojo`.
- **Raw handlers** select the one-slot overload like any other shape: `Request` is a slot kind, and the rule requires `Response` as the result and no placeholder.
- **Diagnostics:** a shape that selects an overload and breaks a rule reports the rule, `constraint failed: <rule>`; the primary line is `function instantiation failed` at the enclosing function, with the registration call in the next note. A call that selects none (more than three slots; with the state passed, a `State` that is owned, `mut`, a plain value or not first; a result outside the `where` clause) is `no matching method` with the eight candidates' notes; a rejected result's note is `violated constraint` and the clause. But when the call does not let the compiler decide the clause, the error is `invalid call to '<method>': lacking evidence to prove correctness` instead. That happens for a result with a local's immutable origin (`origin_text[ImmOrigin(origin_of(s))]`), and for a forwarding helper's generic result whose own `where` is neither one branch of the clause nor the whole clause (no `where`, or a partial disjunction such as `where (R == String or R == StaticString)`) (`tests/registration_api_fail/local_origin_result_rejected.mojo`, `generic_result_disjunction_lacks_evidence.mojo`, `generic_result_without_where_lacks_evidence.mojo`). A typed function value with a borrowed `Int`, `String` or `Headers` slot fails before any overload is chosen (`TODO: function type conversions between closures not supported yet`).
- **Arity budget:** Mojo 1.1.0 prints at most ten notes per diagnostic, counted per method name (`tests/header_access_fail/eleven_candidates_drop_a_note.mojo`, `tests/registration_fail/notes_are_per_method.mojo`), so each of the five method names has its own budget. Slot arity 3 makes eight overloads per method (forty across the five), with every candidate note printed; it is spent on two route values beside a body or `Headers` (M3-022). A route-value record is one slot whatever its field count, so three or more values beside a body or `Headers` fit in it (M3-061); arity 3 still caps the slots. Notes under a candidate count too: a stateful call at slot arity 2 or 3 whose result the `where` clause rejects (`registration_api_fail/immutable_origin_result_*_state_{2,3}.mojo`) prints all eight candidate notes and drops a trailing type-mismatch sub-note (`(1 more notes omitted.)`). Slot arity 4 would make ten, where a rejected result loses one candidate note (M3-014 and M3-022 estimated that cost acceptable; under the growth budget below, adding it is a decision of its own); it is the last arity under the cap, which three route values and another request part on `get` would compete for. Slot arity 5 is past the cap.
- **Growth budget** ([M3-052](history/architecture-decisions.md#registration-complexity-budget-decision-m3-052)): eight overloads per method name, in the two families, is a maintenance ceiling chosen by M3-052, not a compiler boundary (see the sub-note above). A new request part is a slot kind or a rule when it can be one. Raising the ceiling (slot arity 4, a third family) is a decision of its own, taken for a concrete shape and comparing the overloads with a carrier slot kind that holds several parts; a method name beyond the five starts from a copy of the `get` or `post` set, and any rule of its own is decided with it. No check counts the overloads; review enforces the ceiling. In the measured range (1 to 200 routes, eight against forty declared overloads) build time grew with routes, and the declared overload count made no difference distinguishable from noise.

### Request handling

Middleware (M3-035, decided by [M3-034](history/architecture-decisions.md#middleware-decision-m3-034)) wraps everything below. `App.use` appends a thin function value (`Middleware`, generic over the origin of the `Next` it receives) to `App._middleware`. With none registered, either `App.handle` calls `_dispatch` (the route scan below) on the request, borrowed. Otherwise the borrowing `handle` copies the request once, body included, and the owning one moves it (M3-064), and either calls `_run(0, ...)`: `_run(i)` calls middleware `i` with the request and a `Next` holding an immutable `Pointer` to the borrowed `App` (with that borrow's origin) and `i + 1`, inside a `try` whose `except` is the fixed 500 with a `Failure.MIDDLEWARE` report (`_failed`), so a raise is answered at the failing middleware and the one outside it continues with that 500; past the last middleware, `_run` calls `_dispatch` on the owned request without copying it again. `Next.run(deinit self, ...)` consumes the `Next` and calls `_run(i + 1)`. So middleware runs in registration order, outermost first, on every request `handle` receives (404, 405, the 400s, the handler's 500 and `HEAD` included), and wherever `use` sits among the registrations. Every status below is Muntin's own answer, which a middleware outside it may replace or change, `Allow` on a 405 included.

Routes are a list scanned in registration order; the first route whose method and path segments match handles the request and never falls through, even when it answers 400. Because registration refuses route conflicts (Registration surface, above), that first match is the most specific route matching the method and path. Methods compare byte for byte, except that a `HEAD` request also matches a `GET` route and runs that route's steps (M3-026; backend seam, above); a raw route receives the `HEAD` request. When the scan selects no route, a second scan (`_allowed`, beside `_match`) collects the methods of the routes whose path matches by the same `_match` test, nothing decoded: if there are any, Muntin's answer is 405 `Method Not Allowed` with one `Allow` field listing each once, in the order its first such route was registered, `HEAD` right after `GET`; otherwise it is 404 `Not Found` ([M3-030](history/architecture-decisions.md#method-not-allowed-decision-m3-030)). So `HEAD` on a path only routes of other methods match is 405, and `head`, `Head`, `OPTIONS` and unknown methods select nothing: 405 on a path some route matches, 404 elsewhere. `Allow` lists the methods that select a route on that path, not that the selected route's value or body checks pass. The query takes no part in selection. On a typed route, each step runs only if the previous one passed:

| Step | Where | Failure |
|---|---|---|
| method + path match on the raw path (static segments byte-equal, `{name}` one non-empty segment) | `App.handle` | 405 `Method Not Allowed` with `Allow` when a route of another method matches the path, else 404 `Not Found`; nothing decoded or converted |
| query values, one per `{key}` in the literal's order: pairs split on `&`, key/value at the first `=`, byte-equal undecoded keys | `App.handle`, one `try` with the next step | duplicated, or a required value missing: 400 `Bad Request`; an optional value's absent key is passed on as `""` (M3-025) |
| each route value decoded once (`_decode_value`): the path captures in place, left to right, then each query value, with `+` as a space first; `%` and two hex digits become that byte, every other byte is kept | `App.handle`, the same `try` | a required value empty, a bad escape, or decoded bytes that are not UTF-8: 400 `Bad Request`; an optional value's empty value is passed on as `""` |
| each route value `Int`, in order: the decoded text, optional `-`, ASCII digits, `Int` range (leading zeros allowed); a `String` takes the decoded text as is; a `FromRouteValue` slot is `from_route_value` of it (M3-055); an `Optional` slot is `None` for `""` and otherwise converts as its required type | adapter | 400 `Bad Request` |
| `Json[T]` bodies only: exactly one `Content-Type` whose media type is `application/json` | adapter, from the verdict `App.handle` appends | 415 `Unsupported Media Type` |
| `Json[T]` bodies only: body length at most 1,048,576 bytes | adapter | 413 `Content Too Large` |
| `FromBytes` bodies only, bare or carried: body length at most the type's `max_bytes` (M3-043; `Int.MAX` is no limit), measured on the bytes the route receives after middleware (the code compares `len(body)`) | adapter | 413 `Content Too Large`; nothing rebuilt or converted |
| `WithHeaders[B]` bodies and the `Headers` slot only: the fields rebuilt through `Headers.add` | adapter | 500 `Internal Server Error` (only an in-memory `Headers` built through the `_fields` gap fails), reported `Failure.MUNTIN` with fixed text (`_slot` drops the error) |
| text bodies only (`FromBody`, `Json[T]`, `WithHeaders[B]` around a `FromBody`): the body bytes read as UTF-8 (`_body_text`, M3-040; inside `_from_parts` for a carrier) | adapter | bytes that are not well-formed UTF-8: 400 `Bad Request`, `from_body` and handler not called |
| body conversion: `B.from_body(text)` for an ordinary text body (for `Json[T]`: parse and `from_json`); for a `WithHeaders[B]` carrier, `_from_parts` on the borrowed bytes, which converts them as a bare `B` (M3-042); for a `FromBytes` body (M3-041), bare or carried, `B.from_bytes(bytes)` on the request's body bytes, borrowed, after the type's limit and, for a carrier, the field rebuild | adapter | 400 `Bad Request`, handler not called |
| handler call (the only step in the handler `try`) | adapter, `_handler_error[E]` | `T.to_error_response()` if the declared `T` conforms to `ToErrorResponse`, else 500 `Internal Server Error`, the error dropped after `_error_text` reports it `Failure.HANDLER` (its text under `conforms_to(E, Writable)`, else `<` and `reflect[E].name()` and `>`) |
| result: `String` or `StaticString` → 200 text with no fields; `R: ToResponse` → `to_response()` once | adapter | non-raising; a `Json[T]` serialization failure is the fixed 500 without fields and without `ToErrorResponse`, reported `Failure.RESPONSE` with the error's text (in `Json.to_response`, so also when a handler calls it) |

A raise escaping `invoke` is 500, never 400, reported `Failure.MUNTIN` with the error's text, as is a failed `Allow` write; no adapter raises and the `Allow` value is always valid, so neither is reached. Each fixed 500 `src/muntin` makes goes through `_failed`, which builds `Internal Server Error` with no fields and sets `Response._failure`, a `List[Failure]` holding at most that one report ([M3-058](history/architecture-decisions.md#dropped-error-report-decision-m3-058), [M3-059 amendment](history/architecture-decisions.md#dropped-error-report-amendment-m3-059)); `_internal_error()` stays, without a report, for the spikes under `tests/` that import it. Every public `Response` initializer leaves `_failure` empty, the synthesized copy keeps it and no step clears it; what carries a report and what keeps it is `docs/DX.md` section 6. No backend reads it: the Flare adapter converts the status, fields and body only, and its own 500 for an invalid outgoing field carries no report. 400, 404 and 405 run neither the handler nor a conversion. A matched **raw** route runs none of the extraction steps and decodes nothing: `_raw_request` rebuilds a fresh `Request` (method, path, query and header fields, and a copy of the body bytes, unread) and moves it into the handler, which answers with any status; its errors follow the same `ToErrorResponse`/500 rule, and a rebuild failure is the fixed 500.

Error opt-in (M2-013): a raised value converts only when the handler's declared error type declares `ToErrorResponse` in its own struct declaration (directly, through a refining trait, or as a documented conditional conformance). Bare `raises` (`Error`) is never mapped by message; a raised `ToResponse`-only type, a same-named method without the conformance and a `Variant` of opted-in types are 500. A returned value converts with `to_response`, a raised one with `to_error_response`. Undocumented `__extension` behavior is not a supported opt-in.

Transport through the box: an adapter receives `List[String]` raw arguments and, beside them, the request's body bytes, borrowed (`_Erased.invoke(args, bytes)`, M3-040; the body never travels as a `String`). The arguments are, in this order: the route values if the route has any (the path captures left to right, then the query values in the literal's order, already decoded; an absent or empty optional value is `""`, which no decoded value is, so it needs no second channel; a slot's first value is at the sum of the widths of the slots before it, `_width`: a bare value 1, a record its field count, anything else 0), then, on a JSON body route, the verdict (`"1"` or `""`), then, on a carrier route (`WithHeaders[B]`) or a `Headers` route, each header field's name and value. The JSON adapters answer 415 unless the arguments are exactly (route values and) verdict `"1"`, or, for a carrier, the verdict `"1"` at that index followed by an even count. A raw route receives `method`, `path`, `query`, then each header field's name and value. A raw route copies the body once (the rebuild), a typed text body once (its UTF-8 read) and a `FromBytes` body, bare or in a carrier, never (its limit compares only the length; it borrows the bytes; a conversion that keeps them copies them itself, `body.copy()`, which the borrow enforces: `tests/from_bytes_api_fail/from_bytes_keeps_borrowed_bytes.mojo`); with middleware the whole request, body included, is copied once more in the borrowing `App.handle`, and not in the owning one, which `TestClient` and the Flare adapter call. Typed routes without a carrier or a `Headers` slot receive no header strings. A carrier or `Headers` route copies each field twice per request (into the arguments, then into the rebuilt `Headers`), as raw routes do. A state never travels in the arguments; it is bound with the handler. Each route value costs one decoded copy per request, and a `String` value a second copy at its slot; a route's query placeholders together cost one scan of the query, whatever their number (`_query_spans`: each pair's key is compared with the route's keys, or looked up in its `query_index` above `_LINEAR_QUERY_KEYS`, which only such a route builds, and only where each value lies is recorded), and the values are copied in key order after it, so a missing key answers 400 before any later value is copied (measured in pull request #123 with `TestClient`: 2,000 unrelated pairs cost about 50, 100 and 110 µs per request with 1, 15 and 30 query keys, against 54, 693 and 1,335 µs with one scan per key; routes with 0, 1 or 2 keys and short queries showed no clear regression against `main`; `tests/test_query_spans.mojo` checks it reads every query as the one-key `_query_value` did, at 8 and 9 keys and after multibyte text).

### Storage and ownership

- **Handler box `_Erased`:** each route owns one move-only `_Erased`, whose only field is a `ThinAllocation[_Header]` holding the invoke trampoline, the drop function and the erased pointer to the handler value (an `OwnedPointer[F]` allocation). One `__init__[F, call: _Call[F]]` instantiates both functions for the same `F`, so pairing is compiler- or construction-checked (the ownership oracle in `tests/test_handler_storage.mojo` counts live values). Cost: the handler cell and its header, both allocated at registration; nothing per request. `App` is `Movable`, not `Copyable`; `App.handle` iterates routes by index because 1.1.0's `for x in list` needs a `Copyable` element. Copying an `App` would need clone support back, with its own oracle.
- **Middleware:** `App._middleware` is a `List` of thin function values: no erasure, no unsafe operation, nothing in `_handler_storage.mojo`, and nothing stored with a function. A `Next` exists only for one middleware call: its origin is the borrowed `App`'s (a struct field cannot hold `AnyOrigin` on Mojo 1.1.0), so it cannot outlive that borrow, and it is made in `_run`'s frame from `self`, so moving the `App` between requests leaves nothing pointing at its old place. Its initializer takes only `_`-prefixed keyword arguments; code that names `_` members can build one or reach the `App` through `next._app[]`, the standard library's unsafe pointer operations (`unsafe_*`, `UnsafePointer`) can run one twice, and `rebind_var` can give one a longer-lived origin, the same boundary as `_Erased`'s and `State`'s.
- **State:** `State[S]` holds a sealed `_Shared[S]` (one `ThinAllocation` header with an atomic count and an `OwnedPointer[S]`; two allocations per `State`, none per request). `State(value)` moves the value in, `.copy()` shares it, `state[]` is read-only through every handle, and a reference from it is interior to its handle (using it after the handle is reassigned or moved is a compile error). Each registration copies the handle once into the route's `_Bound[H, S]`; requests borrow it. The value is dropped once, after the last handle. Read-only is shallow: interior mutability in `S` is the application's.
- **The State guarantee (M3-004), verbatim:** **Muntin must not introduce a Muntin-specific safe-code path that lets one `State` alias replace, mutate, swap, or prematurely destroy the shared payload observed through another alias. Toolchain-wide primitives that can violate the same property for standard-library types and existing Muntin storage (origin rebind, forged allocation or header replacement, `memmove`, stdlib-private fields) are outside this guarantee and are pinned as Mojo 1.1.0 toolchain-wide soundness gaps.** The pins are `tests/toolchain_soundness_gaps` (must build).
- **No erased value outlives what it borrows, unchecked:** erasing a value's type also drops its origins, even if nothing restores it, and Mojo 1.1.0 gives generic code no way to refuse a type that borrows ([M3-065](history/architecture-decisions.md#request-context-storage-decision-m3-065)). So a request context value is never erased: its type is a type parameter shared statically by the code that writes it and the code that reads it. `State` does not meet this today: a `State` whose type borrows a local registers, and a request reads the local after it is dropped (`tests/state_known_gaps/state_borrows_dropped_local.mojo`, [#122](https://github.com/sano-suguru/muntin/issues/122)). Until it is fixed, the State guarantee below covers the handle and its aliases, not what the value borrows, and Muntin claims no memory safety for a state that borrows.
- **Same boundary for `_Erased`:** the ordinary safe-code paths Muntin exposes are closed (its own fields give no access; its pointer helpers are named `_unsafe_*`); the stdlib's private fields (`ThinAllocation._ptr`), the deprecated `memmove`, forged `alloc` headers and `rebind` reach it as they reach std types.
- **The one rebind** (M3-015): `comptime if A == Int` does not refine `A`, so a parsed `Int`, a rebuilt `Request` or `Headers` and a text result reach their generic type through `rebind_var`, which also accepts a different type of the same layout (`tests/registration_known_gaps/rebind_var_layout_twins.mojo`). It is called only in `_as[T, A]` in `app.mojo`, right after `comptime assert A == T` (exact for origin-free types; for a `StaticString` result exactness comes from the `where` clause), and `tests/registration_api_fail/rebind_rejects_layout_twin.mojo` pins that the helper rejects a twin.
- **Route-value record construction** (M3-062): `_build_record[T, E, convert, at]`, `T` a `RouteValues` (so no other type can be built without its initializer), writes field `i` of a `MaybeUninit[T]` as its own type at `reflect[T].field_offset` (alignment and padding the compiler's), from `convert[F_i, at + i]`, in field order, refining field types with `conforms_to`. Its invariant is its docstring: after `k` fields exactly fields `0` to `k-1` are initialized; when field `k`'s conversion raises, each of them is destroyed once, in field order (the order Mojo destroys a struct's fields in, which the oracle pins), the storage is forgotten without `T`'s destructor and the error propagates; on success the storage becomes the `T` and the helper owns nothing. The record is never erased: the typed adapter receives it as `T` and moves it into the handler within the request, and each field is built from the request's decoded text by its type's own conversion, which in safe code cannot give a field a borrowed origin (`from_route_value` receives only a `String`). The ownership oracle in `tests/test_route_records.mojo` counts each field's conversions and destructions and the record's destructor for a failure at each field and for success, with a heap `String` field before a failing one for `SANITIZE=address`.
- **Unsafe confinement:** `check_unsafe.sh` fails if any other `src/muntin` module names an unsafe pointer/ownership operation or the boxes' fields, imports anything but `_Erased`, `_Shared` or `_build_record` from the storage module, or if the package root names the storage module or `_Erased`, or if the storage module imports anything but `std`, `.http` and `RouteValues` (which bounds `_build_record`'s `T`; `route_value.mojo` imports nothing) or names request, body or conversion names; and unless `src/muntin` contains exactly one `rebind_var[` (storage module, comments and docstrings included), in `app.mojo` on the line after `comptime assert A == T`, with no other module naming `rebind_var`. It is a confinement guard, not a safety proof, and does not check `tests/`. The runtime check of the storage itself, on the paths the tests run, is the test suite under AddressSanitizer ([`SANITIZE=address`](DEVELOPMENT.md#3-verify-with-the-strongest-available-oracle)).

### Headers

- `muntin.Headers` is an ordered list of fields: original casing, repeated names kept in order, ASCII case-insensitive `get` (`Optional[String]`, first value) and `get_all`; `len`, `name(i)`, `value(i)`. `add` appends and `set` removes every same-name field, then appends; both raise on a name that is not an RFC 9110 token or a value with a control byte (other than HTAB) or SP/HTAB at either end. Copies are explicit (`.copy()`).
- `Request.headers` is what the backend received; `Response.headers` is empty from `Response(status, body)` and `Response.text`. Muntin adds no default field: `String` results and `Response.text` set none, and `Json[T]` results set exactly `Content-Type: application/json`.
- Raw handlers read `req.headers` and set fields on their `Response`. Typed `post` handlers read them through a `WithHeaders[B]` body (M3-013): `input.headers` is the request's `Headers`, every field in order with its casing, repeats and empty values, and `input.body` is converted as a bare body of its type, by `B.from_body` or, around a `FromBytes` (M3-042), by `B.from_bytes`; `take_body(deinit self)` moves the body out. Muntin chooses no status for the fields `input.headers` exposes and gives them no meaning (a missing field is `None`; a value's status is the handler's error type to choose). Two existing checks still answer before the handler: a `Json[T]` body's `Content-Type` verdict (415), and the rebuild of a field an in-memory `Headers` holds invalidly (the fixed 500). The carrier composes with `State` and with `Json[T]`, and is the body on `put` and `patch` too. Typed `get` and `delete` handlers read them through a `Headers` parameter, last (M3-017): a fresh `Headers` rebuilt from the transported fields, which the handler borrows or owns, with the same semantics, no status chosen for a field and the same rebuild 500; changing it changes no `Request`. The JSON `Content-Type` check is not header extraction: it is a fixed verdict `App.handle` computes for `Json[T]` body routes only, carried or not.
- Known gap: `headers._fields` is reachable by name and bypasses `add` (`tests/headers_known_gaps`); the Flare adapter re-checks every outgoing field, and a carrier or `Headers` route answers such a request field with the fixed 500.

### JSON

- `Json[T]` conforms to `FromBody` when `T: FromJson` and to `ToResponse` when `T: ToJson` (conditional conformance); `take(deinit self)` moves the value out. `Json(value, *, status=200)` holds the result's status in a private field until `to_response`, which applies it only when `write_json` succeeds (a serialization failure stays the fixed 500); a body built by `from_body` holds the default, which nothing on the request path reads, and Muntin does not validate the value (M3-029, decided by [M3-028](history/architecture-decisions.md#json-response-status-decision-m3-028)). Applications map fields by hand in `from_json(JsonValue)` and `write_json(mut JsonWriter)`; there is no derived codec.
- The codec is Muntin's: the RFC 8259 grammar, strictly, with Muntin's limits (duplicate member names, nesting deeper than 64, comments, trailing commas, leading zeros, `NaN`, a byte order mark and lone surrogates are 400; extra members are ignored). `JsonValue` is a read-only position in a compact tape held in `_Shared`; parsing is linear apart from a per-object name sort, and member lookup scans the object, so reading k fields of an m-member object costs O(k·m). `int()` is exact; `float()` goes through Mojo 1.1.0 `atof` (long literals raise, some values are 1 ulp off), and `String(Float64)` in the writer is not always round-trip; both are pinned toolchain gaps.
- Request rule: exactly one `Content-Type` field whose media type (text before any `;`, SP/HTAB trimmed) is `application/json`, compared ASCII case-insensitively; parameters are ignored; missing, duplicated, other and `+json` types are 415. Fixed 1 MiB cap (1,048,576 bytes accepted, one more is 413); the parser also raises above it, so a raw handler's `Json[T].from_body` never parses an unbounded body. At the cap one parse adds at most about 29 MB of memory (`[0,0,...]`), about 5 MB for typical records. Only `Json[T]` bodies have the check and this cap; application `FromBody` types need no `Content-Type` and have no Muntin cap, and a `FromBytes` type's limit is its own `max_bytes` (M3-043). Backend limits apply first (the `Server`'s `max_body_bytes`, 10 MiB unless set, M3-044).
- `TestClient.post(target, body)` (or `.put`, `.patch`) sends no fields, so a JSON body route answers it 415; a test sends the field with `headers=` (M3-011) or through `app.handle(Request(..., headers^))`.

### Flare adapter

Two handlers implement Flare's `Handler` and answer through one module-level function, `_serve_app(app, request)`, which converts, moves the converted request into the owning `App.handle` through `_handle_owned` (a `var` parameter, so a call without `^` does not build), converts back and applies the `HEAD` rule, and never routes: `MuntinHandler` owns an `App` (the adapter's tests and probes use it), and the private `_BorrowedHandler[origin]`, which `Server` uses (once, or once per worker over that worker's own `App`), holds a `Pointer[App, origin]` to a borrowed one, as `TestClient` does. Policy (module docstring):

- method and request target (path plus query, undecoded; M3-039, decided by [M3-039](history/architecture-decisions.md#request-target-and-method-bytes-decision-m3-039)): copied byte for byte with `String(from_utf8=)` from their `as_bytes()` spans, before `Request` splits the target, so a well-formed UTF-8 method or target (non-ASCII, U+FFFD and percent-encoded bytes included, a method that is not a token too) arrives exactly as received, and one that is not makes the conversion raise and is answered 400 before `App.handle` (no middleware, no route scan; 400 on any path), as a header field below. Over cleartext HTTP/2 Flare v0.12.0 builds `:method` and `:path` with `String(unsafe_from_utf8=)` from the HPACK octets and checks neither for UTF-8, and Mojo 1.1.0's `String` slicing aborts the process when a slice starts on a continuation byte, which `Request`'s split at `?` and `App.handle`'s query scan could do on such a target; the check uses no slice, and `_serve_app`'s `HEAD` comparison before it compares bytes. Over HTTP/1.1 Flare refuses every method or target byte outside `!`..`~` with its own 400 first. Version (once the `Host` rule below has read it) and peer dropped;
- `Host` (M3-073, decided by [M3-073](history/architecture-decisions.md#request-host-decision-m3-073)): `_answer` first answers 400 `Bad Request` to an HTTP/1.1 or HTTP/2 request without a `Host` field (any casing; an empty value counts), before the conversion and `App.handle`; a later HTTP/1 minor version counts as 1.1. It reads Flare's `request.version`: Flare v0.12.0's HTTP/1 parser admits `HTTP/<digit>.<digit>` only and reads a request line without a version as `HTTP/1.1`, and every HTTP/2 request says `HTTP/2`, with `:authority` written as `Host`, so an h2c request without one carried neither. A request upgraded with `Upgrade: h2c`, which Flare answers 101 itself on every cleartext connection, reaches the adapter as such an HTTP/2 request, after the 101. Flare refuses a second `Host` itself. HTTP/1.0 needs none; the value is not checked. Why each: the record;
- request body (M3-040, decided by [M3-040](history/architecture-decisions.md#binary-request-and-response-bodies-decision-m3-040), which replaced [M3-038](history/architecture-decisions.md#request-body-bytes-decision-m3-038)'s refusal): Flare's raw `Request.body` bytes copied into `Request.body`, whatever they are, with no validation, so every body (U+FFFD, NUL and bytes that are not UTF-8 included) reaches `App.handle` byte for byte; a typed text body that is not UTF-8 is `App.handle`'s 400, after routing and through middleware. Flare's own refusals come first; among them, a body over the `Server`'s receive limit (`max_body_bytes`, M3-044, below) and a request its HTTP/1.1 parser or HTTP/2 layer rejects never reach the adapter. Flare's `Request.text()`, which replaces bytes that are not UTF-8 with U+FFFD, is not used. Flare hands the raw bytes over HTTP/1.1 (`Content-Length` or chunked) and h2c (one or several DATA frames), measured by `compat/flare/body/body_probe.mojo` and, through the adapter, by the loopback body case;
- request header fields rebuilt from Flare's public `HeaderMap.encode_to` and verified against `len()` and `get_all(name)` by position (a first-colon parse would misread a name containing `:`, which Flare v0.12.0 refuses over cleartext HTTP/2 but the check does not rely on; a value that is not UTF-8, which Flare passes through byte for byte over HTTP/2, fails the check); a field that fails the check or `Headers.add` is answered 400 before `App.handle`. `get_all` is called once per name, where the name first appears: Flare's by-name lookups scan every field, so the check makes fields × distinct names comparisons inside Flare (the largest header blocks Flare v0.12.0 admits, about 4,000 fields over HTTP/1.1 and about 470 over h2c, are measured by `scripts/bench_headers.sh`), and work in the adapter that is linear when its `Dict` of names does not collide (Mojo 1.1.0's default hasher has a fixed seed, so chosen names could collide; at worst the same fields × distinct names). Names and values are cut from the text's bytes, so a value that a first-colon parse would start inside a code point raises (400) instead of aborting;
- response status, body bytes (whatever they are; no `Content-Type` added) and fields copied, reason left to Flare; fields go out in order except `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Proxy-Connection`, `Upgrade`, `TE`, `Trailer` and every field a `Connection` value names; each field is re-checked with `Headers.add`, and a failure answers 500;
- `HEAD` (M3-027): for a request whose method is exactly `HEAD`, `_serve_app` takes the response it would send at every exit (`App.handle`'s answer, `to_flare_response`'s fixed 500, its own 400), removes the body and, unless the status is 1xx, 204, 205 or 304, adds `Content-Length` with the body's byte length. Both steps are the adapter's because Flare v0.12.0 sends a `HEAD` response's content in DATA frames over cleartext HTTP/2 and over HTTP/1.1 frames an empty 200, 205 or 304 body as `Content-Length: 0`; it honors a declared `Content-Length` beside an empty body on both, and over h2c sends no `content-length` when none is declared. The rule lives in `_serve_app`, not `to_flare_response`, which takes no method. Measured by `compat/flare/head/head_probe.mojo`.

Serving (M3-033, decided by [M3-032](history/architecture-decisions.md#serving-entrypoint-decision-m3-032); user-visible contract: `docs/DX.md` section 1) is `Server`, a public type of the adapter module, outside the package; Muntin core has no `app.run()` and no serving API. `Server(Movable)` holds one field, Flare's `HttpServer`. Its one initializer takes keyword-only `_host` and `_port` and is called by `Server.bind(host, port)`, the one public spelling; no initializer takes a Flare value, so no Flare type appears in `Server`'s signatures. The initializer raises `port out of range: <port>` outside 0 to 65535, before Flare's `UInt16` conversion and before the host is parsed, then builds the configuration with `_server_config` (below), then binds `SocketAddr(IpAddr.parse(host), UInt16(port))` with it (`IpAddr.parse` is `inet_pton`: IP literals only). Flare's bind listens, so a client may connect once `bind` returns. A bind failure raises Flare's error; dropping the `Server` drops the `HttpServer`, which closes the listener. `port()` reads `local_addr()`. `serve(mut self, app: App)` borrows the `App` and calls Flare's single-worker `serve` on the calling thread with `_BorrowedHandler(app)`, and nothing else: the handler's pointer lives no longer than that call, which `app`'s borrow outlives. When Flare's `serve` raises, the raise propagates, unless the watcher acted on a stop signal (below), and then `serve` returns; when it returns, `serve` returns, with no policy of its own: after a graceful stop (below), or when the reactor stopped on a failed poll, which Flare records and answers by returning normally; `serve` returning does not distinguish the two, and a `main` that does nothing after it can end with status 0. There is no backend configuration other than the receive body limit, the grace window, the idle timeout and TLS.

Workers (M3-049, decided by [M3-049](history/architecture-decisions.md#multi-worker-serving-decision-m3-049); user-visible contract: `docs/DX.md` section 1) are `serve[make: def() thin raises -> App](mut self, *, workers)`. It raises `workers out of range: <value>` outside 1 to 256 and refuses `FLARE_BUFRING_HANDLER=1` before anything else, then gives each worker a row in a worker table (a close-on-exec copy of the bound listener (`F_DUPFD_CLOEXEC` on Linux; `dup` then `FIOCLEX` on macOS, as Flare marks its own sockets there), so a program the application starts with `exec` cannot keep the port open after `serve` (a child forked without `exec` inherits every descriptor, the `Server`'s listener included, as with `serve(app)`), a stop byte, a `ServerConfig` copy, a state cell, an error slot and the address of the `Server`'s TLS context or 0 ([M3-060](history/architecture-decisions.md#tls-with-workers-decision-m3-060))), claims the process and installs the stop watcher as `serve(app)` does (`_StopWatch`, with the table's address), and starts one pthread per worker (`_serve_worker[make]`). Each worker calls `make()` on its own thread and runs Flare's `run_unified_reactor_loop_shared` (from Flare's internal `_unified_reactor_impl`, the loop its `Scheduler` runs per worker; on Linux it registers the listener without `EPOLLEXCLUSIVE`, which Linux refuses with the `EPOLLRDHUP` Flare v0.12.0 asks for, so every idle worker wakes for a new connection and the first to accept takes it) on its copy with `_BorrowedHandler` over its `App` and that address, which on a TLS `Server` makes every connection it accepts start as a TLS handshake with the `Server`'s one context (shared read-only, as Flare's own workers share it; the `HttpServer` holding it is borrowed until every worker is joined), and destroys its `App` when the loop ends. The serving thread polls the state cells every `_WATCH_POLL_MS`: when it first sees a worker ended on its own (`make` raised, its loop raised or returned) and no stop signal was delivered by then (the order is that of the serving thread's look, not of the worker's end; `stop_delivered`: the watcher acted on one, or a disposition is already back to `SIG_DFL`, which the watcher may not have read yet), it records what ended it then (the first `make` or reactor raise, else a reactor that returned, which Flare's loop does on a failed poll: `_why_ended`), before the stop makes every other reactor return too, and sets every stop byte (a hard stop, no window). A `make`, a handler or an `App` destructor that does not return cannot be interrupted, so a worker still running `_REACTOR_STOP_MS` after a hard stop began (a worker publishes how it ended only once its `App` is destroyed) makes the serving thread print the error and end the process with status 1 (128 + the signal if the watcher has acted on one meanwhile). When every worker has ended with a stop signal delivered and no hard stop, it waits (up to `_REACTOR_STOP_MS`) for the watcher's next turn to act on that signal, so `serve` returns for it instead of `finish` sending it again. Then it joins every worker, then the watcher, closes the copies and the parking pipe (also when that join's restore raises) and raises the recorded error (or, after a stop signal the watcher did not act on, the first `make` or reactor raise), unless the watcher acted on a stop signal. Flare's `Scheduler` and `HttpServer.serve(handler, num_workers)` are not used: a `Copyable` handler cannot build its `App` on its worker, `HttpServer.drain` does not reach the workers' listeners, and `Scheduler.drain` stops every reactor at once with no window.

Graceful shutdown (M3-045, decided by [M3-045](history/architecture-decisions.md#graceful-shutdown-decision-m3-045); user-visible contract: `docs/DX.md` section 1). Flare v0.12.0's reactor reads its stop flag only between events and its `drain(timeout_ms)` must be called from another thread, and Mojo 1.1.0 has no module-level state for a signal handler to write to, so `serve` wraps Flare's `serve` in `_StopWatch`: it installs `_stop_signal_seen`, a handler that does nothing, on SIGTERM and SIGINT with `SA_RESETHAND | SA_RESTART`, saving the dispositions it replaces; it starts one watcher thread (`_watch_for_stop`, through Flare's `ThreadHandle.spawn_os`, the pattern of Flare's own deadline watchdog) with a control block of atomic cells (done, the `HttpServer`'s address, the grace window, the signal it acted on, `drain`'s error and whether it failed); and after Flare's `serve` returns or raises it marks done, joins the thread and puts the dispositions back. The dispositions are process-wide, so before touching them `_StopWatch` claims the process's one serving cell (a compare-and-swap on an `Int64` that the standard library's internal `_get_global` creates once per process, Mojo 1.1.0 having no module-level `var`) and releases it after the restore; another `serve` meanwhile raises `_ALREADY_SERVING`. Every `sigaction` result is checked: a failed install puts back what was changed and raises before serving; a failed read in the watcher is not taken as a delivery; a failed reset to `SIG_DFL` once the watcher has seen a stop (below) ends the process at once with `_exit(128 + signal)`, without draining, since a second stop signal could otherwise be absorbed by the stop handler; a failed restore makes `serve` raise and keeps the claim held, since that signal may keep the stop handler and a later `serve` would save it as the disposition to put back. A child forked while the claim is held inherits it, so a `serve` there raises as already serving. If the watcher cannot be joined (`pthread_join` failed), it may still read the control block, so `finish` puts the dispositions back and aborts the process rather than free it. If `drain` raises, the watcher keeps its error, falls back to `close` (Flare's hard stop) and `serve` raises after the restore. `_StopWatch` compiles only for Linux x86-64 and macOS arm64 (a `comptime assert`), where the `struct sigaction` layout and flag values it writes were verified. The kernel's reset of a delivered signal's disposition to `SIG_DFL` is the only notification: nothing runs in signal context. The watcher reads both dispositions every 50 ms; when one is `SIG_DFL` it resets both to `SIG_DFL` (a second stop signal then takes the default action) and calls Flare's `drain` with the window from `ServerConfig.shutdown_timeout_ms` (`_server_config` writes `shutdown_grace_ms` there; 0 to 86,400,000, default `_DEFAULT_SHUTDOWN_GRACE_MS`, 5000, Flare's default): `drain` closes the listener, sleeps the whole window while the reactor keeps serving the open connections, then sets the stop flag, and the reactor flips `Cancel.SHUTDOWN` on every live connection and closes it. If the reactor has not returned `_REACTOR_STOP_MS` (1 s) after `drain` returned (the signal's detection, up to 50 ms, plus the window), because a handler is still running (the reactor cannot preempt one), the watcher ends the process with `_exit(128 + signal)`. The thread touches only the control block, the dispositions and the `HttpServer` through Flare's documented cross-thread calls, never the `App`; `App.handle` still runs on the serving thread only. A stop that closes the listener before Flare's `serve` has set up its reactor makes that `serve` raise; `Server.serve` returns normally when the watcher acted on a signal, and raises otherwise; it cannot tell that raise from another Flare setup failure at the same moment, which is then dropped too (the process is stopping). After the join, the restore reads each disposition it replaces in the same `sigaction` call; one back at `SIG_DFL` that the watcher did not act on (a signal as `serve` was ending) is sent again once the previous dispositions are back, to the serving thread itself (`raise(3)`, so the disposition is acted on before it returns, provided that thread does not block the signal: a blocked one stays pending on it past the release, so `serve` is supported only on a thread blocking neither signal, `docs/DX.md` section 1), and before the claim is released (on every path that resends: `finish` and a failed install or start), so no later `serve` can have installed its handler by then. `serve` takes a private `_stage` hook, called at five points (`_STAGE_INSTALLED`, `_STAGE_WATCHING`, `_STAGE_SERVED`, `_STAGE_JOINED`, `_STAGE_RESTORED`, the last after the restore and any resend and before the release), through which the stop tests place a signal at each boundary and check that the claim is still held when the resend has been sent; `serve[make]` also calls it at `_STAGE_WORKER_STARTED`, once its first worker thread runs, and at `_STAGE_WORKER_ENDED`, where its serving thread first saw a worker end and has not yet looked for a delivered signal. With workers ([M3-049](history/architecture-decisions.md#multi-worker-serving-decision-m3-049)) the control block also holds the worker table's address and row count, and the watcher calls `_drain_workers` instead of `drain`: Flare's single-reactor `drain`, done for every worker. It replaces every worker's copy of the listener with the read end of a parking pipe whose write end stays open (`dup2`, retried on `EINTR`; `dup3` with `O_CLOEXEC` on Linux, the flag set after it on macOS; both pipe ends are close-on-exec too) and closes the `Server`'s own listener: once no descriptor refers to the listening socket it closes, so new connections are refused, and the reactors' registrations of it go with it. The numbers stay taken until the serving thread closes them after the joins, so no reactor can register or accept on a number the system reused for another socket (a reactor that read the readiness before the swap gets `ENOTSOCK` and leaves its accept loop; one still starting registers the pipe, which never becomes readable). It then waits the window while every reactor keeps serving its open connections (ending it early once no worker is left serving), then sets every stop byte; `_REACTOR_STOP_MS` then bounds the serving thread's join of every worker. A copy whose `dup2` fails is not closed (its reactor may still have the number registered): it stays open, and the socket listening, until the serving thread closes it after the joins; the others are still parked and the listener closed, every stop byte is set at once and `_drain_workers` raises, which the watcher records as a failed drain, so `serve` raises for a hard stop. A worker that ends after a stop signal was delivered (its `make` raised during the window) does not stop the others; its error is printed to standard error, since `serve` then returns. A worker started after the watcher acted (the signal came while the serving thread was still starting workers) builds its `App` and leaves at once: its stop byte is already set, and Flare's loop reads it before its first poll. Every Flare internal the adapter uses (this loop, the stop byte, `HttpServer`'s private listener and its TLS context's address, Flare's thread and pipe) is reached only through `adapters/flare/flare_internals.mojo`, which says what each is relied on for. The worker table's invariants (fixed-length lists whose addresses outlive every reader, acquire and release cells, one writer per slot) are stated beside its cells in `muntin_flare.mojo`.

The receive body limit (M3-044, decided by [M3-044](history/architecture-decisions.md#server-receive-body-limit-decision-m3-044); user-visible contract: `docs/DX.md` section 1) is `Server.bind`'s keyword-only `max_body_bytes` (default `_DEFAULT_MAX_BODY_BYTES`, 10 MiB, Muntin's constant equal to Flare v0.12.0's default), passed to the initializer's `_max_body_bytes`. `_server_config(max_body_bytes) raises -> ServerConfig` checks it against 0 to `_LARGEST_MAX_BODY_BYTES` (`Int.MAX >> 4`, 2^59 − 1, the largest value Flare's chunk-size scanner handles without overflow) and returns Flare's default `ServerConfig` with both `max_body_size` (read by Flare's HTTP/1.1 connection) and `h2.max_body_size` (copied into each HTTP/2 connection; the first does not reach it) set to it. Flare enforces it while receiving, before `_serve_app`, with its own answers per protocol (`docs/DX.md` section 1); the adapter neither sees nor translates them, and nothing in `src/muntin` changed. It is an upper bound, not an acceptance guarantee (Flare's HTTP/1.1 buffered-bytes check, `docs/DX.md` section 1). Flare's opt-in buffer-ring loop (`FLARE_BUFRING_HANDLER=1`, read inside Flare's `serve`; Muntin neither sets nor clears it) is unsupported: `serve` raises `_BUFRING_UNSUPPORTED`, whose text names the Flare version and changes with the pin, before calling Flare when the variable is `1` (`docs/DX.md` section 1; the loopback suite pins the loop's defect on Flare's own `HttpServer`). It is distinct from `App.handle`'s 413s (`FromBytes.max_bytes`, `Json[T]`'s cap), which measure a body already received. `_BorrowedHandler` is not `Copyable`, which keeps Flare's multi-worker `serve` out of reach (`compat/flare/serve/server_handler_not_copyable.mojo`); that is a guard, not the reason for one thread. Application code that builds Flare's `HttpServer` around `MuntinHandler` itself is still unsupported.

The idle timeout (M3-047, decided by [M3-047](history/architecture-decisions.md#server-idle-timeout-decision-m3-047); user-visible contract: `docs/DX.md` section 1) is `Server.bind`'s keyword-only `idle_timeout_ms` (default `_DEFAULT_IDLE_TIMEOUT_MS`, 500, Muntin's constant equal to Flare v0.12.0's default), passed to the initializer's `_idle_timeout_ms`. `_server_config` checks it after the grace window, against 1 to `_LARGEST_IDLE_TIMEOUT_MS` (86,400,000), and writes it into `ServerConfig.idle_timeout_ms`, the one field Flare's HTTP/1.1 and HTTP/2 connection handles both read; 0 and negative values, which Flare reads as no idle timer, never reach Flare. Flare arms the timer at accept and re-arms it after each read and each completed write, relative to its wheel's last tick, which a long handler leaves stale, so it decides whether requests that waited behind a handler are answered or dropped (M3-046); it does not change the one reactor. It runs during M3-045's window too; the reactor closes what is left at the window's end either way.

TLS (M3-051, decided by [M3-051](history/architecture-decisions.md#server-tls-decision-m3-051); user-visible contract: `docs/DX.md` section 1) is `Server.bind`'s keyword-only `tls: Optional[Tls]` (default `None`, which binds exactly as before), passed to the initializer's `_tls`. `Tls` is the adapter's own value type, two keyword-only paths (`cert_file`, `key_file`), so no Flare or OpenSSL type appears in `Server`'s signatures. With a value, after `_server_config` and the host is parsed, `_check_tls_files` reads both files and raises naming the file when one cannot be opened or read, is empty or is over 1 MiB: `_read_tls_file` opens the path once with `O_NONBLOCK` and reads it in chunks, never more than one byte past the bound, so a FIFO with no writer reads as empty and a device such as `/dev/zero` stops at the bound (`O_NONBLOCK` does not make every read immediate: a slow disk or network file system can still delay `bind`), and no file type, hence no platform's `struct stat`, is needed; it reads through `std.io.FileDescriptor`, which in Mojo 1.1.0 is a trivial register type that does not own the descriptor, and closes the descriptor once itself, in a `finally` that also covers the buffers' allocation (`test_file_descriptor_does_not_close_what_it_wraps` pins the ownership); when the certificate file has no `-----BEGIN CERTIFICATE-----` line, or when the key file's first private key block is encrypted or there is none. `_pem_begins` looks only at lines that begin PEM blocks, in place, without copying the key's other bytes; every buffer Muntin reads either file into (the read chunk, a buffer outgrown while reading, the gathered bytes; the certificate's too, since a key given as `cert_file` or a file holding both lands there) is overwritten with zeros through volatile stores before it is freed, on success and on error (the growth is `_append_wiping`, which is not `raises`, so no error can leave a copy half made), which wipes those buffers only: not the copies OpenSSL makes when it loads the key, nor any temporary copy the compiler or runtime makes (not checked), so it is no guarantee that no copy of the key stays in process memory; the checks are a best-effort diagnosis, and OpenSSL's load decides; then the initializer calls Flare's `HttpServer.bind_tls(addr, cert_file, key_file, ["h2", "http/1.1"], config)` instead of `bind`, with the same `ServerConfig`. Flare's own failure to load the pair (its error starts `flare_ssl_ctx_new_server failed` and carries no reason) is raised as one Muntin message naming both files and no cause; any other error propagates. Flare takes paths and OpenSSL opens them again (`SSL_CTX_use_certificate_chain_file`, so the intermediates are sent; `SSL_CTX_use_PrivateKey_file` with no passphrase callback), so a file replaced between the check and the load is loaded unchecked: the check is a start-up diagnosis, not a guarantee about the bytes OpenSSL reads. ALPN is Flare's too: with no protocol in common it answers without ALPN, which RFC 7301 section 3.2 says it SHALL refuse (`no_application_protocol`). Flare runs each TLS connection's handshake on the same reactor, re-arming the idle timer after each handshake event (so it bounds a pause, not the whole handshake), then hands the connection to its HTTP/1.1 or HTTP/2 handle by the negotiated ALPN, so `serve`, `serve[make]` (above), `_BorrowedHandler`, the stop and every setting are unchanged: nothing else in the adapter and nothing in `src/muntin` knows whether a request arrived over TLS.

`adapters/flare/test_server.mojo` and the loopback suite bind with `Server.bind("127.0.0.1", 0)` in the parent and fork a child that calls `server.serve(app)`, so readiness is `bind` returning, with no sleep or retry; the parent kills the child (SIGKILL, or SIGTERM and SIGINT in the stop tests) and reaps it, and the child arms a 30 s `alarm`. The stop tests' children keep the runtime's handler they inherit through `fork` until `serve` replaces it, and exit 0 only when `serve` returned with it back in place; the parent reaps them within a bound (`_reap_within`) and SIGKILLs one that outlives it, which fails the test.

### Mojo 1.1.0 facts the design rests on

- A function type such as `def() -> String` is a trait, so stored handlers are thin function values; closures and storable capturing handlers do not convert to `_Call[F]` (`tests/spike_fail`, `state_fail/closure_handler_storage.mojo`).
- Parametric raises (`thin raises E`) infer the error type without overload ranking. An explicitly typed non-raising function value (`var f: def() thin -> String`) does not convert to it; spell it `def() thin raises Never -> String` (raw: `def(var Request) thin raises Never -> Response`) (`storage_fail/typed_thin_value_handler.mojo`).
- An explicitly typed function value with a borrowed parameter converts to no generic slot (`registration_fail/typed_value_to_owned_slot.mojo`), so typed values and helper parameters spell each request parameter `var` (`def(var Int) thin raises Never -> String`; a leading `State[S]` keeps its spelling). Plain `def` handlers convert either way.
- `rebind_var` checks layout, not the nominal type (`registration_known_gaps/rebind_var_layout_twins.mojo`, `registration_fail/rebind_var_layout_mismatch.mojo`).
- Generic `==` keeps an origin's mutability but not its identity (`registration_known_gaps/generic_equality_ignores_origin_identity.mojo`), and `Origin.equals` works only in `where` clauses (`registration_fail/origin_equality_not_in_comptime_if.mojo`); a `where` clause on an overload compares by identity at the call site, which is why the result rule is one.
- Reflection exposes struct fields but not function parameter names, so binding is positional; reflection has no constructor, so codecs are hand-mapped.
- Module-level variables do not compile and thin handlers cannot capture, so `State` is the only way a handler reads runtime data. The same two facts make `serve[make]`'s workers share nothing: a closure that captures at run time is not a compile-time value, and a compile-time closure that captures is `capturing`, which a `thin` function type refuses (`compat/flare/serve/serve_workers_runtime_closure.mojo`, `serve_workers_capturing_make.mojo`).
- There are no private fields and no existentials; `__extension` is undocumented and never part of the supported contract (`__extension Int(...)` is rejected and `StaticString` is an alias, but `__extension SIMD(...)` in a trait's own module does give `Int` that bound while `conforms_to(Int, ...)` stays false, which is why the body slot rejects `Int` by type equality).
- `ArcPointer.__getitem__` is mutable through any handle, which is why `State` uses `_Shared` (`tests/state_storage_known_gaps`).
- A trait may require a `comptime` member (`comptime max_bytes: Int` in `FromBytes`, M3-043): a struct whose traits give the member no default that does not declare it, or declares another name (`max_byte`), does not conform (`required member 'max_bytes' is not specified`), but under a refining trait's default a misspelled member is accepted silently and the default inherited, `Int.MAX` included (`tests/bytes_limit_known_gaps`, must build); it declares it once (`invalid redefinition`), as an `Int` (another type does not conform), possibly from a struct parameter (`Blob[limit]`), and a refining trait may give it a default its types inherit or override. Generic code reads it after `conforms_to` (`_slot`, `_kind`, the carrier's `_max_bytes`) at compile time. A struct member Muntin does not require, such as `max_bytes` on a `FromBody` type, is accepted silently (`tests/bytes_limit_api_fail`, `tests/test_bytes_limit.mojo`). Had the member a default in `FromBytes` itself, a misspelling would be accepted silently and a refining trait's default would conflict with it (`conflicting default implementations`), measured for M3-043.
- The runtime installs its own handler for SIGHUP, SIGINT, SIGQUIT and SIGTERM in every binary; it restores the dispositions the process inherited and raises the signal again, so a serving process ends by SIGINT or SIGTERM unless it inherited them ignored (measured by hand on Linux for M3-033 with a built `Server` program and a plain Mojo program). It also replaces an inherited ignore with its handler before `main` runs, so `sigaction` shows a handler, not `SIG_IGN` (measured for M3-045), and `Server.serve` cannot tell an inherited ignore apart. `Server.serve` replaces this handler while it serves and puts it back (M3-045); the stop tests check that it is back (after a return and after a raise), a second stop signal during the window ends the child by the signal itself, and two tests `execv` a built program (`adapters/flare/stop_driver.mojo`, built by `check_flare.sh`) so that the runtime's threads and handlers are present and `main` returns: one stops on SIGTERM with a request in flight, one on SIGINT although it started with SIGINT ignored.
- A Mojo 1.1.0 binary has four runtime worker threads before `main` runs, none blocking any signal, so a signal sent to the process may be delivered on any thread: blocking signals in the serving thread cannot keep them from the runtime's handler, and a handler, not a mask, is what `Server.serve` relies on (M3-045).

- Absolute-form targets (`http://host/path`) become the whole `path` and are 404.
- The adapter checks that an HTTP/1.1 or HTTP/2 request has a `Host` field (M3-073), not its value, which RFC 9112 answers 400 when invalid (a candidate in `docs/SPEC.md`). An `Upgrade: h2c` request without `Host` gets Flare's 101 before the adapter's 400 on stream 1.
- Bodies are whole `List[UInt8]` values (M3-040): nothing is streamed, a request body is held in full (the `Server`'s `max_body_bytes`, 10 MiB unless set, bounds it as Flare receives it, M3-044; a `FromBytes` type's `max_bytes`, M3-043, bounds only what reaches `from_bytes`, after the body was received), and a typed body is either UTF-8 text (`FromBody`) or the whole bytes (`FromBytes`, M3-041); streaming and multipart bodies are not implemented ([M3-040](history/architecture-decisions.md#binary-request-and-response-bodies-decision-m3-040)'s revisit conditions). A `String` that holds bytes that are not UTF-8 comes only from an unsafe-named constructor or from a backend (Flare builds the method, target and header values over h2c that way, and the adapter checks each before `App.handle`).
- Over HTTP/1.1, Flare v0.12.0 frames every 304 with a `Content-Length`: a declared one, or else the body's length, so 0 for an empty body. A `HEAD` 304 therefore goes out with `Content-Length: 0`, which the adapter cannot remove, and a `HEAD` 205 too (0 is a 205's `GET` content length); over h2c neither carries a `content-length` ([M3-026](history/architecture-decisions.md#head-decision-m3-026), measured by `compat/flare/head/head_probe.mojo`).
- Over HTTP/1.1, with Flare v0.12.0's default HTTP/1.1 parser settings, Flare answers a method with any lowercase letter (`get`, `Get`, `delete`) with 400 before `App.handle`, which would answer it as any method no route has (405 on a path some route matches, 404 elsewhere); an unknown uppercase method (`FOO`) reaches `App.handle` and gets that answer ([M3-020](history/architecture-decisions.md#http-methods-decision-m3-020), [M3-030](history/architecture-decisions.md#method-not-allowed-decision-m3-030)).
- Static path segments are not checked for target bytes: `/hello world` compiles and matches in memory but never arrives over Flare's HTTP/1.1, which rejects target bytes outside `!`..`~`.
- `main.mojo` uses `TestClient` because it builds in the default environment, which has no Flare; serving needs the `flare` environment (`examples/hello_server.mojo`).
- The localhost round trip and `test_server.mojo` need `fork(2)` (Windows is out of scope), and `test_server.mojo`'s `::1` case needs IPv6: it is skipped only when `socket(AF_INET6, ...)` fails with `EAFNOSUPPORT` and the environment variable `CI` is unset, so it always runs on the CI runners (GitHub Actions sets `CI`), and a host that creates IPv6 sockets but cannot bind `::1` fails it rather than skipping it; a serving child exits by a signal, the 30 s alarm, or, in the stop tests, a graceful stop. The round trip's first `/hello` request is slow on a cold start (about 26 s locally once, up to 64 s on macOS CI); look there before blaming routing if it flakes.
- `ubuntu-latest` moves to Ubuntu 26 from 2026-10-19. If the `flare` job breaks after that, compare `ImageOS`/`ImageVersion` in the `runner image` step before blaming Muntin or Flare; delete this line once a `flare` job has passed on Ubuntu 26.
- Two reliances of the workers have no test that fails when they stop holding ([M3-070](history/architecture-decisions.md#backend-coupling-decision-m3-070)):
  - Flare's accept loop leaving on `ENOTSOCK` once its listener copy is parked (M3-049's stop). No test can place a reactor between reading readiness and the swap; a control point there, or a Flare change to the loop, is when to add one. If it stopped holding, that reactor would retry the accept and never read its stop byte: its open connections go unserved through the window, and the watcher's bound (`_REACTOR_STOP_MS` after the window) ends the process with `128 + signal` instead of `serve` returning. Risk left: one worker's connections lost and the code after `serve` skipped at a stop.
  - One OpenSSL `SSL_CTX` used by every worker at once (M3-060). OpenSSL's [threads page](https://docs.openssl.org/3.0/man7/openssl-threads/) says a factory object such as an `SSL_CTX` must not be modified after it has created other objects, and says nothing more about creating from one concurrently; the workers rely on Flare not modifying it after `bind_tls` (not read in Flare's source for M3-070), and `test_https_workers_handshake_on_every_worker` shows one handshake on each worker, not several at once (a test that starts handshakes on every worker together closes it). If it stopped holding, concurrent handshakes would race inside OpenSSL: failed handshakes or a crash of the process, every worker with it, and nothing detects or contains it. Risk left: that, on a TLS `Server` with more than one worker; one worker avoids it.
- The `flare` CI job rebuilds Flare's C/C++ FFI wrappers on every run (about a minute, no cache). Flare's `Request` is `Movable` with `List[UInt8]` bodies, so the adapter copies into Muntin's types (one copy each of the method and the target into `String`s, validated as UTF-8 on the way, and one of the body bytes; one copy of the response body out). Measured in pull requests #114 and #125 (`scripts/bench_overhead.sh`, in process, one request, `MuntinHandler.serve` against `App.handle`): the adapter adds about 0.1–0.2 µs to a bodyless request with no header fields and about 145–190 µs to a 1 MiB echo. #125 counts four body-sized allocations per echo through the adapter against two through `App.handle` (the raw `Request` slot's copy and the handler's own) and times one 1 MiB copy alone, its allocation included, at about 50–55 µs; twice that is about 100–110 µs, an estimate of the adapter's two copies, not a measurement of them (they were not timed inside the adapter, where several body buffers are live at once), so what removing them would save is not established; with distinct header names, its request header conversion takes about 4 µs at 8 fields, 11 µs at 16, 26 µs at 32 and 260 µs at 128 after pull request #110, against 12 µs, 45 µs, 170 µs and 2.6 ms before it. Flare HTTP/3 is unavailable from the conda build.

### When M2 reopens

M2 is closed (M2-016); its contract is `docs/SPEC.md`, "M2 completion contract". Reopen it, rather than add an M3 item, when a toolchain upgrade changes what the contract rests on (overload resolution, parametric raises inference, `conforms_to` detection), when a design must change an M2 public signature or semantics instead of adding to them (the `Request(method, target, body)` initializer, the 400/404/500 boundary, a fallible `ToResponse`/`ToErrorResponse`), or when a statement DX labels proven stops passing its test. Exact conditions: [M2 closure (M2-016)](history/architecture-decisions.md#m2-closure-m2-016).

## Request/Response ownership

`Request` and `Response` own their data. Do not optimize around zero-copy wire buffers if that leaks backend lifetimes into the public API; before changing the ownership model, measure the cost and record the concrete requirement that justifies more lifetime complexity.

The owning `App.handle` (M3-064) removes the request copy before middleware, not every copy: the Flare adapter still copies the body out of Flare's request, and routes copy what [request handling](#request-handling) lists.

## Flare policy

Flare is a candidate backend because it already provides a substantial Mojo networking stack, including server/client protocols and its own routing/handler facilities. Muntin must not simply re-export those application abstractions.

Allowed inside the Flare adapter:

- Flare server/bootstrap APIs;
- conversion from Flare request data into Muntin request data/views;
- conversion from Muntin responses into Flare responses;
- transport lifecycle integration;
- backend-specific optimizations hidden behind the adapter.

Not allowed in durable Muntin public APIs:

- Flare `Request`/`Response` types;
- Flare `Router` as Muntin's routing contract;
- Flare middleware types as Muntin's middleware contract;
- Flare extractors as Muntin's only extraction model;
- Flare reactor/cancellation/runtime types in normal application handlers.

A pinned Flare version is required once M1 depends on it. Track `main` only for explicit compatibility investigation, never as the default reproducible dependency.

Three layers ([Backend coupling decision (M3-070)](history/architecture-decisions.md#backend-coupling-decision-m3-070)). `App.handle` and everything behind it is backend-independent (A2, A3). What every network backend owes Muntin's semantics (["Backend seam"](#backend-seam): one `App` never called from two threads at once, the raw target passed undecoded, body bytes copied unchanged both ways, a `HEAD` answer's content kept off the wire with its length) is Muntin's contract, which a second backend keeps. Keeping an `App` on one thread is not in it: a backend that calls one from several threads in turn must order the calls (each returns before the next starts, and happens before it), and the application's `State` values must then be safe to use on another thread, with interior mutability synchronized as that needs; Muntin checks neither. Serving is the Flare adapter's, not a seam: `Server`, its settings, its threads (`serve(app)` keeps its `App` on the calling thread and `serve[make]` each worker's on that worker, so there a `State` value's interior mutability stays on one thread), `serve[make]`'s workers (how many `App`s exist, on which threads, for how long, and so what one `State` value sees) and its stop; with workers its stop watcher, worker table and listener parking drive Flare's per-worker loop through the internals in `adapters/flare/flare_internals.mojo` and rely on how that loop registers, polls and leaves, and its contract (`docs/DX.md` section 1) is in large part Flare v0.12.0's behavior. The first two layers are designed to carry over, not demonstrated: there is one network backend. What applications keep: `docs/DX.md` section 11.

A change that makes the adapter's code (not its tests, which list their own Flare internals in `flare_internals.mojo`'s docstring) rely on something no public contract states:

- a Flare name that is not public;
- a behavior of Flare's, of a library Flare loads (OpenSSL) or of the operating system's that its documentation at the pin does not state (the docstrings of Flare's public names and its README; OpenSSL's and the system's manual pages): a format, an order, a timing, a side effect, a silent fallback. The request and response conversion is included: a loopback case is its test, not an exemption.

Such a change:

- names it where the code relies on it: a Flare name in `flare_internals.mojo` with what it is relied on for, a behavior in a "Relied on" statement beside the code that relies on it (or in `flare_internals.mojo`'s docstring, with a comment at that code pointing to it);
- has a test that fails when it stops holding, on each platform that relies on it, and says whether the test observes the condition itself or only an outcome of it, and which break it would miss (an outcome test does not show an order or a memory ordering). Where no test can, the statement says what a break would do and what, if anything, detects or contains it at run time, and the record names the risk left, which the owner accepts by merging;
- has a record (the decision item's, or the one whose slice it implements) that counts the reliance among the candidate's costs, says why Flare's public API, and a proposal to Flare's maintainers, were not taken instead, and states the adapter's size before and after: the entries in `scripts/check_flare_reliance.sh`'s lists and the lines of the adapter's modules, every `.mojo` file under `adapters/flare` but its `test_*.mojo` tests (2,111 at M3-070).

Removing a reliance needs none of this. Replacing a non-public Flare name with a public one whose undocumented behavior is then relied on needs all three, but the third may be its pull request instead of a record. A change that takes those modules past 2,500 lines together, whatever it relies on, waits for a decision that weighs the growth against a public entry point proposed to Flare and against a narrower `Server`.

`scripts/check_flare_reliance.sh` (run by `check.sh`) is the mechanical part, a ratchet on names rather than a Mojo parser. Over the adapter's modules (`.mojo` or `.🔥`, in any directory under `adapters/flare`, `test_*` tests aside), it fails when a module other than `flare_internals.mojo` imports a `_`-prefixed Flare module or name; when `flare_internals.mojo`'s Flare imports, or the `_`-prefixed members (`._name`) and keyword arguments (`_name=`) its code uses, differ from the script's lists either way, so a new name shows in the diff and a stale entry cannot stay (a `_`-prefixed variable is not a keyword argument); when a module imports a `test_*` module, which it does not read; when the modules pass 2,500 lines together; and when it cannot list or read a module, or a module holds what it does not read (a string, bracket, backquote or template expression left open, or a template expression holding a quote, backslash, `#` or backquote), rather than skip code. It reads statements after strings and comments are removed, so an import after `;`, on a `\` continuation, in a parenthesized list or after `if x:` on one line counts, as do a template string's `{expression}` and a backquoted name, and a name in a docstring does not. `scripts/test_check_flare_reliance.sh` (also run by `check.sh`) runs it on edited copies of the adapter and pins what it reads, what it refuses and what it leaves out. A behavior has no name, and a private member or keyword outside `flare_internals.mojo` looks like Muntin's own, so review applies the rest.

## Adapter translation policy

It is acceptable for `muntin/adapters/flare` to contain inelegant conversion code if that keeps the public/core model stable. Do not contort the Muntin API merely to make one adapter thin.

Conversely, if the adapter repeatedly copies large bodies or cannot express a common feature without severe cost, treat that as evidence for a focused core abstraction change. Measure and document the tradeoff first.

## Architecture tests

At minimum, tests should establish:

1. an application route is dispatched through the Muntin-owned app model;
2. the in-memory backend can drive that route without Flare or sockets;
3. core/public modules do not import Flare;
4. a real localhost request traverses Flare -> adapter -> Muntin app -> adapter -> Flare;
5. the same application handler can be exercised by both in-memory and Flare paths without changing its public signature.

## Architecture decision threshold

Record a decision before:

- exposing any third-party type publicly;
- introducing a custom runtime/executor/task model;
- making a transport mandatory;
- adding unsafe memory/lifetime machinery to a public contract;
- changing request/response ownership semantics;
- changing the backend seam in a way that breaks adapters;
- making the Flare adapter rely on something no public contract states ([Flare policy](#flare-policy));
- making a provisional DX example a frozen compatibility promise.
