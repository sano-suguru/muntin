# Typed header access decision (M3-012)

> **Current.** Now described in [bodies reference, "Header fields with a body (`WithHeaders[B]`)"](../../reference/bodies.md#header-fields-with-a-body-withheadersb) and [headers reference, "Reading fields in a handler"](../../reference/headers.md#reading-fields-in-a-handler).
> Changed in part since:
> - [M3-015 production](m3-015-registration-on-generic-arity-slots-in-production.md): the "no overload added; get and post keep ten" invariant and the eight body overloads gave way to the arity overloads.
> - [M3-016](m3-016-typed-get-header-access-decision.md): typed get handlers now read fields through a last `Headers` parameter (this record gave get no header access).
> - [M3-030](m3-030-method-not-allowed-decision.md): the carrier route order now starts with 404, or 405 with Allow.
> - [M3-042](m3-042-typed-binary-request-bodies-with-header-fields-decision.md): the carrier's bound widened from `B: FromBody` to `_FromBodyOrBytes`, so it also carries a FromBytes body.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-012; `src/muntin` and `adapters/` are unchanged in it; production since M3-013, "Typed header access in production (M3-013)" below). It decides how typed handlers read request header fields, which M3-002 deferred. It settles two costs that earlier records named. First, M3-001 recorded that typed headers would compete for its single injected slot. Second, `get` and `post` already have ten overloads each, which is Mojo 1.1.0's diagnostic note cap (M3-007).

**Selected: C, a Muntin-owned body carrier, `WithHeaders[B]`, in `post`'s existing body slot.**

```mojo
struct WithHeaders[B: FromBody](Deinitable, Movable):
    var headers: Headers              # the request's fields: M3-002's model, unchanged
    var body: B                       # converted by B.from_body, as any body
    def take_body(deinit self) -> B   # moves the body out
```

```mojo
def create_user(
    users: State[Users], input: WithHeaders[Json[CreateUser]]
) raises Unauthorized -> Json[User]:
    var token = input.headers.get("authorization")    # Optional[String]
    if not token or not users[].allows(token.value()):    # a read-only Users method
        raise Unauthorized()                          # ToErrorResponse: 401
    return Json(User(1, input.body.value.name))

app.post["/users"](create_user, users)                # existing stateful overload
app.post["/notes/{id}"](update_note)                  # def(Int, WithHeaders[Note]): existing overload
```

- **How the slot conflict is settled.** M3-012 does not put request headers in the existing injected slot, which stays registration-bound: it holds a `State` bound at the registration call. Header fields are request data, like the body. So they travel with the body, in the body slot, wrapped by a Muntin type the overloads recognize, as `Json[T]` already does there (M3-008). Header access takes no injected slot, adds no injected kind and adds no overload. This decides headers only. Whether request-scoped injection (a middleware context, for example) gets a slot of its own is a separate decision; nothing here rules it out. `State` composes with it unchanged: the stateful body overloads take the carrier as their body (`def(State[S], var WithHeaders[B])`, `def(State[S], Int, var WithHeaders[B])`).
- **Shapes.** The carrier is a body on every shape that takes one: `def(var B)` and `def(Int, var B)`, stateless and stateful, both result policies (the eight body overloads). A handler may borrow it (`input: WithHeaders[B]`) or own it (`var input`). It is not a body on `get`, because `get` has no body slot (below). Raw handlers are unchanged and still receive the whole `Request`.
- **Fields.** `input.headers` is the request's `Headers`, M3-002's model exactly: every field in order, original casing, repeated names as separate fields, empty values as values. `get` returns the first value, matched ASCII case-insensitively, or `None`. `get_all` returns every value in order.
- **Names are runtime values** passed to `get`/`get_all`. The match is ASCII case-insensitive, and an unknown name is `None`. Compile-time names are rejected (below).
- **Missing, repeated and invalid fields: Muntin chooses no status for a header field on a carrier route and gives it no meaning.** A missing field is `None`, and repeated fields are kept. Fields made through the supported `Headers.add`/`set` API, and those the Flare adapter delivers, are valid: `add` validates at insertion, and the adapter answers 400 before `App.handle` to a field Muntin cannot represent (M3-005). The M3-002 known gap (`headers._fields` is reachable by name and bypasses `add`) can build an invalid in-memory `Headers`; on a carrier route that is the fixed 500 (below). Interpreting a value (a scheme, a number, a precondition) belongs to the application. Its failure is a handler error, answered by the declared error type's `ToErrorResponse` or the fixed 500 (M2-013). So there is no pre-handler 400 for header fields. This asymmetry with `from_body`, whose raise is 400, is deliberate. The right status depends on the field: 401 for a missing credential, 412 or 428 for preconditions, 400 for a malformed value. Muntin cannot choose it, and the handler can, through its error type. Two existing checks still answer before the handler on a carrier route: M3-008's `Content-Type` verdict for a `Json[T]` body (415), and the rebuild of a field written through the `_fields` gap (the fixed 500, below). A `FromHeaders` converter with its own 400 would be an additive layer (revisit conditions).
- **The body inside.** `B` must conform to `FromBody` (the struct's bound). It is converted by `B.from_body` exactly as a bare body, and a raise is 400 before the handler. `WithHeaders[Json[T]]` keeps the JSON steps, because the carrier conforms to the private `_JsonBody` exactly when `B` does (conditional conformance). Order on a carrier route: 404 → query value 400 (`App.handle`) → route value 400 → for a JSON body, 415 then 413 → field rebuild 500 (the `_fields` gap only) → `from_body` 400 → handler → result conversion. The carrier is not itself a `FromBody`, so a body alone cannot produce one through body conversion: it has no `from_body`, and nothing can turn a body into an empty-field carrier implicitly. Manual construction stays possible (`WithHeaders(body^, headers^)`), and it takes an explicit `Headers` value. A carrier inside a carrier, `WithHeaders[Int]` and `WithHeaders[Json[T]]` without `T: FromJson` are rejected where the handler is declared.
- **Ownership and cost.** Per request, `App.handle` copies each field's name and value into the route's raw arguments. This is the R1 transport raw routes already use (M3-002), and `_Call`, `_Erased` and the storage module do not change. The adapter rebuilds one `Headers` from those strings and moves it, with the converted body, into the carrier. The carrier is then moved into the handler or lent to it. Cost per request, on carrier routes only: two copies of each field name and value (into the raw arguments, then into the rebuilt `Headers`, whose `add` validates each field again), as raw routes already pay. Every other route's raw arguments are unchanged (measured below). There is no client, route or per-request state, and nothing is copied beyond that transport and rebuild. A field cannot be moved out of the middle of a value on Mojo 1.1.0, so `take_body(deinit self)` moves the body out, as `Json` has `take`.
- **Rebuild failure.** The adapter rebuilds the fields through `Headers.add`, which validates them again. Fields from the supported API and the backend path pass, so the rebuild normally cannot fail. A field written through the `_fields` gap can fail it; the answer is then the fixed 500, as for `_raw_request`, never 400 (`test_invalid_in_memory_fields_are_the_fixed_500`; mutation M14).
- **M2 stays closed.** No M2 signature, binding rule or 400/404/500 boundary changes. Application `FromBody` bodies keep every rule, and the body slot gains a Muntin type besides them. Unlike M3-008's `Json[T]`, which is itself a `FromBody` when `T: FromJson`, the carrier is not one (cost below). The relaxed assert keeps its message, and selection is unchanged (the carrier is not `Int`, `Request` or a `State`).

**`get`: typed `get` handlers get no header access in this decision.** A `get` route that needs header fields uses the raw `get` (`req.headers`), or the stateful raw `get` with its `State`, both existing. Mojo 1.1.0 gives `get` no slot that a Muntin type can ride in for free. Its typed parameters are fixed by type equality (`Int`) or by registration arity (`State[S]`). **Why C now rather than D0.** The question is whether an asymmetric public type that exists because of Mojo 1.1.0's overload budget is worth adding before registration is restructured. Yes, for three reasons:
- D0 is not neutral on `post`. Deferring means a credential beside a typed JSON body either loses M3-008's `Content-Type` rule and cap (raw) or cannot read the credential (typed). C keeps every typed step and adds only the fields.
- C uses an existing structural asymmetry: `post` has a body slot and `get` does not. The typed-header capability it gives is therefore asymmetric (typed `post` handlers read fields, typed `get` handlers do not) until registration is restructured. C adds nothing to `get` and changes no `get` behavior.
- C adds no overload family, and the carrier can stay a useful input type after a later registration redesign. It does rely on the current body overloads recognizing it (the slice edits the eight body overloads' assert and flag), but it is a body type, not an overload: a later registration redesign, a body-less `POST` or a request-scoped context can be added beside it without changing it. If a context later carries headers for every method, `WithHeaders` is still a valid body type, and retiring it would be a pre-1.0 API removal that the record of that decision would have to justify.
The cost accepted: one public type whose scope is `post` bodies, accepted in the body slot without being a `FromBody` (Cost below), and the revisit condition below if a context generalizes request parts.

**Invariants:**
- The existing injected slot stays registration-bound (`State`); request headers do not use it. Introducing request-scoped injection needs its own decision.
- No `get` or `post` overload is added for header access; both keep ten.
- A carrier route's handler sees the request's fields in order, with their casing, repeats and empty values. On a carrier route Muntin chooses no status for a field and gives it no meaning; the `Content-Type` verdict for a `Json[T]` body (415) and the rebuild of an invalid in-memory field (the fixed 500) still answer before the handler.
- Non-carrier routes' raw arguments are unchanged; typed routes without a carrier receive no header strings.
- The raw `Request` handler stays the low-level escape hatch, on both methods, stateless and stateful.
- No backend type reaches the carrier, and `_Call`, `_Erased` and the storage module do not change.

**Cost.** `FromBody` no longer names every type a `post` body slot accepts. `WithHeaders[B]` is a carrier the framework recognizes beside `FromBody` (the overloads and adapters accept `FromBody` or the private `_HeaderCarrier`), so generic application code constrained to `B: FromBody` does not accept it. This is accepted rather than avoided because the alternative, C′, would let a body alone produce a carrier without the request's fields. A handler that reads fields names them in its signature (`WithHeaders[...]`) and reads the body as `input.body` (`input.body.value` for JSON). A missing or malformed field is the application's error type to answer. Typed `get` handlers cannot read fields until a registration-structure decision. Carrier routes copy each field name and value twice per request and validate each field again, as raw routes do.
