# Several route values decision (M3-022)

> **Current.** Now described in [route-values reference, "Two route values"](../../reference/route-values.md#two-route-values), [routing reference, "Route literals"](../../reference/routing.md#route-literals) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Changed in part since:
> - [M3-024](m3-024-optional-query-values-decision.md): a value `V` may also be `Optional[Int]` or `Optional[String]` (later also `FromRouteValue`, M3-054).
> - [M3-048](m3-048-bodyless-typed-post-put-and-patch-handlers-decision.md): `def(V, V)` and `def(V, V, Headers)` also register on post/put/patch (bodyless).
> - [M3-050](m3-050-named-route-values-decision.md): opt-in `Param[name, T]` checks a value's placeholder name; bare values stay positional.
> - [M3-061](m3-061-route-value-records-decision.md): three or more values through a `RouteValues` record, M3-022's rejected candidate D.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-022, PR #54; `src/muntin`, `adapters/` and `tests/` are unchanged in it). It decides how a typed handler receives more than one route value, from several `{name}` path segments, several `{key}` query items or both, on every registration method. Today a typed handler takes at most one, and a raw literal declares none, so `/users/{uid}/posts/{pid}` and `/users/{id}?{fields}` are unreachable by any handler.

**Why this candidate.** Of SPEC's remaining candidates:
- Several route values: nested resources, a path value with a query value, and DX section 3's two-key search cannot be routed at all: a typed handler takes one value and a raw route captures none, so an application whose URL scheme is given (an existing API, a client it does not control) has no way to serve them. [M2-005](m2-005-argument-extraction-decision.md)'s positional rule already covers several values, but no slice was ever cut for them (M2-016's scope note). M3-018 settled what a value is (decoded at capture, `Int` or `String`, non-empty) and said several values are cheaper after that; M3-020 named this item its runner-up. What is still open is public and hard to change once applications depend on it: how many values a handler takes, how the slot arity that costs is paid on five method names (M3-020's slot-arity revisit condition), how values bind to parameters with no parameter-name reflection, what a literal's names must satisfy, and which existing diagnostics change.
- `HEAD`, `OPTIONS` and 405 with `Allow`: RFC 9110 section 9.1 says general-purpose servers MUST support `HEAD`, and today it is 404. But 405 with `Allow`, and `HEAD` or `OPTIONS` answered automatically from the routes, need a resource-level method set the router does not have (M3-020, candidate F), and 405 reopens the M2 contract's 404 for every method. Explicitly registered `head` and `options` handlers would not need that set, but M3-020 left open whether they are registered or automatic, and their semantics are a decision of their own, less settled than the route-value seam: `OPTIONS` is entangled with CORS and middleware, and how Flare treats `HEAD` is unmeasured. It answers new methods on paths that are already routable, but makes no new path or parameter shape routable; several route values, by contrast, build on a seam already settled (M3-018, M3-020).
- Bodyless typed `post`, `put` and `patch` handlers: a `FromBody` type that accepts any body (`def(V, Ignored)`) serves such a route today, so it unblocks no route; it is a rule change on `post`'s family, decided on its own (M3-016 and M3-020 revisit conditions).
- Optional or default query values: most uses need a second value (`?{q}&{limit}` with a default limit), so they come after this item, and how a default reaches a `def(var A)` slot is unresolved (M3-020).
- `Json(value, status=)`, a configurable JSON cap: an application `ToResponse` type answers with any status today; the cap is fixed on purpose until a concurrent backend (M3-008).
- Middleware, lifecycle (`app.run()`), streaming, observability: no handler shape depends on them, so postponing them builds nothing on a wrong seam, and each is larger and less settled on Mojo 1.1.0 (M3-018, M3-020).
- Schema/OpenAPI waits for a derived codec; parameter-name checking waits for function-parameter reflection.

**Question.** How does a typed handler receive several route values? Specifically: how many values one handler may take; which slot arities that needs and what it costs in overloads and candidate notes on `get`, `post`, `put`, `patch` and `delete`, and whether one overload set copied per method name still holds at the new arity; how the values bind to parameters, and what a route literal's placeholder names must satisfy; how `App.handle` captures several path and query values; and which existing rules, diagnostics and M2 statements change.

**What settles it:**
- the overload and note cost of each bound, from the existing measurements: M3-014's scratch copy at slot arity 3 (eight candidates, every note printed), the ten-note cap (`tests/header_access_fail/eleven_candidates_drop_a_note.mojo`) and the per-name budget (`tests/registration_fail/notes_are_per_method.mojo`);
- binding: M2-005's positional rule and its revisit condition (function-parameter names), and, for a named alternative, the reflection facts M2-005 and M3-008 recorded (struct field access, no constructor);
- what changes in `_Route`, `App.handle`, the rules, the adapters and the overloads, read from the current code;
- every existing diagnostic, fixture and test whose text or outcome a candidate changes, found in `_check` and `tests/`, and whether any statement of the M2 contract changes, as an addition or as a reopen under [M2-016](m2-016-m2-closure.md);
- a scratch compile or runtime probe only where these leave a candidate's outcome unknown.

**Boundaries that do not change silently:**
- every shape with zero or one route value: its rules, its runtime behavior, and every existing diagnostic, unless this record names the change and why;
- route-value capture (M3-018): decoded once in `App.handle`, `Int` or `String` by exact type equality, a placeholder binds one non-empty value, the closed invalid set, all 400 before the handler; query keys matched undecoded; `Request.path`, `Request.query` and raw handlers undecoded, raw literals declaring no placeholder;
- the registration structure: overloads per request-slot arity, stateless and stateful, per method name, the `where` clause on the result, the rule guard, one `rebind_var`, the storage module and unsafe confinement;
- `State[S]` as the one injected slot, first; the body last on `post`, `put` and `patch`; `Headers` last on `get` and `delete`; `delete` taking `get`'s shapes and `put`/`patch` `post`'s (M3-020);
- method matching, 404 on a method mismatch, first registered route wins, no fall-through (M3-020);
- the M2 contract's 400/404/500 boundary (SPEC, "M2 completion contract"); a change to it reopens M2;
- the backend seam at `App.handle`, with Flare out of the public API and of `src/muntin`.

**Candidates to measure:**
- the bound: at most two route values (slot arity 3 for `def(V, V, B)` and `def(V, V, Headers)`); two values only where slot arity 2 already fits (`def(V, V)` on `get` and `delete`, no new overload); at most three (slot arity 4, ten overloads per name);
- the overloads at a new arity: copies per method name, as today; a generic entrypoint (M3-020's candidate C); one internal set;
- binding: positional, in the literal's order (M2-005); a named application struct whose field names Muntin checks by reflection; a hand-mapped trait that looks values up by name; a tuple slot;
- a literal's placeholder names: duplicates accepted or rejected;
- deferral.

**Selected: a typed handler takes at most two route values, bound by position in the literal's order, on every registration method. Each method name gains slot arity 3 (one stateless and one stateful overload, copies of its arity-2 pair), so it has eight overloads.** A literal's query keys must be distinct. Nothing that registers or answers today changes; M2 does not reopen ("M2 contract" below). No public type, slot kind or injected kind is added.

```mojo
def post_of(uid: Int, pid: Int) -> String: ...
def user_fields(id: Int, fields: String) -> String: ...
def search(q: String, limit: Int) -> String: ...
def edit_post(uid: Int, pid: Int, body: Json[Edit]) -> Json[Post]: ...
def remove_post(uid: Int, pid: Int, headers: Headers) raises Unauthorized -> String: ...

app.get["/users/{uid}/posts/{pid}"](post_of)
app.get["/users/{id}?{fields}"](user_fields)
app.get["/search?{q}&{limit}"](search)
app.patch["/users/{uid}/posts/{pid}"](edit_post)
app.delete["/users/{uid}/posts/{pid}"](remove_post)
# GET /users/1/posts/2           -> post_of(1, 2)
# GET /users/1?fields=name+email -> user_fields(1, "name email")
# GET /search?limit=5&q=mojo     -> search("mojo", 5)   (the literal's order, not the request's)
# GET /users/1/posts/x, /search?q=mojo, /search?q=a&q=b&limit=5 -> 400 "Bad Request" (handler not called)
```

- **Shapes.** `get` and `delete` add `def(V, V)` and `def(V, V, Headers)`; `post`, `put` and `patch` add `def(V, V, B)` with `B` a `FromBody`, a `Json[T]` or a `WithHeaders[B2]`; each also after a leading `State[S]`. `V` is an `Int` or a `String` (M3-018), in any combination. A handler with two route values needs a literal that declares exactly two placeholders: two `{name}` segments, two `{key}` items, or one of each. Every zero- and one-value shape is unchanged.
- **Binding** is positional, as M2-005 decided for route values in general: the path placeholders left to right, then the query placeholders left to right, fill the route-value parameters in order; then the body or the `Headers`. Names are never compared with handler parameters, because Mojo 1.1.0 cannot reflect them. So two values of one type that the handler declares in the other order (`def(pid: Int, uid: Int)` on `/users/{uid}/posts/{pid}`) compile and receive each other's values; a swapped `Int` and `String` fails at request time only when the text is not an `Int` (400). This is the accepted cost of the selected design: for two values of one type, DX section 2's "a route declaring `{id}` should not silently bind to an unrelated handler parameter" is not met. Under positional binding the checks Muntin makes at registration are the count, the kinds and distinct query keys; none compares a placeholder with a handler parameter, which only candidate D below would, and the slice's DX text states the swap plainly.
- **Distinct query keys.** The `{key}` items of one literal must differ: `?{a}&{a}` reads one query key into both parameters, so no request can give them different values (a request that repeats the key is 400). Path names are not checked: `/x/{a}/{a}` and `/x/{a}?{a}` capture two different sources, and positional binding gives each parameter its own value whatever the names, so they register. Neither rule reduces the swap risk above. No literal that registers today has two placeholders, so the check changes no registration, and it is reported after every other rule, so no existing message changes.
- **Capture.** `App.handle` captures every value of a matched typed route before any conversion: the path captures `_match` already appends, then each query key's value in the literal's order, each found by `_query_value` and decoded as M3-018 decides, all in the one existing `try` (400). Each value keeps M3-018's rules: decoded once, non-empty, the closed invalid set, query keys matched undecoded. The adapter converts the slots in order, so the first invalid value answers 400 and nothing later is converted; all are 400, so the order is not observable in the status. `_Route` holds the literal's query keys in order instead of one key.
- **Statuses.** No new status and no new position: 404 → query values missing or duplicated, or any value empty, a bad escape or not UTF-8, 400 → `Int` conversions 400 → body steps or the `Headers` rebuild → handler → result, as for one value.
- **Bound: two.** Two values cover nested resources, a path value with a query value, and two-key search, with `Headers` or a body beside them, at slot arity 3: eight overloads per method name, every candidate note printed (M3-014's scratch measurement). Three values with a body or `Headers` need slot arity 4, ten overloads per name, Mojo 1.1.0's note cap (a rejected result then loses one candidate note, an accepted cost in M3-014), which would also spend the last arity any other request part could use (M3-016's revisit condition). The bound is uniform: `def(V, V, V)` would fit slot arity 3 on `get` and `delete` but not with `Headers`, and on `post` the last slot is the body, so it is rejected (`a get handler takes at most two route values`) rather than admitted where the arity happens to fit. Admitting three later is additive.
- **Overloads.** Each method name gets its two arity-3 overloads by copying its arity-2 pair with a third slot, as M3-020 copied whole sets per name. M3-020's slot-arity revisit condition is answered here: the reason it rejected a generic entrypoint (candidate C) was one spelling per method, and arity does not change it; the per-name overload signatures are the public spelling whatever their bodies call, and their bodies are already three calls each; Mojo 1.1.0 has no code generation that would emit the sets. Copying costs ten overloads in all, forty across the five names, and makes every later rule change apply to more copies; that is accepted for one spelling per method.
- **Diagnostics.** Rules that name one value keep their text, because they stay true (`def(Int)` on `/x/{a}/{b}` is still `handler takes one Int parameter; route must declare exactly one path or query parameter`). The two-value rules replace the `at most one` rules that this decision makes false:
  - `handler takes two route values; route must declare exactly two path or query parameters` (`get`, `delete`; `def(V, V)` or `def(V, V, Headers)` with another placeholder count);
  - `handler takes two route values and the request body; route must declare exactly two path or query parameters` (`post`, `put`, `patch`; `def(V, V, B)`);
  - `a get handler takes at most two route values` (named after the method; `def(V, V, V)` on `get` and `delete`);
  - `route declares a query parameter twice` (a shape that passes every other rule, on a literal with a repeated `{key}`);
  - `a get handler takes at most one Int route value` and `a get handler takes at most one route value` (and their `delete` forms) are retired: the shapes they rejected either register or get the two-value placeholder message.
  - A call with three request parameters that selected no overload now selects an arity-3 overload and reports a rule instead of `no matching method`. For these stateful handlers registered without their state (`def(State[Db], Int, B)` on `post`, `def(State[Db], V, Headers)` on `get`), that is the existing State rule (`State is injected application state, not the request body; ...` on `post`, `State is injected application state; ...` on `get`) instead of the stateful candidates' `missing required argument: 'state'` (DX section 8 documents the old text). A handler with three request parameters and no leading `State`, given a state, still matches no overload, and so does any handler with four request parameters.
  - M3-018's revisit condition said this item replaces the `Int`/`String` message pairs; it keeps them, because each one-value message stays true, and adds one placeholder message per rule set (`get`'s and `post`'s), neither naming a type.
- **Arity-3 rules** extend each family's existing order, rule by rule across the slots, so every arity-1 and arity-2 message is unchanged. `get`, `delete`: a `State` slot, a `Request` anywhere, a body, a slot of no kind, a `Headers` slot that is not last, three route values, then the placeholder count, then distinct query keys. `post`, `put`, `patch`, each rule checked over both slots before the last before the next rule: a `Request` (the raw messages), a `State` (the State messages), a body (`a post handler takes one request body, as its last parameter`), a `Headers` or a slot of no kind (`... before the body is an Int or String route value`); then the placeholder count; then the last slot's existing body checks (`Int is a route-value type, ...`, `Request is the whole request, not a body; ...`, the State messages, `the handler's last parameter is the request body; ...`); then distinct query keys. A `Request` in the last slot is a body position, as at arity 2.
- **Typed function values and forwarding** reach the arity-3 overloads as they reach arity 2: each request parameter spelled `var` in a typed value, and a generic helper forwarding through the same slots and `where` clause.

**M2 contract: amended, not reopened.** SPEC's M2 contract says "At most one `Int` route value, from one `{name}` path segment or one `{key}` query item, bound by position". [M2 closure (M2-016)](m2-016-m2-closure.md) reopens M2 for a change to existing signatures or semantics, not for an addition. What the slice changes, by kind:
- **Accepted set: expanded only.** Handlers with two route values, rejected at compile time today, register. No handler that registers today is rejected or registers differently.
- **Overload set: added to.** Each method name gains its two arity-3 overloads; the existing declarations, their signatures and their `where` clause are unchanged.
- **Rejected-call diagnostics: specific ones change.** The two `at most one` messages (M3-015's and M3-019's) are retired for the two-value messages; a call with three request parameters and no state argument, which no overload took, now selects an arity-3 overload and reports a Muntin rule instead of `no matching method`, including a stateful handler registered without its state (M3-006's `state_post_fail/missing_state_argument_int_body.mojo`, which pins an M3 behavior, not an M2 one); a three-parameter handler without a leading `State`, given a state, still matches no overload. Every other message is unchanged, but each call that still matches no overload lists eight candidates' notes instead of six.
- **Runtime: unchanged.** Every registered route answers every request as before, and the 400/404/500 boundary is unchanged.

This is [Typed get header access decision (M3-016)](m3-016-typed-get-header-access-decision.md)'s classification: it added accepted `get` shapes and reworded a rule message and kept M2 closed, because the contract states that a rejected call that selects an overload reports the Muntin rule it breaks, which these diagnostics still do. [M3-014](m3-014-registration-structure-decision.md) reopened M2 for the overload declarations, the diagnostics of rejected calls and three accepted-set edges: it replaced every existing overload declaration, changed the accepted set in both directions, and moved rejected calls from the compiler's candidate notes to Muntin's rule messages at a time when the contract said nothing about them. M3-015 then amended the contract to say that rejected calls report the Muntin rule they break; the diagnostics this item changes follow that statement. Nothing here replaces a declaration or rejects a handler that registers. The slice amends the contract text with these four kinds, as M3-015 and M3-019 added amendment paragraphs. DX statements that a handler takes "exactly one route value" or "at most one" describe today's limit; the slice rewrites them together with the fixtures that pin them.

**Measured premise: the new overloads take the calls the rules expect.** On a scratch copy of `src/muntin` with the arity-3 overloads on `get` and `post` and the rules above, Mojo 1.1.0 resolved as predicted. `def(State[P], Int, B)` on `post` without its state selects the stateless arity-3 overload and reports `constraint failed: State is injected application state, not the request body; ...`, in the documented form (`function instantiation failed` at the enclosing function, the registration call in the next note), where `main` gives `no matching method` with the stateful candidates' `missing required argument: 'state'`. A four-parameter `def(Int, Int, Int, Headers)` on `get` is `no matching method in call to 'get'` with all eight candidates' notes printed. `get` `def(Int, String, Headers)` and stateful `post` `def(State[P], Int, Int, B)` register.

**Invariants:**
- A typed handler takes zero, one or two route values; each is an `Int` or a `String`; they bind in the literal's order, path placeholders before query placeholders, and the literal declares exactly as many as the handler takes, with distinct query keys.
- One overload per request-slot arity (0 to 3) and family per method name: eight per name, every candidate note printed; `put`/`patch` keep `post`'s rules and `delete` `get`'s.
- Every value of a matched route is captured and decoded in `App.handle` before any conversion, by M3-018's rules; no new status.
- Every zero- and one-value shape, its messages and its runtime behavior are unchanged; raw handlers capture nothing.

**Cost.** Ten overloads (forty in all), each with its own `where`-clause pin: every overload is a hand-written declaration whose clause is not shared with the overload it copies, and a third slot type through `_rule`, `_check` and `_admits`, so every rejection's instantiation frames change once. Same-typed values swapped by the handler bind silently (positional binding without parameter-name reflection). Two values at most, short of three-level nested resources. One query scan per query placeholder per request.

**Revisit when:**
- Mojo reflects function parameter names (M2-005's condition): check the handler's names against the literal, or bind by name;
- `std.reflection` gains a constructor, or swapped values are reported in applications: revisit D, a named struct carrier, as a kind beside the positional slots;
- a handler needs three route values: slot arity 4 (C) or D;
- optional or default query values are decided: they build on this capture (a missing key may become an absent value instead of 400), and M3-018's empty-value rule is revisited there;
- another request part beside the fields is proposed for `get` (M3-016): it competes for slot arity 4;
- the note cap or the per-name budget changes (the revisit index's toolchain pins).
