> **Current.** Now described in [headers reference, "Reading fields in a handler"](../../reference/headers.md#reading-fields-in-a-handler), [routing reference, "Registering a route"](../../reference/routing.md#registering-a-route) and [ARCHITECTURE, "Request handling"](../../ARCHITECTURE.md#request-handling).

Status: **decision** (M3-016; `src/muntin` and `adapters/` are unchanged in it). It decides how a typed `get` handler reads request header fields without taking the whole raw `Request`. M3-012 left this out because every measured `get` shape exceeded the ten-note cap or changed an M2 signature; M3-014 made it a slot kind or the carrier on the arity overloads, and M3-015 shipped those overloads. The measurements start from M3-015's production (`get`/`post` with six overloads each, `_get_rule`/`_post_rule`, the guard, the one rebind helper).

**Selected: a `Headers` request slot on `get`, as the handler's last request parameter.** A `Headers` slot is the request's whole ordered header collection with M3-002's semantics, rebuilt per request as a fresh, Muntin-owned value. It adds no overload, no public type and no injected kind.

```mojo
def me(headers: Headers) raises Unauthorized -> String:
    var token = headers.get("authorization")         # Optional[String]
    if not token:
        raise Unauthorized()                         # ToErrorResponse: 401
    return "me " + token.value()

def note(id: Int, headers: Headers) -> String: ...                   # route value, then the fields
def me_in(users: State[Users], headers: Headers) -> String: ...      # State first, as today
def note_in(users: State[Users], id: Int, headers: Headers) -> String: ...

app.get["/me"](me)                       # slot arity 1
app.get["/notes/{id}"](note)             # slot arity 2
app.get["/me"](me_in, users)             # stateful slot arity 1
app.get["/notes/{id}"](note_in, users)   # stateful slot arity 2: State + Int + Headers fits the six overloads
```

- **Shapes on `get` after the slice:** `def()`, `def(Int)`, `def(Headers)`, `def(Int, Headers)` and the raw `def(Request) -> Response`, each also after a leading `State[S]`. The `Int` comes from a `{name}` path segment or a `{key}` query item, as today. Results and errors are unchanged: `String`, `StaticString` or a `ToResponse`, through the same `where` clause, and the declared error type's `ToErrorResponse` or the fixed 500.
- **The kind** is decided by exact type equality, `A == Headers`, beside `Int` and `Request` (all origin-free, so the equality and the rebind through `_as[Headers, A]` are exact). It is not a trait: no application type can opt in, so this adds no request-injection mechanism. A request slot is still an `Int` route value, a body, a `Request` or now `Headers`; `State` stays the registration-bound injected parameter.
- **Position: last, once.** A `Headers` slot follows at most one `Int` route value and is the last request parameter, as a body is on `post`. Two reasons, both measured. The transport needs no new rule: `_route[Last]` reads the route's flags from the last slot, and a slot's raw index is its position, so a last `Headers` slot sets the existing `_Route.headers` flag, and `App.handle`, unchanged, already appends each field's name and value after the route value on a route without a body. And the story stays one: on both methods the fields sit in the last request position, as a `Headers` on `get` and inside the body carrier on `post`. On the spike, accepting `def(Headers, Int)` by relaxing the rule alone compiles and crashes on the first request (`index 1 is out of bounds`): the flag comes from the `Int`, so no field is transported and the `Int` is read past the end. Position independence would need an index rule in `_slot` and a flag rule in `_route`, for a second spelling of the same handler; M3-014's spike measured such an index rule (`Headers` declared before a route value, and its mutation "the `Headers` index ignoring the route values"), so it is expressible, and the reason to reject it is the second spelling and the extra rules, not feasibility.
- **Ownership:** the adapter rebuilds one `Headers` from the transported strings through `Headers.add` and moves it into the handler, which may declare `headers: Headers` (borrowed) or `var headers: Headers` (owned); a `mut headers: Headers` parameter selects no overload (`no matching method`, as on production today). The handler's value is its own: changing it does not change the `Request` that `App.handle` received (measured). It is not a view of `request.headers`, because `_Call` carries only the raw argument strings (M3-002's R1 transport); lending the request's own `Headers` needs `_Call` to carry the `Request`, which is M3-012's existing revisit condition for the per-request copy. No backend buffer or lifetime reaches the value.
- **Fields and missing fields:** exactly M3-002's `Headers` (the same type `Request.headers` and `WithHeaders[B].headers` hold): every field in order, original casing, repeated names as separate fields, empty values as values, ASCII case-insensitive `get` (first value or `None`) and `get_all`. Muntin chooses no status for a field and gives it no meaning; a missing field is `None`, and its status is the handler's error type to choose (M3-012's rule, unchanged).
- **Request order on a `Headers` route:** 404 → query value 400 (`App.handle`) → route value 400 → field rebuild → handler → result. The rebuild fails only for a field written through the M3-002 `_fields` gap, and the answer is the fixed 500, as for carrier routes and raw routes; a bad route value is still 400 with such a field present. No new 400, 413 or 415 path. Routes without a `Headers` slot receive the same raw arguments as before.
- **Cost per request,** on `Headers` routes only: each field's name and value is copied twice (into the raw arguments, then into the rebuilt `Headers`, whose `add` validates it again), as carrier and raw routes already pay.
- **Raw `Request`:** unchanged and still the escape hatch. A handler cannot take both: `def(Request, Headers)` and `def(Headers, Request)` keep the raw rule's message.
- **`WithHeaders[B]` and `post`:** `post`'s last request position is its body, so typed `post` handlers keep reading fields through the carrier (`input.headers`), and `post` takes no `Headers` slot. Every `Headers` shape on `post` keeps today's message (measured byte-identical, below): `def(Headers)` is `the handler's parameter is the request body; its type must conform to FromBody`, `def(Headers, B)` is `a post handler's parameter before the body is an Int route value`, `def(B, Headers)` is `a post handler takes one request body, as its last parameter`, and `def(Int, Headers)` is `the handler's last parameter is the request body; its type must conform to FromBody`. A `Headers` slot beside a body would be a second spelling of the carrier, and `State + Int + Headers + B` would be slot arity 3 (eight overloads per method).
- **Typed function values and generic forwarding:** a typed value spells the slot `var Headers` (`var f: def(var Headers) thin raises Never -> String` registers; `def(Headers) thin raises Never -> String` is `TODO: function type conversions between closures not supported yet`, on production today too, the same toolchain cause as for `Int`). M3-015's edge 4 reaches the new kind, as its amendment's revisit condition said a new kind would: `h: def(var A) thin raises Never -> String`, `def(var A, var B)` (an `Int` then `Headers`, so `B = Headers`) and `def(State[S], var A)` forward to `get` with the `Headers` slot generic and answer as the plain handler (measured on the spike).
- **M2 stays closed.** No signature, binding rule, result policy or status boundary changes: the slice adds accepted `get` shapes, as M3-013 added the carrier to `post`, and rewords one M3-015 rule message (below), which keeps the contract's statement that a rejected call that selects an overload reports the Muntin rule it breaks.

**Rules and diagnostics** (the slice's rule edits, measured on a scratch copy of production):
- `_kind`: `A == Headers` is a new kind, checked after `Request`.
- `_get_rule`: one branch after the existing `State`, `Request`, body and no-kind checks, so their messages still win, and before the two-`Int` check: a first slot `Headers` must be alone (then the placeholder rules of a handler without a route value), and a second slot `Headers` follows an `Int` (then the one-route-value placeholder rule). Anything else with a `Headers` slot is the new rule `a get handler takes one Headers, as its last parameter`.
- `_post_rule`: a first slot `Headers` before another slot is reported as a first slot of no kind (`k1 == _OTHER or k1 == _HEADERS`); every other `post` path already reports `Headers` as it reports a type of no kind. Without that edit `Headers` would take the route-value branch: on a route without a placeholder `def(Headers, B)` changes to `handler takes one Int parameter and the request body; ...`, and on a route with one placeholder it registers and binds the route value as a field name and the body as its value (`post["/x/{id}"]` answers 200 with the field `7=hi`; mutation, below).
- The no-kind message on `get` names the new kind: `a get handler's parameter is an Int route value or, for a raw handler, the Request` becomes `a get handler's parameter is an Int route value, the request Headers or, for a raw handler, the Request`. The change is necessary: the message lists what a `get` parameter may be, and keeping it would make it false. It is the only existing compiler text that changes; it re-pins `storage_fail/string_param_handler` and `registration_api_fail/slot_misuse_names_the_rule`, and `docs/DX.md` section 3 quotes it.

**Why the slot.** It delivers the type every other header surface already uses (`Request.headers`, `WithHeaders[B].headers`, `TestClient`'s `headers=`), with the same semantics, transport, rebuild and 500, as a fresh value the handler owns or borrows. It adds no public type, no status for a field and no opt-in mechanism, and it leaves every other route as it is: `App.handle`, `_Route`'s fields, the storage, the result clause and every `post` message are unchanged, and of the existing diagnostics only the message that lists `get`'s parameter kinds changes. That it also fits the arity overloads with no new overload is what M3-014 predicted, measured here; it is not the reason for the choice. The wrapper adds a type without a gain, the trait adds a status and a precedence problem this item has no reason to take on, and deferring keeps typed `get` routes that need a field raw.

**Invariants:**
- `Headers` is a request slot kind by exact type equality only; no trait and no application type is a header slot. `State` remains the only injected kind.
- On `get`, a `Headers` slot is the last request parameter, once, after at most one `Int` route value; `post` takes no `Headers` slot (its fields come through `WithHeaders[B]`), and every `post` message for a `Headers` shape is the one it had before.
- The handler's `Headers` is a fresh value rebuilt from the transported fields, with M3-002's semantics; Muntin chooses no status for a field. The only pre-handler failure it adds is the fixed 500 of the rebuild (the `_fields` gap).
- No overload is added: `get` and `post` keep six each. `App.handle`'s code, `_Route`'s fields, `_Call`, `_Erased`, `_Bound`, the storage module, the result `where` clause and the unsafe surface (one `rebind_var`) are unchanged.
- Typed routes without a `Headers` slot or a carrier receive no header strings; raw routes are unchanged.

**Cost.** One existing message changes (the `get` no-kind message, two re-pinned fixtures). `_Route.headers` comes to mean "the route's handler receives the request's fields" (a carrier or a `Headers` slot), not only "the body is a carrier". The capability is asymmetric in spelling: a `Headers` parameter on `get`, `input.headers` in a carrier on `post`. Both are the same `Headers` type with the same transport, rebuild and 500, and the asymmetry follows from `post`'s last position being its body. Typed function values spell `var Headers`. A `Headers` route copies each field twice per request.

**Revisit when:**
- `POST` without a body is decided: revisit whether a bodyless `post` takes a `Headers` slot as `get` does;
- the R1 transport changes (for example `_Call` carrying the `Request`): revisit whether the slot lends the request's `Headers` instead of rebuilding it (M3-012's condition, now for both header surfaces);
- `get_headers_fail/typed_borrowed_headers_value.mojo` compiles: typed borrowed values convert, and the `var Headers` spelling rule can go (with `registration_fail/typed_value_to_owned_slot.mojo`);
- applications repeat the same field parsing with a 400, or ask for typed header values: revisit `FromHeaders` (candidate 3), with `Headers` conforming to it so the shapes chosen here stay; compile-time names stay under M3-012's `struct_level_assert.mojo` condition;
- several route values, or a second request part beside the fields (cookies, the method), is proposed: revisit whether `Headers` stays one slot, last, and count it in the slot arity (`def(Int, Int, Headers)` is slot arity 3, eight overloads per method);
- applications need the fields before a route value: revisit position independence with its index and flag rules (1′).
