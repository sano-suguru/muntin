# Request body bytes decision (M3-038)

> **Superseded** by [M3-040](m3-040-binary-request-and-response-bodies-decision.md). Its rule that no body byte is replaced still holds. Now described in [raw reference, "Binary bodies"](../../reference/raw.md#binary-bodies), [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter) and [ARCHITECTURE, "Backend seam"](../../ARCHITECTURE.md#backend-seam).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-038, PR #76). It decides what the Flare adapter does with request body bytes that a `String` body cannot hold exactly, and implements the choice in the same item: the decision is recorded first, as section 2 requires, and its production slice ships in the same pull request rather than a second one, because the slice is one line of the adapter and the defect it closes is reproduced on the wire. The question and what settles it were committed before any measurement (`docs/DEVELOPMENT.md` section 2). Its refusal of request bodies that are not UTF-8 was replaced by candidate B in [M3-040](m3-040-binary-request-and-response-bodies-decision.md); its invariant that no body is replaced still holds.

**Why now.** An external review reported that `Request.body` and `Response.body` are `String`s and that the Flare adapter builds `Request.body` with Flare's `Request.text()`, which replaces invalid UTF-8 with U+FFFD, so input bytes may be changed without any signal. The adapter docstring, `docs/ARCHITECTURE.md` ("Flare adapter") and `docs/DX.md` (sections 4 and 9) state the replacement as current policy, M1-002 chose it, and M3-008 measured it again (`compat/flare/json/json_loopback_probe.mojo`: a JSON string holding `0xFF` parses as `"�"`), but no record weighed it as a data-integrity question: a handler cannot tell a replaced byte from a U+FFFD the client sent, and two different request bodies (`0xFE`, `0xFF`) reach it as the same text. M3-018 refused exactly this for route values ("a lossy value would give `%FE` and `%FF` the same name") and M3-005 for header fields (answered 400 before `App.handle`); the body is the one request part still converted lossily.

**Question.** When a network backend receives request body bytes, what reaches `App.handle`? Specifically: whether the bytes a `String` body cannot hold exactly (bytes that are not well-formed UTF-8) are replaced (main), rejected before `App.handle` with a status of the adapter's, or carried exactly in a new body representation; if rejected, which status and body, where (before or after middleware and routing), on which protocols, and how a well-formed U+FFFD the client sent is kept apart from a replaced byte; what a response body can carry onto the wire and whether it can lose bytes; and which statements of DX, ARCHITECTURE, SPEC and the earlier records (M1-002's conversion policy, M2-016's M2 contract, M3-008's JSON premise) change.

**What settles it:**
- the conversion path traced in code, boundary by boundary: the bytes Flare v0.12.0 reads off the wire, the body Flare's `Request` holds (`body: List[UInt8]`, `text()`), the adapter's conversion into `Request.body`, `App.handle` (middleware, the route scan, `FromBody`, `WithHeaders[B]`, `Json[T]`, raw handlers), the `Response` body and the adapter's conversion back into the bytes Flare sends, over HTTP/1.1 and cleartext HTTP/2;
- a loopback probe with a Flare handler of its own (not the adapter): over HTTP/1.1 and h2c, for each request body below, whether Flare delivers it to a handler at all, and whether `Request.body` equals the bytes sent; and what `Request.text()` and Mojo 1.1.0's `String(from_utf8=)` make of the same bytes (measured);
- the same bodies through the unchanged adapter and `Server`, over HTTP/1.1 and h2c, with a raw route that reports the body bytes it received in a form the wire cannot alter (hex), a typed `FromBody` route, a `Json[T]` route and middleware: the bytes `App.handle` receives, the status, body and fields on the wire;
- the bodies: ASCII; well-formed non-ASCII UTF-8; `0x80` alone; `0xFF` alone; a truncated multi-byte sequence (`0xE3 0x81`); a well-formed U+FFFD (`EF BF BD`) the client sent, beside a replaced byte; a body with NUL bytes; an empty body; an `application/octet-stream` body that is not UTF-8; and an octet stream that happens to be well-formed UTF-8;
- a response body with non-ASCII UTF-8, U+FFFD and NUL: the bytes on the wire against `Response.body`'s bytes, over both protocols; and whether safe Mojo code can put bytes that are not UTF-8 into a `String` at all (so whether a binary response is expressible);
- the existing contracts read from their records, docs and tests: M1-002's conversion policy; M2-016's M2 contract (the body converted by `from_body`; raw handlers with no pre-handler 400) and its reopen conditions; M3-005's rule for request data Muntin cannot represent (400 before `App.handle`); M3-008's codec premise and its revisit condition "Muntin gains a bytes body"; M3-018's closed invalid set for route values; M3-027's `HEAD` rule at every exit of the adapter; M3-034's middleware contract (what middleware sees);
- per candidate below: what changes in `src/muntin`, `adapters/`, the public API and existing user code (typed bodies, JSON, middleware, `TestClient`), copies of the body per request, and what a test can pin.

**Boundaries that do not change silently:** `App.handle`'s routing, 400/404/405/500 and middleware contract; `Request`, `Response`, `Headers`, `FromBody`, `Json[T]` and `TestClient` signatures; the adapter's header rules, its `HEAD` rule and the HTTP framing Flare sends; well-formed UTF-8 bodies, U+FFFD included, reaching every handler byte for byte as today; one-thread serving; no Flare type in Muntin's API and no vendored Flare code. A change to any of them is named here, with its classification against M2-016.

**Candidates to measure:**
- A: the adapter reads Flare's raw body bytes and builds `Request.body` only from well-formed UTF-8; any other body is answered by the adapter before `App.handle` (status to be settled by the measurement and the existing contracts), with no `String` built from it;
- B: a body representation that holds bytes (a bytes field on `Request` and `Response`, or a byte body type), with the body conversions (`FromBody`, `Json[T]`, middleware, `TestClient`) taught to read it;
- C: a change Flare's public API would need first, if the measurement shows neither A nor B can see the received bytes;
- baseline: lossy replacement (main).

**The path today, boundary by boundary** (read from the code at the base):
- Flare v0.12.0 reads the body into its `Request.body: List[UInt8]`; `Request.text()` returns `utf8_lossy_string(body)` (`flare/http/proto/utf8.mojo`), which copies well-formed UTF-8 and replaces each maximal ill-formed subpart with one U+FFFD.
- The adapter's `to_muntin_request` passed `request.text()` as the `Request` body: the only lossy step on the request path. Header fields go through `to_muntin_headers`, which answers 400 for a field it cannot represent (M3-005).
- `App.handle` and everything in it (middleware, the route scan, `FromBody.from_body(String)`, `WithHeaders[B]`, `Json[T]`, raw handlers, `TestClient`) see only the `String`; nothing in `src/muntin` converts bytes.
- Outbound, `to_flare_response` sends `List(response.body.as_bytes())`: the `String`'s bytes, unchanged. No step on the response path loses a byte of it. A `String` an application builds with safe Mojo 1.1.0 code is well-formed UTF-8 (`String(from_utf8=)` raises on anything else, measured below; the constructors that accept other bytes are `String(from_utf8_lossy=)`, which replaces, and the unsafe-named `String(unsafe_from_utf8=)`). The fresh-context review found that a `String` a backend builds need not be: over h2c the request target Flare builds can hold bytes that are not UTF-8, which reach `App.handle` and can abort the serving process (present before this item; `docs/ARCHITECTURE.md`, "Other current limits", the known defect). That is the request target, not the body, and outside this record's question.

**Measured premises.** Mojo 1.1.0 (`8189361e`), Flare v0.12.0 (`8c6e1400`), Linux, the `flare` environment. Bodies: ASCII `hello`; `hé✓`; `0x80`; `0xFF`; `E3 81` (the first two bytes of U+3042); the overlong `C0 AF`; the surrogate `ED A0 80`; `61 EF BF BD 62` (a U+FFFD the client sent); `EF BF BD FF` (a sent U+FFFD, then `0xFF`); `61 00 62 00` (NUL); empty; the PNG signature `89 50 4E 47 0D 0A 1A 0A` (an octet stream that is not UTF-8); `00 01 7F 0A` (an octet stream that is UTF-8).
- `compat/flare/body/body_probe.mojo` (3 tests, all pass; a Flare `Handler` of its own, no Muntin, answering `raw=<hex of Request.body>;text=<hex of Request.text()>`): over HTTP/1.1 (`Content-Type: application/octet-stream`, `Content-Length`) and over h2c (one DATA frame), Flare delivers every body to the handler (200 on all 26 exchanges; none answered by Flare itself) and `Request.body` equals the bytes sent on both protocols. `text()` gives `efbfbd` for `80`, `ff` and `e381`, `efbfbdefbfbd` for `c0af`, three for `eda080`, `efbfbdefbfbd` for `efbfbdff` (a sent U+FFFD and a replaced byte are the same text) and `efbfbd504e470d0a1a0a` for the PNG signature; it leaves every well-formed body unchanged. `String(from_utf8=)` raises on exactly the seven bodies `text()` changes and, for the other six, holds the same bytes with the same length (NUL kept). Added after the review: a body sent in pieces that split a code point, chunked over HTTP/1.1 and in two DATA frames over h2c, arrives joined (`68 C3` + `A9` is `68c3a9`, unchanged by `text()`; `C3` + `FF` is `c3ff`, which `text()` makes `efbfbdefbfbd`), so framing replaces nothing and the adapter's check sees the whole body; Flare's server path decodes no request `Content-Encoding` (read from its server sources: only the `Compress` middleware, which the adapter does not use, touches encodings, on responses).
- Through the unchanged adapter and `Server` (`adapters/flare/test_localhost_roundtrip.mojo`'s new `bodies_app()`: middleware adding `X-Seen: 1`, a raw `POST /bytes` answering the hex of the body it received and its byte count in `X-Body-Length`, a raw `POST /echo-raw` answering its body unchanged, the typed `POST /echo` (`RawText: FromBody`, `[` body `]`), the `Json[Greeting]` route `POST /greet` and `GET /hello`), over HTTP/1.1 and h2c:
  - each well-formed body reaches `App.handle` byte for byte (`/bytes` answers its own hex, `X-Body-Length` its length, `X-Seen: 1`), and `/echo-raw` and `/echo` send its bytes back unchanged; the empty body is `X-Body-Length: 0`;
  - each other body reaches `App.handle` replaced, as a 200: `/bytes` answers `efbfbd` with `X-Body-Length: 3` for `80`, `ff` and `e381`, `efbfbdefbfbd` (6) for `c0af` and for `efbfbdff`, nine bytes for `eda080` and `efbfbd504e470d0a1a0a` (10) for the PNG signature; `/echo` answers `[�]`; `POST /hello` is 405 with `Allow: GET, HEAD` and `POST /missing` 404, both through the middleware;
  - `POST /greet` with `{"name":"` `0xFF` `"}` and `Content-Type: application/json` is 200 `{"hello":"�"}` on both protocols, the same answer as for a JSON string holding a U+FFFD the client sent.

  So the loss is reproduced on the wire: one step (`text()` in `to_muntin_request`) makes different request bodies the same `Request.body` with no signal, on both protocols, and every route and middleware then acts on the replaced text.
- Mojo 1.1.0's `String(from_utf8=Span(bytes))` is the validator Muntin already uses for decoded route values (M3-018); it raises on the overlong and surrogate forms as Flare's lossy decoder classifies them, so the two agree on what is UTF-8 for all thirteen bodies.

**Selected: A, with the adapter's existing 400.** The adapter builds `Request.body` from Flare's raw `Request.body` bytes with `String(from_utf8=)`, never `Request.text()`: well-formed UTF-8 is kept byte for byte (a U+FFFD the client sent and NUL included), and a body that is not well-formed UTF-8 makes `to_muntin_request` raise, which `_answer` already answers 400 `Bad Request` before `App.handle`, as it does for a header field Muntin cannot represent (M3-005). `App.handle`, `Request`, `Response`, `FromBody`, `Json[T]`, `TestClient` and every other public type are unchanged.

- **Where and when.** In the adapter, on the raw bytes, before any `String` is built from them and before `App.handle`: so no middleware, route scan, conversion or handler runs, and a path no route matches (404) or only other methods match (405) is 400 too, as for an unrepresentable header field. The `HEAD` rule applies to this 400 as to the adapter's other one (no content, `Content-Length: 11`; M3-027). This holds for every request Flare hands to the adapter; Flare's own refusals come first and are unchanged; among them, a body over its `max_body_size` (10 MiB by default) and a request its HTTP/1.1 parser or HTTP/2 layer rejects never reach the adapter.
- **Status.** 400 `Bad Request`, body `Bad Request`, no field: the adapter's existing answer, the same status Muntin gives a route value whose decoded bytes are not UTF-8 (M3-018) and a request field it cannot represent (M3-005). 415 was weighed: RFC 9110 allows it for a format found by "inspecting the data directly", but in Muntin 415 is `App.handle`'s answer to a `Json[T]` route's `Content-Type`, after routing and through middleware; an adapter 415 before routing, for every route whatever its type, would be a second meaning of the status at another layer, and a client that sent `Content-Type: text/plain; charset=utf-8` with a body that is not UTF-8 sent malformed content, not an unsupported type.
- **What is distinguished.** Only well-formedness: a body is kept if and only if `String(from_utf8=)` accepts it. U+FFFD is an ordinary character (`EF BF BD` is kept); nothing is decided from the text after a conversion.
- **Protocols.** HTTP/1.1 and h2c alike: Flare hands both the raw bytes in `Request.body` (measured), and the check is the adapter's, before either protocol's difference matters. Framing is Flare's, unchanged: over HTTP/1.1 the 400 carries `Content-Length: 11`, over h2c no `content-length` (as for every non-`HEAD` answer the adapter sends).
- **Copies.** One copy of the body into the `String`, as `text()` made (read from the code; not timed); the validation is the one `text()` already ran.
- **What it is not.** It is the safe rejection of bodies a `String` cannot hold, not binary support: an application still cannot receive a body that is not UTF-8 (an image, a protobuf message, a Latin-1 form), and receives an octet stream that happens to be well-formed UTF-8 as text, byte for byte. A response body is still a `String`, so it is UTF-8 text.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A: reject in the adapter before `App.handle`, 400 | **chosen**: no body changes on its way to the application, nothing in `src/muntin` or the public API changes, one line in the adapter, and every well-formed body, U+FFFD and NUL included, is answered exactly as before (measured on both protocols) |
| A with 415 | rejected: a second meaning of 415 at another layer (above) |
| A inside `App.handle` (middleware or routing first, then 400) | not expressible without B: `Request.body` is a `String`, so a body that is not UTF-8 can reach `App.handle` only already converted or with a new field carrying its bytes or its validity, which is a change to `Request` (B's cost) for an answer no application can act on |
| B: a bytes body (`Request.body_bytes`, a `Bytes` type, `FromBody` over bytes, a bytes `Response` body) | deferred, not rejected: it is what binary bodies need (SPEC, "more body shapes"), but it changes `Request` and `Response` (the `Request(method, target, body)` initializer is part of the M2 contract), `FromBody`'s input contract, `Json[T]`'s input (the codec would then validate UTF-8 itself, M3-008's revisit condition), the middleware copy (a second body per request, or a choice of one) and `TestClient`'s spelling; and the data-integrity defect is closed by A without any of it. Its own decision item, with the revisit condition below |
| C: an upstream Flare change | not needed: Flare's public `Request.body` holds the received bytes on both protocols (measured), so the adapter can validate before anything is lost |
| baseline: lossy replacement (main) | rejected: measured above, it gives different bodies one `Request.body` with no signal, a sent U+FFFD and a replaced byte included |

**M2 contract: reopened, for one class of requests over the Flare backend.** The M2 contract holds "through `TestClient` and, for the same `App`, a real loopback request through the Flare adapter", and its raw escape hatch receives the whole `Request` "with no pre-handler 400". Over Flare, a request whose body is not well-formed UTF-8 was routed with a replaced body (the handler's answer, or 400, 404 or 405 by the route scan) and is now the adapter's 400 before `App.handle`: a different 400/404 boundary for that class, so it is an M2 reopen under [M2-016](m2-016-m2-closure.md), and this record is the explicit decision it requires. By kind:
- `App.handle` and `TestClient`: unchanged; nothing in `src/muntin` changes, so every answer `App.handle` gives to a `Request` is the same;
- the wire: over HTTP/1.1 and h2c, a request Flare hands to the adapter whose body is not well-formed UTF-8 gets the adapter's 400 `Bad Request` before routing and middleware, whatever its method and path (a `HEAD` one under the `HEAD` rule); every other request, U+FFFD and NUL bodies included, is answered exactly as before;
- the raw escape hatch: a raw handler receives the whole `Request` for every request that reaches `App.handle`; over Flare, a body that is not UTF-8 does not reach it, as a header field Muntin cannot represent does not (M3-005);
- the accepted set, the overload set and every diagnostic are unchanged.

**Invariants:**
- For every request Flare hands to the adapter, `Request.body` holds exactly the request body bytes Flare received, or the request is answered 400 by the adapter before `App.handle`. No request body is replaced, truncated or normalized on its way to an application.
- A response body goes onto the wire as the bytes of `Response.body`, unchanged (framing aside: no content for `HEAD`).
- A well-formed U+FFFD in a body is a character like any other: no step decides anything from it.

**Cost.** A client that sent a body that is not UTF-8 to a route that accepted the replaced text (a handler that ignored the body, a `FromBody` that accepted anything) now gets 400 where it got that route's answer; one sent to a path no route matches gets 400 instead of 404, and to a path only other methods match, 400 instead of 405 with `Allow`. A binary upload is still not supported, only refused instead of corrupted. Middleware cannot observe or log these requests (as for unrepresentable header fields).

**Revisit when:**
- applications need bodies that are not UTF-8 (binary uploads, other charsets, protobuf): decide B, a bytes body, as its own item; the JSON codec then validates UTF-8 itself (M3-008's condition);
- a second network backend is added: it inherits the obligation (no lossy body conversion; a body it cannot represent is answered before `App.handle`), and B's representation becomes the place to state it once;
- middleware or observability needs to see refused requests (logging, metrics): the refusal then needs a place inside `App.handle`, which needs B;
- Flare changes what `Request.body` holds, or Mojo's `String(from_utf8=)` changes what it accepts (`compat/flare/body/body_probe.mojo` fails).
