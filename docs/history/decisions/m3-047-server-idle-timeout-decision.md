# Server idle timeout decision (M3-047)

> **Current.** Now described in [serving reference, "Idle timeout"](../../reference/serving.md#idle-timeout) and [serving reference, "`Server.bind`"](../../reference/serving.md#serverbind).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-047, [pull request #85](https://github.com/sano-suguru/muntin/pull/85); `src/muntin` unchanged). It decides whether `Server` should let an application set Flare's `ServerConfig.idle_timeout_ms`, which `Server` leaves at Flare v0.12.0's default (500 ms). Two records name it: [M3-032](m3-032-serving-entrypoint-decision.md) ("applications need a backend limit or protocol setting changed (body size, timeouts, TLS): revisit whether `Server` takes a Muntin-owned configuration") and [M3-046](m3-046-head-of-line-blocking-decision.md) ("`Server` gains backend configuration: an `idle_timeout_ms` would let an application trade the dropped requests for longer waits"), which declined its candidate E (the adapter setting a longer timeout for everyone) because it would change every application's keep-alive close. The question, candidates, criteria and pass conditions below were written before any measurement; what precedes them was read from the records named above and from Flare v0.12.0's source.

**Why now.** M3-046 pinned that a handler running longer than the idle timeout (counting a connection's idle time before it) makes Flare close open HTTP/1.1 keep-alive and h2c connections whose requests arrived meanwhile, unanswered: with the default, such a handler loses requests rather than only delaying them, and an application has no way to change that short of building Flare's `HttpServer` itself, which M3-032 rejected as API.

**Question.** Should `Server` expose Flare's idle timeout, and if so how: its spelling and where it lives; whether every existing `Server.bind(...)` call and `server.serve(app)` keep building and answering exactly as today, the 500 ms default included; the unit, the valid values and where an invalid one is caught (0, which Flare documents as "disables", a negative value, a value whose arithmetic in Flare could overflow, and the largest value worth accepting); whether one value reaches HTTP/1.1 and h2c alike; what a longer value changes on the wire (requests that waited behind a long handler answered after it, never during it) and what it does not (the blocking itself); what it costs (idle connections, and connections that never send a byte, held longer); how it interacts with M3-045's stop (the grace window, the bound, the keep-alive close during the window); whether two `Server`s keep their own values; and what changes in the accepted set, the overload set, the diagnostics and the runtime, classified against M2-016.

**What it is not.** Other timeouts (`write_timeout_ms`, `read_body_timeout_ms`, `request_timeout_ms`, `handler_timeout_ms`, which Flare does not enforce), keep-alive limits, connection counts, TLS and workers are out of scope; so is any change to the blocking itself (M3-046's deferral stands).

**Candidates.**
- A, a keyword-only argument of `Server.bind`: `Server.bind(host, port, *, ..., idle_timeout_ms=n)`, whose omission keeps the 500 ms default, checked by `bind` before anything is bound and written by the adapter into Flare's configuration.
- B, a typed timeout configuration: a Muntin-owned type (for example `Timeouts(idle_ms=...)`) passed to `bind`, holding this timeout now and others later.
- C, change the default: the adapter sets a longer idle timeout for every `Server`, with no API change (M3-046's candidate E).
- D, decision only: leave the API and the adapter unchanged, and record the blockers and revisit triggers.

**Comparison criteria**, per candidate: the spelling beside `max_body_bytes` and `shutdown_grace_ms`; the public API added; whether every existing call keeps building and answering as today with the same default on both protocols; ownership; how the next setting would be added; the unit, range and zero semantics, and where an invalid value is caught, with what message; whether one value reaches HTTP/1.1 and h2c, and how a partial propagation would be caught; the effect on M3-046's dropped requests and on its pinned default-configuration tests; the cost of idle connections; the interaction with M3-045's stop; whether Flare types reach application code (A1, A2); the code added; accepted set, overload set, diagnostics and runtime by kind (M2-016). The smallest candidate that meets the pass conditions is chosen; a configuration is not chosen merely because it can be built.

**Pass conditions** for an implementing candidate (each with executable evidence in real child processes, each child reaped within a bound):
- with an explicit timeout longer than a 1 s held handler, a request sent during the hold on an HTTP/1.1 keep-alive connection answered before the hold, stream 3 on the held stream's h2c connection, and stream 1 on another h2c connection set up before the hold are each answered after the release and never during the hold, and no other handler runs before the held one returns (the order pipe); these tests fail before the change;
- with no value given, M3-046's default-configuration tests pass unchanged (the waiting requests dropped), so the default is still 500 ms on both protocols;
- two `Server`s bound in one process with different values keep their own;
- the range's boundaries, zero included, are checked by `bind` with the message the record names, before anything is bound (on a port a child serves, so a raise is not `AddressInUse`), and the accepted ends bind;
- SIGTERM still stops a `Server` bound with a long idle timeout within its own `shutdown_grace_ms` and bound (the window plus 1 s), with an idle keep-alive connection open, exit 0;
- `max_body_bytes`, `shutdown_grace_ms`, the one reactor, the signal claim, `_BorrowedHandler`'s non-`Copyable` guard, the serving fixtures and every existing test are unchanged and pass; `src/muntin` is unchanged and `check_boundaries.sh` passes;
- scratch mutations, each turning a listed test red: the propagation removed (the value never reaching Flare's configuration), the default changed, and the validation broken (each end).

If no candidate meets them, D: the API and the adapter stay unchanged, and the record names the blockers and what would lift them.

**Read in code** (Flare v0.12.0, `8c6e1400`):
- `ServerConfig.idle_timeout_ms: Int`, default 500, documented "Max ms a connection may stay idle before the reactor closes it (default 500), including a connection that has not sent its first byte yet. 0 disables." It is one field: the HTTP/1.1 handle (`flare/http/_reactor/conn_handle.mojo`) and the HTTP/2 handle (`flare/http/_h2_conn_handle.mojo`, whose `on_readable` and `on_writable` take the `ServerConfig`, not `Http2Config`) both re-arm their timer with it after each read and each completed write, and the accept loop arms it for every new connection (`_arm_accept_timer`), so one value reaches both protocols. Unlike M3-044's body limit there is no second field.
- Zero and negative values: `_arm_accept_timer` arms nothing for a value `<= 0`; the per-step re-arm (`_apply_step`, `_apply_step_h2`) cancels the connection's timer for 0 and ignores a negative value (`-1` is the "unchanged" sentinel of `StepResult`). So 0 and any negative value leave every connection without an idle timer. `ServerConfig.check` (compile time, not called by `HttpServer`) asserts only `>= 0`.
- Large values: `TimerWheel.schedule` computes `fire_at = current_tick + UInt64(delay)` (a 512-slot wheel of 1 ms slots, longer delays in an overflow list promoted once per rotation); for any `Int` up to `Int.MAX` that sum stays below 2^64, so nothing overflows; a value that large never fires.
- Which timer applies when: the idle timer while nothing has arrived, between keep-alive requests, after every h2c read or write (a stalled h2c body included: nothing in Flare's HTTP/2 path reads `read_body_timeout_ms`), and while an HTTP/1.1 head is incomplete; while an HTTP/1.1 body is still arriving, `read_body_timeout_ms` (30,000) instead, and while a response is being written, `write_timeout_ms` (5,000). `request_timeout_ms` (60,000 from a request's first byte) is checked only when bytes arrive, so it never closes a connection that has gone silent: the idle timer is the only bound on a connection that never sends a byte or stalls inside its head.
- The stale tick (M3-046): timers are armed relative to the wheel's last advance, which a long handler leaves behind, so a connection is closed after a hold when its idle time before the handler plus the handler's run time exceeds the idle timeout. A longer timeout moves that threshold; it does not remove the serial dispatch or the stale tick.
- M3-045's stop: `drain` keeps the reactor serving open connections for the whole window and the reactor then closes every connection still open (`_drain_remaining_conns_unified`), whatever its timers. The idle timer only closes connections earlier, inside the window.

**Measured** (Mojo 1.1.0, Flare v0.12.0, Linux x86-64; a scratch probe, not retained, served a fixed `200 hello` handler on Flare's own `HttpServer` with `idle_timeout_ms` set, two runs each unless noted; then the retained tests in `adapters/flare/test_server.mojo`, "Idle timeout (M3-047)"):
- **Default and timing.** `ServerConfig().idle_timeout_ms` is 500. With 500, 1,000 and 2,000, an HTTP/1.1 keep-alive connection after its answer, a connection that never sent a byte, and an h2c connection after the SETTINGS exchange were each closed (EOF) 500 to 505, 1,000 to 1,002 and 2,000 to 2,005 ms later.
- **0, −1 and `Int.MAX`:** each of the three connections stayed open for the probe's whole 3 s: no idle timer, as read in code. Nothing crashed.
- **Partial requests**, with 500 and 2,000: a head without its blank line was closed at the idle timeout (503, 2,002 ms); a complete head declaring 100 bytes with 10 sent stayed open past 3 s with both values (the 30 s body timer).
- **Tiny values:** with 1 ms, of 20 requests each written right after `connect`, 19, 20, 20 and 19 were answered (four runs); with 5 ms, 20 of 20 each time. A timeout shorter than a client's gap can close its connection first.
- **Idle cost** (Linux, `/proc`): 500 connections that never send a byte took the serving process from 6 to 506 file descriptors and its RSS up by about 0.8 to 1.5 MB (1.5 to 3 KB each) in three runs; 1.5 s later the 500 ms server was back at 6 descriptors and the 60 s server still held 506. The memory was not returned to the system after the close in either case. `ServerConfig.max_connections` is 0 (unlimited), so the process's descriptor limit is what bounds them.
- **`Server`, red before the code:** the new tests did not build against the base (`invalid call to 'bind': unexpected keyword argument 'idle_timeout_ms'`); against a scratch adapter that accepted the keyword but did not write it into Flare's configuration (so it served exactly as the base does), all seven failed, and M3-046's three `Server` cases passed (an eighth test, added after the docs were drafted, failed the same way: with 1,000 given, a silent connection, an incomplete HTTP/1.1 head and an idle h2c connection were closed after 500 to 502 ms): the waiting keep-alive request was dropped (`''`, reset), stream 3 and the other h2c connection's stream were dropped (handler order `a`), and under SIGTERM with a 1,500 ms window the idle keep-alive and h2c connections were closed after 499 and 501 ms, by the idle timer.
- **`Server`, with `idle_timeout_ms=60_000`** (green): with a 1 s held handler, nothing was answered during the hold; afterwards the keep-alive request and the new connection were answered (order `abb`), stream 3 on the held stream's connection and the stream on another h2c connection were answered (order `ab`). Under SIGTERM with a 1,500 ms window, new connections were refused after 48 ms, the idle keep-alive and h2c connections were closed 1,636 ms after the signal (the window's end) and the child exited 0 after 1,693 ms. Two `Server`s bound in one process, with 3,000 and with no value, closed an idle keep-alive connection after 3,000 and 500 ms. With 1,000, a silent connection, an incomplete head and an idle h2c connection, each opened and timed on its own, were closed after 1,000 to 1,003 ms, and an HTTP/1.1 request stalled inside its body was still open after about 3,000 ms (three runs, after the review below; an h2c stream stalled inside its body was added after the scoped review and closed at the idle timeout). M3-046's default-configuration cases passed unchanged.

**Selected: A. `Server.bind(host: String, port: Int, *, max_body_bytes: Int = 10485760, shutdown_grace_ms: Int = 5000, idle_timeout_ms: Int = 500) raises -> Server`.** The adapter writes the value into Flare's `ServerConfig.idle_timeout_ms` before binding. Contract: `docs/DX.md` section 1.
- **Meaning.** How long Flare keeps a connection open, over HTTP/1.1 and h2c alike, while nothing arrives on it: a new connection before its first byte, a keep-alive connection between requests, an h2c connection between frames, and an HTTP/1.1 request whose head is incomplete. It does not bound an HTTP/1.1 request whose body is arriving (Flare's 30 s body timer; h2c has no body timer, so there the idle timeout bounds a stalled body too), a response being written (5 s), or a handler. A connection is closed when its idle time before a handler plus that handler's run time exceeds it (M3-046's stale tick), so an application whose handlers can run for up to `t` ms sets it above `t` plus the idle time its clients leave before a request: waiting requests are then answered after the handler instead of dropped. It does not let any request be answered while a handler runs.
- **Default.** 500, Muntin's constant (`_DEFAULT_IDLE_TIMEOUT_MS`), equal to Flare v0.12.0's default and not read from Flare, so a Flare upgrade that changes its own default does not change `Server`'s.
- **Values.** 1 to 86,400,000 (one day). 0 is refused: Flare reads it as "no idle timer", the opposite of what 0 ms reads like, and with no timer a connection that sends nothing, or stops inside its head, is held until the client closes it (measured open past 3 s; nothing else bounds it). A negative value is refused for the same reason (Flare reads it as no timer too). The upper end matches `shutdown_grace_ms`: Flare handles larger values without overflow, but one day already holds a silent connection for as long as any process is likely to run, and the cap catches a unit mistake. Outside the range `bind` raises `idle_timeout_ms out of range: <value>`, after `shutdown_grace_ms` and before the host is parsed or anything is bound. A small value is accepted: one shorter than a client's gap between connecting and sending, or between requests, closes its connection first (1 ms dropped about one request in 20 sent right after connecting).
- **Ownership and independence.** An `Int` copied into the `ServerConfig` that `HttpServer.bind` takes by value; two `Server`s keep their own (measured).
- **Initializer.** `Server(*, _host, _port, _max_body_bytes, _shutdown_grace_ms, _idle_timeout_ms)`, the last with the same default; `_server_config(max_body_bytes, shutdown_grace_ms, idle_timeout_ms)` checks the range and sets the field. Positional calls still do not build (`compat/flare/serve/server_bind_positional_limit.mojo` pins `bind`'s third positional argument).
- **Kept as before:** `max_body_bytes`, `shutdown_grace_ms`, the one reactor, the serving claim and the signal handling, `_BorrowedHandler` and its non-`Copyable` guard, `src/muntin`, every other `ServerConfig` field.

**By kind (M2-016): not an M2 reopen.** `Server` is an M3 type of the adapter; `App.handle`, the accepted registrations, the overload set and every existing diagnostic are unchanged. `Server.bind` takes one more keyword-only argument with a default (the accepted set grows), a new run-time message `idle_timeout_ms out of range: <value>` exists, and a `Server` bound without the argument behaves exactly as before.

**Cost.** One more argument on `Server.bind`. A longer value makes every idle connection (including one that never sends a byte) cost a file descriptor and 1.5 to 3 KB of the serving process for that long, with no Muntin or Flare default cap on their number; the application chooses that trade, and the docs say so. The value's meaning depends on Flare's timer order (the stale tick), which a Flare release could change.

**Invariants:**
- The value given to `Server.bind` is Flare's `idle_timeout_ms`, which both protocols read; with none given it is 500.
- `Server.bind` never hands Flare 0 or a negative idle timeout, so a `Server` always has an idle timer.
- `max_body_bytes`, `shutdown_grace_ms` and their checks are unchanged, and the idle timeout is checked after them.

**Revisit when:**
- the Flare pin moves: re-measure the default, whether 0 and negative values still mean no timer, whether HTTP/1.1 and h2c still share one field, which timer applies while a body arrives, and the stale tick (M3-046's default cases and this record's `_MUNTIN_PATIENT` cases);
- Flare advances its timer clock after a handler or handles readable events before expiring timers (M3-046's "What Flare would need"): a long handler would then delay, not drop, waiting requests with any idle timeout, and the docs' advice to raise it for slow handlers changes;
- an application needs no idle timeout at all, or a cap on the number of connections (`ServerConfig.max_connections`): each is its own setting;
- a second timeout or a setting that must be built, validated or shared as one value is exposed: revisit B, as M3-044's record says;
- `compat/flare/serve/server_bind_positional_limit.mojo` builds: `bind`'s arguments became positional.

**Verification.** Scratch mutations of the adapter, each run with the new tests and M3-046's three `Server` cases: the value not written into Flare's configuration, the initializer not passing it to `_server_config`, and `bind` not passing it to the initializer each turn all eight new tests red; the default changed to 60,000 turns M3-046's three `Server` cases, `test_server_config_sets_the_idle_timeout` and `test_servers_keep_their_own_idle_timeouts` red; the default changed to 1,000 turns the last two red (M3-046's cases still drop with a 1 s hold), and with the configuration checks removed from a scratch copy of that test, its wire check alone (closed after 1,000 ms, above 500 + 400) turns it red; 0 accepted, the lower check removed, the upper check removed, either end off by one, and the whole check removed each turn `test_bind_raises_for_an_idle_timeout_out_of_range` red.

**Fresh-context review.** A review of the diff against Flare's source confirmed the code claims (0 and negative values arm no timer, one field for both protocols, no overflow, the order of checks, a check before anything is bound) and found nothing blocking; its findings, each acted on:
1. *The idle-close test opened three connections and read them one after another,* so a connection closed early would still have measured about 1,000 ms (the reviewer showed a partial head and an h2c connection closed at 500 ms passing). Each is now opened and timed on its own; with the value not propagated all three measured 500 to 502 ms and the test failed.
2. *A read timeout was set on an h2c connection the server had already closed* (on macOS `setsockopt` can fail with `EINVAL` then), in the stop test; the call was redundant and is gone, as is one set on a still-open connection in the idle-close test.
3. *"Does not bound an arriving body" had no retained test.* The idle-close test now keeps a request stalled inside its body open from the start and checks that it is still open after the three closes.
4. *The record's mutation count was stale,* and DX said "tested for each of these with 1,000" for the keep-alive case, which is tested with 3,000 and the default: both corrected.
5. *`docs/SPEC.md` and DX's cost bullet said to cover the slowest handler,* leaving out the idle time before it that M3-046's rule counts: both now name it.
6. *An assertion on an h2c stream that was never opened could not fail:* removed.
7. *The second child in the independence test was forked outside the `try`,* so a failed fork would have left the first unreaped until its alarm: it is now forked inside it. The first child also inherits the second's listener, which it never serves; the docstring says so. The default case's upper bound was relaxed from 300 to 400 ms over the timeout for slower runners; the wire check still catches a 1,000 ms default.

A review scoped to those fixes confirmed each and found one error: "does not bound a request whose body is arriving" held only over HTTP/1.1. Flare's HTTP/2 path has no body timer (nothing there reads `read_body_timeout_ms`; every h2c read wait re-arms the idle timer), and its probe closed an h2c stream stalled inside its body at the idle timeout (1,000 ms). The record, `docs/DX.md` and the idle-close test now say and check so (the h2c case closed at the idle timeout, the HTTP/1.1 case stays open). It also noted that a failing body check printed no timings (it now prints them first) and that one assertion was implied by the others (removed).

**macOS** (the CI runner, arm64, [run 38388912198](https://github.com/sano-suguru/muntin/actions/runs/38388912198), head `1b27429`; first run of these tests there): all 51 `Server` tests passed, `::1` included. With `idle_timeout_ms=60_000` and the 1 s hold, the waiting keep-alive request and both h2c streams were answered after the release and not during it (handler order `abb`, `ab`, `ab`), while the default-configuration cases still dropped them (`ab`, `a`, `a`). With 1,000, the silent connection, the incomplete head, the idle h2c connection and the stalled h2c body were closed after 1,008, 1,003, 1,002 and 1,002 ms, and the stalled HTTP/1.1 body was still open after 4,015 ms. Two `Server`s closed idle keep-alive connections after 3,002 ms (3,000 given) and 502 ms (none given). Under SIGTERM with 60,000 and a 1,500 ms window, new connections were refused after 158 ms, the idle connections were closed after 1,637 ms and the child exited 0 after 1,811 ms. Every timing is inside the tests' bounds; one run, not a distribution.
