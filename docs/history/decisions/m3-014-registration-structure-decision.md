# Registration structure decision (M3-014)

> **Current.** Now described in [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface), [routing reference, "Registering a route"](../../reference/routing.md#registering-a-route) and [routing reference, "Compile-time diagnostics"](../../reference/routing.md#compile-time-diagnostics).
> Changed in part since:
> - [M3-015 amendment](m3-015-registration-structure-amendment-generic-forwarding.md): a fourth accepted-set edge: generic forwarding helpers register.
> - [M3-052](m3-052-registration-complexity-budget-decision.md): headroom through slot arity 4 became a maintenance ceiling of eight overloads (arity 3) that only a decision raises.
> - [M3-053](m3-053-route-conflict-decision.md): first-registration-wins, listed as unchanged, gave way to refusing overlapping registrations.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-014; `src/muntin` and `adapters/` are unchanged in it). It decides how registration grows past the ceiling M3-007, M3-008 and M3-012 measured. Today `get` and `post` have ten overloads each, Mojo 1.1.0's ten-note cap. Every typed shape costs four overloads: two result policies (`String`, `R: ToResponse`), each stateless and stateful. So typed header access on `get`, non-`Int` and several route values, `POST` without a body and broader raw handlers each push one method past the cap (`docs/SPEC.md`, "Remaining candidates").

**Selected: C4r, generic-arity slots on the existing method names. It reopens M2 when its production slice (M3-015) lands; this record is the explicit decision that M2-016 requires for that reopen.** Each registration method keeps one overload per *request-slot arity*, the number of request-derived handler parameters, in a stateless and a stateful family. The stateful family keeps a fixed leading `State[S]`, not counted in the arity; every request-derived parameter is a generic slot `var A`, and its kind is decided at compile time from its type. So slot arity 0 is `def()` and `def(State[S])`, slot arity 1 is `def(var A)` and `def(State[S], var A)`, and so on. Slot kinds:
- route value: `Int` today;
- body: a `FromBody`, or a `WithHeaders` carrier;
- raw: `Request`;
- `State`: first, through the stateful overloads.

The result type `R` is generic too, and its policy is chosen at compile time: `String` or `StaticString` give the 200 text response, a `ToResponse` converts itself. Which result types an overload accepts is a `where` clause checked by identity at the call site, because a check in the body cannot tell `StaticString` from other immutable-origin string slices. One compile-time rule check per overload gives each shape that selects an overload and passes its result `where` clause but breaks a registration rule a Muntin message; a rejected result type reports the clause's `violated constraint`. Call spellings, binding order, the request steps and their statuses, first-registration-wins and the storage do not change. What changes is in "C4r in detail" below: the overload declarations, the diagnostics of rejected calls, and three edges of the accepted set. C4r does not remove the ceiling. It turns the combinatorial growth along feature axes into linear growth in slot arity. It gives structural headroom through slot arity 4 (ten overloads per method). Full candidate-note visibility holds through slot arity 3 (eight overloads); at slot arity 4, a call that selects no overload can lose its last candidate note (a result rejected by the `where` clause adds an eleventh note), and that degradation is an accepted cost of this decision. Slot arity 5 (twelve overloads) is past the cap.

```mojo
# one overload per arity, stateless; the stateful family has the same arities after State[S]; every overload carries the same where clause
def get[E: Deinitable, R: Movable & Deinitable, //, path: StaticString](mut self, handler: def() thin raises E -> R) where (R == String or R == StaticString or conforms_to(R, ToResponse))
def get[A: Movable & Deinitable, E: Deinitable, R: Movable & Deinitable, //, path: StaticString](mut self, handler: def(var A) thin raises E -> R) where (R == String or R == StaticString or conforms_to(R, ToResponse))
def get[A: ..., B: ..., E: ..., R: ..., //, path: StaticString](mut self, handler: def(var A, var B) thin raises E -> R) where (R == String or R == StaticString or conforms_to(R, ToResponse))
def get[S: ..., A: ..., E: ..., R: ..., //, path: StaticString](mut self, handler: def(State[S], var A) thin raises E -> R, state: State[S]) where (R == String or R == StaticString or conforms_to(R, ToResponse))
```

- **C1, status quo.** The note budget is per method name. A failing call to the scratch `put` lists exactly `put`'s ten candidates, by the same rule `notes_are_per_method.mojo` pins below. So a new HTTP method fits the budget as its own copy, about 500 lines of overloads per method, and does not need restructuring; `docs/SPEC.md`'s grouping of methods with the others is corrected. Shapes on an existing method stay blocked: every `get` header shape drops candidate notes or reopens M2 (M3-012). A `String` route value costs `get` four more overloads (`def(String)`, both policies, each stateless and stateful) and `post` four, and `POST` without a body costs `post` eight. Deferring has a cost today. `/users/{name}` cannot be routed by a typed handler at all (M2-016 names non-`Int` route values as the most visible gap). Typed `get` handlers read headers only through application raw adapters (M3-012's `headers_of[me]`). DX section 3's `search(query: String, limit: Int)` has no typed form. **Rejected:** these stay blocked on Mojo 1.1.0 as long as each shape costs four overloads (the selection does not depend on the cap rising).
- **C2, named surfaces.** All 269 fixtures are identical. A header handler passed to `app.get` gets `get`'s ten notes and none names `get_headers`, so the right surface cannot be found from the error. A misuse on `get_headers` lists only that surface's candidates. Names multiply with combinations. Take headers or not × `Int` or `String` × zero to two route values: 7 route-value combinations × 2 = 14 shapes, at 4 overloads each that is 56 overloads, or 6 names of at most ten. **Rejected:** one concept spread over several names (M3-012 recorded the same for G), no error that leads to the sibling, and the name count grows with feature combinations.
- **C3, builder.** The chain registers and dispatches. A builder must hold `Pointer[App, mut origin]`, and the scratch copy reproduces M3-001's A2 gap with it: an interior reference into `App._routes` taken after the builder exists survives a hundred registrations through it and compiles (`registrar_blind_mutation.mojo` pins the mechanism). Splitting axes across builder types (`.state(users)`) still ends in one overload set for the shapes. **Rejected:** the blind-mutation path.
- **C3v, route value.** `app.add(get["/me"](me))` runs, and the route value owns its box, so no pointer is held. Shape selection is C4's engine. The only difference is the spelling, and every route changes to it: `app.get[route](h)` becomes `app.add(get[route](h))`, against DX's decision rule. **Rejected:** a spelling change for every route, with no capability C4r lacks.
- **C4b, engine beside.** All 269 fixtures are identical. Typed `get` headers run under `route["GET", ...]` (`def(Headers)`, `def(Int, Headers)`, `def(State[S], Headers)`). But `get` and `post` stay frozen, so `/users/{id}` stays `app.get[...]` while `/users/{name}` would need `app.route["GET", ...]`. That is two spellings for one method, permanently unless M2 is reopened later. **Rejected:** a second spelling for every in-method feature, against DX's decision rule and section 18. M2 stays closed only until one spelling is wanted.
- **C5, engine behind unchanged signatures.** Each of the 20 production overloads keeps its signature and names an engine adapter instead of its own. The twelve without an `Int` slot report no error. The eight with `def(Int)` or `def(State[S], Int)` fail: `cannot pass 'def(Int) raises E thin -> String' value, expected 'def(var Int) raises E thin -> String'` (the `_Bound` forms likewise). A typed borrowed value converts to no generic slot (`borrowed_overload_cannot_forward.mojo`, `typed_value_to_owned_slot.mojo`). So the engine and the signature change are one step and cannot be cut into an invisible refactor first. **Rejected** as a separate slice.
- **D. Generic descriptor (method and shape in one type or value).** One generic entrypoint over the handler's own type is not expressible: Mojo 1.1.0 has no variadic function types (`state_fail/variadic_handler_type.mojo`) and no reflection over function parameters. The method as a compile-time parameter (`route[method, path]`, measured as C4b) is expressible. A shape type the handler declares (a parts tuple `Parts[Int, Headers]` as its one parameter) is expressible with variadic struct parameters, but it replaces `def get_user(id: Int)` with positional access into a tuple. **Rejected:** the expressible forms are C4b's spelling or a handler-signature change.

**C4r in detail.**
- **Shapes and selection.** Arity selects the overload, and the argument count separates the stateful family, as today. Inside an arity no overload competes, so the raw `post` handler no longer depends on the "shorter parameter list" rule (`Request` is a slot kind). On the scratch copy, a call with more parameters than the largest arity gets `no matching method` with all eight candidates printed (9 notes, none omitted). Under the slice's six overloads, slot arity 3 costs two more per method (eight, every candidate note still printed) and slot arity 4 two more again (ten, where a rejected result can lose one candidate note: the accepted cost above).
- **What was measured.** The scratch engine classifies each slot with `comptime if A == Int` / `conforms_to(A, FromBody)`. It extracts with one helper per slot (`raises` a typed reject carrying the status) and keeps production's order, since route values come first and the body last: query 400 (`App.handle`), route value 400, 415, 413, rebuild 500, `from_body` 400, handler, result. It reuses `_Erased`, `_Call`, `_Bound`, `_handler_error`, `_json_status`, `_carrier_fields`, `_raw_request`, `_Route` and `App.handle` unchanged, and it kept the unused hand adapters, which older spikes import. All 295 existing tests pass on it, including the JSON and carrier order tests (`test_request_order_on_json_body_routes`, `test_json_inside_the_carrier_keeps_the_full_order`), and so does the Flare loopback suite. Typed `get` headers (a `Headers` slot) run on it with no overload added: `def(Headers)`, `def(Int, Headers)`, `def(State[S], Headers)`, and a bad route value is still 400.
- **The rule check must guard the adapter.** A first build reported an adapter's own empty `constraint failed:` for `def(String)` on `get`, not the rule. Mojo 1.1.0 elaborates the `_Erased.__init__[call=...]` statement's parameters before the rule function the overload called first. With the adapter named only under `comptime if <rule holds>`, every rejected shape reports its rule's message (`slot_misuse_names_the_rule.mojo` pins this on the spike). The Bool and the asserts must accept exactly the same shapes. Otherwise a stricter Bool would compile, register nothing and leave a silent 404. A compile-time `else: comptime assert False` does not close that hole well: Mojo 1.1.0 reports it instead of the rule (measured on the spike: `constraint failed: internal: guard and rules disagree` replaces the rule's message). So the guard's `else` is a run-time `abort` at registration. It keeps the rule's message, and a drifted Bool aborts the program at startup (the guard-drift mutation below).

- **Three changes to the accepted set** (an M2 reopen, besides the declarations). For plain `def` handlers the result side matches production: every result type production's `String` overloads accept (`String`, `StaticString`, and a handler declared `-> StringLiteral[...]`, whose function type returns `String`) registers on the model with the same answer, and the types production rejects are rejected (with the result rule below):
  - *widened:* an owned route value, `def h(var id: Int, body: Note)`, registers. Slots are `var A`, because owned bodies (`var body: Note`, move-only bodies) must keep registering. Borrowed slots reject them (the borrowed-slots mutation below). M2-009's fixture `body_fail/post_owned_int_and_body` pins the old rejection. The handler receives its own copy of an `Int`, so nothing else observes the difference.
  - *narrowed:* an explicitly typed function value, or a helper parameter, whose type has a borrowed `Int` route value no longer registers: `def(Int) ...`, `def(Int, var B) ...`, `def(State[S], Int) ...` and `def(State[S], Int, var B) ...`, all with `thin raises Never` or a generic `E`. On `main` these register. A borrowed body or `Request` in a typed value already fails on `main` (`def(Note) thin raises Never -> String` on `App.post` is the same `TODO` error, and DX already requires `var Request`), so those positions do not change. The leading `State[S]` is not a slot: `def(State[S], var Request) thin raises Never -> Response` and `def(State[S]) thin raises Never -> String` still register. Examples: `var f: def(Int) thin raises Never -> String = get_user; app.get["/u/{id}"](f)`, or a generic `def register[E](mut app: App, h: def(Int) thin raises E -> String)` forwarding to `app.get`. It fails with `TODO: function type conversions between closures not supported yet`. The `var` spelling (`def(var Int) thin raises Never -> String`) registers on C4r. `main` rejects that spelling (`no matching method`), so code written for one does not compile on the other. Plain `def` handlers, the form every DX example uses, are unaffected, and typed values with no parameter or only owned ones (`def() ...`, `def(var Request) ...`) still register. No existing test registers a typed borrowed value, which is why all 295 pass. The slice adds the spelling rule to DX next to the existing `raises Never` rule.
  - *widened:* an explicitly typed function value or helper parameter whose result type is `StaticString` (`var f: def() thin raises Never -> StaticString`, or a generic `def register[E](mut app: App, h: def() thin raises E -> StaticString)` forwarding to `app.get`) registers as text. With a borrowed `Int` route value (`def(Int) thin raises Never -> StaticString`) it is the `TODO` error on both, under the narrowed edge; the `var Int` spelling registers on the model and is `no matching method` on `main`. On `main` it is the `TODO: function type conversions between closures not supported yet` error, because production's text overloads take `def(...) -> String` and a typed value does not convert. On the model `R` is exactly `StaticString` and passes the `where` clause. Both the local and the generic helper are measured: spike test `test_typed_static_string_value_registers` registers each, and on `main` each is the `TODO` error. A handler value typed `-> StringLiteral[...]` is the `TODO` error on both, so it does not change.
- **The result rule is a `where` clause.** A text-result check written in the overload's body (`R == String or R == StaticString`) would widen the accepted set: Mojo 1.1.0's generic `==` keeps an origin's mutability but not its identity (`registration_known_gaps/generic_equality_ignores_origin_identity.mojo`), so every immutable-origin `StringSlice` result a handler can express and bind would pass as `StaticString`. Production accepts only `StaticString` itself. Measured with the body-level check on the spike model, the forms that bind and would register are:
  - `StringSlice[ImmutAnyOrigin]` (also spelled `ImmUnsafeAnyOrigin`, `AnyOrigin[mut=False]`, `ImmOrigin(MutAnyOrigin)`). Safe code can give it data, including a slice of a dropped local (`registration_known_gaps/safe_dangling_any_origin_slice.mojo`: the explicit `StringSlice[ImmutAnyOrigin](local)` constructor erases the origin), so copying it would read freed memory;
  - `StringSlice[ImmUntrackedOrigin]` (only the empty value can be built safely);
  - a local's origin through an explicitly instantiated parametric handler (`def origin_text[o: ImmOrigin]() -> StringSlice[o]`, registered as `origin_text[origin_of(local)]`), one type per local, empty value only. Even a direct comparison reports this type equal to `StaticString`;
  - the `_`-prefixed interior and subtree origins of the static origin (undocumented members, evidence only), in handlers that always raise.

  Mutable origins stay unequal and are rejected. A result origin tied to a handler argument does not bind to the generic overload. The raw MLIR spelling `#lit.static.origin` crashes the compiler on registration in production and in the model. The list is what was measured, not a complete enumeration.

  No check inside a generic body tells these apart. `==` against `StaticString` or `StringSlice[ImmStaticOrigin]`, a wrapping struct or tuple, a function type, a struct over the origin parameter, `reflect[R].name()` (it prints the origin erased) and `conforms_to` all erase the origin. `Origin.equals` may be used only in `where` clauses (`registration_fail/origin_equality_not_in_comptime_if.mojo`). An exact `-> StaticString` overload beside the generic one makes a `String` handler fail on the exact candidate (`registration_fail/exact_static_overload_rejects_string.mojo`).

  A `where` clause on the overload is checked at the call site, by identity: `where (R == String or R == StaticString or conforms_to(R, ToResponse))` is printed as `identical(R, StringSpan[ImmStaticOrigin])` and so on. With it on all six spike overloads, every form above is rejected (`registration_fail/immutable_origin_result_rejected.mojo`), while `String`, `StaticString`, `Response`, `Json[T]` and other `ToResponse` results keep registering (all spike tests pass). So M3-014 closes the result edge with this clause: the result types accepted for plain `def` handlers equal production's (typed `-> StaticString` values are the third edge above).

  The cost: a rejected result type no longer gets the Muntin rule message. A `-> Int` handler gets `no matching method` with `candidate not viable: violated constraint` and the expanded `identical(...)` condition, which is production's class for result errors today (`no matching method` with `does not conform to trait 'ToResponse'`). A clause that calls a function to keep the message (`where not _loose_static[R]() or R == StaticString`) is `lacking evidence to prove correctness` even for `String`, and a composite predicate measured in review let immutable-origin slices through, so the clause is pinned exactly as written. A result with a local's immutable origin (`origin_text[ImmOrigin(origin_of(s))]`) is rejected differently, as `invalid call to 'on': lacking evidence to prove correctness`; it is still rejected.
- **`rebind_var`.** `comptime if A == Int` does not refine `A` (`header_access_fail/generic_slot_does_not_refine.mojo`), so a parsed `Int` (and a `String` result) reaches the handler through `rebind_var`. On Mojo 1.1.0 `rebind_var` accepts a different struct with the same layout (`registration_known_gaps/rebind_var_layout_twins.mojo`: `Meters` read as `Seconds`) and rejects a different layout (`registration_fail/rebind_var_layout_mismatch.mojo`). So every rebind, of slots and of the result alike, sits behind a type-equality assert in one helper (`_as[T, A]` in the spike; `guarded_rebind_rejects_layout_twin.mojo`). For origin-free types (`Int`, `String`, `Request`, `Headers`) that equality is exact, and the rebind is an identity cast. For `StringSlice` the helper's own assert is not exact (generic `==` drops the origin), so exactness for results comes from the `where` clause: a text result reaching the helper is `String` or exactly `StaticString`, and the rebind is an identity cast. The helper's message says what it checks itself: `rebind requires generic type equality`. `check_unsafe.sh` does not flag `rebind_var` today. Adding `rebind` to its existing pattern would exempt the storage module, so the slice adds a dedicated check: exactly one `rebind_var[` in all of `src/muntin`, storage module included, comments and docstrings counted; it is in `app.mojo`, on the line after `comptime assert A == T`; and the `rebind_var` import appears only in `app.mojo`.
- **Unchanged under C4r:** `State` and its guarantee (the handle is still copied once into `_Bound` and borrowed per request); move-only bodies and handlers; the raw `Request` escape hatch (still the whole request, `Response` only, no route values); `ToErrorResponse` and the fixed 500; `Json[T]` and `WithHeaders[B]` as bodies; route-literal validation at the registration call, with the placeholder count matched against the route-value slots; first-registration-wins and the 404/400/415/413/500 boundaries (`App.handle` is unchanged); backend independence (no adapter change, `check_flare.sh` passes); `_Call`, `_Erased`, `_Bound` and `_handler_storage.mojo`. `App` stays non-generic.
- **Implementation and storage cost.** The ten hand adapters (`_call_none` to `_call_state_raw`) become one adapter per arity, stateless and stateful, over a shared slot extractor and result policy. The scratch file grew by 300 lines (to 1,942) while it still contained the unused hand adapters. Nothing is allocated per request beyond today's raw arguments; registration still boxes one value per route. The `rebind_var` helper and its `check_unsafe.sh` rule are new. Build time was not compared (the timing runs were cache-warm).

**`String` is a route value, never a body.** Binding by type works only for disjoint types (M2-005), so raw `String` cannot be both a route value and a body. This holds under any positional design, not only C4r: once the status quo adds `String` route values, `def(String)` on `post` is just as ambiguous. M3-014 decides it: raw `String`, like `Int`, is a route-value type, as DX section 3 writes `search(query: String, ...)` and as SPEC's `/users/{name}` candidate needs. A body is never a raw `String`. A text body is a Muntin type conforming to `FromBody`, and its name and shape are decided by the body item that adds it. Whether other builtins (bytes, numbers) can be bodies is not decided here; that is the body item's decision. M3-015 changes nothing here: `String` stays no slot kind there, and `def(String)` on `post` keeps today's message. The String route-value item makes `String` a value kind.

**Why C4r rather than deferral or C4b.** The in-method features (`String` and several route values, typed `get` headers, `POST` without a body) are blocked on Mojo 1.1.0 under every candidate except a restructure: C1 measures them past the cap. Of the candidates that unblock them, only C4r keeps one spelling per method. C4b avoids the M2 reopen only while `get` and `post` stay frozen beside a second entrypoint. C2 hides the right surface from the error. C3 adds a write path the compiler does not track. C4r's costs are the diagnostics of rejected calls (of the 68 texts lost on the scratch copy, 29 changed class, 17 kept `no matching method` with new candidate notes, 21 were rewordings the slice avoids, and 1 compiled; in the slice the six result-rule and two arity-3 fixtures among the 29 stay `no matching method`), two widened edges and one narrowed edge, the `rebind_var` discipline, and result errors reported by the `where` clause instead of a Muntin message. In exchange, rejected calls that select an overload name the Muntin rule they break, as DX section 16 asks, instead of up to ten candidate notes. Calls that select an overload report one rule, not candidate notes. Calls that select none list every candidate, which fits the cap at six or eight overloads; at ten, a result rejected by the `where` clause adds a `constraint declared here` note that pushes out the last candidate, and some stateful calls that select no overload add two trailing notes after the candidates (observed for `var db: State[Db], id: Int`, `mut db: State[Db], id: Int`, `db: Db, id: Int` and `id: Int, db: State[Db]`: 8 notes for 6 overloads; `var db: State[Db]` alone adds none), which drop after the candidates. Each in-method feature then becomes a slot kind or a rule, not four overloads. One cost goes the other way: the primary error line moves from the registration call to the enclosing function, and the call appears in the next note. M3-015 adds no new feature family, but it intentionally widens two accepted edges (`var Int` route values, typed `-> StaticString` function values) and narrows one (typed function values with a borrowed `Int` route value). Its payoff comes in the later items. The restructure still goes first and alone, so that the re-pinned diagnostics, the three edges and the reopened contract are reviewed in one PR without a new feature family; otherwise they would be mixed into the first feature's tests. The reopen is decided here, at this record's merge. Undoing it needs a new decision, not a review of M3-015; M3-015's own review checks that the slice matches this record.

**Invariants** (for M3-015 and after):
- One overload per arity and per family (stateless, stateful) on each method, at most ten per method. A result rejected by the `where` clause adds one note for its candidate, so at ten overloads (slot arity 4) such an error prints eleven notes and loses one: the accepted cost. The argument count separates the families, and no two overloads of a method accept the same handler.

- Raw `String` is never a body; once `String` becomes a slot kind it is a route value.
- The request steps, their order and statuses, first-registration-wins, `App.handle`, `_Route`, `_Call`, `_Erased`, `_Bound` and the storage module are unchanged by the restructure.
- The raw `Request` handler stays the escape hatch on every method, stateless and stateful.
