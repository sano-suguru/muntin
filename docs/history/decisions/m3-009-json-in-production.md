# JSON in production (M3-009)

> **Current.** Now described in [bodies reference, "JSON (`Json[T]`)"](../../reference/bodies.md#json-jsont), [routing reference, "Order of checks"](../../reference/routing.md#order-of-checks) and [ARCHITECTURE, "JSON"](../../ARCHITECTURE.md#json).
> Changed in part since:
> - [M3-015 production](m3-015-registration-on-generic-arity-slots-in-production.md): the four body adapters carrying the JSON step were replaced by the arity adapters (`_json_status`).
> - [M3-028](m3-028-json-response-status-decision.md): `Json(value, status=)` added; the result is no longer always 200.
> - [M3-030](m3-030-method-not-allowed-decision.md): the order's first step is 404, or 405 with Allow.
> - [M3-040](m3-040-binary-request-and-response-bodies-decision.md): the body left the raw arguments, so the JSON verdict moved to the body's former position (the arity checks described here changed), and a UTF-8 400 precedes from_body.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **production**, the M3-008 slice. The contract, the codec's rules, the rejected candidates and the revisit conditions are "JSON codec decision (M3-008)" above; this section records what production does and how it differs from the slice as written.

- `src/muntin/json.mojo` (new): `FromJson`, `ToJson`, `Json[T]` (conditional `FromBody`/`ToResponse`, `take(deinit self)`), `JsonValue` (the compact tape and child table in `_Shared`, keyword-only internal initializer) and `JsonWriter`, as in the spike, with the parser, `_Node`, `_Doc`, `_JsonBody` and `_json_content_type` private. `muntin` exports exactly `Json`, `FromJson`, `ToJson`, `JsonValue` and `JsonWriter`. Differences from the spike:
  - private names: the parser is `_parse_json` (no export; a raw handler decodes with `Json[T].from_body(req.body)`), the limits are `_MAX_BODY_BYTES` (1,048,576) and `_MAX_DEPTH` (64), and the spike's `JsonWriter.finish` is `_finish`: the decided writer API has no `finish`, and `Json.to_response` is its only caller.
  - one copy of the body: the parser takes its copy of the borrowed `from_body` argument and the document takes that copy by move (the spike copied twice). `FromBody.from_body(body: String)` borrows, so this copy remains; removing it would change the public body contract. Measured peak memory over a no-parse baseline (macOS, `/usr/bin/time -l`, the same driver against production and the spike): 1 MiB of `[0,0,...]` adds about 29 MB and parses in 13 ms, 1 MiB of typical records adds about 5 MB in 12 ms, production and spike within measurement noise of each other (the node list's growth dominates the peak, not the body copy).
  - member lookup (`get`, `value[name]`) scans the object's members and decodes escaped names on each comparison, so a `from_json` reading k fields of an m-member object costs O(k·m), bounded by the cap (a review measured about 3 ms per missing-name lookup on a 60k-member object of escaped names); caching decoded names is a possible follow-up, not part of the slice.
  - it imports `_Shared` from the storage module (allowed by `check_unsafe.sh`), `.body` and `.http`; no unsafe operation, no backend import, no `rebind`, reflection or `__extension`.
- `src/muntin/app.mojo`: `_Route` gains `json: Bool` (default `False`); the eight body overloads (stateless and stateful, `def(B)` and `def(Int, B)`, both result policies) pass `json=conforms_to(B, _JsonBody)`. In `App.handle` a JSON route appends `"1"` when `_json_content_type(request.headers)` holds and `""` otherwise, after the body; other routes' arguments are unchanged. `_call_body`, `_call_int_body`, `_call_state_body` and `_call_state_int_body`, under `comptime if conforms_to(B, _JsonBody)`, after the route value: 415 (`_unsupported_media_type()`, `Unsupported Media Type`, no fields) unless the arguments are exactly the route value if any, the body and the verdict `"1"` (`len(args) == 2` and `args[1] == "1"` for a body-only route, `len(args) == 3` and `args[2] == "1"` with a route value; the state never travels in `args`), then 413 (`_content_too_large()`, `Content Too Large`, no fields) when the body argument is longer than `_MAX_BODY_BYTES` bytes, then `from_body`. The slice said "415 when the last argument is empty"; the exact check gives the same answers while the flag is transported, and a body overload that forgot the flag answers 415 on every request: without the verdict the argument count is one short, so a body that reads `"1"` cannot stand in for it (comparing the last argument with `"1"` alone would accept that body; a test sends it, and the mutations below show the arity check is what catches it).
- Unchanged: every overload signature and message (`get` and `post` keep ten overloads each), `_Erased`, `_Call`, `_Bound`, `_handler_storage.mojo`, `check_unsafe.sh` and the unsafe surface, `State` and its marker, `http.mojo`, `body.mojo`, `state.mojo`, `testing.mojo`, `adapters/flare/muntin_flare.mojo`. `App` stays non-generic. The M3-008 spike files are unchanged and still pass: the spike's `Json` conforms to the spike's own `_JsonBody`, so production treats its routes as ordinary `FromBody` routes (`test_body_size_cap`'s "400 without the step" still holds).
- Behavior on production: order on a JSON body route 404 → query value 400 (`App.handle`) → route value 400 → 415 → 413 → JSON 400 (`from_body`: parse or `from_json`) → handler → result conversion, each step measured with every later failure present. `Content-Type`: exactly one field, media type `application/json` compared ASCII case-insensitively with SP/HTAB trimmed, parameters ignored; missing, empty, two fields (equal or not), other types, `+json` types and Unicode look-alikes are 415. Exactly 1 MiB is parsed, one byte more is 413 on every JSON body shape; at the cap a malformed body reaches the parser (400), over it 413 comes first. The parser raises above the cap itself: a raw handler's `Json[T].from_body` raises `JSON body too large`, which its own error model answers (the fixed 500 for a bare `raises`, or the handler's own mapping). A JSON result is 200 with exactly `Content-Type: application/json`; a serialization failure (NaN, infinity, a repeated name, an unbalanced or raising `write_json`) is the fixed 500 without fields and without `ToErrorResponse`, also after a stateful JSON body; a set after `to_response()` wins. `String` results and `Response.text` add no field; application `FromBody` routes need no `Content-Type`, have no cap and keep their 400.
- Diagnostics: the 249 existing must-fail fixtures (every `tests/*_fail` directory), built before and after against production: 119 byte-identical; 130 differ only in `app.mojo` line numbers (the module comment, the two answer helpers and the adapter steps shift the overloads). With line numbers normalized all 249 are identical: error lines, columns, notes and carets (the stack trace that follows `state_fail/closure_handler_storage`'s diagnostic, a pre-existing toolchain crash, excluded). Every expected text matches.

  - `tests/test_json_dx.mojo` (1): DX sections 4 and 5's JSON examples as written there, against production: JSON bodies through `App.handle`, the 415 cases (missing, `text/plain`, two fields, `application/problem+json`, `TestClient.post`), 413, three 400s, the override through `TestClient`.
  - `tests/json_api_fail` (6, `check.sh`): `Json[T]` without `FromJson` as a body and a bare `FromJson` type as a body (`... its type must conform to FromBody`), `Json[T]` without `ToJson` as a result (`argument type 'Json[In]' does not conform to trait 'ToResponse'`), `body.value^` (`field 'body.value.secret' destroyed out of the middle of a value ...`), a non-raising `write_json` that writes (`cannot call function that may raise ...`), a second `JsonValue` clearing the tape (`invalid use of mutating method on rvalue of type 'List[_Node]'`; it names the internal `_parse_json` and `_doc` only to reach a second handle). The first two prove `Json[T]` is not a `FromBody` without `FromJson`, with the same text as any other non-body type.
  - `adapters/flare/test_localhost_roundtrip.mojo`: `json_app()` serves `POST /greet` (`Json[Greeting]` in and out) and the stateful `POST /greet/{id}`. Over HTTP/1.1, `application/json; charset=utf-8` is 200 with `Content-Type: application/json` on the wire, a missing field (a request built without one) and `text/plain` are 415, a body of 1,048,577 bytes is 413, malformed JSON is 400, and a bad route value with an oversized `text/plain` body is 400; each status, body and `Content-Type` equals `App.handle` with the same fields. The adapter is unchanged.
  - Mutations (planted in scratch copies of `src/muntin`, never in the tree; 49, of which 46 red): the `json` flag missing on each of the eight body overloads; the verdict not transported, or always `"1"`; the arity check dropped together with a missing flag (a body `"1"` then passes as the verdict); the step missing in each of the four adapters; 415 answered as 400; the 413 step missing (stateful `Int` body); 413 before 415; the JSON steps before the route value (stateful); the cap off by one in an adapter and in the parser, and missing from the parser; the `Content-Type` rule accepting a missing field, a second field or `+json`, rejecting parameters, comparing case-sensitively or lowercasing Unicode first; the parser accepting trailing commas, duplicate members, leading zeros, a lone low surrogate, control bytes, trailing content or one level past the cap; duplicate detection by list scan and element access by walking the siblings (the cost oracle); `int()` accepting fractions; `float()` accepting infinity; an absent member returned as a value; the writer accepting a repeated name or non-finite numbers, leaving control bytes unescaped or finishing an open container; a serialization failure answered 200; a JSON result without its field. Green, and observationally inert (no request distinguishes them from production while every body overload sets the flag): the verdict appended for every body route (the slice listed it; the non-JSON adapters read their arguments from the front, so a trailing extra argument changes nothing); the verdict read as "non-empty" instead of `"1"`; the arity check dropped alone. The last two matter only when a flag is missing, which the combined mutation above covers. M3-009's acceptance records inert mutations with their reason instead of forcing them red.
