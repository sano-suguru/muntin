# Graceful shutdown decision (M3-045)

> **Current.** Now described in [serving reference, "Stopping"](../../reference/serving.md#stopping), [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter) and [serving reference, "`serve`"](../../reference/serving.md#serve).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-045, [pull request #83](https://github.com/sano-suguru/muntin/pull/83)). It decides how a `Server` stops when the process is asked to stop (SIGTERM from a supervisor on deploy or restart, SIGINT from Ctrl-C), which [M3-032](m3-032-serving-entrypoint-decision.md) left out ("Muntin adds no stop call, graceful shutdown or signal handling") with a revisit condition ("Flare offers a stop the serving thread can request, or the toolchain gives the process a thread or signal primitive Muntin would use"), and implements the choice in the same item. The question, candidates, criteria and pass conditions below were written before the wire measurements; what precedes them was read from Muntin's and Flare v0.12.0's source and from three probes of Mojo 1.1.0 (named below).

**Why now.** Every deploy or restart of a `Server` program cuts the requests it is answering: SIGTERM ends the process by the runtime's re-raise (M3-032, measured), with nothing drained. That is the largest remaining obstacle to running a `Server` behind a supervisor.

**Question.** When a serving process receives SIGTERM (and SIGINT, if the same policy fits), can `Server.serve` (1) stop accepting new connections, (2) let the requests already in progress finish and reach their clients, and (3) end within a bounded time whatever clients and handlers do; and with what API (does `server.serve(app)` keep its spelling, is there a stop handle, where the time bound is set, its default and range), what serve returns or how the process exits, and what is promised about new connections, HTTP/1.1 keep-alive connections, h2c connections, partly received bodies and handlers that do not return.

**The path at the base** (read from the code and probed):
- Flare v0.12.0's single-worker `serve` runs `run_unified_reactor_loop` on the calling thread. The loop re-reads `HttpServer._stopping` (an acquire load through its address) once per iteration; its poll waits at most 100 ms, and `epoll_wait`/`kevent` interrupted by a signal (EINTR) count as an empty poll. A handler runs synchronously inside the loop, so the flag is not read while one runs; an HTTP/1.1 response is written eagerly right after the handler returns. When the loop sees the flag it flips `Cancel.SHUTDOWN` on every live connection (h2c: `signal_drain`, which sends nothing) and closes each, then `serve` returns.
- `HttpServer.close()` sets the flag and closes the listener ("hard stop"). `HttpServer.drain(timeout_ms)` closes the listener, sleeps the whole `timeout_ms` while the reactor keeps serving the open connections, then sets the flag; its documentation and Flare's operations guide say it is called "from a thread other than the one running serve()", that it cannot return early (the single-worker reactor publishes no live-connection count), and that Flare installs no signal handler because "Mojo does not yet allow the process-global mutable state an async-signal-safe handler needs". `ServerConfig.shutdown_timeout_ms` (default 5000) is a stored value `drain` does not read. Flare's own background-thread pattern is `flare.runtime.watchdog` (a control block and `ThreadHandle.spawn_os`).
- Probes (Mojo 1.1.0, Linux x86-64): a module-level `var` does not compile (`global variables are not supported`); a Mojo binary has five threads before `main` does anything (the runtime's four `🔥 Thread` workers), none of them blocking any signal, and the runtime has a handler on SIGINT and SIGTERM in every thread's process (`SigCgt`), installed over an inherited `SIG_IGN` too (a process started with both ignored showed them caught, not ignored); a `sigaction` with `SA_RESETHAND` and a handler that does nothing let the process survive SIGTERM, and a later `sigaction` read showed the disposition reset to `SIG_DFL`.

**Candidates.**
- A, a Muntin stop mechanism: the adapter turns SIGTERM/SIGINT into a stop request without a global and without work in the signal handler, and a helper thread carries the request to Flare (close the listener, keep serving for a bounded window, then stop).
- B, wrap Flare's lifecycle API minimally: as A, but the helper thread calls Flare's own `drain(timeout_ms)` and Muntin adds only the signal detection, the bound on the whole stop and the restore.
- B0, signal handler sets Flare's stop flag directly, no thread: the handler writes `_stopping`.
- C, decision only: if no candidate both finishes in-flight requests and bounds the stop, record what Flare would need and change nothing.

**Comparison criteria**: whether in-flight requests finish and reach the client; whether new connections are refused; whether the stop is bounded when a client stalls or a handler never returns; what runs in the signal handler (nothing that allocates, raises, locks or touches a Flare or Mojo object); global state needed; threads added and their lifetime; the API added and whether `server.serve(app)` keeps building; HTTP/1.1 keep-alive and h2c behavior during the window, measured; exit status; Linux and macOS.

**Pass conditions** (each with executable evidence on the wire, a real child process, on both CI systems):
- an HTTP/1.1 request whose handler is waiting when SIGTERM arrives is released after the signal and its response (status and body that only the released handler can produce) reaches the client; the child then ends with the documented status, within the documented bound;
- after SIGTERM, a new connection is refused within the documented time; what an HTTP/1.1 keep-alive connection and an h2c connection open before the signal see during the window and at its end is measured and only what holds is promised;
- with no request at all, SIGTERM ends the child within the bound; with a client that sent half a request and stalls, and with a handler that never returns, the child still ends within the bound, with the status the record names for each;
- the parent reaps every child it forks, kills it if it outlives the bound (the test then fails, not hangs), and the port can be bound again after the child ends;
- SIGINT: the in-flight case and the no-request case as for SIGTERM; a second stop signal during the window and the bound value's range checked;
- existing `Server` tests, the loopback suite (HTTP/1.1 and h2c, raw and typed handlers), M3-044's receive limit and refusal, `_BorrowedHandler`'s non-`Copyable` guard and the serving fixtures keep passing;
- scratch mutations turning a listed test red: the signal ignored (no stop request), the drain skipped (stop at once), the bound removed;
- `src/muntin` unchanged; `check_boundaries.sh` passes.

**Measured premises** (Mojo 1.1.0, Flare v0.12.0, Linux x86-64; the final tests in `adapters/flare/test_server.mojo`, run first against a scratch copy of the adapter, then against the code):
- **Notification.** A handler that does nothing, installed with `SA_RESETHAND | SA_RESTART`, lets the process survive SIGTERM and SIGINT on whichever thread receives them, and the disposition reads `SIG_DFL` afterwards; a thread polling `sigaction` every 50 ms saw it within that time. Nothing else is needed in signal context, and no global.
- **Flare's `drain` from a second thread** (a pthread through Flare's `ThreadHandle.spawn_os`, given the `HttpServer`'s address while the serving thread is inside Flare's `serve`): new connections were refused 48 to 53 ms after the signal; an HTTP/1.1 request whose handler was blocked when SIGTERM (or SIGINT) arrived, released after the refusal was seen, was answered 200 with the body only the released handler produces, and the child exited 0 about 1,610 ms after the signal with a 1,500 ms window; with 300 ms and no request it exited after about 425 ms, with 0 after about 125 ms. A connection opened while the handler blocked the reactor (queued by the system, not yet accepted by Flare) was reset with no answer when the listener closed.
- **During the window:** an HTTP/1.1 keep-alive connection that had been answered before SIGTERM got a second request answered after the refusal (`200`, `Connection: keep-alive`), then was closed 500 ms later (Flare's `idle_timeout_ms`); on an h2c connection whose stream 1 was blocked in its handler, stream 3, sent after the refusal, was answered too, both after the release, and the connection was closed about 550 ms after the signal, before the window ended, with no `GOAWAY`.
- **Bounds:** a client that sent a head declaring 100 bytes and 10 of them did not delay the stop (exit 0 after the window) and got no answer. A handler that never returned held the reactor past the window: Flare's `serve` did not return, and only the watcher's `_exit(128 + 15)` ended the child, 1,350 ms after the signal with a 300 ms window and a 1 s bound. A second SIGTERM or SIGINT after the refusal ended the child by that signal within 5 ms.
- **Mojo:** a `sigaction` buffer must stay alive past the call (a `List` destroyed after its last named use was read freed: the first prototype installed a garbage handler and crashed); one module-wide signature per C symbol (`write`, `_exit` conflict with the standard library's and Flare's declarations).

**Selected: B.** `Server.bind(host, port, *, max_body_bytes=..., shutdown_grace_ms: Int = 5000)`; `server.serve(app)` keeps its spelling and, while it runs, turns SIGTERM and SIGINT into a graceful stop: the listener closes, the open connections are served for the whole window, Flare closes the rest and `serve` returns normally. Contract: `docs/DX.md` section 1; mechanism: `docs/ARCHITECTURE.md`, "Flare adapter".
- **Why a thread.** Flare's reactor gives Muntin control only inside a handler and reads only its own stop flag; `drain` is documented as called from another thread. One watcher thread is the least that reaches it: it starts and is joined inside `serve`, touches no `App`, and uses Flare's own thread handle (an internal module, `flare.runtime._thread`, the one Flare's watchdog uses), so Muntin adds no thread code of its own.
- **Why `SA_RESETHAND`.** Mojo 1.1.0 has no module-level state, so a handler cannot tell anyone anything by writing memory; a blocked-signal design fails on the runtime's threads (B1). The kernel's own reset of the disposition is state the watcher can read without any shared memory, and the handler is empty.
- **The window is waited in full.** Flare v0.12.0's single-worker reactor publishes no live-connection count, so neither `drain` nor Muntin can tell when the last request ended; returning when Muntin's own handler count reaches zero would cut a body still arriving or a response still being written. A stop with nothing in flight therefore takes the window.
- **The default, 5,000 ms,** is Flare's `ServerConfig.shutdown_timeout_ms` default: with the 1 s bound a stop ends within about 6 s, inside Docker's default 10 s and Kubernetes' default 30 s before they kill. **The range,** 0 to 86,400,000 (one day), keeps Flare's `now + timeout` and the watcher's deadline far from overflow and rejects what is almost certainly a unit mistake; it is checked by `bind` after `max_body_bytes` and before the host.
- **The bound, 1 s after the window,** is ten of the reactor's longest poll waits (100 ms): past it, only a running handler can be keeping the reactor, and Mojo cannot interrupt it. Exit status 128 + the signal is the shell's convention for "ended by that signal" and tells it apart from a stop that drained (0); `_exit` works for process 1 in a container, where the kernel ignores a re-raised default-action signal.
- **A second stop signal** takes the default action, so an operator can still force a stop (Ctrl-C twice).
- **Kept as before:** the receive limit and its refusals (M3-044), the buffer-ring refusal, HTTP/1.1 and h2c answers, raw and typed handlers, `_BorrowedHandler`'s non-`Copyable` guard (the watcher never touches the handler), `App.handle` on one thread, `src/muntin`.

**By kind (M2-016): not an M2 reopen.** `App.handle`, the accepted set, the overload set and every diagnostic are unchanged; `Server` is an M3 type. What changes is the adapter's runtime: during `serve`, SIGTERM and SIGINT no longer end the process at once (by the runtime's re-raise) but stop it gracefully, so a `main` that does nothing after `serve` now exits 0 after a stop instead of being terminated by the signal; a process that inherited them ignored now stops on them while it serves (the runtime already replaced that ignore before `main`). `Server.bind` gains one keyword-only argument with a default.

**Cost.** One more thread for the life of `serve`, polling every 50 ms. Every stop takes the whole window. The handlers of SIGTERM and SIGINT belong to `serve` while it runs. Muntin depends on an internal Flare module (`flare.runtime._thread`) and on `struct sigaction`'s layout and flag values on Linux (glibc) and macOS, written in the adapter. No GOAWAY or `Connection: close` during the window: keep-alive clients learn of the stop by a closed connection.

**What Flare would need for more** (upstream, not required by this item): the single-worker reactor publishing its live-connection count (as its multi-worker workers do through their stats cell) would let `drain` return when the last connection closes; sending GOAWAY and `Connection: close` while draining would tell keep-alive clients before the close; a public thread handle or a stop request the serving thread can make would remove the internal import.

**Revisit when:** Flare publishes a live-connection count, a public thread handle or a serving-thread stop; Flare's `drain` changes (returns early, sends GOAWAY or `Connection: close`, stops serving open connections), which the stop tests would show; the Mojo runtime changes its signal handlers or threads; Mojo gains module-level state (a handler could then write a flag, and the poll could go); applications need a stop call, an early return or a hook before the stop.

**Verification.** Red before the code: the stop tests did not build (no `shutdown_grace_ms`); with the keyword removed, every one of them failed on the base, the children ended by the runtime's handler. Scratch mutations: the handler not installed turned nine stop tests red; `close()` instead of `drain` turned six red (the window not waited, the in-flight and h2c cases); the `_exit` removed turned the never-returning handler's test red (the child outlived its bound and was killed by the test); the dispositions not put back turned every test that reaches the end of `serve` red (exit 4).

**Fresh-context review.** A review of the diff against Flare's source found no high-severity defect (the `struct sigaction` layouts and flags, the empty handler, the buffers' lifetimes and the spawn-failure restore checked out) and these, each acted on:
1. *The stop tests ran only in forked children,* which have neither the runtime's worker threads nor a `main` that returns, although ARCHITECTURE named an exec-based test as due once Muntin took on graceful shutdown. `adapters/flare/stop_driver.mojo`, built by `check_flare.sh`, is now `execv`d by two tests: a request held when SIGTERM arrives is answered and the program exits 0 by returning from `main` (six threads when counted by hand in `/proc`: the runtime's four, the main one and the watcher); started with SIGINT ignored, it still stops on SIGINT.
2. *A stop before Flare's `serve` set up its reactor* would make that `serve` raise on the closed listener (`drain` closes it before setting the flag), so `Server.serve` would raise on a stop. The watcher now records the signal it acts on, and `serve` returns normally when Flare's `serve` raised after one. Not pinned: the window is between `_StopWatch` and Flare's first poll, and no test can place a signal there.
3. *A second signal as process 1 of a container* takes the default action, which the kernel ignores there; `docs/DX.md` now says so and names `--init`.
4. *"The dispositions are back when it raises" had no evidence.* Each stop test's child now serves a second time on the closed listener, which raises, and checks the dispositions again; skipping the restore on that path turned nine tests red.
5. *A stop signal arriving as `serve` ends for another reason* was swallowed by the empty handler. `finish` now sends it again once the previous dispositions are back. A SIGINT within the watcher's 50 ms poll after a SIGTERM is absorbed rather than ending the process; `docs/DX.md` says the second signal counts once the stop has begun. Neither timing can be placed by a test.
6. *Two lower bounds were measured from the start of the reap,* not from the signal; they now use a timestamp taken before `kill`.
7. *Forked children inherited the runner's ignored SIGPIPE;* each now restores the default right after `fork`.
8. *"Reset" was stronger than its test* (which also accepted EOF); `docs/DX.md` says closed without an answer, reset when measured on Linux.
9. *Code that resets a stop signal to the default during `serve` starts a stop;* `docs/DX.md` says so.

A review scoped to those fixes found no high-severity defect and these, each acted on: the module docstring, `serve`'s docstring, `docs/ARCHITECTURE.md` and `docs/DX.md` still said a raise always propagates (now they state the exception, and that a Flare setup failure coinciding with a stop is dropped with it); a signal could still slip between `finish`'s check and the restore (the restore now reads each disposition it replaces in the same `sigaction` call); the exec'd driver had no `alarm` (a driver stalling before its port would hang the run) and the helper leaked a pipe and the child on a failed read (both fixed); the ignored-SIGINT test's docstring credited the runtime for what `serve`'s unconditional handler does (reworded); the thread count was not measured by a test (marked as counted by hand). It confirmed that a second `serve` on the closed listener raises (`fcntl` on fd -1) on Linux and macOS without creating a reactor, and that a signal is never sent again after a stop the watcher drained.

**macOS** (the CI runner, arm64; first run of the stop tests there): all 28 `Server` tests passed, `::1` included. New connections were refused 167 to 185 ms after the signal (50 ms on Linux); an in-flight request was answered and the child exited 0 about 1,950 ms after the signal with a 1,500 ms window; the never-returning handler ended with 143 after 1,453 ms (300 ms window); keep-alive and h2c behaved as on Linux (no `GOAWAY`), and a queued connection was reset. The first macOS run did not build the tests: Flare's macOS reactor declares `pipe` with a pointer argument, which conflicted with the test helper's own declaration; the helper now uses Flare's wrapper.

**Owner review of the pull request.** The owner's adversarial review (static, of the adapter and test diff) confirmed the main path (the `SA_RESETHAND` notification, Flare's `drain`, the `_exit` bound, which works for process 1) and withdrew an earlier remark about process 1; it accepted the 5 s default and the window waited in full. It withheld approval for one blocking finding and five more, each acted on:
1. *Two `serve`s in one process corrupted the process-wide dispositions* (blocking). Each `_StopWatch` saved what it replaced, so a second one saved the first one's handler and, finishing last, put that handler back with no watcher behind it; finishing first, it could undo a stop the other still needed. Neither was refused nor documented. Decision: one `serve` per process owns the stop signals. `_StopWatch` first claims a process-wide cell (compare-and-swap from 0 to 1) and raises `Server.serve is already serving in this process` before touching any disposition when another holds it; it releases the cell after the restore, on every path. Mojo 1.1.0 has no module-level `var`, so the cell is created by the standard library's internal `std.ffi._get_global`, which creates a named global once per process under its own lock (probed: 16 threads racing to claim it, one won, three runs). Rejected: a process-level signal manager shared by several `serve`s (more machinery for a configuration nothing needs: a `Server` is one thread, and a process that needs several sockets can serve them from several processes); using the disposition itself as the lock (a second `serve` starting while the first is draining, with both dispositions back at `SIG_DFL`, would look free). Red on the base: `test_a_second_serve_in_the_process_is_refused`, where a handler of a serving `Server` binds and serves a second one, timed out (the second `serve` started its own watcher and Flare loop inside the handler). Mutations: the claim check removed turns that test red; the release skipped turns 14 tests red (`_serve_stoppable`'s second `serve` is then refused as already serving, exit 7). A forked child of a serving process inherits the claim, so a `serve` there is refused; nothing in Muntin forks.
2. *`sigaction` results were ignored.* A failed read in the watcher would have left the zeroed buffer looking like `SIG_DFL` and started a stop; a failed install would have served with one signal handled and the other not. Now an install that fails puts back what was changed (sending again a signal delivered meanwhile), releases the claim and raises before serving; a failed read is not a delivery (the watcher reads again); a failed restore makes `serve` raise. `ThreadHandle.join` raises only if `pthread_join` fails (Flare's contract; with a thread `spawn_os` created joinable and never detached, the possible errors do not apply); if it ever did, the watcher could still read the control block, so `finish` puts the dispositions back and aborts the process rather than free the block, instead of skipping the restore. None of these failures can be produced by a test on a supported system; they were checked by reading the code and are untested.
3. *The stop boundaries were declared untestable.* `serve` now takes a private `_stage` hook (not API, like the initializer's `_`-keywords), called with both handlers installed and the watcher not yet started, with the watcher running before Flare's `serve`, after Flare's `serve` ended while the watcher still runs, and after the join before the restore. Four tests place a SIGTERM at each point in a forked child that serves the same `Server` twice (the second time Flare's `serve` raises on the closed listener at once): at the first two points `serve` returns, with the dispositions back and the claim released (the second `serve` raises on the listener, not as already serving); after Flare's `serve` ended, the signal is either acted on or sent again (both outcomes accepted; the second was the one measured); after the join it is sent again and ends the process by SIGTERM (the runtime's handler being back). Each child's dispositions are compared before and after, and every child ends within its bound. Mutations: `serve` re-raising after a stop turns the four red; the resend removed turns the last two red. These show the watcher ends and the dispositions return at each boundary; that the watcher never touches the server after `serve` returns rests on the structure (it is joined in `finish`, before `serve` returns, and reads the server only after it saw a signal), not on a memory checker.
4. *A `drain` that raised fell back to `close` silently.* The watcher now keeps the error, still falls back to `close` (Flare's hard stop), and `serve`, after the join and the restore, raises `serve: the graceful stop failed and open connections were closed at once: Flare's drain raised: <error>` instead of returning as for a graceful stop. On Flare v0.12.0 `drain` cannot raise (its one fallible step, closing the listener, does not raise), so this path is untested. The bound is now stated as measured from `drain`'s return: the signal's detection (up to 50 ms), the window, then `_REACTOR_STOP_MS`.
5. *The h2c stop test did not acknowledge the server's SETTINGS,* the defect M3-044 fixed in another client, *and did not check how the connection ended.* It now sends SETTINGS with ACK for the server's SETTINGS, and asserts that the connection ended by a close or a reset (not the read timing out) within the window plus the bound (measured: closed after about 553 ms, three runs).
6. *The `struct sigaction` layout was split only by macOS or not.* The offsets and flags were verified on Linux x86-64 (glibc) and macOS arm64, the project's two platforms (`pixi.toml`), so `_StopWatch` now has a `comptime assert` admitting only those: cross-compiled, `hello_server` builds for `x86_64-unknown-linux-gnu` and `arm64-apple-darwin` and fails the assertion for `aarch64-unknown-linux-gnu` and `x86_64-apple-darwin` (`CompilationTarget.is_apple_silicon()` failed for a cross-compiled arm64 target, so the macOS test is "not x86").

**Revisit when** (added): Mojo removes or changes `std.ffi._get_global` or gains module-level state (the serving cell moves to it); an application needs several `serve`s in one process (a shared signal manager); a new platform is supported (its layout and flags, then the assertion).

A fresh-context review scoped to these fixes found nothing blocking; its findings, each acted on:
- *A failed restore released the claim* although that signal might keep the stop handler with no watcher behind it, so a later `serve` would have saved that handler as the disposition to put back (the blocking finding, degraded). The claim now stays held when a restore fails (the install-failure and spawn-failure paths too), and `serve` raises saying the process cannot serve again; a signal delivered on the disposition that was put back is still sent again. `errno` is now taken at the failing call, not after later calls; the serving cell's allocation is checked (the process aborts without it); a raise from the cleanup after Flare's `serve` raised now carries Flare's error.
- *`test_a_stop_before_flare_serves_returns` relied on a 300 ms sleep* for the watcher to close the listener first; a late watcher would have let the test pass through the reactor instead. Its hook now waits until SIGINT reads `SIG_DFL` (the watcher resets it right before `drain`, whose first step closes the listener) and then 50 ms. `drain` then holds the watcher for the whole window, which is why Flare's `serve` meets a closed listener and raises.
- *The h2c test acknowledged the server's SETTINGS only after the stop.* Acknowledging them before the stop showed that Flare writes nothing on that connection while stream 1's handler holds the reactor (the read timed out), so the test now sends the preface and SETTINGS, reads the server's SETTINGS, acknowledges them, and only then opens stream 1. The connection's close at about 553 ms after the signal is Flare's 500 ms idle close (`docs/DX.md` section 1), not the end of the window.
- Not tested: a second `serve` from another thread (the same compare-and-swap as from inside a handler, which is tested; the claim itself was probed with 16 racing threads).

**Owner re-review of the pull request.** The owner accepted `_get_global` as a known internal-API risk and asked for three changes before approving, each made:
1. *The claim was released before a late signal was sent again.* Between the release and the `kill`, another thread's `serve` could claim and install its handler, so the resent signal would stop that `serve` instead (or be absorbed by it). `finish` now restores, sends the signal again, and only then releases the claim (when the restore succeeded; a failed restore still keeps it, and the restore failure, then a `drain` failure, are still raised after it). The install-failure and spawn-failure paths follow the same order. A fifth `_stage` point, `_STAGE_RESTORED`, comes after the restore and any resend and before the release. `test_a_stop_sent_again_is_sent_before_the_claim_is_released` gives SIGTERM a do-nothing handler with `SA_RESETHAND` before serving, so the resend is seen (that disposition goes back to `SIG_DFL`) without ending the child, places a SIGTERM after the join, and at `_STAGE_RESTORED` requires the claim still held and the resend delivered; after `serve` raises it requires the claim released. Mutations: releasing before the resend turns it red (exit 30, the claim already released); the resend removed turns it and both late-signal stage tests (after Flare's `serve`, after the join) red. A forked child has one thread, so the test cannot tell `raise` from `kill` to the process. The test's first form gave SIGTERM a do-nothing handler with `SA_RESETHAND` and failed on macOS CI only (exit 32, the resend never seen): macOS's `sigaction` does not report `SA_RESETHAND` in the disposition it returns (xnu's `sigaction` builds the old action's flags from `SA_ONSTACK`, `SA_RESTART`, `SA_SIGINFO` and `SA_NODEFER` only), so the handler `serve` put back had lost the flag. The test's handler now sets its signal back to `SIG_DFL` itself; `docs/DX.md` states the macOS loss for an application's own handler. The scoped review of this fix found the order alone insufficient: `kill(2)` to the process makes the signal pending before it returns, but with the runtime's worker threads not blocking signals the kernel may run a handler on another thread, after the release. The resend is now `raise(3)`, which sends it to the serving thread and returns only after its disposition was acted on (a terminating default ends the process, a handler has run, an ignored signal is dropped); a signal that thread blocks would stay pending on it, and Muntin blocks none.
2. *The watcher's two resets to `SIG_DFL` were unchecked.* If one failed, a stop signal could keep the stop handler and a second signal would be absorbed instead of ending the process. Decision: if either reset fails, the watcher ends the process at once with `_exit(128 + signal)`, the status of the existing bound, without draining. Continuing the graceful stop and raising afterwards was rejected: it keeps a stop that the documented second-signal escape no longer covers, for a 24-hour window at most, and adds state for a failure `sigaction` cannot produce here (only `EINVAL` or `EFAULT`, neither possible with these signals and buffers). Untested for that reason.
3. *Docs:* `docs/DX.md`'s Protocols line still said `max_body_bytes` was the only backend configuration (now with `shutdown_grace_ms`), and the adapter's docstring did not list `_shutdown_grace_ms` among the initializer's keywords.

**Owner's third review of the pull request.** The owner accepted the three changes above and leaned to approving, with one precondition to state before merging: `raise` acts on the signal before it returns only if the calling thread does not block it. A serving thread that blocks SIGTERM, while the runtime's threads do not, lets a late SIGTERM run the stop handler on another thread; `finish` restores, `raise` leaves the resend pending on the serving thread, the claim is released, a later `serve` installs its handler, and when the first thread unblocks SIGTERM that later `serve` stops. Decision: the supported contract excludes it. `serve` is supported only on a thread that blocks neither SIGTERM nor SIGINT, before or during the call; `docs/DX.md` section 1, `serve`'s docstring and `docs/ARCHITECTURE.md` say so (Muntin blocks neither). Rejected: unblocking the signal around the resend (`pthread_sigmask`), which would deliver a signal the application chose to hold for its own `sigwait` or `signalfd`, and any mechanism keeping a pending resend from reaching the next `serve`, which is more machinery for a configuration Muntin does not create. Untested: a documented exclusion, not a path the code handles.
