# Request target and method bytes decision (M3-039)

> **Current.** Now described in [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter), [serving reference, "`serve`"](../../reference/serving.md#serve) and [ARCHITECTURE, "Current limits"](../../ARCHITECTURE.md#current-limits).
> Changed in part since:
> - [M3-040](m3-040-binary-request-and-response-bodies-decision.md): the body is no longer a String the adapter validates, so the invariant's "body" among the well-formed UTF-8 Strings handed to App.handle no longer applies; the method and target check is unchanged.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-039, PR #77). It decides what the Flare adapter does with a request method or target whose bytes are not well-formed UTF-8, and implements the choice in the same item, as M3-038 did: the defect it closes stops the serving process, so a decision-only pull request would leave every `Server` stoppable for one more merge cycle, and its reproduction is part of the evidence below. The question and what settles it were committed before any measurement beyond the base reproduction that confirmed the defect (`docs/DEVELOPMENT.md` section 2).

**Why now.** M3-038's fresh-context review found that over h2c Flare v0.12.0 passes request-target and method bytes that are not UTF-8 through to the adapter, which copies them unchecked, and that some such requests abort the serving process (`docs/ARCHITECTURE.md`, "Other current limits", the known defect): one unauthenticated request stops a `Server`, which accepts h2c on its port, for every client. M3-005 (header fields) and M3-038 (bodies) answer request data Muntin cannot represent with the adapter's 400 before `App.handle`; the method and the target are the request parts still copied verbatim (M1-002, restated by M2-002).

**Question.** When Flare hands the adapter a request whose method or target bytes are not well-formed UTF-8, what reaches `App.handle`, and can the serving process survive it? Specifically: the first point on the path where such bytes can be inspected by an operation that cannot itself abort; whether they are rejected there and with which status, before or after middleware and routing, on which protocols; which requests Flare refuses itself (so that Muntin does not claim them); whether a method or target that is well-formed UTF-8 (non-ASCII, U+FFFD, percent-encoded, an empty or unknown method) is answered exactly as today; whether the same `Server`, on a new connection and on the same one, answers the next well-formed request; and which statements of DX, ARCHITECTURE, SPEC and the earlier records (M1-002's verbatim method and target, M2-002's target boundary, M2-016's M2 contract, M3-005, M3-038) change.

**What settles it:**
- the path traced in code, boundary by boundary: Flare's HPACK string decoding, its request-field validation for `:method` and `:path`, `take_request`, the h2 reactor's dispatch and what it does with a handler that raises; the adapter (`_serve_app`'s `HEAD` comparison, `to_muntin_request`); `Request.__init__`'s split at `?`; `App.handle` (middleware, `_match`, `_allowed`, `_query_value`, `_decode_value`, raw handlers); and the same for HTTP/1.1, whose parser runs first;
- a reproduction on the base, one disposable `Server` child per request on localhost, over h2c and HTTP/1.1: method bytes and target bytes separately (path, query, a byte at a split position), the status and fields on the wire, a middleware's view of the bytes `App.handle` received, whether the child survives (its exit status and diagnostic when it does not) and whether it then answers a well-formed request on a new connection; the inputs: ASCII; well-formed non-ASCII UTF-8; a U+FFFD the client sent; `0x80`, `0xFF`, a truncated sequence, an overlong form, a surrogate; `%FF` (percent-encoded, which is ASCII and route-value decoding's to refuse, M3-018); an empty method, an unknown uppercase method, a lowercase one; the 404, 405 and `HEAD` baselines;
- which Mojo 1.1.0 operation aborts, and which operations inspect a `String`'s bytes without slicing or iterating code points (`as_bytes()`, `String(from_utf8=)`), measured on `String`s built as Flare builds them (`String(unsafe_from_utf8=)`);
- the same requests through the changed adapter: the status, whether middleware and handlers run, the child's survival, a new connection, and a later stream on the same connection as far as Flare's connection contract allows;
- the existing contracts read from their records, docs and tests: M1-002 and M2-002 (method and target copied verbatim; the target split in `Request`); M2-016's M2 contract and its reopen conditions; M3-005 and M3-038 (400 before `App.handle` for what cannot be represented); M3-018 (route values decoded and validated in `App.handle`); M3-027's `HEAD` rule at every exit of the adapter; M3-030 (405 with `Allow`); M3-034 (what middleware sees);
- per candidate below: what changes in `src/muntin`, `adapters/`, the public API and existing behavior, and what a test can pin.

**Boundaries that do not change silently:** `App.handle`'s routing, 400/404/405/500 and middleware contract; `Request`, `Response`, `Headers` and `TestClient` signatures; the route-value grammar and decoding; the query left undecoded; the adapter's header and body rules, its `HEAD` rule and the HTTP framing Flare sends; a well-formed UTF-8 method or target answered as today, U+FFFD and non-ASCII included; no syntax rule for methods beyond what is needed here (this item is not a method grammar); one-thread serving; no Flare type in Muntin's API and no vendored or patched Flare code. A change to any of them is named here, with its classification against M2-016.

**Candidates to measure:**
- A: the adapter checks that the method's and the target's bytes are well-formed UTF-8, through their byte spans and before any `String` operation that slices or iterates them (so before `Request` is built), and answers anything else with its existing 400 before `App.handle`;
- A-target: A for the target only, the method passed on as today;
- B: Muntin core made safe for any bytes (`Request`'s split and the route scan working on bytes), letting such a method or target reach `App.handle`;
- C: an upstream Flare change (validating pseudo-header bytes over HTTP/2 as its HTTP/1.1 parser does), if the measurement shows the adapter cannot see or check them first;
- baseline: copied verbatim (main).

**The path today, boundary by boundary** (read from the code at the base):
- Flare v0.12.0's HPACK decoder keeps a field's octets unchanged and, when any is 0x80 or above, builds the `String` with `String(unsafe_from_utf8=)` (`flare/http2/hpack.mojo`; its docstring: "Consumers that need text must validate or convert it themselves"). Its request-field check (`validate_request_fields`, `flare/http2/state.mojo`) refuses NUL, CR, LF and surrounding whitespace in a value, and requires exactly one `:method` (any value, the empty one included) and a non-empty `:path` starting with `/` (or `*` for `OPTIONS`); nothing checks UTF-8 or a method token. `take_request` copies `:method` into `Request.method` and `:path` into `Request.url`, and the h2 connection calls the handler's `serve` with it; a raise from `serve` becomes a response, and an abort ends the process.
- Over HTTP/1.1 Flare's parser runs first and answers its own 400 (body `400 Bad Request`, `Content-Type: text/plain`, `Connection: close`) to a method byte that is not a token character or a target byte outside `!`..`~` (well-formed UTF-8 included), and to a lowercase or empty method; such a request never reaches the adapter.
- The adapter's `_serve_app` compares `request.method` with `HEAD` (a byte comparison), and `to_muntin_request` passed `request.method` and `request.url` to `Request` unchecked.
- `Request.__init__` finds the first `?` and slices the target there (`target[byte=:mark]`, `target[byte = mark + 1 :]`). Mojo 1.1.0's `String` byte slicing asserts that a slice starts on a code point boundary (`std/collections/string/string_span.mojo`, enabled in a default `mojo build`), and a failed assertion aborts the process. In a well-formed UTF-8 target every byte after an ASCII delimiter starts a code point, so the assertion cannot fail; in one that is not UTF-8 the byte after a delimiter can be a continuation byte.
- In `App.handle`, `_query_value` splits the query at `&` and slices each pair at `=`, with the same assertion; `_match` splits the path at `/` and compares segments byte for byte; `_decode_value` works on bytes and validates what it decodes (M3-018). Middleware and raw handlers receive `req.method`, `req.path` and `req.query` as `String`s and may slice them.

**Measured premises.** Mojo 1.1.0 (`8189361e`), Flare v0.12.0 (`8c6e1400`), Linux, the `flare` environment, the base adapter and `Server`; a scratch program (not committed) forked one `Server` child per request on 127.0.0.1, sent one request with a raw client whose method and path bytes it chose, recorded the answer, the child's state (`waitpid` with `WNOHANG`) and then a well-formed request on a new connection over both protocols. Its app had a middleware reporting the hex of the method, path and query `App.handle` received, `GET /hello`, the typed `GET /users/{id}`, `GET /names/{name}` (`String`) and `GET /items?{limit}`, and the raw `POST /raw`.
- Over h2c Flare handed every request below to the adapter, method and target bytes unchanged. A method or target that is not UTF-8, wherever no slice started on a continuation byte, reached `App.handle` with those bytes and was answered by routing through the middleware: a path `0xFF`, `0x80`, a truncated sequence, an overlong form, a surrogate or a U+FFFD then `0xFF` was 404; the same byte as a route's capture was 400 (route-value decoding); a query value on `/items` was 400 and an unread query on `/hello` 200; a method `0xFF`, `G E 0x80` or `G 0xC3` was 405 with `Allow: GET, HEAD`. Where a slice started on a continuation byte (in `Request.__init__`, before any middleware, or in `_query_value`, after it), the serving process aborted: the child ended by signal 4 (SIGILL) after printing Mojo's `Assert Error: String span starts on <n> which is not a codepoint boundary` with `Request::__init__` or `App::_dispatch` in its stack, the connection closed with no response, and nothing answered afterwards. So the defect is both an abort (availability) and `String`s that are not UTF-8 reaching middleware and handlers.
- Well-formed methods and targets over h2c were answered as any other text: `/é` and a sent U+FFFD 404, `/names/` with a sent U+FFFD 200 with that character, `/users/%FF` 400 (M3-018), and the methods `é`, U+FFFD, `get`, `FOO` and the empty method 405 with `Allow`.
- Over HTTP/1.1 every method or target above with a byte outside `!`..`~` (the well-formed `é` and U+FFFD included), the lowercase and the empty method got Flare's own 400 (`400 Bad Request`); the child survived and answered the next request. The ASCII baselines (200, 404, 405 with `Allow`, `HEAD` with `Content-Length: 5`, `FOO` 405, `/users/%FF` 400) were the same on both protocols.
- On `String`s built with `String(unsafe_from_utf8=)` from those bytes, `as_bytes()` gives the span of exactly the bytes held, without validating or slicing; `byte_length()` and `==` work on bytes (`== "HEAD"` is false for each); and `String(from_utf8=span)` raises for exactly the ill-formed ones (`0x80`, `0xFF`, a truncated sequence, an overlong form, a surrogate, a code point above U+10FFFF, a target with a continuation byte after `?`) and copies the well-formed ones (U+FFFD, `é`, NUL, empty) byte for byte. None of these operations aborts. It is the validator M3-018 and M3-038 already use.
- Through the changed adapter (below), the same scratch program and the committed loopback case: every method or target over h2c that is not UTF-8 is 400 `Bad Request` without the middleware's field, the child keeps running, a new connection is answered, and so is the next stream on the same connection; every well-formed one is answered as before, and every HTTP/1.1 answer is byte for byte the base's.

**Selected: A, with the adapter's existing 400.** `to_muntin_request` builds the method and the target with `String(from_utf8=)` from Flare's `request.method.as_bytes()` and `request.url.as_bytes()`, as it builds the body. Both arguments are evaluated before `Request.__init__` runs, so nothing searches, splits or slices either before the check; one that is not well-formed UTF-8 makes the conversion raise, which `_answer` already answers 400 `Bad Request` before `App.handle`, as for a header field (M3-005) or a body (M3-038). `App.handle`, `Request`, `TestClient` and every other public type are unchanged.

- **Where and when.** In the adapter, before `Request` is built and before `App.handle`: no middleware, route scan, decoding or handler runs, so a path no route matches (404) or only other methods match (405) is 400 too. `_serve_app`'s `HEAD` comparison runs before it and only compares bytes, so the `HEAD` rule applies to this 400 as to the adapter's other ones (no content, `Content-Length: 11`; M3-027) when the method is exactly `HEAD`. This holds for every request Flare hands to the adapter; Flare's own refusals come first and are unchanged, HTTP/1.1's parser refusing every such byte among them.
- **Status.** 400 `Bad Request`, body `Bad Request`, no field: the adapter's existing answer, the one Muntin gives a route value whose decoded bytes are not UTF-8 (M3-018) and a request field or body it cannot represent; and the status Flare gives the same bytes over HTTP/1.1. A malformed request target or method is a client error, not a missing resource (404) or an unsupported method (405, 501).
- **What is distinguished.** Only well-formedness: a method or target is kept if and only if `String(from_utf8=)` accepts its bytes. U+FFFD is an ordinary character, and percent-encoded bytes are ASCII: `%FF` passes the adapter and stays route-value decoding's 400 in `App.handle` (M3-018); nothing is decided from text after a conversion.
- **Not a method grammar.** A well-formed method that is not an HTTP token (`é`, U+FFFD, a lowercase or empty one) passes the adapter and is answered by `App.handle` as before (405 with `Allow` on a path some route matches, 404 elsewhere; M3-030); over HTTP/1.1 Flare still refuses it first. Which methods are tokens is not this item's question.
- **Protocols.** HTTP/1.1 and h2c alike, as the check is the adapter's; over HTTP/1.1 it never fires today, because Flare's parser refuses every non-ASCII byte first.
- **Same connection.** A raise from the conversion is the adapter's ordinary 400 on its stream; Flare keeps the connection, and the next stream on it is answered (measured), including one sent only after the 400 was read.
- **Copies.** One copy of the method and one of the target before `Request` copies its parts, as for the body (read from the code; not timed).

**Candidates.**

| Candidate | Verdict |
|---|---|
| A: the adapter checks method and target through their byte spans before `Request` is built, 400 | **chosen**: no request stops the process, no `String` that is not UTF-8 reaches `App.handle`, two lines in the adapter, nothing in `src/muntin` or the public API changes, and every well-formed method and target is answered as before (measured on both protocols) |
| A-target: the target only | rejected: a method that is not UTF-8 does not abort today (Muntin only compares it), but it reaches middleware and raw handlers as `req.method`, where an application's own slice aborts the same way, and it would leave one `String` from the adapter that is not UTF-8. A's extra cost is that such a method gets 400 instead of 405 or 404, which is what Flare answers over HTTP/1.1 |
| B: Muntin core safe for any bytes | rejected: it changes `Request` and `App.handle` for one backend's input, needs byte-level splitting wherever a target is cut (`src/muntin` has no unchecked `String` constructor to rebuild the parts with, by `check_unsafe.sh`), and still hands middleware and handlers `String`s that are not UTF-8, where their own slicing aborts |
| C: an upstream Flare change | not needed: Flare's `Request.method` and `Request.url` hold the received bytes and the adapter can check them before anything slices them (measured). Flare validating pseudo-header bytes over HTTP/2 as its HTTP/1.1 parser does would be a reasonable upstream improvement; A does not depend on it |
| baseline: copied verbatim (main) | rejected: measured above, one request stops the `Server` for every client |

**M2 contract: reopened, for one class of requests over the Flare backend.** Over Flare, a request whose method or target is not well-formed UTF-8 (which Flare v0.12.0 hands to the adapter over h2c only) was routed with those bytes (the handler's answer, or 400, 404 or 405 by the route scan) or stopped the serving process, and is now the adapter's 400 before `App.handle`: a different 400/404 boundary for that class, so it is an M2 reopen under [M2-016](m2-016-m2-closure.md), and this record is the explicit decision it requires. By kind:
- `App.handle` and `TestClient`: unchanged; nothing in `src/muntin` changes;
- the wire: a request Flare hands to the adapter whose method or target is not well-formed UTF-8 gets the adapter's 400 `Bad Request` before routing and middleware, whatever its path (a `HEAD` one under the `HEAD` rule), and the `Server` keeps serving; every other request, non-ASCII UTF-8, U+FFFD, percent-encoded bytes and methods that are not tokens included, is answered exactly as before; over HTTP/1.1 nothing changes (Flare refuses such bytes first);
- the raw escape hatch: a raw handler receives the whole `Request` of every request that reaches `App.handle`; over Flare such a method or target does not reach it;
- the accepted set, the overload set and every diagnostic are unchanged.

**Invariants:**
- For every request Flare hands to the adapter, `Request.method` holds exactly Flare's method bytes and `Request` is built from exactly Flare's target bytes, or the request is answered 400 by the adapter before `App.handle`; the adapter searches, splits or slices neither before the check.
- Every `String` the Flare adapter hands `App.handle` (method, path, query, body, header names and values) is well-formed UTF-8, so no request can make Muntin's own `String` operations, or an application's, abort on its bytes.
- No request Flare hands the adapter stops the serving process through the adapter's conversion.

**Cost.** Over h2c, a request with such a method or target that a route answered (an unread query, a `FromBody` that ignored it) now gets 400, and one on a path no route matches 400 instead of 404, or only other methods match 400 instead of 405 with `Allow`. Middleware cannot observe or log these requests, as for the adapter's other 400s. A client that sends a target in another charset (Latin-1, Shift_JIS) unescaped over h2c is refused; percent-encoding it is what RFC 3986 requires anyway. Every request now pays a validated copy of its method, its target and its body before `Request` copies its parts ("Copies" above); none of it is measured, and a comparison of Muntin over Flare with Flare alone must include it.

**Revisit when:**
- Flare starts refusing such pseudo-header bytes itself over HTTP/2 (the loopback case then fails on Flare's refusal, not the adapter's 400): the check stays as the adapter's guarantee, and the docs move the refusal to Flare;
- Mojo changes what its `String` slicing asserts or what `String(from_utf8=)` accepts;
- a second network backend is added: it inherits the obligation (every `String` it hands `App.handle` is well-formed UTF-8, checked before any slice);
- applications need targets that are not UTF-8: that needs a bytes target, as binary bodies need M3-038's candidate B.

**Next production slice (M3-039, in this item).** The slice is implemented in the same pull request as this record, so this record is its contract:
- Code: `adapters/flare/muntin_flare.mojo` only: `to_muntin_request` passes `String(from_utf8=request.method.as_bytes())` and `String(from_utf8=request.url.as_bytes())` instead of `request.method` and `request.url`, and its docstring and the module's conversion policy say so. No change to `src/muntin`, `_answer`, `_serve_app`, the `HEAD` rule, the header and body rules, `to_flare_response` or `Server`.
- Tests: in `adapters/flare/test_muntin_flare.mojo`, tests that the conversion keeps well-formed methods and targets byte for byte (non-ASCII, U+FFFD, percent-encoded, empty and lowercase methods, a second `?`), raises for each one that is not UTF-8 (path, query, a continuation byte after `?`, `=` and `&`, a truncated sequence before `?`; methods), and that `MuntinHandler` answers those 400 `Bad Request` with no field, without running middleware, on a route, a 405 path and a 404 path and under the `HEAD` rule, while well-formed ones reach `App.handle` through middleware (a query 200, `%35` decoded, `%FF` `App.handle`'s 400, `é` 405 with `Allow`). In `adapters/flare/test_localhost_roundtrip.mojo`, `test_request_target_and_method_bytes_over_h2c_and_http1` serves `targets_app()` through `Server` and, over h2c, sends each such method and target with the next stream on the same connection carrying a well-formed request, twice: both streams written at once, and the well-formed one written only after the 400 has been read (`h2_in_turn`, so the connection is shown to take a new stream after answering the 400, not only to finish streams it had already received); each time the first is 400 `Bad Request` without the middleware's field, the second 200 through it, a new connection then gets 200 and the child is still running; a `HEAD` one is 400 with `content-length: 11` and no DATA frame; well-formed methods and targets equal `App.handle`'s answer (status, body bytes, `allow`) through the middleware. Over HTTP/1.1 the same bytes get Flare's own `400 Bad Request` body and the child keeps answering. The raw h2c client's reader is shared by `h2_exchange` and the new `h2_streams` (several requests on one connection). Every other test runs unchanged.
- Mutations, on scratch copies of the adapter: the method passed unchecked; the target passed unchecked; both converted lossily (`String(from_utf8_lossy=)`); converted lossily with any U+FFFD rejected (a check that confuses a sent U+FFFD with a replaced byte); and the check run on `Request`'s parts after it is built. Each must turn a listed test red.
