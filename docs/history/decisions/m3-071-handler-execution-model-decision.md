# Handler execution model decision (M3-071)

> **Current.** Now described in [ARCHITECTURE, "Backend seam"](../../ARCHITECTURE.md#backend-seam) and [serving reference, "Workers"](../../reference/serving.md#workers).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision, standing constraint** (M3-071, pull request #129; `src/muntin` unchanged). The readings, the probes and the measurement are in the pull request.

**Question and what settles it.** A handler runs on the thread of the reactor that owns its connection ([M3-046](m3-046-head-of-line-blocking-decision.md)): while it runs, that worker accepts, reads, writes and times out nothing, so with `workers=n`, n handlers that block stop every new connection, and nothing stops a running handler (Flare v0.12.0 documents `handler_timeout_ms` as "not enforced yet"). An outside review of pull request #120 asked which execution model should lift it: other threads, cooperative (async) handlers, or isolated processes. Settled by: what Mojo 1.1.0 offers for asynchronous code (its documentation, and a probe registering an `async def` handler); what Flare v0.12.0, its newest tag on 2026-10-16, offers to answer a request later or run work elsewhere (read in code); what each candidate does to the account `App` and `State` rely on (M3-001, [M3-049](m3-049-multi-worker-serving-decision.md)); and how many blocking handlers stop a `Server` today (`scripts/bench_hol.sh`, "capacity").

**Choice: settle the application boundary now, leave how a backend runs handlers open, and fix what deciding it must settle.**
- Handlers stay synchronous `def`s, and `App.handle` the synchronous, backend-independent boundary. No async handler kind: Mojo 1.1.0's documentation calls its async and coroutine support "unfinished" with "no stability guarantees" and keeps the task primitives private, and an `async def` handler converts to no `get` overload (probe). No executor, task, future or wakeup in the public API (A4, A6), and no cancellation token (M3-056).
- Open: whether and how handlers run off the thread that owns their connections (handler threads each owning an `App`, an `App` per worker with its own reactor, processes, an async backend), and how many of each there are. With its request traits, the ones `Server` uses, Flare v0.12.0 cannot: `Handler`, `CancelHandler` and `ViewHandler` return their `Response` from the call, `Reactor.wakeup` has no caller, and `block_in_pool` holds the handler until its thread ends; the one trait answered later, `StreamHandler` with `attach_upstream`, carries raw bytes over HTTP/1.x without TLS, so Muntin would parse HTTP itself (A5). AGENTS.md lets an accepted milestone build an executor, but an executor without a way to answer later changes nothing. This is a deferred candidate (`docs/SPEC.md`, "handler execution"), and this list is its settling condition: beside the rule above and what every backend owes ([M3-070](m3-070-backend-coupling-decision.md): one `App` never called from two threads at once), its decision settles
  - progress, separately: the reactor's (network events while handlers block); the application's (another request runs when execution capacity is free; `serve(app)` has one `App`, so one handler at a time whatever the backend, and more `App`s mean one `State` each, which applications can observe); and overload (how many requests wait, and whether a full server waits or refuses, with which status);
  - affinity: whether each `App` stays on one thread, as the Flare adapter keeps it (`serve(app)` on the calling thread, whose scope destroys it; `serve[make]` on the worker that built it and destroys it), or is called from several in turn, which M3-070 allows a backend if the calls are ordered and `State` values are safe on another thread; and so on which threads an `App`, its `State` values and a stream source ([M3-056](m3-056-streaming-responses-and-cancellation-decision.md)'s, once shipped) are made, used and destroyed, since one thread at a time is not enough for a value bound to its thread; and how an application learns, and a check finds, whether its `State` values meet a backend's condition (M3-070: Muntin checks neither);
  - ownership: how a request and its response cross threads, and what happens to a stream source after a client goes and after a raise;
  - exclusion: ordering `App.handle` calls is not enough. A stream source can reach its `App`'s `State` values, its `next()` mutates unsynchronized, and copies of a streamed `Response` share it (M3-056), so one request's pull or source destruction could overlap another request's `App.handle`; the decision states what orders each pull and destruction against `App.handle` and against each other, whichever thread runs them;
  - lifecycle with [M3-045](m3-045-graceful-shutdown-decision.md): which work a stop admits or starts, told apart for a new connection, a new request on an open connection and a request accepted but not started, keeping or explicitly revisiting M3-045's drain (during its window a second request on an open HTTP/1.1 keep-alive connection and a new stream on an open h2c connection were answered); every owner outliving the work in flight; a completion whose connection is gone dropped on a thread the affinity answer allows; and a handler that never returns ending the stop as today or by a stated rule;
  - configuration: reactor threads, handler threads and `App`s are separate counts, and what `workers` then means;
  - evidence, on the wire: one blocked stream while another stream of the same h2c connection completes, every execution slot full, a client gone during a handler, a stop with a late completion, TLS; and the cost of a Flare change, another backend or a bounded adapter executor, compared.

**Rejected.**
- `async def` handlers or a Muntin yield (cooperative execution) on Mojo 1.1.0: its async is neither public nor stable, Flare's request handler traits are synchronous, and A6.
- A pool of threads calling one `App` at once: what every backend owes (M3-001, M3-070).
- Offloading inside the handler (Flare's `block_in_pool`, or a Muntin equivalent) as the remedy: the handler waits, so its worker stays held.
- Choosing one off-reactor model now: no candidate's feasibility, cost, overload or lifecycle contract is shown.

**Revisit when:**
- Flare or another backend can answer a request after its handler call has returned, over HTTP/1.1 and h2c: the deferred handler-execution decision (`docs/SPEC.md`) can be settled;
- a milestone to weigh an execution model's feasibility and cost (a Flare change, another backend, a bounded adapter executor) is accepted: it settles the list above, and until one is, waiting on Flare is a project choice, not a precondition;
- Flare sets `Cancel` while a handler runs (enforces `handler_timeout_ms`): M3-056's cancellation revisit;
- Mojo documents its async support as public and stable, or a backend runs async handlers: the rule above;
- Mojo gains a compiler-checked notion of thread-safe sharing: M3-049's shared-state revisit.
