# Server receive body limit decision (M3-044)

> **Current.** Now described in [serving reference, "Receive body limit"](../../reference/serving.md#receive-body-limit), [serving reference, "`Server.bind`"](../../reference/serving.md#serverbind) and [serving reference, "`serve`"](../../reference/serving.md#serve).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-044, [pull request #82](https://github.com/sano-suguru/muntin/pull/82)). It decides how an application sets the request body limit that the network backend enforces while it receives a request, which [M3-032](m3-032-serving-entrypoint-decision.md) left out of `Server` ("Backend configuration. None is exposed") with a revisit condition ("applications need a backend limit or protocol setting changed (body size, ...): revisit whether `Server` takes a Muntin-owned configuration"), and [M3-043](m3-043-typed-binary-request-body-size-limits-decision.md) named as a remaining candidate ("a receive-time limit (backend configuration)"). It implements the choice in the same item. The question, the candidates, the comparison criteria and the pass conditions below were committed before any measurement; what precedes them was read from Muntin's and Flare v0.12.0's source.

**Why now.** Every body a `Server` accepts is received and buffered in full before `App.handle` sees it, up to Flare's default 10 MiB per request. Muntin's own limits (`Json[T]`'s fixed 1 MiB since M3-009, a `FromBytes` type's `max_bytes` since M3-043) run in `App.handle` on that buffered body: they bound what reaches a conversion and a handler, not what the server reads off the socket. An application whose largest legitimate body is a few KiB has no way to stop the server reading ten MiB per request, and one that accepts uploads above 10 MiB has no way to raise the bound, without building Flare's `HttpServer` itself, which M3-032 rejected as API (it puts Flare types in application code).

**Question.** How does an application that serves through `Server` set the largest request body the backend receives, so that a longer body is refused while it is being received, before the adapter, middleware, routing and any conversion, over every protocol `Server` serves (HTTP/1.1 with `Content-Length` or chunked framing, and HTTP/2 with prior knowledge)? Specifically: its spelling and where it lives (`Server.bind`, a new Muntin type, Flare's own types, nothing); whether every existing `Server.bind(host, port)` call keeps building and answering exactly as today, with the same default; the unit and the valid values (0, a negative value, `Int.MAX`, a value whose arithmetic in the backend could overflow) and where an invalid one is caught (compile time, `bind`, never); how one value reaches each of Flare's receive paths, and whether a value that reaches only some of them can be mistaken for a working limit; what a client sees on a refusal on each transport, measured on the wire and not inferred; whether the `Server`, the same HTTP/1.1 keep-alive connection and the same HTTP/2 connection keep serving after a refusal; how the limit is told apart from `App.handle`'s 413s (`Json[T]`, `FromBytes.max_bytes`) in the docs, in the answers and in the tests; who owns the value once `bind` returns; how the spelling extends to later backend settings without committing to them; and what changes in the accepted set, the overload set, the diagnostics and the runtime, classified against M2-016.

**What it is not.** Timeouts, TLS, several workers, streaming bodies and a per-route receive limit are out of scope: each is its own item ([M3-032](m3-032-serving-entrypoint-decision.md)'s revisit conditions, [M3-043](m3-043-typed-binary-request-body-size-limits-decision.md)'s). The limit is the backend's receive bound for one request body; it is not a defense against denial of service in general (header size, connection count, slow clients, many concurrent streams and the time a handler takes are other bounds, Flare's defaults), not protection before authentication, and not a replacement for `FromBytes.max_bytes`, which stays the per-format limit in `App.handle` (M3-043 is unchanged).

**The path at the base** (read from the code):
- Muntin: `Server(*, _host, _port)` calls `HttpServer.bind(SocketAddr(...))`, so Flare's `ServerConfig()` defaults apply. `serve` hands `_BorrowedHandler(app)` to Flare's single-worker `serve`, which runs `run_unified_reactor_loop(listener, self.config, self.config.h2.copy(), handler, ...)`: each connection is HTTP/1.1 or, when its first 24 bytes are the RFC 9113 preface, HTTP/2.
- Flare v0.12.0 keeps two body limits. `ServerConfig.max_body_size: Int` (default `10 * 1024 * 1024`) is read by the HTTP/1.1 connection (`flare/http/_reactor/conn_handle.mojo`): after each `recv` the bytes buffered on the connection minus `max_header_size` are compared with it (413 `Content Too Large`; on every `recv`, body included, as the review below established); once the head is in, a `Content-Length` above it is 413 before the body is read; a chunked body is scanned by `scan_chunked_resume(..., max_body_size)`, which returns `CHUNKED_MALFORMED` (answered 400 `Bad Request`) when a chunk size or the running total exceeds it; the request parser checks again. `ServerConfig.h2: Http2Config` has its own `max_body_size: Int` (default 10 MiB), copied into `Connection.max_request_body_size` by `Http2Connection.with_config`; a DATA frame that would take a stream's buffered body over it resets that stream with `RST_STREAM` `ENHANCE_YOUR_CALM` (`flare/http2/state.mojo`), and no HTTP response is sent for it. Setting `ServerConfig.max_body_size` alone leaves HTTP/2 at 10 MiB.
- Values in Flare: `Http2Config.validate()` raises for a negative `max_body_size` when each HTTP/2 connection is set up, not at `bind`; nothing checks the HTTP/1.1 field at run time. `ServerConfig.check[cfg]()`, a compile-time check for a `comptime` configuration that `HttpServer` does not call, also asserts `max_body_size >= max_header_size` (8192 by default). The HTTP/1.1 buffer check is written to survive `Int.MAX` (its comment: "wraps for an 'unlimited' body cap such as `Int.MAX`"); the chunk-size scan accumulates `size = size * 16 + digit` and compares with the limit only afterwards, so a limit near `Int.MAX` lets a long chunk-size line overflow before the comparison.

**Candidates.**
- A, `Server.bind` takes the limit: an optional argument of the existing entrypoint (`Server.bind(host, port, max_body_bytes=n)`), whose omission keeps today's default, propagated by the adapter to both of Flare's fields.
- B, a Muntin-owned configuration type: `Server.bind(host, port, config)` (or a builder), the type holding the body limit now and later settings, propagated the same way.
- C, document how to configure Flare directly: application code builds Flare's `ServerConfig` (setting both fields) and an `HttpServer` around the adapter's handler; Muntin adds documentation only.
- D, no change: Flare's 10 MiB defaults stay the only receive limit; the docs say so.

**Comparison criteria**, per candidate: the spelling in an application's `main` beside `Server.bind` and how it reads next to `FromBytes.max_bytes`; the public API added (functions, types, overloads); whether every existing `Server.bind(host, port)` call and the `server.serve(app)` call keep building and answering as today, with the same default on both protocols; ownership (who holds the value, whether the application keeps a reference into the backend); how the next backend setting (a timeout, TLS) would be added without a breaking change, and what it would cost to add now; the unit, the valid range and where an invalid value is caught (0, negative, `Int.MAX`, overflow in the backend's arithmetic), with what message; whether one value reaches HTTP/1.1 and HTTP/2 alike, and how a partial propagation would be caught by a test; whether Flare types reach application code (A1, A2); diagnostics, accepted set, overload set and runtime by kind (M2-016).

**Pass conditions** (the item is complete only when each holds, with executable evidence):
- the chosen spelling builds in a user program with `--Werror` (the `docs/DX.md` example as written), and `Server.bind(host, port)` with no limit and `server.serve(app)` build and answer as before, the 10 MiB default included on both protocols;
- a body over the configured limit `N` is refused by the backend while receiving, before the adapter: over HTTP/1.1 with `Content-Length` (with the body sent, and with only the head sent, within a timeout), over HTTP/1.1 chunked (each chunk at most `N`, the total `N + 1`), and over h2c (one DATA frame, and two DATA frames each at most `N` with a total of `N + 1`); for `N - 1` and `N` bytes the body reaches the handler byte for byte (NUL, `0x80`, `0xFF` included); `N + 1` and a body far over `N` are refused; what the client receives on each transport (status and body, `RST_STREAM` and its code, a closed connection) is measured and pinned, not assumed equal across transports;
- refused before Muntin, shown by a middleware field and handler and converter counters: with the backend limit 64 and a `FromBytes` `max_bytes` of 256, a 65-byte body is the backend's refusal with no middleware field, and neither the middleware, `from_bytes` nor the handler runs; with the backend limit 256 and `max_bytes` 16, a 17-byte body is `App.handle`'s 413 with the middleware field and neither `from_bytes` nor the handler runs. A 413 status alone never decides which layer refused;
- the backend limit applies to every route, a raw route and a path no route matches included;
- after a refusal the same `Server` answers a valid request; whether the same HTTP/1.1 keep-alive connection and the same HTTP/2 connection keep serving is measured and stated;
- two `Server`s bound with different limits in one process keep their own;
- an invalid value is refused where the record says, with the message it names, before anything is bound; 0 accepts only empty bodies;
- the default (no limit given) is the base's 10 MiB on both protocols, shown on the wire;
- `FromBytes.max_bytes`, `Json[T]`'s 1 MiB, text bodies, raw handlers, `HEAD`, the adapter's UTF-8 checks, `_BorrowedHandler`'s non-`Copyable` guard and the existing `Server` fixtures are unchanged (the existing suites pass);
- scratch mutations, each turning a listed test red: the propagation removed; the default substituted for the given value; the limit off by one either way; the HTTP/1.1 field or the HTTP/2 field left at its default; the invalid-value check removed; the backend limit and `max_bytes` swapped in the distinction case;
- `src/muntin` is unchanged, or the record says why not; `check_boundaries.sh` passes.

**Measured premises** (Mojo 1.1.0 `8189361e`, Flare v0.12.0 `8c6e1400`, Linux x86-64; a scratch probe, not retained, served an `App` with a middleware adding `X-Seen` and a raw echo route through `MuntinHandler` on Flare's `HttpServer` bound with a `ServerConfig` whose two body fields were set independently, and sent raw HTTP/1.1 and h2c bytes over loopback with a 2 s read timeout):
- **HTTP/1.1, `Content-Length`**, limit 64: 63 and 64 bytes (`0x00` to `0x3F`) reached the handler byte for byte through the middleware; 65 and 4096 bytes were Flare's `413 Content Too Large` with `Content-Type: text/plain`, `Connection: close` and the body `413 Content Too Large`, without `X-Seen`, and the connection closed. A head declaring 65 bytes, and one declaring 10,000,000, with no body sent, got the same 413 at once, without waiting for the body.
- **HTTP/1.1, chunked**, limit 64: one 64-byte chunk reached the handler; chunks of 32 and 33 bytes (each within the limit, 65 in total) and one 65-byte chunk were Flare's `400 Bad Request` (body `400 Bad Request`, `Connection: close`), not 413 at these sizes (see Chunk framing): Flare's chunk scanner reports an over-limit body as malformed framing.
- **HTTP/1.1 keep-alive**: after the 413 the server closed the connection; a request written after it on the same connection got no answer. Two requests within the limit on one keep-alive connection were both answered.
- **h2c**, limit 64: one 64-byte DATA frame reached the handler; one 65-byte frame, and frames of 32 and 33 bytes, got `RST_STREAM` with error code 11 (`ENHANCE_YOUR_CALM`) on that stream and no HEADERS, and a request on stream 3 of the same connection was then answered 200 through the middleware.
- **Partial propagation**: with only `ServerConfig.max_body_size` set to 64 (`h2.max_body_size` left at 10 MiB), 65 bytes over h2c, in one and in two DATA frames, reached the handler (200); the HTTP/1.1 field alone does not limit h2c.
- **0**: an empty body was answered over both protocols; one byte was 413 (HTTP/1.1 `Content-Length`), 400 (chunked) and `RST_STREAM` 11 (h2c). Flare's compile-time `ServerConfig.check` would reject 0 and 64 (`max_body_size must be >= max_header_size`); nothing applies it at run time, and both values behaved as above.
- **Large values**: with both fields `Int.MAX`, a chunk-size line of `8000000000000000` (2^63, which wraps the scanner's `size * 16 + digit` to a negative size) aborted the serving process (`chunked.mojo:350: Assert Error: index -9223372036854775711 is out of bounds`), and `1000000000000000F` left the request unanswered until the client's timeout. With `576460752303423488` (2^59) the first line still aborted the server; with `576460752303423487` (2^59 − 1, `Int.MAX >> 4`) every such line (`FFFFFFFFFFFFFFFF`, `10000000000000001`, `1000000000000000F`, `FFFFFFFFFFFFFFFFF`, `8000000000000000`) was `400 Bad Request` and the server kept answering, as with 10 MiB. Below 2^59 the scanner's comparison runs before its multiplication can overflow (a size within the limit times 16 plus 15 is at most `Int.MAX`); the other comparisons (`Content-Length`, the buffered-bytes check, the chunked total, HTTP/2's `max - len(data)`) stay within `Int` for any value up to 2^59 − 1.
- **Pipelining**: with the limit 64, 300 pipelined `POST`s of one byte each (about 17 KB in one write) got 413 for the burst, because Flare's per-`recv` check compares everything buffered on the connection minus `max_header_size` with the limit; 10 and 100 such requests were all answered. With 10 MiB the same 300 were answered up to Flare's `max_keepalive_requests` (100). A small limit therefore also bounds how much a client may pipeline in one burst.
- **Chunk framing** (measured after the fresh-context review pointed at the buffered-bytes check): with the limit 64, chunks of 8192 and 8192 bytes (or 4096 and 4096) in one write were 413, not 400; with 4096, 4096 bytes in two chunks were received, and the same 4096 bytes in one-byte chunks (about 24.7 KB of raw bytes) were 413; with 65,536, 65,536 bytes in 16-byte chunks were 413. Flare's per-`recv` check (`len(read_buf) - max_header_size > max_body_size`) sees everything buffered on the connection, the request line, head, chunk-size lines and CRLFs and any pipelined bytes after the request included, and runs before the chunk scanner: a request is refused when all of that exceeds the limit plus 8 KiB. Reading after such a 413, the test client then got `ConnectionReset` (Linux): Flare closes without draining the rest of the request.
- **Spelling** (a scratch copy of the adapter): `bind(host: String, port: Int, *, max_body_bytes: Int = 10 * 1024 * 1024) raises -> Server` builds with `--Werror` in a user program called both as `Server.bind("127.0.0.1", 0)` and `Server.bind("127.0.0.1", 0, max_body_bytes=64 * 1024)`. `Server.bind("127.0.0.1", 0, 1024)` fails with `invalid call to 'bind': unexpected argument` (on the base too, with the same text), and Flare's spelling `max_body_size=1024` with `unexpected keyword argument 'max_body_size'`.

**Selected: A. `Server.bind(host: String, port: Int, *, max_body_bytes: Int = 10485760) raises -> Server`.** The value is an upper bound, in bytes, on the request body the backend receives for one request on any protocol `Server` serves (not a promise to accept every body within it: over HTTP/1.1 Flare's buffered-bytes check also counts the head, chunk framing and pipelined bytes); the adapter writes it into both of Flare's fields (`ServerConfig.max_body_size` for HTTP/1.1 and `ServerConfig.h2.max_body_size` for h2c) before binding.
- **Spelling.** A keyword-only argument of the one public entrypoint, named for its unit and distinct from `FromBytes.max_bytes`, which is a format's limit in `App.handle`. Keyword-only so a bare number after the port cannot be mistaken for something else, and so later settings can be added in any order; `Server.bind(h, p, n)` does not build (pinned). Flare's name (`max_body_size`) is not accepted.
- **Default.** `10 * 1024 * 1024` (10,485,760), Muntin's value, equal to Flare v0.12.0's default for both fields, so every existing call answers exactly as before. It is written in the adapter, not read from Flare: a Flare upgrade that changed its own default would not change `Server`'s.
- **Values.** 0 to 576,460,752,303,423,487 (2^59 − 1). 0 accepts only empty bodies (measured). A negative value, and one above the maximum, raise `max_body_bytes out of range: <value>` from `bind`, after the port check and before the host is parsed or anything is bound. The maximum is the largest value Flare v0.12.0's chunk-size scanner handles without overflowing; 2^59 and `Int.MAX` let one chunk-size line abort the serving process (measured above). There is no "no limit" value: the maximum is far beyond any buffer the process can hold. A value below Flare's `max_header_size` (8192), which Flare's compile-time check would refuse, is accepted: it behaved as documented on both protocols.
- **Ownership.** The value is an `Int` copied into the `ServerConfig` that `HttpServer.bind` takes by value; `Server` keeps no other copy and nothing borrows it. Two `Server`s keep their own values.
- **Initializer.** `Server(*, _host, _port, _max_body_bytes)`, the last with the same default; keyword-only and `_`-prefixed as before, so `Server.bind` stays the one public spelling (the existing fixtures are unchanged). The configuration is built by one private function the initializer calls, `_server_config(max_body_bytes) raises -> ServerConfig`, which checks the range and sets both fields.
- **What a client sees** (Flare's answers, pinned on the wire, not Muntin's): over HTTP/1.1 with `Content-Length`, `413 Content Too Large`, as soon as the head declares more, and the connection is closed; over HTTP/1.1 chunked, `400 Bad Request` once the chunks' total exceeds the limit, or 413 when Flare's buffered-bytes check sees it first (below), and the connection is closed; over h2c, `RST_STREAM` `ENHANCE_YOUR_CALM` (11) on that stream, with no response, and the same connection answers its next stream. Over HTTP/1.1 Flare also refuses (413) when everything buffered on the connection (request line, head, chunk framing, the body and anything pipelined after it) exceeds the limit plus its 8 KiB header allowance: a chunked body within the limit is refused when head, framing and body together exceed that, and so can a within-limit request followed in the same burst by more bytes. A refused HTTP/1.1 connection is closed without reading the rest, so a client still sending can see a reset (added after review, below). Muntin does not translate or unify these: the refusal happens inside Flare, before the adapter. The `Server` keeps serving after each.
- **Not included.** Any other `ServerConfig` field (header size, timeouts, keep-alive, connection count), TLS, workers, streaming, a per-route receive limit, a Muntin-owned configuration type, a change to `MuntinHandler`, `_BorrowedHandler`, `_serve_app`, `src/muntin` or `App.handle`.

**Two limits, kept distinct.** `max_body_bytes` is the backend's receive bound: a longer body is refused while it arrives and never reaches the adapter, middleware, routing, a converter or a handler, on every route and on paths no route matches. `FromBytes.max_bytes` (M3-043) and `Json[T]`'s 1 MiB are `App.handle`'s 413s, on a body already received, after middleware and the route values, for one route's format. A body over `max_body_bytes` never reaches them; a body within it and over a type's `max_bytes` is `App.handle`'s 413, through middleware. The tests tell them apart by the middleware's field and by counters, never by the status alone: both can be 413 over HTTP/1.1.

**Backend seam and M2: not reopened, not amended.** `Server` is the adapter's type (M3-032), not part of the M2 contract, and `App.handle` is unchanged. By kind: the accepted set grows (`Server.bind` takes the new argument); the overload set is unchanged (`bind` is still one function; no registration overload changes); diagnostics: none of the existing ones change (`src/muntin` is unchanged, so the registration fixtures cannot), a new run-time message (`max_body_bytes out of range: <value>`) and a must-not-build pin for the positional call; runtime: `Server.bind(host, port)` binds with the same 10 MiB on both protocols as before, and every answer `App.handle` and the adapter give is unchanged. Amended after the owner's re-review (below): `Server.serve` gains a second run-time message, `FLARE_BUFRING_HANDLER=1 is unsupported by Muntin with Flare v0.12.0`, and a program whose environment sets that variable to `1` now fails to start where it served before.

**Cost.** One more argument on `Server.bind`, and a value range that comes from a Flare overflow, not from HTTP: a Flare release that fixes the scanner could allow more, and the bound must be re-measured when the pin moves. Refusals differ by protocol (413, 400, a stream reset) because they are Flare's; an application that needs one status cannot have it from this limit. A small limit also bounds an HTTP/1.1 pipelined burst, and refuses a heavily framed chunked body that is within it (measured). The value is per `Server`, not per route. Since the owner's re-review, `Server.serve` also refuses `FLARE_BUFRING_HANDLER=1` on hosts where Flare would not take the buffer-ring loop (macOS, Linux without io_uring or with `FLARE_DISABLE_IO_URING` set), where that variable alone did no harm.

**Invariants:**
- The value given to `Server.bind` is the receive limit on every protocol `Server` serves: both of Flare's fields always hold it.
- `Server.bind` never hands Flare a value outside 0 to 2^59 − 1.
- With no value given, `Server` receives what it received before M3-044 (10 MiB on both protocols).
- Muntin's docs never call a check in `App.handle` a receive limit, and never call this limit protection against denial of service in general or before authentication.
- Muntin's docs never present `max_body_bytes` as a promise to accept every body within it.
- `Server.serve` never enters Flare's buffer-ring loop: it refuses `FLARE_BUFRING_HANDLER=1` before calling Flare, and `_server_config` leaves `use_bufring` off.

**Revisit when:**
- a second backend setting is exposed (timeouts, header size, connection count, TLS): keep keyword-only arguments while they are independent values; revisit B when settings must be built, validated or shared as one value (read from a file, reused across `Server`s);
- the Flare pin moves: re-measure the refusals (HTTP/1.1 `Content-Length` 413 and its close, chunked 400, the buffered-bytes 413 for chunk framing and pipelining, the reset after a refusal, h2c `RST_STREAM` 11 and the connection's reuse), the overflow bound (`adapters/flare/test_server.mojo` and the loopback chunk-size case), the two field names, and whether Flare's default still equals Muntin's;
- Flare applies `ServerConfig.check` at run time, or its scanner stops overflowing: the lower or upper end of the range changes;
- applications need one refusal status across protocols, or the refusal visible to middleware or logging: that needs the backend to hand an over-limit request to the adapter, which Flare v0.12.0 does not;
- applications need a per-route receive limit or streaming bodies: a receive limit that knows the route needs routing before the body is read ([M3-040](m3-040-binary-request-and-response-bodies-decision.md)'s and M3-043's revisit conditions);
- `compat/flare/serve/server_bind_positional_limit.mojo` builds: the limit became positional; revisit the spelling;
- the buffer-ring pin in `test_receive_limit_on_flare_bufring_path` fails (Flare's `FLARE_BUFRING_HANDLER` loop answers a request over 8192 wire bytes, or stops stalling other connections): re-measure the limit on that loop and revisit whether `Server.serve` keeps refusing the variable; or a Linux runner without io_uring makes that test fail under `CI`; or the Flare pin moves (the refusal's message names v0.12.0).
