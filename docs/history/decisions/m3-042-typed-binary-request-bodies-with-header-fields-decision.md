# Typed binary request bodies with header fields decision (M3-042)

> **Current.** Now described in [bodies reference, "Header fields with a body (`WithHeaders[B]`)"](../../reference/bodies.md#header-fields-with-a-body-withheadersb), [bodies reference, "Binary bodies (`FromBytes`)"](../../reference/bodies.md#binary-bodies-frombytes) and [ARCHITECTURE, "Modules and public surface"](../../ARCHITECTURE.md#modules-and-public-surface).
> Changed in part since:
> - [M3-043](m3-043-typed-binary-request-body-size-limits-decision.md): a carried FromBytes now has a size limit: 413 after the JSON steps and before the field rebuild (M3-042 had no size cap for a bytes carrier).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-042). It decides how a typed handler receives a `FromBytes` body and the request's header fields together, which M3-041 left out of its slice with a revisit condition ("applications need a typed bytes body with the header fields"), and implements the choice in the same item. The question and what settles it were committed before any candidate was measured.

**Why now.** Since M3-041 a typed `post`, `put` or `patch` handler takes a body of any bytes as a `FromBytes` type, and since M3-013 a typed handler takes the header fields beside a text body as `WithHeaders[B: FromBody]`. The two do not compose: `WithHeaders[B]` around a `FromBytes` is rejected where the handler is declared (`tests/from_bytes_api_fail/bytes_body_in_with_headers.mojo`), so an application whose binary upload needs a field (a signature, a digest, a content type, a credential) writes a raw handler and loses the typed route values, `State[S]` beside the body and the pre-handler 400 again.

**Question.** How does a typed handler take a `FromBytes` body and the request's `Headers` through one body-slot value, on every shape a body takes (body only, one or two route values then the body, `State[S]` first, both result policies), with no new slot kind or overload? Specifically: which candidate (A: `WithHeaders[B]` taking a `FromBody` or a `FromBytes`; B: `WithHeaders[B: FromBody]` unchanged beside a new bytes-only carrier; C: anything smaller that Mojo 1.1.0 can express) keeps every existing `WithHeaders` user, diagnostic and answer, passes the body to `from_bytes` with no text read, no lossy step and no copy, and reads most naturally (`WithHeaders[Payload]` preferred, unless it breaks existing users); what the private `_HeaderCarrier._from_parts(String, Headers)` and `_two_conversions()` become; how a type that conforms to both traits is rejected, alone and inside the carrier, so Muntin never picks a conversion silently; in which order the field rebuild (500 on the `_fields` gap), the conversion (400 on a raise) and the route values (400) run; and what changes in the accepted set, the overload set, the diagnostics and the runtime of routes that register today, classified against M2-016.

**What settles it:**
- the carrier's path traced in code: `WithHeaders`'s bound, `_HeaderCarrier`, `_kind`, `_post_rule`, `_route`'s `headers` and `json` flags, `_slot`'s carrier branch, `_carrier_fields`, `_json_status`;
- Mojo 1.1.0 facts measured with the installed toolchain, per candidate: whether a struct parameter bound can admit a `FromBody` or a `FromBytes` and nothing else, and what the compiler then reports for `WithHeaders[Int]`, a nested carrier and `WithHeaders[Json[T]]` without `FromJson`; whether the carrier can call `from_bytes` or `from_body` on its parameter in a `comptime if` branch; whether `conforms_to` still sees both conversions of a type through the carrier;
- per candidate: the public API added or changed, what an application writes, the copies of the body per request (read from the code), and every existing fixture's normalized compiler output against the base;
- through `App.handle`, `TestClient` and middleware, on every shape taken: header fields (order, casing, repeats, empty values) and bodies (NUL, `0x80`, `0xFF`, a truncated UTF-8 sequence, every byte value) reaching the same handler, compared byte for byte; a raise 400, a bad route value 400 with no conversion, 404 and 405 with no conversion;
- the wire: the Flare loopback over HTTP/1.1 (`Content-Length`, chunked) and h2c (one and two DATA frames), header fields and bytes that are not UTF-8 reaching one typed handler;
- negative evidence: scratch mutations (a text read before `from_bytes`, a dropped or copied body, a lost repeated field, the rebuild after the conversion, the two-conversion check disabled, a raise answered other than 400), each turning a listed test or fixture red.

**Boundaries that do not change silently:** `WithHeaders[B]` over a `FromBody` (its spelling, fields, `take_body`, the UTF-8 400 and the `from_body` 400), `WithHeaders[Json[T]]` and the JSON order (415, 413, UTF-8 400, JSON 400), a bare `FromBody` or `FromBytes` body, raw handlers, middleware, `HEAD`, 404, 405 and `Allow`, the rebuild failure's fixed 500, the `Headers` model, `Request.body` as the one body representation (M3-040), the Flare adapter, the registration overload set, and no `Content-Type` rule or size cap for a bytes body. A change to any of them is named here, with its classification against M2-016.

**The path at the base** (read from the code): `WithHeaders[B: FromBody]` conforms to the private `_HeaderCarrier`, whose `_from_parts(body: String, var headers: Headers)` calls `B.from_body`, and to `_JsonBody` exactly when `B` does. `_kind` gives a carrier the body kind unless `_two_conversions()` (whether `B` also conforms to `FromBytes`) is true. `_route` sets `headers` for a carrier and `json` for a `_JsonBody`, so `App.handle` appends the field pairs after the route values (and the verdict). `_slot`'s carrier branch runs the JSON steps if any, rebuilds the fields (`_carrier_fields`; 500 on the `_fields` gap), reads the bytes as UTF-8 (`_body_text`; 400) and calls `_from_parts` (400 on a raise). Nothing on that path needs the body to be text except `_from_parts`'s argument and `B`'s bound.

**Measured premises** (Mojo 1.1.0 `8189361e`, Linux; scratch copies of `src`, then the fixtures named below):
- A struct parameter bound can be a trait that `FromBody` and `FromBytes` both refine (`trait _FromBodyOrBytes(Deinitable, Movable)`, `trait FromBody(_FromBodyOrBytes)`, `trait FromBytes(_FromBodyOrBytes)`): `WithHeaders[B: _FromBodyOrBytes]` accepts a `FromBody` and a `FromBytes`, and `Json[T]` through its conditional `FromBody` conformance.
- Inside the carrier, `comptime if conforms_to(Self.B, FromBytes)` then `Self.B.from_bytes(body)`, and in the `else` branch `comptime assert conforms_to(Self.B, FromBody)` then `Self.B.from_body(...)`, compile with only the parent bound, as `_slot`'s branches do with none (M3-041). `conforms_to` sees both conversions of a type through the carrier's parameter, so the count of conversions is one comptime expression.
- With that bound, `WithHeaders[Int]`, a nested carrier and `WithHeaders[Json[T]]` without `FromJson` are still rejected where the handler is declared, with the bound's name in the text: `'WithHeaders' parameter 'B' has '_FromBodyOrBytes' type, but value has type 'AnyStruct[Int]'` (was `'FromBody' type`).
- The bound does not close the set of carried types: Mojo 1.1.0 lets an application conform a type to `_FromBodyOrBytes` itself (the leading `_` marks it as not API but does not forbid it), and `WithHeaders[Neither]` for such a type is then declared without error. It is rejected at registration, where `_conversions()` is 0 and `_kind` gives the carrier no kind (`tests/bytes_headers_api_fail/carrier_of_bound_only.mojo`).
- Generic code keeps working on both sides: `def wrap[B: FromBody](var b: B, var h: Headers) -> WithHeaders[B]` compiles as before, and the same function bounded by `FromBytes` compiles (on the base: `invalid bindings in signature: lacking evidence to prove correctness`).
- Candidate C (below), the bound relaxed to `Movable & Deinitable` with `_HeaderCarrier` conformed `where conforms_to(B, FromBody) or conforms_to(B, FromBytes)`, compiles, and `tests/with_headers_api_fail/carrier_of_int.mojo`, `nested_carrier.mojo` and `carrier_of_json_without_from_json.mojo` then build: their types become declarable and would be rejected only when registered.
- Fixture diagnostics: every must-not-build fixture of the base (427) was built against the base's `src` and this item's, each with its own tree's `tests` (the raw and state spikes call `_from_parts`, so they pass it the text's bytes in this item), the whole output normalized (repository root and toolchain path removed, `src/muntin` and `tests` line and column numbers replaced): 421 identical; 3 (`tests/with_headers_api_fail/carrier_of_int.mojo`, `nested_carrier.mojo`, `carrier_of_json_without_from_json.mojo`) differ in the error line (`'FromBody' type` becomes `'_FromBodyOrBytes' type`) and in the echoed `struct WithHeaders[B: ...]` line, and are re-pinned; 2 (`tests/from_bytes_api_fail/from_bytes_takes_owned_bytes.mojo`, `from_bytes_takes_text.mojo`) differ only in the echoed `trait FromBytes(...)` declaration under their note, their error line and expected text unchanged; and `tests/from_bytes_api_fail/bytes_body_in_with_headers.mojo` builds, as this item intends, and is removed. Each new fixture in `tests/bytes_headers_api_fail`, built against the base's `src`, fails differently (`'WithHeaders' parameter 'B' has 'FromBody' type, but value has type 'AnyStruct[Blob]'`, or for `carrier_of_bound_only.mojo` `module 'body' does not contain '_FromBodyOrBytes'`), except `both_conversions_in_carrier_after_state_and_value.mojo`, which fails there with the same text: a regression pin of M3-041's carrier rule on a stateful shape with a route value, kept because the carrier's conversion changed under it.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A: `WithHeaders[B]` bounded by a private parent trait of `FromBody` and `FromBytes` (`_FromBodyOrBytes`); `_from_parts` takes the borrowed bytes and converts them as a bare `B` | **chosen**: the natural spelling (`WithHeaders[Upload]`) on every body shape, no new public name, no overload or slot; every existing carrier, generic helper and answer unchanged; the bytes reach `from_bytes` unread and uncopied; an ordinary non-body type (`Int`, a nested carrier, `Json[T]` without `FromJson`) is still rejected where the handler is declared, the one exception being a type conformed directly to the private bound, which registration rejects; the cost is the bound's private name in three declaration-site diagnostics |
| B: `WithHeaders[B: FromBody]` unchanged beside a new public bytes carrier (say `WithBytesHeaders[B: FromBytes]`) | rejected: a second public type for one concept, with its own `take_body`, `_HeaderCarrier` and `_JsonBody` conformances and docs, read from the code as a near copy of `headers_body.mojo`; `WithHeaders[Upload]` would stay an error whose text (`'FromBody' type`) points the user away from the type they need; it keeps every existing diagnostic, which A changes only in the bound's name |
| C: the bound relaxed to `Movable & Deinitable`, the carrier conforming to `_HeaderCarrier` only when `B` has a conversion | rejected: smaller than A by one trait, but `WithHeaders[Int]` and the other two become declarable types rejected only at registration (measured above), which M3-012 rejected as its mutation M12; A keeps the declaration-site rejection for every type that does not reach for the private bound by name |
| C': `WithHeaders[B]` taking the bytes always, a text `B` converting inside `from_bytes`-like code | rejected: it is A without the trait split; a `FromBody`'s UTF-8 read moves into the carrier either way, which A does through the one `_body_text` |
| A-pub: A with the bound public (a named "request body" trait applications see) | rejected: the type-level hole is the same as A's (a type conformed to the bound alone passes the declaration and is rejected only at registration, `carrier_of_bound_only.mojo`); the difference is what Muntin promises. A public bound would be an API Muntin documents and keeps stable, whose only conformance it accepts is through `FromBody` or `FromBytes`: a public name nobody may conform to is surface without a use, and its nicer diagnostic does not outweigh that. A's private bound is not API, so a direct conformance to it is outside the supported surface |
| F: no carrier for bytes; a `Headers` parameter on `post`, `put` and `patch` before the body, as `get` takes one last | rejected: it would make the two families alike, but `def(V, V, Headers, B)` and its `State` twin need slot arity 4, two more overloads per method name, which reaches Mojo 1.1.0's ten-note cap (`AGENT_PROGRESS.md`; [M3-022](m3-022-several-route-values-decision.md)'s revisit condition) and changes every method's overload set and candidate notes; without arity 4 the two-route-value shapes lose header access. The carrier covers every shape with no overload. It is a registration-structure decision of its own, not this item's |
| G: one body trait over bytes (`FromBody.from_body(body: List[UInt8])`), dropping the text trait | rejected: it would remove the two-conversion rule, the parent trait and `_conversions`, but every text body type (over 130 conformances in this repository's sources, tests and adapters) would decode UTF-8 itself, so the strict UTF-8 400 Muntin guarantees before `from_body` (M3-040) would become each type's own and could be lossy; two traits keep two input contracts in the types, validated text and raw bytes. It reopens M3-041's choice, not only the carrier |

**Re-evaluation under the pre-release criterion.** After the first measurement round the owner set the criterion for this item: Muntin has no external users before its first release, so backward compatibility is not a design priority; API consistency, simplicity, type safety, ownership and maintainability decide, existing APIs may change, and each change is recorded as intentional or as a regression, with its impact and migration. Re-evaluated on that basis (A-pub, F and G above were added then; the question's preference for a candidate that keeps existing users was dropped as a criterion), A still wins on its own merits: one carrier for every body conversion is the consistent and simplest API (B duplicates it, F needs a registration restructuring); it rejects an ordinary non-body type where the handler is declared, which C gives up entirely (A-pub has the same reach as A and differs only in promising the bound as API; neither closes the set: a type conformed directly to the bound reaches registration, where `_kind` rejects it); the bytes are borrowed with no copy, as for a bare `FromBytes`; and the implementation is one bound and one branch in the carrier, with the UTF-8 read shared through `_body_text`. That A also keeps existing carriers working is a consequence, not the reason.

**Selected: A.**
- **Public API.** `WithHeaders[B]` accepts a `B` that conforms to `FromBody` or `FromBytes`. Nothing is added to `muntin`'s exports. `FromBody` and `FromBytes` refine the private `_FromBodyOrBytes(Deinitable, Movable)` instead of `Deinitable, Movable` directly: their requirements, every conforming type and every generic bound over them are unchanged.
- **The carrier's private surface.** `_HeaderCarrier._from_parts(body: List[UInt8], var headers: Headers) raises -> Self` replaces `_from_parts(body: String, ...)`: it receives the request's bytes borrowed from `_slot`, and converts them as a bare body of its `B`: `B.from_bytes(body)` for a `FromBytes`, with no UTF-8 read and no copy, else `B.from_body(_body_text(body))`, the same strict UTF-8 read a bare text body gets (`_body_text` moves from `app.mojo` to `body.mojo`, so both callers share it). `_two_conversions() -> Bool` becomes `_conversions() -> Int`, the number of the two traits `B` conforms to: `_kind` gives the carrier the body kind for 1, `_TWO_BODIES` for 2 and `_OTHER` for 0 (a `B` conforming only to the private bound, which has no conversion).
- **Order.** Unchanged in its steps: 404 or 405, the route values (400), for a `Json[T]` body 415 then 413, the field rebuild (500 on the `_fields` gap), the conversion (400: the UTF-8 read or `from_body` for a text body, `from_bytes` for a bytes body), the handler. A bytes carrier is never a JSON body, so `App.handle` appends no verdict for it, and no `Content-Type` rule or size cap applies.
- **Not included.** A Muntin-provided bytes type, a `FromHeaders` converter, a `Content-Type` rule or size cap for bytes bodies, a public name for the bound.
- **Copies of the body per request** (read from the code, not timed): a bytes carrier route, none by Muntin, as a bare `FromBytes` (the conversion's own `body.copy()` if it keeps the bytes); a text carrier route, one (the UTF-8 read), as before.

**M2 contract: amended, not reopened.** The carrier is an M3 type and every M2 signature, binding rule and answer is unchanged. By kind:
- the accepted set only grows: handlers whose carrier holds a `FromBytes` register on every body shape; no handler that registered is rejected or registers differently;
- the overload set is unchanged;
- specific diagnostics change: the declaration-site rejection of `WithHeaders[X]` for an `X` that is neither a `FromBody` nor a `FromBytes` names `'_FromBodyOrBytes' type` instead of `'FromBody' type`; `WithHeaders[X]` for a `FromBytes` `X` is no longer rejected; every `constraint failed:` message is unchanged, and so is every other fixture's whole normalized output (above);
- runtime: every previously valid route answers as before (text carriers, `WithHeaders[Json[T]]`, bare bodies, raw handlers, middleware, 404, 405, `HEAD`, the Flare adapter).

**Changes to existing APIs, classified.** Intentional (each made by this item on purpose):
- `WithHeaders[B]`'s bound changes from `FromBody` to the private `_FromBodyOrBytes`. Impact: a `FromBytes` `B` is accepted; for a `B` that is neither, the compiler's text at the declaration names `'_FromBodyOrBytes' type` instead of `'FromBody' type`. Migration: none for code that compiles; a check that matches the old text matches the new one (three fixtures re-pinned).
- `FromBody` and `FromBytes` refine `_FromBodyOrBytes` instead of `Deinitable, Movable` directly. Impact: their requirements are the same, so no conforming type or generic bound changes; a note that echoes a trait's declaration shows the new line (two fixtures, text unchanged). Migration: none.
- Private: `_HeaderCarrier._from_parts(String, Headers)` becomes `_from_parts(List[UInt8], Headers)`, `_two_conversions() -> Bool` becomes `_conversions() -> Int`, and `_body_text` moves from `app.mojo` to `body.mojo`. Impact: code outside `src/muntin` that calls them (the raw and state spikes) stops compiling. Migration: pass the bytes (`List(text.as_bytes())`); import `_body_text` from `muntin.body`.
- `tests/from_bytes_api_fail/bytes_body_in_with_headers.mojo` is removed: the shape it rejected now registers, and `tests/test_bytes_headers_body.mojo` exercises it.

Unintended regressions: none remain. The full suites pass; the whole normalized output of every other must-not-build fixture is identical to the base's; every text-carrier, JSON-carrier, bare-body, raw, middleware, `HEAD`, 404 and 405 test passes unchanged. The one found during the item (the spikes calling the private `_from_parts` with a `String`, which stopped 32 test files from building) was fixed before review closed.

**Invariants:**
- A carried `FromBytes` receives exactly the request's body bytes as `App.handle` holds them after middleware, borrowed: no step reads them as text, replaces, drops or adds a byte, or copies them before `from_bytes`.
- A body has exactly one conversion, alone or in a carrier: registration rejects a carried type with both or neither. `_kind` (through `_conversions`) is the final check, not the bound: `_FromBodyOrBytes` is a private marker, not a closed set, and a type conformed to it directly is declared without error and rejected only here.
- The carrier's fields are the request's, in order, with casing, repeated names and empty values; Muntin gives them no meaning and chooses no status for them.
- The carrier's field rebuild answers before its conversion, and the route values before both.

**Cost.** The carrier's bound is a private trait whose name appears in the compiler's text for a carrier of a non-body type (three existing fixtures re-pinned, documented in `docs/DX.md`); neither public trait names every type a body slot accepts, as before.

**Revisit when:**
- applications need a public name for "a body conversion" (generic code over both traits, or a diagnostic without the private name): revisit whether `_FromBodyOrBytes` becomes public;
- a third body conversion is added (streaming, multipart): it refines the same bound, and `_conversions` counts it;
- Mojo prints a refining trait's name or a custom message for a parameter-bound failure, or allows a struct-level assert (`tests/header_access_fail/struct_level_assert.mojo` compiles): revisit the diagnostic;
- M3-041's other conditions (a Muntin-provided bytes type, an owned or `Span` input, a size cap or `Content-Type` rule for bytes bodies) hold for the carrier too.
