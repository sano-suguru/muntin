# HEAD decision (M3-026)

> **Current.** Now described in [routing reference, "`HEAD`"](../../reference/routing.md#head), [ARCHITECTURE, "Backend seam"](../../ARCHITECTURE.md#backend-seam) and [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter).
> Changed in part since:
> - [M3-030](m3-030-method-not-allowed-decision.md): HEAD (and head, Head, OPTIONS) on a path only routes of other methods match is 405 with Allow, not the 404 M3-026 kept for a method mismatch.
> - [M3-036](m3-036-testclient-head-decision.md): TestClient gained head (M3-026's candidate E, left out), returning App.handle's answer with its body.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-026, PR #58; `src/muntin`, `adapters/` and `tests/` are unchanged in it). It decides how Muntin answers a `HEAD` request. Today `HEAD` is 404 on every path, a path a `get` route serves included, and no handler, typed or raw, can register for it.

**Why this candidate.** M3-024 compared SPEC's remaining candidates and named `HEAD` its closest competitor: "a decision of its own, with a reopen and a wire probe". Nothing shipped since then changes the others' standing:
- `HEAD`: RFC 9110 section 9.1 says "All general-purpose servers MUST support the methods GET and HEAD", and section 9.3.2 defines `HEAD` as `GET` without content. A client cannot be made to send `GET` instead (caches, link checkers and monitors send `HEAD`), so no route design works around it. What is open is public and hard to change once applications depend on it: whether `get` routes answer `HEAD` (every existing `get` route would start answering a method that is 404 today) or applications register it, what a handler sees as the method, and who keeps the content off the wire, `App.handle` or the backend, which no record owns yet.
- Lifecycle: a serving API belongs to the backend, and the pinned Flare v0.11.0 cannot shut down gracefully and drops its old server spellings in v0.12 (M3-024).
- Middleware and observability (logging dropped handler errors): each needs a hook stored with the `App`, an injection or storage decision of its own on Mojo 1.1.0 (no captures, no module-level variables); no handler shape depends on them (M3-020, M3-022, M3-024).
- `OPTIONS` and 405 with `Allow`: M3-020 tied 405 to a resource-level method set, which `OPTIONS`, CORS preflight and middleware would also need. `HEAD` can be decided without that view only if its design does not need one; this record says whether it does.
- Bodyless typed `post`, `put`, `patch`, a typed `DELETE` body and `FromHeaders`: their revisit conditions have not fired. JSON follow-ups, three route values, other value types, schema output and parameter-name checking: as M3-024 recorded.
- Static path segments are not checked for target bytes (`/hello world` compiles and never arrives over Flare; `docs/ARCHITECTURE.md`, "Other current limits"): a smaller correctness item that adds no capability and would reject literals that compile today.

**Question.** How does Muntin answer a `HEAD` request? Specifically: whether a `HEAD` request reaches the handler of a `get` route automatically, an application registers `HEAD` handlers, both, or neither; what a typed and a raw handler see as the request's method; which part of the system keeps the content of a `HEAD` response off the wire while its framing (`Content-Length`) stays what a `GET` would have sent, `App.handle` or the backend, and what the in-memory backend (`TestClient`) shows; what a `HEAD` request gets on a path no `get` route serves; and which statements of the M2 contract, DX and existing tests change.

**What settles it:**
- HTTP's requirements: RFC 9110 sections 9.1 (`GET` and `HEAD` MUST be supported), 9.3.2 (`HEAD` is `GET` without content; a server SHOULD send the same header fields), 6.4.1 (a response to `HEAD` has no content) and 8.6 (a server MAY send `Content-Length` in a `HEAD` response, and MUST NOT unless its value equals the length `GET` would have sent), and RFC 9112 section 6.3 (a `HEAD` response's framing). These decide which answer is correct on the wire, independent of where it is produced;
- the backend premise, measured over loopback through the pinned Flare v0.11.0 and the unchanged adapter (raw TCP, so the response bytes are seen unparsed): whether a `HEAD` request reaches `MuntinHandler` with its method unchanged; what Flare sends for the response `App.handle` returns (status line, `Content-Length`, any content bytes), for a response with a body and one without; whether a following request on the same connection is answered correctly (content on the wire would be read as the next response); the same over cleartext HTTP/2 (prior knowledge), which the default `ServerConfig()` accepts on the same port (M3-002's probe), scoped to what the probe sends. Flare's source (`flare/http/_reactor/write_path.mojo`) suggests HTTP/1.1 sends no content for `HEAD` and a `Content-Length` of the handler's own field or the body's length, and the adapter drops a handler's `Content-Length` (M3-005); the probe settles what is sent;
- for each candidate, which existing tests, DX statements and M2 contract sentences change (`tests/test_methods.mojo` and DX section 4 assert `HEAD` 404 on `get`, `put` and `delete` paths), and whether that is an addition or an M2 reopen under [M2-016](m2-016-m2-closure.md);
- for a registered `HEAD`, the overload and note budget (M3-020's per-name copies, eight overloads per name at slot arity 3).

**Boundaries that do not change silently:**
- `GET`, `POST`, `PUT`, `PATCH` and `DELETE`: their routes, shapes, rules, diagnostics and answers; the eight overloads per method name and the note budget;
- method matching byte for byte for every method this record does not name (`head`, `Head` and `OPTIONS` stay 404 in memory), first registered matching route wins, a matched route never falls through;
- 404 on a method mismatch, without 405 or `Allow`, for every request this record does not decide (M3-020, candidate F);
- the 400/404/500 boundary and the order of steps on a typed route; route values decoded once at capture; `Optional` values query-only;
- the raw escape hatch; `State`, `Headers`, `WithHeaders[B]` and `Json[T]` as they are;
- the backend seam `App.handle(Request) -> Response`, `Request`'s and `Response`'s fields, the adapter's header policy, Flare out of the public API and of `src/muntin`; unsafe confinement and the one rebind.

**Candidates to measure:**
- automatic: a `HEAD` request is answered by the first `get` route whose path matches, as a `GET` would be, and the content is kept off the wire by the backend, or removed by `App.handle`;
- registered: `app.head[route](handler)` with `get`'s shapes, eight overloads, and `HEAD` 404 where none is registered;
- both: automatic, with a registered `HEAD` route taking precedence;
- what the handler sees: `Request.method` `"HEAD"` or `"GET"` for a raw handler;
- `TestClient`: a `head` method, or none (`App.handle(Request("HEAD", ...))`);
- deferral, with the RFC gap kept as an explicit limit.

**Selected: a `get` route answers `HEAD` automatically. `App.handle` matches a `HEAD` request against `GET` routes and answers it exactly as it would answer the same `GET`, body included; the backend keeps the content off the wire. The Flare adapter answers a `HEAD` request with the response it would send for that `GET`, with no body and a `Content-Length` equal to that body's byte length (none for a status that never carries content: 1xx, 204, 205, 304).** No overload, public type, slot kind or `TestClient` method is added. It reopens M2 (below).

```mojo
def get_user(id: Int) -> String:
    return String("user ", id)
def report(var req: Request) -> Response: ...       # raw

app.get["/users/{id}"](get_user)
app.get["/report"](report)
app.delete["/cache"](purge)
# HEAD /users/7   -> App.handle: what GET /users/7 answers (200 "user 7"); on the wire: 200, Content-Length: 6, no content
# HEAD /users/abc -> App.handle: 400 "Bad Request" (get_user not called); on the wire: 400, Content-Length: 11, no content
# HEAD /report    -> report receives req.method == "HEAD"
# HEAD /cache, HEAD /missing, head /users/7, OPTIONS /users/7 -> 404 "Not Found"
```

- **Matching.** A route matches a request when its method equals the request's byte for byte, or when the request's method is `HEAD` and the route's is `GET`. Everything else about the scan is unchanged: routes are tried in registration order, the first match handles the request and never falls through, and a path matched only by routes of other methods is 404 (`HEAD` on a path only a `delete`, `post`, `put` or `patch` route serves included). Only the exact token `HEAD` maps: `head` and `Head` stay 404 in memory (Flare answers them 400 before `App.handle`, M3-020).
- **The answer.** Every step of a `GET` runs for `HEAD`: route values, the `Headers` slot, `State`, the handler, the result or error conversion, the 400/404/500 boundary. `App.handle` returns the response the `GET` would have returned, body included. That body is what the backend derives the framing from (RFC 9110 section 8.6: a `Content-Length` sent for `HEAD` equals the length a `GET` would have sent), so `App.handle` does not remove it. Removing it is wire framing, a protocol mechanic (A5), and it is the backend's.
- **What a handler sees.** A typed handler cannot tell `HEAD` from `GET`: the method is not a slot, and it gets the same arguments. A raw `get` handler receives the whole `Request` as received, `req.method == "HEAD"` included (M2-014's raw escape hatch). It answers `HEAD` with the response it would give `GET`: the backend sends the length of the body the handler returned, so a raw handler that returns a shorter body for `HEAD` (to skip work) makes the backend send a wrong `Content-Length`. Muntin cannot check that, so DX states it as the raw handler's rule.
- **The backend.** The Flare adapter, for a request whose method is `HEAD`, takes the `FlareResponse` it would send for the same `GET` at every exit of `MuntinHandler.serve`: `App.handle`'s answer converted by `to_flare_response`, that conversion's own fixed 500, and the 400 it answers before `App.handle` for a request field it cannot represent. It sends that response's status and fields and no body, and declares a `Content-Length` equal to the body's byte length, except for a status that never carries content. RFC 9110 closes that set: 1xx, 204 and 304 (section 6.4.1) and 205 (section 15.3.6: a server MUST NOT generate content in a 205); a 2xx to `CONNECT` is the only other case, and no route has that method. For those statuses the body's length is not the length the `GET` content would have, so the adapter declares none:
  - 1xx and 204: a server MUST NOT send `Content-Length` (section 8.6). Flare drops a declared one over HTTP/1.1 but forwards it over HTTP/2 (read from its source, not measured).
  - 205: a `GET` sends no content, so a length taken from Muntin's body would be wrong. Measured with the body removed and no length declared: HTTP/1.1 `Content-Length: 0` (Flare's own framing, which equals the `GET`'s content length of 0), h2c no `content-length`.
  - 304: Muntin's 304 body has no defined relationship to the representation's length, so the adapter does not synthesize one; defining that relationship is a question of its own. Flare v0.11.0 frames every HTTP/1.1 304 with a `Content-Length` itself (the body's length, or a declared one), which this record pins separately (measured below); h2c sends none. For every other method the adapter is unchanged. It is adapter-local conversion code ("Adapter translation policy"), not a change to M3-005's header policy: a handler's own `Content-Length` is still dropped. Measured (below), it is correct over HTTP/1.1 and cleartext HTTP/2, where leaving the body in place is not: Flare v0.11.0 sends a `HEAD` response's content in DATA frames over h2c today, Muntin's current 404 included, and the adapter change ends that too. The in-memory backend has no wire: `App.handle(Request("HEAD", ...))` shows the response with its body.
- **`TestClient`.** No `head` method. A test sends `HEAD` through `App.handle(Request("HEAD", target))`, as M3-020's candidate E left any other request; `TestClient.head` would follow M3-010's pattern and is additive later.
- **405 and `OPTIONS`.** Mapping `HEAD` to `GET` is decided per route and needs no resource-level method set, so M3-020's candidate F stays deferred: a method mismatch is 404, `OPTIONS` is 404. When `Allow` is decided, it lists `HEAD` wherever it lists `GET`.

**Measured premises.** `compat/flare/head/head_probe.mojo` (run by `scripts/check_flare.sh`) serves an unchanged `App` (`get /hello`) through the unchanged `MuntinHandler`, and through a probe handler that answers `HEAD` with `App.handle`'s answer to the same `GET` and converts it with the adapter's own `to_muntin_request`/`to_flare_response`. It reads raw response bytes over HTTP/1.1 (`Connection: close`, and keep-alive) and frames over h2c (prior knowledge, one stream). TLS and ALPN-negotiated HTTP/2 are not measured.
- Flare delivers a `HEAD` request to the handler with the method `HEAD`.
- HTTP/1.1, the `GET` response passed through: `200`, `Content-Length: 5`, no content. Flare suppresses the content itself and frames the length from the body. On a keep-alive connection, `HEAD` then `GET` gives two whole responses.
- HTTP/1.1, the body removed before the adapter: `Content-Length: 0`, not the `GET`'s 5, which RFC 9110 section 8.6 forbids. So `App.handle` must not remove the body while the backend frames from it.
- HTTP/1.1, a handler's own `Content-Length: 99` beside a 3-byte body: the adapter drops it and `Content-Length: 3` goes out (M3-005's policy).
- h2c, the `GET` response passed through: `HEADERS{:status: 200}` then `DATA{hello}`: content on a `HEAD` stream, which RFC 9110 section 6.4.1 says a `HEAD` response does not have. Through the unchanged `MuntinHandler`, today's 404 goes out the same way (`DATA{Not Found}`).
- The body removed and a `Content-Length` of its length added after the adapter's conversion: HTTP/1.1 `Content-Length: 5`, no content; h2c `HEADERS{:status: 200; content-length: 5}` with END_STREAM and no DATA (RFC 9113 section 8.1.1 allows a nonzero `content-length` on a response defined to have no content). This is the one measured form that is correct on both protocols. With the body removed and no length added, h2c sends no `content-length`, which section 8.6 also allows, but HTTP/1.1 sends 0.
- A raw route answering 304 with a 3-byte body, the body removed and no length added: HTTP/1.1 `304 Not Modified`, `Content-Length: 0`, no content (Flare frames a 304's length from the body when none is declared); h2c `HEADERS{:status: 304}` with END_STREAM, no `content-length` and no DATA.
- The same with 205: HTTP/1.1 `205 Unknown` (Flare's reason phrase), `Content-Length: 0`, no content; h2c `HEADERS{:status: 205}` with END_STREAM, no `content-length` and no DATA.
- Today's answers (observation 1, and h2c through `MuntinHandler`) are recorded as "before" values; the production slice re-pins them.

**M2 contract: reopened.** A `get` registration now also answers a request M2 answers 404: `HEAD` on a path the route matches. That changes the semantics of an existing registration rather than adding one, so it is an M2 reopen under [M2-016](m2-016-m2-closure.md) ("a different 400/404/500 boundary"), as M3-018 was. By kind:
- `App.handle`'s answer changes for one request class only: a `HEAD` request whose path a `get` route matches gets that route's `GET` answer instead of 404. The contract's "No route match is 404" stays true for every other request, `HEAD` on a path no `get` route matches included;
- on the wire, every `HEAD` response changes: through Flare it carries no content, the 404 for a path no `get` route matches included (over h2c it carries `Not Found` in DATA today), and the length the adapter's rule gives;
- a raw `get` handler can now receive `req.method == "HEAD"`; before, it received only `GET`. The raw escape hatch's statement (the whole `Request`, `method` included) is unchanged;
- the accepted set, the overload set and every diagnostic are unchanged: nothing registers or fails to register differently;
- the Flare adapter's answer to a `HEAD` request carries no content, on both protocols, and the length the backend rule above gives: the `GET` body's byte length for a status that can carry content, and no adapter-declared length for 1xx, 204, 205 and 304. Today it carries the 404's content over h2c;
- one guarantee is no longer decided in `App.handle` alone: SPEC's "Every guarantee is decided in `App.handle` and the registration overloads, so both backends inherit it" holds for the answer, but keeping a `HEAD` response's content off the wire and its length is each network backend's obligation, and for `HEAD` the in-memory response (with its body) and the loopback response (without) differ, where the contract's opening sentence holds the same guarantees through both. Every future backend inherits that obligation (A3).

**Invariants:**
- `HEAD` is answered only through `GET` routes, as the `GET` would be answered; `App.handle` never removes a body.
- A backend sends no content for `HEAD`. Its adapter declares a `Content-Length` equal to the byte length of the body it would have sent for the `GET` (`App.handle`'s, or the backend's own answer where it answers without `App.handle`), and declares none for a status that never carries content (1xx, 204, 205, 304).
- Method matching is byte for byte except the one `HEAD`-to-`GET` mapping; a method mismatch is 404.

**Cost.** Every `HEAD` computes and converts the whole `GET` body only for the backend to drop it. A raw `get` handler that branches on `HEAD` must still return the `GET` body. Applications cannot answer `HEAD` differently from `GET` (no registered `HEAD`). The in-memory response to `HEAD` has a body that a network backend never sends. Over HTTP/1.1, Flare v0.11.0 frames a `HEAD` 304 with `Content-Length: 0` itself; the adapter cannot remove a field Flare frames. One existing test case changes (the slice names it).

**Revisit when:**
- an application needs a `HEAD` answer cheaper than computing the `GET` body, or different from it: revisit B, a registered `HEAD` ahead of the automatic mapping (additive);
- tests need `HEAD` through `TestClient`: add `TestClient.head(target, *, headers=)` (candidate E, M3-010's pattern);
- 405 with `Allow`, `OPTIONS` or CORS preflight is decided: list `HEAD` wherever `GET` is listed (M3-020, candidate F);
- a Flare upgrade, or another backend, changes how it frames a `HEAD` response (it suppresses content over HTTP/2, stops honoring a declared `Content-Length` with an empty body, or lets a 304 go out over HTTP/1.1 without `Content-Length`): re-run `compat/flare/head/head_probe.mojo` and re-derive the adapter rule;
- streaming responses are decided: a streamed `GET` answer has no length to declare, and the `HEAD` rule has to say what is sent then.
