# HTTP methods decision (M3-020)

> **Current.** Now described in [routing reference, "Methods"](../../reference/routing.md#methods), [testing reference, "`TestClient`"](../../reference/testing.md#testclient) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Changed in part since:
> - [M3-022](m3-022-several-route-values-decision.md): eight overloads per method name instead of six.
> - [M3-026](m3-026-head-decision.md): `HEAD` is answered by `get` routes instead of 404.
> - [M3-030](m3-030-method-not-allowed-decision.md): a path match with no method match is 405 with `Allow`, not 404.
> - [M3-048](m3-048-bodyless-typed-post-put-and-patch-handlers-decision.md): bodyless typed `put` and `patch` shapes, left a compile error here, are accepted.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-020, PR #51; `src/muntin`, `adapters/` and `tests/` are unchanged in it). It decides which request methods beyond `GET` and `POST` an application can register, under which spelling and with which handler shapes, so that a typed application can update and delete resources. Today every other method is 404 whatever the application registers, typed or raw.

**Why this candidate.** Of SPEC's remaining candidates:
- More HTTP methods (`put`, `patch`, `delete`): an application cannot answer `PUT`, `PATCH` or `DELETE` at all. No typed or raw handler can register for them, and the client chooses the method, so no route design works around it. A small typed framework whose API covers create and read but not update and delete is incomplete. M3-014 settled the structure (each method its own arity overloads over the shared rules, within a per-method note budget), and M3-018 called that "production work, not a decision". What it left open is public and hard to change once shipped: whether a `DELETE` handler may take a body, whether `PUT` and `PATCH` take exactly `post`'s shapes, the spelling, `TestClient`'s spelling for the new methods, and what a request gets when the path matches but the method does not. `DX.md` proves that `PUT /users` is 404 today. DEVELOPMENT.md section 2 needs a decision record to name a production slice.
- Several route values, path and query together: the closest competitor. Nested resources (`/users/{uid}/posts/{pid}`) and DX section 3's two-key search are unreachable today. But an application can choose its URLs (`/posts/{pid}`), and it cannot choose the method a client sends. Several values also carry a binding risk the methods do not: with no parameter-name reflection, two `Int` values bind by position only, and a swapped pair compiles. That needs its own decision, and it is not made easier by deciding it first. Deciding methods first does make several values dearer: slot arity 3 adds two overloads to every method name (M3-014), ten across five names instead of four across two. The cost is accepted because the overloads are mechanical copies under one rule set, while the missing methods block whole applications.
- Optional or default query values: useful on their own (`def list(limit: Int = 20)`), but what a default means for a registered handler is unresolved: a default cannot be expressed through a `def(var A)` slot, which has no default. Deciding them now gives less than restoring the missing methods.
- `POST` without a body, `FromHeaders`: M3-016 revisit conditions whose triggers have not fired.
- Middleware, lifecycle (`app.run()`), streaming: no handler shape depends on them, so postponing them builds nothing on a wrong seam, and each is larger and less settled on Mojo 1.1.0 (no captures, no existentials, serving owned by the backend).
- Schema/OpenAPI waits for a derived codec; parameter-name checking waits for function-parameter reflection.

**Question.** For which request methods beyond `GET` and `POST` does Muntin provide registration, under which public spelling, and with which handler shapes (route values, body, `Headers`, raw `Request`, `State`) and diagnostics for each? How does `TestClient` send them? And what does a request get when its path matches a route but its method matches none: 404 as today, or 405 with an `Allow` field?

**What settles it:**
- each method's semantics as HTTP defines them: RFC 9110 sections 9.3.4 (`PUT`), 9.3.5 (`DELETE`: content "has no generally defined semantics") and 15.5.6 (405 and its required `Allow` field), and RFC 5789 (`PATCH`). These decide which methods take a body, and whether one shape set can serve several methods;
- the spelling on Mojo 1.1.0: whether `put`, `patch` and `delete` compile as `App` method names and call as `app.delete[route](handler)`, and how a misuse's diagnostic names the method (measured with a compile probe);
- the backend premise: whether Flare v0.11.0 delivers `PUT`, `PATCH` and `DELETE` requests, with and without a body, to the handler with the method and body unchanged (measured with the smallest raw-TCP probe through Flare). The adapter copies the method verbatim, so no adapter change is expected; the probe settles whether Flare does too;
- the existing measurements: M3-014's C1 (a scratch `put` with its own overload set, `PUT /notes/7` answered through it, `POST` to it 404) and `tests/registration_fail/notes_are_per_method.mojo` (the note budget is per method name);
- for 405: what changes in `App.handle`'s scan and in the M2 contract ("No route match is 404"), and whether that follows M2-016's reopen conditions.

**Boundaries that do not change silently:**
- `get` and `post`: their six arity overloads each, their shapes, their rules and every existing diagnostic, unless this record names the change and why; the note budget per method name;
- the registration structure: generic-arity slots, the `where` clause on the result, the rule guard, one `rebind_var`, the storage module and unsafe confinement;
- `State` as the one registration-bound injected slot; the body and header rules (`FromBody`, `Json[T]`, `WithHeaders[B]`, the `Headers` slot on `get`);
- the raw `Request -> Response` escape hatch;
- route-value capture decoding (M3-018) and raw query keys;
- the backend seam at `App.handle`, with Flare out of the public API and of `src/muntin`;
- method matching byte for byte (`Request.method` as received), first registered matching route wins, a matched route never falls through;
- the M2 contract's 400/404/500 boundary (SPEC, "M2 completion contract"); a change to it, 405 included, reopens M2.

**Candidates to measure:**
- the method set: `put`, `patch` and `delete`; a subset first; or a generic `app.route[method, path]` entry for any method name, beside or instead of named methods;
- per method, the shapes: `post`'s (a required body last) or `get`'s (no body, a `Headers` slot last), with `DELETE` as the open case;
- `TestClient`: one method per new HTTP method, mirroring `get` and `post`; one generic `request(method, ...)`; or none (`app.handle(Request(...))`);
- a matched path with no matching method: 404 (unchanged) or 405 with `Allow` (M2 reopen);
- deferral.

**Selected: `put`, `patch` and `delete` as `App` methods, each with its own six arity overloads. `put` and `patch` take exactly `post`'s shapes, `delete` takes exactly `get`'s, and `TestClient` gains one method per new HTTP method.** A request whose path matches a route but whose method matches none stays 404. Nothing changes for `get`, `post`, `App.handle` or the adapters, so M2 does not reopen. No public type, slot kind or injected kind is added.

```mojo
def replace_user(id: Int, body: UserForm) -> String: ...              # `post`'s shapes
def rename_user(users: State[Users], id: Int, body: Json[Rename]) -> Json[User]: ...
def remove_user(id: Int, headers: Headers) raises Unauthorized -> String: ...  # `get`'s shapes

app.put["/users/{id}"](replace_user)
app.patch["/users/{id}"](rename_user, users)
app.delete["/users/{id}"](remove_user)
# PUT /users/7 "name=Ada"  -> the handler's answer (7 and the converted body)
# PUT /users/7 "Ada"       -> 400 "Bad Request" (from_body raised; handler not called)
# DELETE /users/abc        -> 400 "Bad Request" (before the handler)
# POST /users/7, HEAD /users/7, OPTIONS /users/7 -> 404 "Not Found" (no route of that method)

var client = TestClient(app)
client.put("/users/7", "name=Ada")
client.patch("/users/7", body, headers=h^)
client.delete("/users/7")
```

- **Shapes.** `put` and `patch` accept every shape `post` accepts and no other, with `post`'s rules: a required body last (a `FromBody`, a `Json[T]` or a `WithHeaders[B]`), at most one `Int` or `String` route value before it, the raw `def(Request) -> Response`, and each after a leading `State[S]` passed as the registration's second argument. `delete` accepts every shape `get` accepts and no other, with `get`'s rules: no body, at most one route value, a `Headers` slot last, the raw handler, each after a leading `State[S]`. Results, errors, route values (decoded at capture, M3-018), the `where` clause and binding are those of the method whose shapes it takes.
- **Why these shape sets.** `PUT` creates or replaces the target's state with the enclosed representation (RFC 9110 section 9.3.4) and `PATCH` applies the enclosed patch document (RFC 5789), so both need a body, as `post` does. Content received in a `DELETE` request "has no generally defined semantics" and "might lead some implementations to reject the request" (RFC 9110 section 9.3.5), word for word what section 9.3.1 says of `GET`, and `get` already takes no body. Admitting a body on `delete` later accepts more handlers and breaks none, while rejecting one later would break handlers that compile now. A handler that must read a `DELETE` body registers as a raw handler, which receives `req.body`.
- **Spelling.** `app.put[route](handler)`, `app.patch[route](handler)` and `app.delete[route](handler)`, with the state as the second argument, exactly as `get` and `post`. `put`, `patch` and `delete` compile as `App` method names and call with that syntax on Mojo 1.1.0 (measured). The route literal's grammar and checks are unchanged.
- **Matching.** A route of method `M` matches only a request whose `Request.method` is `M` byte for byte (`PUT`, `PATCH`, `DELETE`), as today. Routes are scanned in registration order across all methods, and the first route whose method and path match handles the request and never falls through. A path that matches routes of other methods only is 404: Muntin's routes are independent `(method, path)` registrations, not resources that carry a set of allowed methods, and `App.handle` answers only whether a whole route matches. Its scan and the M2 contract's 404 (no route match) are unchanged; this departs from RFC 9110's recommended 405 on purpose (candidate F).
- **Diagnostics.** Each Muntin message that names `get` or `post` names the method instead (`a delete handler takes no request body`, `a put handler takes the request body as its last parameter`, `a stateful raw patch handler takes State first, then only the Request, and returns Response`). Messages that name no method are shared unchanged (`handler takes one Int parameter; route must declare exactly one path or query parameter`). `get`'s and `post`'s messages stay byte-identical. A call that selects no overload is expected to be `no matching method in call to 'put'` (or `'patch'`, `'delete'`), as for `get` and `post`, with that method's six candidate notes, because the note budget is per method name (`tests/registration_fail/notes_are_per_method.mojo`). A `comptime assert` message may be a compile-time concatenation, and Mojo 1.1.0 prints it as the concatenated text (`constraint failed: a delete handler takes no request body`, measured), so one rule set with the method's name substituted serves every method of a shape family.
- **`TestClient`.** `put(target, body, *, headers=)`, `patch(target, body, *, headers=)` and `delete(target, *, headers=)`, with `post`'s and `get`'s parameters and M3-010's keyword-only, defaulted, moved-in `headers` (M3-010's revisit condition "`TestClient` gains another request method" is met by following that pattern). Each builds `Request("PUT", target, body, headers^)` (`"PATCH"`, or `"DELETE"` with an empty body) and calls `App.handle`, nothing else. A test that sends a `DELETE` body builds the `Request` and calls `App.handle`.
- **Raw handlers** register on each new method with the raw shape of its family and receive the whole `Request`, its `method` included.
- **Generic forwarding** reaches the new methods as it reaches `get` and `post`: the overloads have the same slots and the same `where` clause.

**Measured premise: Flare delivers the new methods.** A raw-TCP probe through Flare v0.11.0 sent `PUT`, `PATCH` and `DELETE` over HTTP/1.1, each with a 3-byte body and with none. Flare delivered each one to the handler, and the adapter's `to_muntin_request` gave a Muntin `Request` with the method, path and body unchanged, so no adapter change is needed. Flare answered `get`, `post`, `Get`, `put` and `delete` with 400 itself, before the handler, where `App.handle` would answer 404, and passed `FOO` and `OPTIONS` through; its HTTP/1.1 parser rejects any lowercase letter in a method unless `H1LeniencyConfig.allow_mixed_case_method` is set, which is off by default (`flare/http/_server/parse.mojo`). This is a current Flare limit for every method (`docs/ARCHITECTURE.md`, "Other current limits and operational risks"): method handling differs between backends in ways route shapes do not, which is why the slice covers the new methods over loopback.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A. `put`, `patch`, `delete`, each with six arity overloads; `put` and `patch` with `post`'s shapes, `delete` with `get`'s | **chosen** |
| B. a subset first (`delete` alone, or `put` and `patch`) | rejected: the three share every design choice above, and a subset leaves an application able to update but not delete, or the reverse. The slice is the same mechanical change per method |
| C. a generic `app.route[method, path](handler)` for any method, beside `get` and `post` or instead of new names | rejected: `PUT` would be registered differently from `POST` (`app.route["PUT", ...]` beside `app.post[...]`) while `get` and `post` keep their names, or, instead of named methods, every method including `GET` would need it, which changes M2's spelling. No current requirement needs a method outside the three (A7). (M3-014's C4b was the same entrypoint beside frozen `get` and `post`, rejected for giving one method two spellings; this case differs, and the reason here is consistency across methods.) Revisit condition below |
| D. `delete` with `post`'s shapes, or with an optional body | rejected: RFC 9110 gives `DELETE` content no semantics, `get` already rejects a body, and a raw `delete` handler reads one; admitting a body later is additive (above) |
| E. `TestClient`: one generic `request(method, target, body, headers=)`, or no new methods (`App.handle` only) | rejected: one method per HTTP method keeps a test's call reading like its registration (`client.delete` for `app.delete`); a generic client method is candidate C on the client side, and M3-010 kept a builder that opens arbitrary methods out of scope (its C2); `App.handle(Request(...))` already covers any other request |
| F. 405 with an `Allow` field when the path matches routes of other methods only | rejected now, as a deliberate deviation from HTTP's recommendation, because it needs a concept the router does not have. RFC 9110 section 9.1 says an origin server receiving a method that is "recognized and implemented, but not allowed for the target resource, SHOULD respond with the 405 (Method Not Allowed) status code", and a 405 MUST carry `Allow`, "a list of the target resource's currently supported methods" (section 15.5.6). To produce it, Muntin would have to treat the routes whose paths match as one resource and synthesize its method set: decide whether `HEAD` and `OPTIONS` are listed, how a raw route counts, and what a path that matches a typed route but would fail its route value answers. Those are the `HEAD`, `OPTIONS` and CORS questions, so 405 is decided with them or with another feature that needs a resource-level method set, not ahead of them. Until then Muntin keeps its whole-route-match semantics: no `(method, path)` match is 404. That is an explicit current limitation, not a claim that 404 is HTTP's preferred answer to a method mismatch: it departs from a SHOULD, for the reason this row states. Its cost when it comes: it changes `App.handle`'s scan and the M2 contract's 404 for every method, `get` and `post` included (DX proves `PUT /users` is 404, and `tests/test_body.mojo` and `tests/test_int_body.mojo` assert 404 for `PUT`, `PATCH` and `DELETE`), an M2 reopen under M2-016. The new methods do not raise that cost: method mismatch is already 404 for `get` and `post` routes. Revisit condition below |
| defer | rejected: no application can update or delete through Muntin, typed or raw |

**Not decided here:** `HEAD` and `OPTIONS`, whether answered automatically (a `HEAD` request through a `get` route, an `Allow` listing) or registered (RFC 9110 section 9.1: "All general-purpose servers MUST support the methods GET and HEAD"; today `HEAD` is 404); other methods (section 9.1 recommends 501 for a method the server does not implement; today they are 404). Each stays 404 until its own decision. Also not decided: bodyless typed `post`, `put` and `patch` handler shapes (`def()`, `def(V)`), which are compile errors (`def()` is `a put handler takes the request body as its last parameter`; `def(V)` gets the existing body messages) until M3-016's bodyless-`POST` condition is decided for all three. A request with an empty body is not that question: a typed body handler accepts it or answers it under the existing body rules (415 first for a `Json[T]` body without its `Content-Type`, then 400 if `B.from_body("")` raises), and a raw handler reads `req.body == ""`.

**Invariants:**
- One overload set per registration method name, six overloads each (slot arities 0 to 2, stateless and stateful), with the shared `where` clause; the note budget is per method name.
- `put` and `patch` accept exactly `post`'s shapes, `delete` exactly `get`'s, with the same rules in the same order; only the method's name in a message differs.
- Method matching is byte for byte, in registration order across methods; method mismatch is 404.
- `get`, `post`, `App.handle`, `_Route`, the adapters (`_call_*`), the storage module, the one `rebind_var` and the Flare adapter are unchanged.

**Cost.** Eighteen overloads, each a copy of its family's overload with the method name changed; a later slot arity 3 or 4 adds two overloads to every method name. A rule change to a shape family now applies to two or three methods. `DELETE` bodies reach only raw handlers. Method mismatch stays 404 without an `Allow` field, short of RFC 9110 section 9.1's SHOULD (405).

**Revisit when:**
- an application needs a typed `DELETE` body: admit `post`'s shapes on `delete` (additive);
- an application needs a method outside `GET`, `POST`, `PUT`, `PATCH`, `DELETE`: revisit a generic entrypoint (candidate C) or another name;
- clients or a later feature (CORS preflight, middleware, `OPTIONS`) need 405 with `Allow` or another resource-level method set, or `HEAD` and `OPTIONS` are decided: revisit candidate F, introducing that view deliberately, with the M2 reopen;
- bodyless typed `post` handler shapes are decided: apply the decision to `put` and `patch`, or record why they differ;
- slot arity 3 or more is decided: every method name gains two overloads per arity (eight per name, forty across five names at slot arity 3), so re-evaluate copying an overload set per method against candidate C or generating the sets internally;
- a Flare upgrade, or another backend, changes how it delivers these methods or their bodies: re-run the measured premise.
