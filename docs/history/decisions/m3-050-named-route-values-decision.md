# Named route values decision (M3-050)

> **Current.** Now described in [route-values reference, "Named route values (`Param`)"](../../reference/route-values.md#named-route-values-param) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

**Question and what settles it.** Pull request #94. Under [M3-022](m3-022-several-route-values-decision.md) two route values bind by position, so `/users/{uid}/posts/{pid}` with `def f(pid: Int, uid: Int)` compiles and answers with right-looking wrong data, which an outside review judged worse than Flare's runtime 400 for a misspelled name. Can a registration compare route values with the literal's placeholder names at compile time on Mojo 1.1.0, through what public spelling, and should every two-value handler have to use it? Settled by probes on Mojo 1.1.0 (whether parameter names can be reflected, whether a name carried as a type parameter reaches the registration rules and a `comptime assert` message, whether the slot conversion reaches the value type without a second rebind) and by weighing what a required name costs every handler and test.

**Choice and why.** `Param[name, T]` is a public, opt-in route value that names its placeholder (`uid: Param["uid", Int]`, read as `uid.value`); the name has to be in the type because function parameter names cannot be reflected (`reflect_fn` offers `display_name()` and `linkage_name()` only). `_kind` gives exactly `Param` the kind of its `T`, and `_slot` converts `T` as a bare slot and wraps it; binding stays positional. After the family rules accept a shape, `_rule` checks that of two route values both or neither are `Param`s (one of each would leave unclear how much is checked) and that each `Param`'s name equals the placeholder at its position. A lone value may be either. The guarantee is that the name written in the annotation matches the placeholder it binds; the variable's own name is not compared, so `pid: Param["uid", Int], uid: Param["pid", Int]` compiles and `pid` holds the user's id, and two bare values keep M3-022's swap caveat. Bare handlers stay valid because Muntin's value is that a plain Mojo function is a handler: requiring `Param` would break every existing two-value handler, cost `.value` in every handler body, and, through a Mojo 1.1.0 crash (`TestSuite.discover_tests` beside any function with a `StaticString`-parameterized type, `tests/named_values_api_fail/discover_tests_crash.mojo`), keep such handlers out of every test module that discovers its tests. The owner judged that cost larger than the added guarantee for now. Importing a `Param` handler does not crash, so `tests/test_named_values.mojo` discovers its tests and imports its handlers from `tests/named_value_handlers.mojo`; that was chosen over listing the tests by hand, which needed a checker script of its own (pull request #94). The existing routing and decoding paths are unchanged; the run-time cost of building the wrapper is unmeasured.

**Rejected.**
- `Param` required for two route values: breaks every bare two-value handler, adds `.value` to every handler body and moves every such handler out of the test module that exercises it, a larger cost than the added guarantee while the crash stands.
- Requiring names only for two values of one type: an `Int` and a `String` swapped still bind whenever the text parses, and the rule would depend on types the reader must compare.
- Allowing one `Param` beside a bare value: how much is checked would differ per parameter and be hard to explain.
- Binding by name in any parameter order: a second binding rule where a compile error naming the fix suffices.
- A named struct carrier per route (M3-022 candidate D): `std.reflection` still has no constructor.

**Revisit when:**
- Mojo reflects function parameter names: compare the parameters' own names with the literal, which closes the variable-name gap (`test_variable_names_are_not_compared` then fails) and may make `Param` unnecessary;
- requiring `Param` is proposed again: only once the `discover_tests` crash is fixed (`discover_tests_crash.mojo` builds), applications show bare two-value swaps to be a real problem, and a DX comparison including the spelling and `.value` still favors it; a breaking change then comes with its migration steps;
- the `discover_tests` crash is fixed: the handlers in `tests/named_value_handlers.mojo` may move back into `tests/test_named_values.mojo`;
- a third route value or another value type is proposed: it may be a `Param` under the same rules.
