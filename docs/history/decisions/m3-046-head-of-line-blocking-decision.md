# Head-of-line blocking decision (M3-046)

> **Current.** Now described in [serving reference, "One request at a time"](../../reference/serving.md#one-request-at-a-time), [serving reference, "Workers"](../../reference/serving.md#workers) and [ARCHITECTURE, "Revisit index"](../../ARCHITECTURE.md#revisit-index).
> Changed in part since:
> - [M3-047](m3-047-server-idle-timeout-decision.md): made idle_timeout_ms an application setting, so the drops pinned here can be turned into waits (the guidance changed).
> - [M3-049](m3-049-multi-worker-serving-decision.md): added `serve[make](workers=n)`, one App per worker, replacing this record's explicit deferral of more serving threads.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-046, [pull request #84](https://github.com/sano-suguru/muntin/pull/84); `src/muntin` unchanged). [M3-032](m3-032-serving-entrypoint-decision.md) chose one reactor thread for `Server.serve` and left a revisit condition: "an application needs more than one serving thread: revisit whether `App.handle` may run concurrently ([M3-001](m3-001-application-state-decision.md) interior mutability, [M3-008](m3-008-json-codec-decision.md) the JSON cap) and whether `Server` takes a worker count". This record measures what the one thread costs on the wire, and decides whether Muntin can change it now. The question, candidates, criteria and pass conditions below were written before the wire measurements.

**Why now.** `Server.serve` calls `App.handle` synchronously on Flare's one reactor thread, so one slow handler may hold every other request in the process. That is the largest remaining property of `Server` that applications cannot see from its API, and M3-045's stop tests already observed one symptom (a connection queued while a handler held the reactor was not accepted).

**Question.**
1. Over HTTP/1.1, while a handler on connection A has not returned, is a light `GET` on another connection B answered, or even accepted?
2. Over prior-knowledge h2c, while stream 1's handler has not returned, is stream 3 on the same connection answered? And a stream on another h2c connection?
3. Is the cause Muntin's code, Flare's single reactor, or the handler being synchronous: does Flare's own `HttpServer` with a Flare handler (no Muntin) behave the same?
4. With more workers, what improves: progress across connections, progress of streams within one h2c connection, or both? The two are not to be conflated.
5. Can any of it be had while `App.handle`, middleware, `State`, the borrowed `App` and `_BorrowedHandler`'s non-`Copyable` guard keep their contracts, with the ownership, data races and lifetimes explained rather than asserted?

**What settles it:**
- the serving path in Muntin's adapter and Flare v0.12.0's single- and multi-worker reactors, read in code (the dispatch of a request to the handler, the multi-worker overload's signature, how connections and h2c streams are assigned to workers, any API that runs a handler off the reactor and posts its answer back);
- wire tests in real child processes, with a handler held by a pipe (M3-045's `held`), so that whether a second request progresses before the first is released is decided by the order of events, not by sleeps or CPU speed: HTTP/1.1 and h2c separately, the h2c client acknowledging the server's SETTINGS; each child reaped within a bound (a child that outlives it is killed and the test fails);
- the same tests against Flare's own `HttpServer` with a Flare-only handler, single-worker and, where it builds, multi-worker (the second only as evidence about Flare, never as a Muntin path);
- for any candidate that would call `App.handle` from more than one thread: an account of every piece of state it reaches (the `App`'s routes and erased handlers, `_Shared`'s counts, `State[S]` values, middleware, the JSON cap's memory bound) and whether Mojo 1.1.0 can make the compiler reject a state type that is unsafe to share.

**Candidates.**
- A, Flare's multi-worker `serve`: a `Copyable` handler sharing the borrowed `App` across worker threads, a worker count on `Server`. Only if the safety account above holds.
- B, separate the reactor from handler execution: the reactor hands each request to other threads and the answer goes back to the reactor that owns the connection. Only if Flare v0.12.0 offers the hand-off and the way back.
- C, keep one reactor per `Server` and recommend several OS processes (each binding its own `Server`), stating what improves and what remains.
- D, decision only: if no safe implementation exists, pin the current blocking with tests and record what Flare or Mojo would need.

**Comparison criteria:** progress of other connections while a handler blocks; progress of other streams of the same h2c connection; CPU use across cores; the ownership safety of `App` and `State` (who may touch them from which thread, and what the compiler checks); compatibility of `Server.bind`/`serve`, M3-044's receive limit and M3-045's stop and one-`serve`-per-process claim; the code added; dependence on Flare internals; testability on Linux x86-64 and macOS arm64.

**Pass conditions** for an implementing candidate (each on the wire, on both CI systems): a test that fails before the change and passes after, for each protocol the change claims to improve; a test that pins what it does not improve; the safety account above with each claim backed by a test, a fixture or the compiler; scratch mutations that turn the new tests red; M3-044's and M3-045's tests and the serving fixtures unchanged and passing. If no candidate meets them, D.

**Read in code** (Flare v0.12.0, the pinned commit):
- Single worker: the loop (`flare/http/_unified_reactor_impl.mojo`, `_run_unified_loop_for_fd`) polls, then advances the idle-timer wheel (`_advance_timer_wheel_unified`), then handles the poll's events one at a time. HTTP/1.1 calls `handler.serve(req^)` inline in `ConnHandle.on_readable` (`flare/http/_reactor/conn_handle.mojo`); h2c calls it inline, once per completed stream, in a loop in `Http2ConnHandle.on_readable` (`flare/http/_h2_conn_handle.mojo`). While a handler runs, the thread accepts, reads, writes and times out nothing. Flare's `docs/concurrency.md`: "flare uses a thread-per-core reactor with **synchronous** handlers … `def serve(req) raises -> Response` runs on a pthread worker and *blocks that worker until it returns*."
- Multi-worker (`serve[H: Handler & Copyable](mut self, var handler: H, num_workers: Int, pin_cores: Bool = True)`, `flare/http/server.mojo`): closes the bound listener and starts a `Scheduler` whose workers each get `handler.copy()` and their own reactor, and, by default, their own `SO_REUSEPORT` listener (`FLARE_REUSEPORT_WORKERS=0`: one shared listener). A connection stays on the worker that accepted it for its whole life (`docs/concurrency.md`: "Connections are owned by one reactor worker for their entire lifetime"), so all streams of an h2c connection go to one worker. Each worker still runs its handler synchronously.
- `HttpServer.drain` closes `self._listener` and then sets the stop flag. On the multi-worker path that listener was already closed by `_serve_multicore`, and the per-worker listeners belong to the `Scheduler`, which `drain` does not reach (`Scheduler.drain` exists, but `HttpServer` never calls it). So M3-045's stop, run on the multi-worker path, would keep accepting new connections for the whole window (read in code, not measured).
- Off-reactor execution: no handler trait completes later. `block_in_pool` runs a function on a new pthread but its caller blocks until `pthread_join` (its docstring: releasing the reactor "would need either Mojo async or a new 'park this connection' reactor state"). The one way to get a completion back into a reactor, `StreamConn.attach_upstream(fd)` with `serve_streaming`, is a different handler trait (`StreamHandler`), HTTP/1.x only and without TLS. `Reactor.wakeup()` exists but nothing calls it.
- Thread safety: Flare's `docs/concurrency.md` says the pinned Mojo has "no compiler-checked notion of state that is safe to share across threads (no `Send` / `Sync` traits)", quoting Modular's forum, and that the standard library's `String`/`List`/`Dict` reference counts are not safe to share. Muntin did not verify either claim; the decision below does not rest on them.

**Measured** (Mojo 1.1.0, Flare v0.12.0, Linux x86-64 container with 4 CPUs (macOS arm64, the pull request's CI runner: every observation in the table identical, resets included; the first macOS run failed four h2c cases because macOS `setsockopt` rejects a receive timeout on a connection the server has reset with `EINVAL`, so the client now sets its timeouts while the connection is open); the retained tests in `adapters/flare/test_server.mojo`, "Head-of-line blocking (M3-046)", three runs each, all alike). Each test holds request A's handler on a pipe (M3-045's `held`, which also writes `a` to the pipe when released), sends a light request whose handler writes `b` to the same pipe, waits `HOLD_PROBE_MS` (1 s) for its answer, releases A, reads every answer, ends the child within a bound (`Server`: SIGTERM, exit 0 required; Flare's server: SIGKILL), and only then reads the pipe to its end. The pipe's order is what the tests assert about progress; it does not depend on timing. `kind` is `Server` with `blocking_app`; Flare's own `HttpServer` serving `_FlareHold` (the same routes with no Muntin code) with its default configuration; and the same with `idle_timeout_ms` 60 s ("patient"), to separate two effects:

| Case | While A is held (1 s) | After A is released | Handler order |
|---|---|---|---|
| HTTP/1.1, keep-alive connection answered before the hold, request sent during it | not answered | `Server` and Flare: closed with its request unread (reset), no answer; patient: answered | `Server`, Flare `ab` (its handler never ran); patient `abb` |
| HTTP/1.1, new connection opened during the hold | not answered (queued by the system; Flare does not call `accept` while a handler runs, read in code) | answered | as above |
| HTTP/1.1, A's own connection (keep-alive) | — | A answered, then the connection closed; patient: not checked | — |
| h2c, stream 3 on A's connection (SETTINGS acknowledged before the hold) | not answered | A's stream 1 answered, then the connection reset with stream 3 unread; patient: stream 3 answered | `Server`, Flare `a`; patient `ab` |
| h2c, stream 1 on another connection set up before the hold | not answered | that connection reset with its stream unread; patient: answered | `Server`, Flare `a`; patient `ab` |

- **Two effects.** (1) Serial dispatch: no other handler ran before A's returned, on any connection or stream, in every case and every kind. (2) Flare's idle timer, read in code: the loop advances the timer wheel once per iteration, after the poll and before the events, and `TimerWheel.schedule` arms a timer relative to the wheel's last tick (`flare/runtime/timer_wheel.mojo`), which a long handler leaves stale. So every idle timer armed before the handler or during the same iteration (A's own connection after its answer, any connection handled later in that batch) is due within `idle_timeout_ms` (500 ms by default; Muntin does not set it) of that stale tick, and the next iteration's advance fires it before reading the events that arrived meanwhile: the connection is closed although its request has arrived. What decides a drop is a connection's idle time before the handler plus the handler's run time, not the run time alone (a 100 ms handler can drop a connection already idle for 450 ms; read in code, not measured); a connection with a partly received request or awaiting its h2c preface has the same timer. With a hold of 1 s, the tests show the drops: requests on already open keep-alive and h2c connections get no answer, and A's own keep-alive connection is closed right after its answer; only connections still queued by the system are answered afterwards. With the patient configuration every request was answered after A.
- **Cause.** Flare alone behaves exactly as `Server` does in every case, so neither is Muntin's code: it is Flare's single reactor running a synchronous handler, plus its timer order.
- **More workers** (scratch, not retained: the Flare-only handler declared `Copyable`, `serve(..., num_workers=N, pin_cores=False)`, patient configuration, Linux only). With one handler held: of 16 new HTTP/1.1 connections, 7 to 9 were answered during the hold with 2 workers, 11 or 12 with 4 (three runs): the kernel's `SO_REUSEPORT` hash still sends some connections to the held worker, where they wait. Of 8 new h2c connections, 7 and 8 (two runs) completed their SETTINGS and a stream with 4 workers. Stream 3 on the held stream's own connection was not answered during the hold, as with one worker, and was answered after it. More workers improve progress across connections, probabilistically by the hash; they do nothing for streams of one h2c connection.
- **Several processes** (scratch, not retained, Linux only): `Server.bind` once, then two forked processes each calling `server.serve(app)` on the shared listener. With one process's handler held, 16 of 16 new HTTP/1.1 connections were answered during the hold (three runs): the held process does not poll, so the other accepts every connection. Not measured on macOS; not a supported form today (below).

**The safety account for running `App.handle` on several threads (A and B).**
- What `App.handle` reaches: the `App`'s route list and erased handlers (read, not changed, by `handle`), per-request values (the request copy, decoded route values, a JSON tape), `_Shared`'s count (atomic), and the application's `State[S]` values, borrowed with no count change (M3-001).
- `State[S]` is read-only only through `state[]`, and shallowly: "a type `S` with interior mutability … changes under its own rules, and Muntin does not synchronize it" (M3-001). Applications may have such types today (M3-001's spike counted calls through an `ArcPointer[Int]` in `Users.calls`); they are single-threaded because `App.handle` is never called concurrently, which M3-001 and `docs/ARCHITECTURE.md` state as the reason they are safe. Running `handle` on several threads could turn those whose interior mutability is not synchronized (atomics or a lock would be safe) into data races, without a compile error or a change to the application's code. Muntin has no way today to require `S` to be safe to share: no marker trait on `State`, and none that Muntin knows the compiler checks. Requiring one would change `State`'s contract (M3-001, M3-004), which is a decision of its own, not this item's. Workers as an opt-in with a documented thread-safety obligation on the application is rejected for the same reason: it would be an unchecked rule in a framework whose point is checked ones.
- Middleware is compile-time functions with no state of their own, but middleware reads what handlers read. The JSON cap bounds memory per parse, "one per `App` today" (M3-008): N workers multiply it.
- The borrowed `App`'s lifetime would hold (Flare's multi-worker `serve` joins its workers before it returns, and `serve` borrows the `App` for that call), but that is the only part of the account that holds.

**Selected: D.** `Server` keeps one reactor and calls `App.handle` on one thread. The blocking is now pinned on the wire (`adapters/flare/test_server.mojo`: `Server` over HTTP/1.1 and h2c, and the same cases on Flare alone, default and patient) and documented (`docs/DX.md` section 1, `docs/ARCHITECTURE.md`). `src/muntin`, the adapter, `Server`'s API, M3-044's limit, M3-045's stop and claim, and the `_BorrowedHandler` guard are unchanged.

- **What applications are told** (`docs/DX.md` section 1): one request's handler holds every other request of the process; a long handler can make Flare's idle timer close open keep-alive and h2c connections that waited meanwhile, with their requests unanswered (reproduced with a 1 s hold; the general rule is read in Flare's code): it can lose requests rather than only delay them. Handlers must therefore be short. Requests that must make progress while one is slow are served by several processes, each with its own `Server`, behind a load balancer (each process binds its own port). That improves progress across processes only: within one process, and for every stream of one h2c connection, it is as above.
- **Why not the shared-listener form as supported now** (a candidate for a later serving-lifecycle item, `docs/SPEC.md`): it was measured once, on Linux, and its stop has different semantics (a process that stops closes only its copy of the listener, so new connections keep being accepted by the others; one stop then refuses nothing on that address). Making it supported is a serving-lifecycle item with its own tests, not part of this decision.

**What Flare would need** (upstream, for A or B to become possible):
- multi-worker `drain` that closes every worker's listener and drains every worker (`Scheduler.drain` reached from `HttpServer.drain`), so M3-045's contract can hold with workers;
- a handler completion that does not hold the reactor, for HTTP/1.1 and h2c: park a connection or stream, run the handler elsewhere, post the response back (Flare's `block_in_pool` names this as a follow-up);
- dispatch of h2c streams that does not run one connection's streams in sequence on one thread, for streams of one connection to progress at all;
- the idle timer not closing a connection whose request has already arrived: advance the wheel's clock after a handler returns (before arming timers) and handle readable events before expiring timers; re-arming on readiness alone would not do, since the timers are armed from the stale tick. That would make a long handler cost delay instead of lost requests even with one worker.

**What Mojo or Muntin would need:** a way for Muntin to require at compile time that a `State` value (and anything else a handler shares) is safe to use from several threads, or an accepted decision that changes `State`'s contract to such a bound. Until then no concurrent `App.handle` can be shown safe.

**By kind (M2-016): not an M2 reopen.** Nothing `App.handle` answers, no API and no diagnostic changes; tests and documentation of the current behavior only.

**Cost.** Throughput and latency under slow handlers stay bounded by one thread per process, and a handler longer than 500 ms drops waiting keep-alive and h2c requests. The new tests take about 14 s of the `Server` suite (each holds a handler for 1 s and stops its child).

**Revisit when:**
- Flare's multi-worker `drain` stops new connections on every worker, or Flare offers a deferred handler completion for HTTP/1.1 and h2c: revisit A or B, still subject to the safety account;
- Mojo gains a compiler-checked notion of thread-safe sharing, or a decision gives `State` a thread-safety bound: revisit the safety account;
- the blocking tests' observations change (a light request answered during the hold, or a waiting keep-alive or h2c request answered after a hold longer than the idle timeout): Flare changed its dispatch or timer order; revisit `docs/DX.md` section 1 and this record;
- `Server` gains backend configuration ([M3-032](m3-032-serving-entrypoint-decision.md)): an `idle_timeout_ms` would let an application trade the dropped requests for longer waits; revisit the guidance;
- an application asks for several processes serving one address as a supported form: a serving-lifecycle item (its stop semantics, macOS, tests).

**Next action: explicit deferral.** No production slice follows: the revisit conditions above name what would make a concurrent `Server` decidable. Revisited by [M3-049](m3-049-multi-worker-serving-decision.md): several workers, each with its own `App`, so no `App` or `State` value is shared and no thread-safety bound is needed.
