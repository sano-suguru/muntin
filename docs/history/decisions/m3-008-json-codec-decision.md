# JSON codec decision (M3-008)

> **Current.** Now described in [ARCHITECTURE, "JSON"](../../ARCHITECTURE.md#json), [bodies reference, "JSON (`Json[T]`)"](../../reference/bodies.md#json-jsont) and [responses reference, "JSON results"](../../reference/responses.md#json-results).
> Changed in part since:
> - [M3-028](m3-028-json-response-status-decision.md): a Json[T] result can choose its status (Json(value, status=)); the convert-then-edit override is no longer the only way.
> - [M3-030](m3-030-method-not-allowed-decision.md): the JSON route order now starts with 404, or 405 with Allow.
> - [M3-040](m3-040-binary-request-and-response-bodies-decision.md): Request.body is bytes; the body slot rejects invalid UTF-8 (400) before from_body, so the codec never sees a replaced byte.
> - [M3-078](m3-078-json-float-reading-decision.md): float() is Muntin's own correctly rounded conversion, of any length; atof's 1-ulp errors and long-literal 400s are gone.
> - [M3-082](m3-082-derived-json-codecs-decision.md): derived codecs are decided (`JsonFields`): `List[<struct>]` is reachable through `Iterable`'s element type, an unsupported field is refused at registration, and decoding builds field by field as route-value records do; built by M3-083.
> - [M3-089](m3-089-text-and-json-body-limits-decision.md) (not built yet, M3-090): the 1 MiB cap becomes `Json[T, limit=n]`'s default, chosen per route.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-008; production and adapters are unchanged in it; production since M3-009, "JSON in production (M3-009)" below). It decides Muntin's first JSON API, who owns the codec, the request and response `Content-Type` rules, where JSON failures go in the error model, and the production slice that follows.

**Selected: A, a Muntin-owned `Json[T]` wrapper over application `FromJson`/`ToJson` traits, with a Muntin-owned codec: a strict parser for the RFC 8259 grammar with Muntin-specific duplicate-name, depth, size and numeric limits, and a writer.** `Json[T]` is a body through the existing `FromBody` and a result through the existing `ToResponse`, so no `App` overload, adapter shape or storage changes for it to register.

```mojo
trait FromJson(Deinitable, Movable):
    @staticmethod
    def from_json(value: JsonValue) raises -> Self       # raise -> 400

trait ToJson:
    def write_json(self, mut out: JsonWriter) raises     # raise -> fixed 500 (serialization failure)

struct Json[T: Movable & Deinitable](
    Deinitable, Movable,
    FromBody where conforms_to(T, FromJson),
    ToResponse where conforms_to(T, ToJson),
    _JsonBody,                                            # private marker: the Content-Type step
):
    var value: T
    def __init__(out self, var value: T)
    def take(deinit self) -> T                            # body^.take(): moves the value out

struct JsonValue(Copyable, Movable, Sized):               # a read-only position in a parsed document; made only by the parser and accessors
    def is_null(self) -> Bool
    def bool(self) raises -> Bool
    def int(self) raises -> Int                           # integer literal (no fraction/exponent) that fits Int
    def float(self) raises -> Float64                     # a number literal through Mojo 1.1.0 `atof` (finite; see Parsing)
    def string(self) raises -> String
    def __len__(self) -> Int                              # elements or members; 0 for scalars
    def __getitem__(self, index: Int) raises -> JsonValue # array element, constant time
    def __getitem__(self, name: String) raises -> JsonValue  # object member; raises when absent
    def get(self, name: String) raises -> Optional[JsonValue]  # None when absent; null is a value

struct JsonWriter(Movable):
    def begin_object / end_object / begin_array / end_array (mut self) raises
    def name(mut self, name: String) raises               # a name repeated in one object raises at end_object
    def null / bool / int / float / string (mut self, ...) raises   # float raises on NaN/infinity
    def value[T: ToJson](mut self, value: T) raises       # a nested application value
```

```mojo
def create_user(body: Json[CreateUser]) -> Json[User]:   # or `var body` and body^.take()
    return Json(User(1, body.value.name))

app.post["/users"](create_user)                          # existing overload; unchanged syntax
```

- **Opt-in is explicit, per type.** The application declares `FromJson` and/or `ToJson` on its own types and maps fields itself; Muntin never names them. `Json[T]` conforms to `FromBody` only when `T: FromJson` and to `ToResponse` only when `T: ToJson` (documented conditional conformance with `where`-gated methods, Mojo manual "Conditional trait conformance"). A wrong `T` fails at the registration with the existing messages (`json_fail/body_without_from_json`: the production `FromBody` assert; `result_without_to_json`: `argument type 'Json[In]' does not conform to trait 'ToResponse'`).
- **Ownership.** `Json` moves its value in (`Json(v^)`) and out (`body^.take()`, `deinit self`). A field cannot be moved out of the middle of a `Json` on Mojo 1.1.0 (`json_fail/move_value_out_of_json`), so `take` exists. Move-only `T` works as body and as result (`test_move_only_body_and_result`). A handler may borrow (`body: Json[T]`, read `body.value`) or own (`var body`).
- **Parsed document.** Mojo 1.1.0 rejects a struct that holds a list of itself (`json_fail/recursive_value_tree`), so a document is a flat tape and `JsonValue` is a position in it. The tape owns no text: a node (28 bytes) holds its kind, flags and byte spans into the document's one copy of the body (a number's literal, a string's contents and a member's name, escapes decoded on access), and each container's child node indices sit contiguously in one table, so `value[i]` is constant time and an index loop is linear. Duplicate member names are found by sorting each object's decoded names and comparing neighbours (O(m log m) per object and deterministic; a hash set would be linear only for a seed an attacker cannot predict, and Mojo 1.1.0's `String` hash is the same in every run, found by the review). Parsing is otherwise linear in the body (`test_parsing_and_access_are_linear`: an 80k-member object and a 200k-element array read by index, both under the 1 MiB cap; the first spike's list scans took 1.1 s at 40k members and 8.8 s for an 80k-element index loop, found by the review). The tape is held in M3-004's sealed `_Shared` box: copies of a `JsonValue` share it, and no copy can clear or replace it on an ordinary path (`json_fail/second_handle_mutates_document`; with `ArcPointer`, `v2._doc[].nodes.clear()` compiles and empties the tape another position indexes, measured). Accessors return values, never references into the tape. `JsonValue`'s initializer takes keyword-only internal arguments (`_doc=`, `_at=`): positions come from the parser and accessors, and an out-of-range position traps on the list bounds check rather than reading other memory. This adds no unsafe code outside `_handler_storage.mojo` (`check_unsafe.sh` already allows importing `_Shared`).
- **No `rebind`, no reflection, no `__extension` in the selected codec.** It uses safe std types, `conforms_to` and conditional conformance only.

**Codec source.** Mojo 1.1.0's standard library has no JSON module (`import std.json`: `unable to locate module 'json'`). The only JSON package on the pinned lock is `json` vendored inside Flare's conda package (`lib/mojo/json`, with `lib/libsimdjson_wrapper.so`), so it exists only in the `flare` environment (`json_fail/flare_json_package_in_default_env`), its reflection serde relies on `__extension` (undocumented retroactive conformance, never a supported opt-in here) and `MaybeUninit`, and depending on it would make core depend on the backend's package (A2). Flare's own JSON extractors (`flare/http/extract.mojo`) are not used either. So Muntin owns a small codec: no new dependency, and it is replaceable later behind `FromJson`/`ToJson`, whose requirements name only Muntin types.

**Parsing (the RFC 8259 grammar, strictly, with Muntin's limits; the slice's supported set).** RFC 8259 recommends unique member names without making duplicates a grammar error, and sets no depth or size limit; rejecting duplicates, nesting past 64 and bodies over 1 MiB, and the numeric gaps below, are Muntin's profile, not RFC requirements.
- Accepted: one JSON text of any kind (objects, arrays, strings, numbers, `true`, `false`, `null`), with SP/HTAB/LF/CR whitespace; string escapes `\" \\ \/ \b \f \n \r \t \uXXXX`, surrogate pairs combined; nesting up to 64 arrays/objects (`MAX_DEPTH`); unknown object members are kept and ignored unless `from_json` reads them.
- Rejected (400 through `from_body`): an empty body, trailing content or a second text, comments, trailing commas, single quotes, unquoted names, leading zeros, `+`, `.5`, `1.`, `NaN`/`Infinity`, a byte order mark, unescaped control bytes in strings, bad escapes, lone surrogates, duplicate member names (parser differentials), nesting past 64.
- Field access: a missing member, a wrong kind, `int()` on `1.5`/`1e2` or beyond `Int`, `float()` overflowing to infinity all raise, so `from_json` raises and the request is 400. Absent and `null` are told apart (`get` -> `None` vs `is_null()`), which is how an `Optional` field is read.
- Numbers through Mojo 1.1.0: `atof` is lenient (it accepts `1.`, `.5`, `01`, `+1`, ` 1`, `nan`, `inf`), so the parser validates the RFC grammar itself. `atof` raises on long literals, by length and magnitude rather than significant digits (`123456789012345678901234`, `100000000000000000000000`, `0.000000000000000000000000000001`), so `float()` answers 400 for those valid numbers. And `atof` is not always correctly rounded: shortest round-trip doubles as JavaScript and Python clients send them (`-2.7546748226290886e+20`, 2 of 2997 random doubles in the review) and long integer literals read as floats (`123456789012345678`; 447 of 2000 16–19-digit integers in the review) come back 1 ulp off, silently. `int()` is exact. All are pinned (`test_number_limits_on_mojo_1_1_0`, `test_float_rounding_gaps_on_mojo_1_1_0`); the decision accepts them as Mojo 1.1.0 limits of `float()` rather than ship a Muntin float parser, and an application that needs exact values reads integers with `int()`.
- Invalid UTF-8 is not representable in `Request.body` (a `String`); through Flare it arrives replaced by U+FFFD (the M2-016 fact, measured again in `compat/flare/json/json_loopback_probe.mojo`), so the codec cannot reject it.

**Writing.** `JsonWriter` emits separators itself and raises on structural misuse (a value without a name in an object, a name outside one, a name repeated in one object, which Muntin's own parser would reject (found at `end_object` by sorting the object's names, as the parser does: names may come from request data, so the writer depends on no predictable hash), an unmatched close, a second top-level value, an unfinished document) and on NaN or infinity, which JSON cannot represent (`String(Float64)` prints `nan`/`inf`). Strings escape `"`, `\` and every byte below 0x20 (`\n`, `\r`, `\t`, else `\u00XX`); other bytes are written as the UTF-8 they are. Finite floats use `String(Float64)`, which is valid JSON (`1e+16`, `1e-07`, `5e-324`, `-150.0`) but, on Mojo 1.1.0, not always the text of the same double: bits `0xc360b3b71251310b` print as `-3.760958796054742e+16`, which reads back 1 ulp off (7 of 6999 in the review; pinned).

**Content-Type.**
- Responses: `Json[T].to_response()` answers 200 with exactly one field, `Content-Type: application/json` (no `charset`: RFC 8259 defines none). `String` results and `Response.text` still add no field (`test_text_results_keep_no_default_fields`), so no existing wire byte changes. Override: the application converts and edits, `var r = Json(v^).to_response(); r.status = 201; r.headers.set("Content-Type", "application/problem+json")`, returning `Response`; a `set` after the conversion wins and Muntin never re-adds or checks the field. The adapter's outbound rule does not touch `Content-Type` (measured over loopback).
- Requests: a `Json[T]` body requires exactly one `Content-Type` field whose media type, the text before any `;` with SP/HTAB trimmed, is `application/json`, compared ASCII case-insensitively byte by byte (Unicode case folding is not used: `applİcation/json` is 415). Parameters are not interpreted (`application/json; charset=utf-8` is accepted; the body is read as UTF-8 per RFC 8259 §8.1). A missing field, two fields, `text/plain`, `application/x-www-form-urlencoded`, `application/problem+json` and other `+json` types are 415 `Unsupported Media Type` (body `Unsupported Media Type`, no fields), before JSON parsing and before the handler. (The body has already been received: the backend built `Request.body` before `App.handle`; the step avoids parsing it, not receiving it.) Why require it: browsers send cross-site "simple" requests without a preflight with `text/plain`, a form type, or no `Content-Type` at all (a `Blob` body with an empty type), the known CSRF path into JSON endpoints that accept any type; and starting strict is reversible, since accepting `+json` or a missing field later is additive while tightening later breaks deployed clients. Why 415 rather than 400: it is the status for this condition (RFC 9110 §15.5.16), and it keeps "the body is not valid JSON" (400) distinguishable. Other bodies are unchanged: an application `FromBody` type still sees no headers and requires no `Content-Type`.
- `FromBody.from_body(String)` cannot see headers, so the step is the body adapters', keyed on the private marker `_JsonBody` (as M3-006 keys the `State` guard on `_InjectedState`). Order on a JSON body route: 404 → query value 400 (`App.handle`) → route value 400 (adapter) → 415 (adapter) → 413 (adapter, body cap below) → JSON 400 (`from_body`: parse or `from_json`) → handler → result conversion. Measured on the spike's mirror (`model_post`, `model_post_int`; `test_selected_order_on_the_adapter_mirror`, `test_body_size_cap`): a malformed body with a wrong type is 415, a bad `Int` segment with a wrong type is 400, an oversized body is 415 with a wrong type, 400 with a bad `Int` segment and 413 otherwise.
- M2 stays closed: the M2 contract's "a request failure ... `from_body` raise is 400" is about application-defined `B: FromBody`, and every such route keeps its 400/404/500 boundaries; 415 and 413 exist only for `Json[T]`, a new Muntin-owned body type.
- M3-005 is unchanged: `Headers` validation, the adapter's inbound rule and its outbound filtering apply to `Content-Type` as to any field (the codec sets it with `Headers.set`, and `Content-Type` is not an omitted field).

**Body cap: a fixed 1 MiB for JSON request bodies, 413 above it.**
- `MAX_BODY_BYTES = 1_048_576`, compared with the body's byte length. A typed JSON route answers a larger body 413 `Content Too Large` (body `Content Too Large`, no fields; RFC 9110 §15.5.14) after the 415 step and before `from_body`, so nothing is parsed. Only `Json[T]` bodies are capped; application `FromBody` types and raw handlers keep whatever the backend delivers.
- The parser enforces the same cap: `Json[T].from_body` raises on a larger body wherever it is called, so a raw handler that decodes with it gets an error (its own error model applies), never an unbounded parse. Through `from_body` alone the answer would be 400, because `FromBody`'s raise is the request-side 400; that is why typed routes need the adapter step for 413 (`test_body_size_cap`: production `App` without the step answers 400).
- Why a cap in Muntin: the codec is reachable without any backend (`App.handle`, `TestClient`, `Json[T].from_body`), and a parse costs up to about 37 bytes of memory per body byte. At the cap the measured worst case (`[0,0,...]`, 1 MiB) adds 28 MB of peak memory and parses in 20 ms; a 1 MiB array of typical records adds 4.8 MB. `App.handle` is never called concurrently today ("Application state decision (M3-001)", Concurrency: Flare's multi-worker `serve` needs a `Copyable` handler and `App` is move-only), so the current Flare use never invokes one `App` concurrently. The cap bounds each active JSON parse at about 30 MB; total use is that times the number of parses running at once (one per `App` today, more if a process runs several `App`s or a backend calls `handle` concurrently).
- Why fixed: a setting (per `App` or per route) is new public API with its own lifetime and binding questions, and adding one later is additive; lowering a default later would break clients, so the first value is conservative. 1 MiB sits between Express's 100 kB `json()` default and axum's 2 MB default body limit. Backend limits still apply first (Flare's default `max_body_size` is 10 MB).
- Exactly `MAX_BODY_BYTES` is accepted and one more byte is 413 (`test_body_size_cap`).

**Errors.** Malformed JSON and `from_json` raises are request failures: 400 before the handler, handler not called (`test_malformed_json_is_400_before_the_handler`, 34 texts; `test_field_errors_are_400_and_extra_members_are_ignored`). Handler raises are unchanged: `ToErrorResponse` or the fixed 500. A response-serialization failure (`write_json` raises, NaN, infinity, an unbalanced writer) happens after the handler returned, inside the non-raising `ToResponse.to_response`; `Json` answers it itself with the fixed 500's bytes (`Internal Server Error`, no `Content-Type`), and the handler's `ToErrorResponse` is not called (`test_serialization_failure_is_not_a_handler_error`: a handler declared `raises AppError` whose conversion is 418 still gets 500, and the conversion counter stays 0). It is the same answer as an unconverted handler error but a different path: it is not a handler error, and no partial body is sent.

**Allocation and copies visible to Muntin.** Request: `App.handle` already copies `request.body` into the adapter's arguments. Parsing walks the bytes once and builds one tape (a node list and a child table, no per-value strings; one list of decoded names per object while parsing) in one `_Shared` (two allocations, as for `State`); the spike keeps one more copy of the body in the document, which production can take by move from the adapter argument. `JsonValue` copies add a reference, not a tape copy (`test_json_value_copies_share_the_document`); `string()` decodes and copies out. Measured peak memory over a no-parse baseline: a 4.5 MB array of 50,000 typical records adds 22 MB (about 5x the body, the body copy included), and the worst case, a 5 MB `[0,0,...]` of one-byte values, adds 184 MB (about 37x; the review measured 482 MB with the first spike's string-owning nodes). With the 1 MiB cap above, one parse adds at most about 28 MB (measured). Response: one `String` grown by the writer plus small stacks and one name list per open object, then one header field (two `String`s); the body moves into the `Response`.

**Overload budget.** None added: `get` and `post` keep ten overloads each, and no existing diagnostic changes (the first slice adds a `_Route` field and an adapter step, no signature). Every typed shape takes `Json[T]` where it takes a `FromBody` body or a `ToResponse` result, stateful shapes included (`test_production_app_accepts_json_through_existing_overloads`).

**Revisit when:**
- the Mojo manual documents a refining trait implementing its parent's requirement (or `json_known_gaps/refining_trait_default` stops building): re-measure B against A;
- `std` gains a JSON module, or a standalone JSON package for the default environment needs only documented features: weigh replacing the codec behind `FromJson`/`ToJson`;
- `std.reflection` gains a constructor, or reflection exposes a field type's parameters (or `__extension` is documented): a derived `from_json`, and a derived `write_json` covering `List[<struct>]`, become possible; a derived `write_json` for the fixed set is possible now, and needs a decision on its late diagnostics;

- Muntin gains a bytes body: the codec should reject invalid UTF-8 itself;
- applications need JSON bodies over 1 MiB, or a lower bound: decide a setting (per `App` or per route) for `MAX_BODY_BYTES`;
- `App.handle` becomes concurrent (a `Copyable` `App`, Flare multi-worker, another backend): memory for JSON parsing becomes the per-parse bound times the parses running at once; re-derive the cap;
- clients need `+json` media types or a missing `Content-Type`: an additive relaxation of the request rule;
- `TestClient` gains a way to send header fields (the slice adds none, below: `TestClient.post` reaches a JSON route as 415, an accepted DX cost of requiring `Content-Type`);
- `get`/`post` gain an 11th overload for any reason: re-run the note-budget measurement (this decision adds none).
