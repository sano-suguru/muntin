# Route conflict decision (M3-053)

> **Current.** Now described in [routing reference, "Route conflicts"](../../reference/routing.md#route-conflicts) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

**Question and what settles it.** Pull request #95. Routes are scanned in registration order and the first match never falls through, so `app.get["/users/{id}"](get_user)` registered before `app.get["/users/me"](me)` answers `GET /users/me` with 400 and `me` is unreachable (pinned in pull request #95 before the change). An outside review judged it inconsistent that handler types are checked at compile time while the meaning of overlapping routes rests on registration order, which moves when routes come from several modules. Which pairs of routes should Muntin refuse, when and how can it refuse them on Mojo 1.1.0, and what happens to applications that register them today? Settled by what the compiler can see at a registration call and by scanning the repository's own registrations.

**Choice and why.** Two routes of one method *overlap* when their paths have the same number of segments and, at every position, both have the same static text or a placeholder faces a placeholder or a non-empty static segment (a placeholder matches no empty segment); the query never takes part (it takes none in selection). Route `A` is *more specific* than `B` when they overlap, every placeholder of `A` is a placeholder in `B`, and they differ somewhere. Registering a route that overlaps an earlier route of the same method is refused unless the earlier one is more specific: identical paths (`/fw/{a}/{b}` twice, `/search` beside `/search?{q}`, placeholder names aside), a more general route first (`/users/{id}` then `/users/me`), and routes neither of which is more specific (`/a/{x}` and `/{y}/b`) all fail. Then every pair of routes a request matches is ordered most specific first, so the first match is always the most specific one: registration order can no longer change which route answers a request, only whether registration succeeds. The refusal is an `abort` at the registration call (before the first request when, as usual, every route is registered before the `App` serves; `App` does not forbid registering after `handle`), naming the method, both paths (without their query parts) and, for a more general route first, the fix (`register GET /users/me first`). It cannot be a compile error: each `app.get[...]` call sees only its own literal, and an `App`'s type does not record its routes, so a check across two registrations needs every registration to return a new `App` type, which `var app = App(); app.get[...](h)` cannot express (a `mut self` method cannot change `app`'s type). `get` and its siblings do not raise today; making them `raises` would change every registration and every function that builds an `App`. Selection, 404, 405 and `Allow` are unchanged; no override is offered (follow-up). The check runs once per registration on every worker's `App`; an index (`_RouteIndex`) avoids comparing routes without placeholders with each other, but every registration still compares with each earlier route with a placeholder, of any method, and pull request #95 records what it adds to building an `App`, a mixed table included.

**Rejected.**
- Static before parameter at dispatch (most specific wins whatever the order): silently changes the answer of applications that registered a general route first, and still needs a rule for routes neither of which is more specific.
- Refusing every overlap: forbids `/users/me` beside `/users/{id}` in any order until an override exists.
- A compile-time check across registrations (a route list in `App`'s type): every registration would rebind `app`, a public API rewrite out of proportion to the defect.
- `raises` registration: a signature change on every registration and builder function for a fault that is a programming error.
- An explicit priority or override mechanism now: deferred until an application needs two overlapping routes in the refused order.

**Revisit when:**
- an application needs overlapping routes in an order this rule refuses (a catch-all before specific routes): an explicit opt-in per registration;
- applications compose routes from modules whose order they do not control and the refusal is too strict: sort by specificity at registration instead of refusing (the order already defines it);
- Mojo can carry state across calls at compile time: move the check to compile time;
- building an `App` with thousands of routes with placeholders, or with many routes of any kind registered after them, shows up in start-up time: narrow the compared routes further (by method, by segment count, or by a static segment at some position);
- a route gets a segment kind other than static text and `{name}` (prefix, wildcard, typed segment): extend overlap and specificity.

**Next production slice:** this item. `src/muntin/app.mojo`: `_covers`, `_overlaps` and `_conflict` beside `_match`, `_RouteIndex`, and `App._add`, through which every registration appends its route and which aborts with `_conflict`'s message, found through the index; `handle`'s docstring states the rule. `docs/DX.md` (section 2's "Route conflicts", the first-match bullet, matching under the HTTP methods, section 12), `docs/ARCHITECTURE.md` (Registration surface, the routes paragraph and a revisit index row) and `docs/SPEC.md` (the M2 errors line, its reopen list and the capability table). Evidence: `tests/test_route_conflicts.mojo` checks the helpers, the index against `_conflict` on random registration sequences, and `_conflict`'s three messages against an `App` registered most specific first (identical paths, placeholder names only, a parameter route first, neither more specific, other lengths and methods, raw beside typed) and that such an `App` dispatches each request to the most specific route; `tests/route_conflict_abort`, a new `must_abort` kind in `scripts/build_one.sh` that `scripts/check.sh` builds and runs, expects each abort (a parameter route first, the same path with another name and a query, neither more specific, a raw route after a typed one). `test_parameter_route_registered_first_shadows_a_static_one`, which pinned the old answer, becomes `parameter_route_first.mojo`. Existing tests that registered duplicate or wrongly ordered routes on one `App` to pin first-match behavior move to distinct paths or register the more specific route first; examples, adapters and `compat` register none. No overload, `where` clause or call chain to `_check` changes, and nothing reaches the wire.
