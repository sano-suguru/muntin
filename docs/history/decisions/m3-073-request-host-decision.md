# Request Host decision (M3-073)

> **Current.** Now described in [headers reference, "Through the Flare adapter"](../../reference/headers.md#through-the-flare-adapter) and [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-073, pull request #130; `src/muntin` unchanged). The Flare reading, the RFC text and the tests' observations are in the pull request. It changes what the Flare adapter answers for one class of requests, so it reopens M2 under [M2-016](m2-016-m2-closure.md), as [M3-039](m3-039-request-target-and-method-bytes-decision.md) did.

**Question and what settles it.** RFC 9112 section 3.2: "A server MUST respond with a 400 (Bad Request) status code to any HTTP/1.1 request message that lacks a Host header field". Flare v0.12.0 refuses a second `Host` but admits an HTTP/1.1 request with none (`compat/flare/headers/flare_header_probe.mojo`, "2. HTTP/1.1 request without Host accepted"), and the adapter did not look, so `App.handle` answered it; no document listed the gap. Should the adapter answer it 400, and what of HTTP/1.0, h2c and an HTTP/1.1 request upgraded with `Upgrade: h2c`, or should the gap be recorded with a revisit condition? Settled by the RFCs' requirements per protocol, what Flare v0.12.0 hands the adapter for each (read in its source: the HTTP/1 parser's version, `take_request`'s `:authority`, the upgrade path), and loopback requests through the changed adapter.

**Choice: the adapter answers an HTTP/1.1 or HTTP/2 request without `Host` with its 400 `Bad Request`, before the conversion and `App.handle`.** `_answer` checks `request.version` and `request.headers.contains("host")` (any casing) first; the 400 is the adapter's existing one, under the `HEAD` rule (M3-027) for `HEAD`, with no middleware, route scan or handler, whatever the path.
- HTTP/1.1, and a later HTTP/1 minor version, which RFC 9110 section 6.2 says a server should process as 1.1 (Flare's HTTP/1 parser admits `HTTP/<digit>.<digit>` only, and reads a request line without a version as `HTTP/1.1`). An empty `Host` value is kept: RFC 9112 section 3.2 has a client send one when the target URI has no authority. HTTP/1.0 needs no `Host` and is served as before.
- HTTP/2 (Flare's `HTTP/2`): Flare writes `:authority` as `Host` (`take_request`), so the request without `Host` carried neither `:authority` nor `host`. RFC 9113 section 8.3.1 asks no server to refuse it, so this 400 is Muntin's policy, not an RFC requirement on servers, and no handler sees a request without an authority. What a sender must do is separate: RFC 9110 section 7.2 requires a user agent to send `Host` unless it conveys the authority in `:authority`, and RFC 9113 section 8.3.1 has a client that generates HTTP/2 requests directly use `:authority` when there is authority information to convey. A `host` field alone is served.
- `Upgrade: h2c` (RFC 7540 section 3.2, obsolete in RFC 9113, still honoured by Flare v0.12.0 on every cleartext connection with no setting to turn it off): Flare answers the HTTP/1.1 request 101 itself and hands it to the adapter on stream 1 as `HTTP/2`, with `:authority` taken from its `Host`. The HTTP/2 rule therefore refuses an upgraded request that had no `Host`, after the 101, which is the only point the adapter sees it. That 400 is the final answer to the HTTP/1.1 request (RFC 9110 section 7.8, RFC 7540 section 3.2), so RFC 9112's MUST for a request without `Host` is met; this says nothing of whether Flare's h2c upgrade conforms as a whole. Refusing before the upgrade would be cleaner, and is Flare's to offer.
- The value is not checked (RFC 9112's 400 for "a Host header field with an invalid field value"): the first remaining candidate in `docs/SPEC.md`, since it leaves that MUST unmet.

**Rejected.**
- Record it as a known gap and keep serving: a MUST of the protocol the `Server` speaks, which costs one check where the adapter already answers requests it refuses.
- Refuse in `App.handle`: `TestClient` and in-memory requests have no version and no `Host`; which protocol requires it is the backend's knowledge.
- HTTP/1.1 only, h2c served as before: the upgraded request without `Host` would be served, a MUST of RFC 9112 left unmet on a path every cleartext `Server` offers.
- An upstream Flare change (refuse before the 101, or an option to turn the upgrade off): the pin moves only with the owner's approval, and the HTTP/2 rule closes the path from the adapter now; a 400 before the 101 would be Flare's to add.

**Revisit when:**
- the Flare pin moves and Flare refuses such a request itself (the probe's case changes) or stops honouring `Upgrade: h2c`: the adapter's check stays as Muntin's guarantee, and the docs say whose answer the client sees;
- a backend reports the protocol in a way other than `version`, or hands over an upgraded request with `Host` taken from elsewhere;
- an application needs the `Host` value validated or routed on.
