# Binary request and response bodies decision (M3-040)

> **Current.** Now described in [raw reference, "Binary bodies"](../../reference/raw.md#binary-bodies), [ARCHITECTURE, "Backend seam"](../../ARCHITECTURE.md#backend-seam) and [ARCHITECTURE, "Request handling"](../../ARCHITECTURE.md#request-handling).
> Changed in part since:
> - [M3-063](m3-063-request-context-decision.md): an owning App.handle (shipped as M3-064) moves the request into middleware instead of copying it, so M3-040's 'middleware copy, one, as before' now holds only for the borrowing overload; the Flare adapter uses the owning one.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-040). It decides how a raw handler receives request body bytes that are not UTF-8 and returns a response body of arbitrary bytes, which M3-038 deferred as its candidate B, and implements the choice in the same item. The question and what settles it were committed before the design was chosen and before any measurement beyond reading the code (`docs/DEVELOPMENT.md` section 2).

**Why now.** M3-038 closed the lossy body conversion by refusing, in the Flare adapter, every request body that is not well-formed UTF-8 (400 before `App.handle`), and named binary bodies as its candidate B with the revisit condition "applications need bodies that are not UTF-8 (binary uploads, other charsets, protobuf)". The raw escape hatch exists for webhooks, custom content types and protocol integrations (DX section 9), and today it cannot receive an image, a protobuf message or a signed binary payload, nor send one: `Request.body` and `Response.body` are `String`s, which safe Mojo 1.1.0 code cannot fill with bytes that are not UTF-8.

**Question.** How does a raw handler receive the exact bytes of any request body and return a response body of any bytes, through `TestClient` and through Flare over HTTP/1.1 and h2c, with one representation of the body that cannot disagree with itself? Specifically: which of the candidates below (bytes beside the `String` body; bytes as the one representation with a strict UTF-8 text view; a body type that tags text and bytes) is the smallest consistent design; what each costs in compatibility (the `Request` and `Response` fields and initializers, `Response.text()`, `FromBody`, `Json[T]`, `WithHeaders[B]`, middleware, `TestClient`), in copies per request and in implementation size; what typed text bodies (`FromBody`, `Json[T]`, `WithHeaders[B]`) do with a body that is not UTF-8 once it reaches `App.handle`, at which step and with which status; what middleware sees and may change; which of M3-038's adapter refusals stay and which go; and which statements of DX, ARCHITECTURE, SPEC and the earlier records (M2-016's M2 contract, M3-002's raw-route transport, M3-008's codec premise and its revisit condition "Muntin gains a bytes body", M3-027's `HEAD` rule, M3-034's middleware copy, M3-038) change.

**What settles it:**
- the body path traced in code, boundary by boundary: `Request` and `Response` (their fields, initializers and `Response.text`), how `App.handle` copies the request for middleware and passes it through `Next.run`, how `_dispatch` hands the body to a raw route (the `List[String]` raw arguments and `_raw_request`'s rebuild, M3-002) and to a typed body slot (`_slot`, `_json_status`'s 413, `WithHeaders[B]`'s `_from_parts`, `FromBody.from_body(String)`, `Json[T].from_body`), `TestClient`, and the Flare adapter's request and response conversions and `HEAD` rule;
- Mojo 1.1.0 facts measured with the installed toolchain where the design relies on them: `List[UInt8]` as a `Copyable` field and its copies; `String(from_utf8=Span(...))` as the strict validator (raises, keeps well-formed bytes); overload resolution between a `String` and a `List[UInt8]` initializer argument (string literals, list literals, moved lists); whether a `List[UInt8]` compares and prints in a test;
- per candidate: the public API that changes and how existing application code migrates; whether any state lets the text and the bytes of one body disagree; the copies of the body per request on each path (raw, typed, with and without middleware, the adapter's conversions), read from the code and not timed; what a test can pin;
- the bodies, through the changed code: ASCII; well-formed Japanese UTF-8; a U+FFFD the client sent; NUL; empty; `0x00`, `0x80`, `0xFF` alone; the PNG signature; a truncated UTF-8 sequence; an arbitrary binary payload holding every byte value; a raw echo route reached directly, through middleware and through `TestClient`, compared by byte length and byte by byte, never through a lossy `String`;
- the wire, through the adapter and `Server`: the same bodies over HTTP/1.1 with `Content-Length` and chunked, and over h2c in one DATA frame and split across frames; the response bytes against the request bytes; `HEAD` (no content, `Content-Length` the body's byte length); the same `Server` answering a later request;
- the existing contracts read from their records, docs and tests: M2-016 (the raw escape hatch, the `Request(method, target, body)` initializer, the body converted by `from_body`) and its reopen conditions; M3-002's R1 raw transport; M3-008's codec premise; M3-027's `HEAD` rule and statuses without content (204, 205, 304); M3-030's 405; M3-034's one copy for middleware; M3-038's refusal and its invariants;
- negative evidence: scratch mutations of the changed code that convert the body lossily, drop or truncate bytes, or treat the bytes as text, each turning a listed test red.

**Boundaries that do not change silently:** `App.handle`'s routing and its 400/404/405/500 and middleware contract for well-formed UTF-8 bodies; `FromBody.from_body(String)`, `Json[T]` and `WithHeaders[B]` answering every well-formed UTF-8 body exactly as today; the adapter's header, method and target rules, its `HEAD` rule and the HTTP framing Flare sends; no `Content-Type` added, guessed or rewritten by Muntin or the adapter; no lossy conversion and no unsafe UTF-8 construction anywhere on the body path; one-thread serving; no Flare type in Muntin's API. A change to any of them is named here, with its classification against M2-016.

**Candidates to measure:**
- A: a bytes API beside the existing `String` body (a second field or accessor on `Request` and `Response`), the `String` body kept;
- B: bytes as the one body representation of `Request` and `Response`, with a text view that is a strict UTF-8 conversion (raising on anything else) and the typed body conversions fed through it;
- C: a single Muntin body type that distinguishes text from bytes (a tag or variant), used by `Request` and `Response`;
- baseline: M3-038 (main): text bodies only, the adapter's 400 for a request body that is not UTF-8.

**The path at the base, boundary by boundary** (read from the code):
- `Request.body: String` and `Response.body: String`; `Request(method, target, body: String = "")`, `Response(status, body: String)`, `Response.text(body, status)` and a non-raising `response.text()` returning the field. A `String` built with safe Mojo 1.1.0 code is well-formed UTF-8 (M3-038), so neither type can hold an image or a protobuf message.
- `App.handle` copies the whole request once when middleware is registered (M3-034) and borrows it otherwise. `_dispatch` hands the body to the adapters inside the `List[String]` raw arguments: a raw route gets method, path, query and body as `args[0]` to `args[3]` and `_raw_request` rebuilds the `Request` from them (M3-002's R1); a body route gets the body as its last raw argument, a JSON route the `Content-Type` verdict after it (`_json_status` reads `args[body_at + 1]` and the body's `byte_length()` for 413), a carrier route the header pairs after both. `_Erased.invoke(args)` takes only those strings (`_Call[F] = def(F, List[String])`), so anything that reaches an adapter must be a `String`.
- `FromBody.from_body(String)`, `Json[T].from_body(String)` (whose parser assumes a `String`, M3-008) and `WithHeaders[B]._from_parts(String, Headers)` read the text.
- `TestClient.post`, `.put` and `.patch` take `body: String`.
- The adapter copies Flare's `Request.body: List[UInt8]` into a `String` with `String(from_utf8=)` and answers 400 when that raises (M3-038), and sends `List(response.body.as_bytes())`; the `HEAD` rule declares `len(response.body)` of Flare's byte list.

**Measured premises** (Mojo 1.1.0 `8189361e`, Flare v0.12.0 `8c6e1400`, Linux):
- `List[UInt8]` is a `Copyable` field with explicit `.copy()` and compares with `==` and in `assert_equal`; a `Span` of one compares with `"x".as_bytes()` (`Span(req.body) == "signed".as_bytes()`), so a raw handler can compare bytes without raising. `String(from_utf8=Span(bytes))` raises (`Cannot construct a String from invalid UTF-8 data`) exactly on the bodies M3-038 listed and copies every other one unchanged.
- Overloads: beside `Request(method, target, body: String = "", headers)` and `Response(status, body: String)`, an initializer taking `var body: List[UInt8]` is selected for a `List` value or a list literal (`[UInt8(0x89), 0x50]`) and never for a string literal or a `String`; every existing call keeps its overload. Beside `TestClient.post(target, body: String, *, headers=)`, a `List[UInt8]` overload leaves every accepted call as it was, but a rejected call now has two candidates: a positional `Headers` is `no matching method in call to 'post'` with `candidate not viable: unexpected argument` for each, where it was `invalid call to 'post': unexpected argument` (`tests/testclient_headers_api_fail/positional_headers_on_post.mojo` and the `put` and `patch` fixtures of `tests/methods_api_fail`, re-pinned). The `cannot be implicitly copied` fixtures keep their text.
- Fixture diagnostics: every must-not-build fixture of the base was built against the base's `src` and this item's, the whole output normalized (repository root removed, `src/muntin` and `tests` line and column numbers replaced): 404 fixtures, identical except five. Three are the `TestClient` re-pins above. Two pin `_Call[F]`'s type, which gains the body bytes parameter: `tests/state_fail/closure_handler_storage.mojo` (expected text re-pinned to `'def(F, List[String], List[UInt8]) raises thin -> Response'`) and `tests/error_fail/typed_error_escaping_the_adapter.mojo` (its trampoline gains the parameter; still rejected for its error type alone). Forty-five fixtures whose raw handlers read `req.body` as text were rewritten to byte-level bodies (`Response(200, req.body.copy())`, `req.path`) so that their outputs stay identical.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A: a bytes API beside the `String` body (`Request.body_bytes`, `Response.body_bytes`, or a bytes accessor) | rejected: either both fields hold the body, and a middleware that sets `request.body = "x"` leaves the bytes stale (two bodies that disagree, which this item may not allow), or the `String` is empty or partial whenever the bytes are not UTF-8, so `req.body` silently means "the body, unless it is binary". Keeping them in step needs private fields, which Mojo 1.1.0 lacks. It keeps `req.body` compiling only by making it untrustworthy |
| B: bytes as the one representation (`Request.body: List[UInt8]`, `Response.body: List[UInt8]`), `text()` a strict UTF-8 read that raises, typed text bodies fed through it | **chosen**: one field per body, so nothing can disagree; no conversion anywhere on the path unless code asks for text, and then it is strict; the typed contracts (`FromBody.from_body(String)`, `Json[T]`, `WithHeaders[B]`) keep their signatures; the text initializers keep every existing construction compiling. Cost: code that read `req.body` or `response.body` as a `String`, or called a non-raising `response.text()`, must migrate (below) |
| C: a Muntin body type that tags text and bytes (`Body.text(...)`, `Body.bytes(...)`) | rejected: a tagged union can keep each tag consistent with its value, but the same bytes would then have two representations (a "bytes" body that is valid UTF-8 and a "text" one with the same bytes), so equality, printing and conversion between them would need rules of their own, and it is a new public type with implicit conversions from `String` to keep old code compiling, which hides copies; nothing in this item needs the tag |
| baseline: M3-038 (main) | rejected for raw handlers: a binary body cannot reach the escape hatch, nor can a handler send one |

**Selected: B.**
- **Public API.** `Request.body` and `Response.body` are `List[UInt8]`: the body's bytes exactly as received or as the handler built them, whatever they are. `Request(method, target, body: String = "", headers)` and `Response(status, body: String)` copy the text's UTF-8 bytes, as before; new overloads `Request(method, target, var body: List[UInt8], headers)` and `Response(status, var body: List[UInt8])` take bytes by move. `Request.text()` (new) and `Response.text()` (now `raises`) return a copy of the bytes as text when they are well-formed UTF-8 and raise otherwise; no byte is ever replaced. `Response.text(body, status)` is unchanged. `TestClient.post`, `.put` and `.patch` gain a `var body: List[UInt8]` overload. Muntin adds, guesses or rewrites no `Content-Type`, for bytes as for text.
- **Typed bodies.** The body slot reads the bytes as UTF-8 (`_body_text`) right before `from_body` (after the 415 and 413 steps of a JSON body and the field rebuild of a carrier); bytes that are not UTF-8 are 400 `Bad Request` before `from_body`, the status a `from_body` raise already has. So `FromBody.from_body(String)`, `Json[T]` and `WithHeaders[B]` receive exactly the text the client sent or are not called: the JSON codec never parses a replaced byte, and M3-008's revisit condition ("Muntin gains a bytes body: the codec should reject invalid UTF-8 itself") is met by the slot, which validates once for every text body, with no change to the codec. Order on a JSON body route: 404 or 405, query or capture 400, `Int` 400, 415, 413, UTF-8 400, JSON 400, handler.
- **Raw handlers.** A raw route receives the whole `Request`, its body bytes unread; `req.text()` is the handler's explicit choice, and its raise is a handler error (the fixed 500 or the error type's `to_error_response`), so a handler that must answer 400 to a body that is not text catches it or compares bytes.
- **Middleware.** `App.handle` still copies the request once when middleware is registered, body bytes included; `Next.run` moves it on. A middleware may replace `request.body` with other bytes, and the routes see exactly those bytes; nothing converts them to text.
- **Transport through the box.** The body leaves the `List[String]` raw arguments: `_Erased.invoke(args, bytes)` passes the request's body bytes beside them, borrowed and unread (`_Call[F] = def(F, List[String], List[UInt8])`); `_raw_request` rebuilds the `Request` from method, path, query and header pairs plus one copy of the bytes, and a body slot reads them. A JSON route's verdict now sits at the body's former position, and a carrier's header pairs follow the route values and verdict; `_Route.body` is gone (nothing reads it). The storage module still reads no request data (`scripts/check_unsafe.sh`), it only passes the bytes through.
- **The Flare adapter.** `to_muntin_request` copies Flare's raw body bytes into `Request.body`, whatever they are, with no validation: M3-038's body refusal is removed. The method, target and header-field refusals (M3-039, M3-005) are unchanged, and Flare's own refusals still come first (a body over its `max_body_size`, 10 MiB by default; requests its parsers reject). `to_flare_response` copies `Response.body`'s bytes; the `HEAD` rule is unchanged and declares the byte length (a binary answer's `Content-Length` is its byte count).
- **Copies of the body per request** (read from the code, not timed): the adapter's copy in and out, one each, as before; the middleware copy, one, as before; a raw route one (the rebuild), where the base made two (the raw argument and the rebuild); a typed text body one (the UTF-8 read), where the base made one (the raw argument), plus one validation pass that over Flare the adapter ran before; `Request(..., text)` and `Response(status, text)` one, as before; `Response(status, bytes^)` none. The largest body held at once is therefore unchanged for typed routes and one copy smaller for raw routes; nothing is streamed, and Flare's 10 MiB default cap still bounds a request body. No performance claim is made: nothing was measured.
- **Typed binary bodies later.** A future binary extractor (a `FromBody`-like conversion over bytes, a bytes body type) reads the same `List[UInt8]` the body slot already receives; nothing here fixes its spelling.

**M2 contract: reopened.** The contract's raw escape hatch receives "Muntin's whole `Request` (`method`, `path`, `query`, `body`)" and its ownership bullet names `Request` and `Response`; this item changes those types' public fields and `Response.text()`, which is "a design must change an M2 public type" ([M2-016](m2-016-m2-closure.md)), and it changes the 400/404/405 boundary for one class of requests over Flare. By kind:
- public API: `Request.body` and `Response.body` change from `String` to `List[UInt8]`, and `Response.text()` gains `raises`; added: `Request.text()`, the bytes initializers and the `TestClient` bytes overloads. Migration: a text read `req.body` becomes `req.text()` in a raising handler (or a byte comparison, `Span(req.body) == "x".as_bytes()`, in a non-raising one); a byte echo is `Response(200, req.body.copy())`; `response.body` compared with text becomes `response.text()` (raising code, as tests are); `request.body = "x"` becomes `request.body = List("x".as_bytes())`; a non-raising caller of `response.text()` becomes raising or reads `response.body`. In this repository that touched every test, spike and fixture that read a body as text (DX section 9's example among them) and no registration or typed handler;
- `App.handle` and `TestClient`: a typed text body that is not UTF-8, which no `Request` could hold before, is 400 before `from_body`; every other answer, well-formed UTF-8 bodies included, is unchanged;
- the wire: over HTTP/1.1 and h2c a request body that is not UTF-8 reaches `App.handle` byte for byte, where M3-038 answered it 400 in the adapter: a raw route receives it and may send any bytes back (a raw handler that reads it with `text()` and does not catch the raise now answers the fixed 500, where M3-038's adapter answered 400 before it ran); a typed text route answers 400 after routing and through middleware; a path no route matches is 404 and a path only other methods match 405 with `Allow`, through middleware, where both were the adapter's 400; a typed route with no body slot (a typed `GET`, `HEAD` through it, or `DELETE`) ignores the body and gives its usual answer, where it was the adapter's 400; a `HEAD` under M3-027's rule. Well-formed UTF-8 bodies are answered as before;
- the accepted set and the registration overload set are unchanged; diagnostics change only for the three `TestClient` positional-`Headers` calls above.

**Invariants:**
- `Request.body` holds exactly the request body bytes the backend received, and the backend sends exactly `Response.body`'s bytes (framing aside: no content for `HEAD`). No step on either path replaces, drops, adds or reorders a byte, and none converts the body to text unless code asks with `text()` or a typed text body.
- A body has one representation: there is no second field, cache or tag that can disagree with `body`.
- Text read from a body is strict: `text()` and the typed body slot accept well-formed UTF-8 only; a U+FFFD the client sent is a character like any other and never stands for a replaced byte.

**Cost.** The migration above; `Response.text()` raising, so a non-raising helper that read it must change; a raw handler that reads text now writes `raises` or compares bytes, and over Flare a migrated text-reading raw handler that does not catch `text()`'s raise answers a body that is not UTF-8 with the fixed 500 instead of M3-038's adapter 400 (catch it to answer 400); three `TestClient` diagnostics read differently. A client that sent a body that is not UTF-8 to a path no route matches gets 404 (or 405) instead of the adapter's 400, and middleware now sees such requests.

**Revisit when:**
- applications need a typed binary body (a bytes extractor, `FromBody` over bytes) or a body other than UTF-8 text in a typed handler: its own decision item, reading `Request.body` as the body slot does;
- streaming bodies are taken up: `List[UInt8]` holds the whole body; a stream is a different representation;
- a second network backend is added: it inherits the obligation (copy the body bytes both ways, unchanged);
- Mojo gains private fields or computed properties: a read-only view could then replace the public field;
- Flare changes what `Request.body` holds or `String(from_utf8=)` changes what it accepts (`compat/flare/body/body_probe.mojo` fails).
