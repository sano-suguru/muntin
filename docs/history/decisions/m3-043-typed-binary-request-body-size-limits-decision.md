# Typed binary request body size limits decision (M3-043)

> **Current.** Now described in [bodies reference, "Body size limits (`max_bytes`)"](../../reference/bodies.md#body-size-limits-max_bytes), [routing reference, "Order of checks"](../../reference/routing.md#order-of-checks) and [ARCHITECTURE, "Mojo 1.1.0 facts the design rests on"](../../ARCHITECTURE.md#mojo-110-facts-the-design-rests-on).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-043, [pull request #81](https://github.com/sano-suguru/muntin/pull/81)). It decides how an application gives a `FromBytes` body, bare or inside `WithHeaders[B]`, a Muntin-side size limit answered 413 before the conversion, which M3-041 and M3-042 left out with a revisit condition ("a size cap ... for bytes bodies"), and implements the choice in the same item. The question, the candidates, the comparison criteria and the pass conditions below were committed before the design was chosen; the only measurement before them was a scratch probe of how Mojo 1.1.0 treats a trait's `comptime` member with a default (needed to know whether one candidate exists at all).

**Why now.** Since M3-041 a typed handler takes a body of any bytes as a `FromBytes` type, and since M3-042 inside `WithHeaders[B]`. Neither has a Muntin limit: `from_bytes` receives every body the backend hands over, up to Flare's own `max_body_size` (10 MiB by default), and the only way to refuse a larger one is a raise in `from_bytes`, which is 400, after the conversion has started, or middleware that re-derives which route a request will select. A `Json[T]` body has had a fixed 1 MiB, 413 step since M3-009; a bytes body, whose sizes vary far more by format (an avatar, a signed blob, an archive), has none and no way to say one.

**Question.** How does an application state a byte limit for a `FromBytes` body so that `App.handle` answers 413 `Content Too Large` without calling `from_bytes` or the handler when the body is longer, for a bare `FromBytes` and for `WithHeaders[B]` around one? Specifically: at which unit the limit is configured (the `App`, the route, the body type), by what spelling (a new public name, a method, a registration argument or parameter, a trait member), with which default (none, the baseline, or a reason for one), which values are valid (0, the largest `Int`, a negative value, a non-`Int`) and what setting it twice means; where in the order it answers (404/405, the route values' 400, the limit's 413, the carrier's field rebuild 500, `from_bytes`' 400, the handler), and in particular whether 413 or the rebuild's 500 comes first; that it measures the body `_dispatch` hands the route after middleware, with no copy and no UTF-8 read; and what changes in the accepted set, the overload set, the diagnostics and the runtime of routes that register today, classified against M2-016.

**What it is not.** A limit Muntin checks in `App.handle` measures a body the backend has already received and buffered in full: it bounds what reaches the conversion and the handler, not receive memory, not a stream, and not what an unauthenticated client can make the server read. Those stay the backend's (Flare's `max_body_size`) and are not claimed here.

**Candidates.**
- A, the `App`: one limit for every `FromBytes` route of an application (an `App` field, set by a method or an initializer argument), carried to the body slot at run time.
- R, the route: a limit on each registration (a parameter or argument of `post`, `put` and `patch`), carried by the route.
- T, the body type: the `FromBytes` type declares its limit, read at compile time where the body is converted; a carrier reads its carried type's.
- T-wrap, the body type through a Muntin wrapper (`Limited[B, n]` around a `FromBytes`).
- Z, no new API: `from_bytes` raises (400) or middleware answers 413 by path and method.

**Comparison criteria**, per candidate: how the application spells it and how natural it reads beside `FromBytes` and `WithHeaders[B]`; what registration changes (overloads, signatures, rules, candidate notes; a candidate that adds overloads or densifies every registration signature counts against itself); how easily a route is left unlimited by mistake, or configured with no effect; whether one type can carry different limits on different routes; how it extends to other body forms later (a `FromBody` limit, a configurable `Json[T]` cap); run-time cost per request on a limited and on an unlimited route; where invalid values are caught (compile time with Muntin's message, at run time, never); and whether it needs new state in `_Erased`, `_Route` or `App`.

**Pass conditions** (the item is complete only when each holds, with executable evidence):
- with the chosen API, a bare `FromBytes` body and `WithHeaders[B]` around one each get the limit, on every body shape (`def(B)`, `def(V, B)`, `def(V, V, B)`, stateless and with `State`, on `post`, `put` and `patch`);
- within the limit, an empty body, ASCII, Japanese UTF-8, NUL, `0x80`, `0xFF`, the PNG signature and every byte value reach `from_bytes` byte for byte, as before; a body of exactly the limit is accepted, one byte more is 413 with neither `from_bytes` nor the handler called; a limit of 0 accepts only the empty body;
- a bad route value is 400 before the limit, whatever the body's length; 404 and 405 convert nothing; the limit measures the body after middleware (a middleware that shrinks a long body gets it accepted, one that lengthens a short body gets it refused);
- the carrier keeps every field in order, with casing, repeats and empty values; its order between 413 and the rebuild's 500 is fixed by this record and pinned;
- a `from_bytes` raise is still 400; a route whose type sets no limit, text, `Json[T]` (415, 413 at 1 MiB, UTF-8 400, JSON 400), raw handlers, middleware, `HEAD`, 404, 405 and `Allow` answer as before;
- an invalid limit is rejected with a must-not-build fixture, and every new fixture is also built against the base's `src`;
- through `App.handle` and `TestClient`, a test that is red on the base and green with the change; over the Flare loopback, HTTP/1.1 (`Content-Length`, chunked) and h2c (one and two DATA frames), a body within and one over a Muntin limit far below Flare's 10 MiB, the 413 shown to be Muntin's (it passed through `App.handle`), and the same `Server` answering a valid request afterwards;
- scratch mutations (`>` as `>=`, the check removed, 413 answered 400, the check after `from_bytes`, the check on the body before middleware, the carrier's check removed, the invalid-value rule removed) each turn a listed test or fixture red;
- every existing fixture's whole normalized compiler output compared against the base where the change can reach compiler output outside the checked texts.

**The path at the base** (read from the code): `_dispatch` hands each route `request.body` (the request after middleware: `handle` copies the request once for the chain, and the last `Next.run` passes that copy to `_dispatch`) beside the decoded route values, through `_Erased.invoke(args, bytes)`. In the adapters, `_slot` converts the slots in order, so every route value is converted before the body. Its bare `FromBytes` branch calls `A.from_bytes(body)` (400 on a raise); its carrier branch runs the JSON steps if any (`_json_status`: 415, then 413 over `_MAX_BODY_BYTES` = 1 MiB), rebuilds the fields (`_carrier_fields`, 500 on the `_fields` gap) and calls `_from_parts`, which calls `from_bytes` for a `FromBytes` `B`. `_rejected` maps a `_Reject` of 413 or 415 through `_json_answer` (413 is `Content Too Large`, no field). Nothing on the path knows a length other than JSON's constant, and the conversion is selected at compile time from the slot's type alone, with no route data. Flare buffers the whole body before calling the adapter: `ServerConfig.max_body_size` (10 MiB by default) is checked by its HTTP/1.1 parser against `Content-Length` and the chunked total, and by its HTTP/2 layer (`max_request_body_size`); over HTTP/1.1 its refusal is its own 413 `Content Too Large`, queued before any handler runs.

**Measured premises** (Mojo 1.1.0 `8189361e`, Linux; scratch probes, then the fixtures and tests named below):
- A trait may declare a `comptime` member with a default (`comptime max_bytes: Int = Int.MAX` in `FromBytes`). A conforming struct that declares nothing gets the default; one that declares `comptime max_bytes = 64 * 1024` (or `= Self.limit` from a struct parameter: `Upload[1024].max_bytes` is 1024) overrides it. Generic code reads `A.max_bytes` inside `comptime if conforms_to(A, FromBytes)` with `A` bounded only by `AnyType` (`_kind`) or `Movable & Deinitable` (`_slot`), and a carrier reads `Self.B.max_bytes` with `B` bounded by `_FromBodyOrBytes`; the value is a compile-time constant there.
- A second declaration in the same struct is `invalid redefinition of 'max_bytes'`; a declaration of another type (`comptime max_bytes: UInt = 1024`, `= "x"`) does not conform (`comptime member 'max_bytes' type 'UInt' does not conform to trait's required type 'Int'`). With a default in `FromBytes` itself, an application trait refining `FromBytes` that gives the member a second default makes every type conforming to it fail (`trait member 'max_bytes' has conflicting default implementations in FromBytes and Small; you must implement it manually`). These are the toolchain's, not Muntin's, checks: `tests/bytes_limit_api_fail` pins the redefinition and the `UInt` declaration; the conflicting default was measured by a scratch probe, since with the chosen design (a required member) the same refining trait compiles.
- A struct member Muntin does not read is accepted silently: on the base, `comptime max_bytes = 4` on a `FromBytes` type compiled and was ignored (the acceptance test's first version builds there and fails at run time), and with a defaulted trait member a misspelled `max_byte`, or `max_bytes` on a `FromBody` type, is still an ordinary member.
- A trait may instead require the member with no default (`comptime max_bytes: Int`): a conforming struct that declares none, or declares `max_byte`, fails where it is declared (`'Upload' does not implement all requirements for 'FromBytes'` with the note `required member 'max_bytes' is not specified`), and a trait refining `FromBytes` may then give it a default (`comptime max_bytes: Int = 16`) that a conforming struct inherits or overrides and generic code reads through `conforms_to` (`tests/bytes_limit_api_fail/limit_missing.mojo`, `limit_misspelled.mojo`, `tests/test_bytes_limit.mojo`).
- Under a refining trait's default the required member no longer catches a misspelling (measured after an external review): a struct conforming through `trait SmallUpload(FromBytes): comptime max_bytes: Int = 16` that writes `comptime max_byte = 4096` compiles, keeps `max_byte` as an unrelated member and inherits 16, and the route registers with it; with a family default of `Int.MAX` the same misspelling registers with no limit (`tests/bytes_limit_known_gaps/misspelled_override_inherits_family_default.mojo`, `misspelled_override_under_unlimited_default.mojo`, must build). Mojo 1.1.0 does not check a struct's member names against the traits it conforms to, so no Muntin rule can see it.
- A negative `Int` is a valid value for the member as far as Mojo is concerned; only Muntin's registration rule rejects it.

**Re-evaluation after review.** The first implementation chose T-default (the question's baseline: no declared limit means none). The fresh-context review pointed out that the record had not weighed a required member, and measured that it closes both of T-default's costs for a type whose traits give `max_bytes` no default: a misspelled `max_byte` compiled and left the body unlimited, and a refining trait could not provide a default. (An external review later showed the first does not hold under a refining trait's default, where a misspelled override inherits the family's value; measured above, and the claim is limited here and in the docs.) Re-evaluated under the pre-release criterion the owner set for this item too (Muntin is unreleased with no external users, so API consistency, simplicity, safety, ownership and maintainability come before backward compatibility, and each change to an existing contract is classified as intentional or a regression; M3-042 recorded the same criterion for its own item), T wins: a size limit on bodies of any bytes is a safety setting, and T-default fails open on the one mistake the compiler cannot see, while T fails closed at the declaration of a type whose traits give `max_bytes` no default, with the compiler's own message, adds a family default for free, and costs one line per type (`Int.MAX` keeps the old answers). What the required member guarantees is an explicit choice, a limit or `Int.MAX`, not a safe value; and a type under a family default falls back to the family's value on a misspelled override, which is a limit unless the family's default is `Int.MAX` (DX advises a finite family default). T still wins: T-default fails open on that typo for every type, T only under an unlimited family default. The baseline the question named ("no limit without explicit configuration") becomes "no limit only when the type says `Int.MAX`".

**Selected: T.** The limit is a property of the body's format, declared where its conversion is: `FromBytes` gains the required `comptime max_bytes: Int`, and nothing else is added to the public surface.
- **Default.** None in `FromBytes`: every type states its limit, so none is left unlimited by omission or a typo when its traits give `max_bytes` no default; under a refining trait's default a typo falls back to that default (with `Int.MAX`, to none; measured above). `Int.MAX`, a value no `List` length exceeds, is the explicit "no limit", which needs no sentinel and no branch: the check is `len(body) > max_bytes` for every `FromBytes` body. A finite default was not taken either: it would change M3-041's and M3-042's answers for every bytes route, and no size fits avatars and archives alike; the backend's receive limit already bounds every body. An application that wants a default for its own types declares a trait refining `FromBytes` with one.
- **Values.** A byte count compared with the body's length: a body of `max_bytes` bytes is accepted, `max_bytes + 1` is 413. `0` accepts only the empty body. A negative value is rejected at registration with Muntin's message (`_NEGATIVE_LIMIT`, in the body position `the request body's max_bytes is negative; a FromBytes type's max_bytes is a byte count, 0 or more`; elsewhere the body rules it breaks, as for any body). A missing member, another type and a second declaration are the compiler's errors (above), and so is a misspelled one when the type's traits give `max_bytes` no default (under a family default it is inherited instead, above). A limit is set once, in the type's own declaration or its refining trait's default, and never at run time.
- **Order.** 404 or 405 (nothing measured); the route values (400, whatever the body's length); the limit (413; nothing rebuilt or converted); for a carrier, the field rebuild (500, the `_fields` gap only); `from_bytes` (400 on a raise); the handler. 413 comes before the rebuild's 500 because the length is known without rebuilding the fields (`App.handle` has already copied the carrier's field names and values into the arguments; only their rebuild through `Headers.add` comes after), a carrier around `Json[T]` already answers its JSON 413 before the rebuild, and the rebuild's 500 is reachable only through the M3-002 gap, so no well-formed request sees the difference; the order is pinned (`test_the_carrier_answers_413_before_its_field_rebuild`). A body over the limit that `from_bytes` would also reject is 413.
- **What is measured.** `len(body)` of the bytes `_slot` receives, which are `_dispatch`'s `request.body`, after middleware; the code adds no copy, no UTF-8 read and no new field in `_Route`, `_Erased` or `App` (a description of the code, not a tested guarantee).
- **Code.** `body.mojo`: the required member and its contract. `headers_body.mojo`: `_HeaderCarrier._max_bytes()`, `B.max_bytes` for a `FromBytes` `B`, else `Int.MAX`. `_registration_rules.mojo`: `_kind` gives a `FromBytes` with a negative limit, bare or carried, the kind `_NEGATIVE_LIMIT`, which `_is_body` counts as a body and `_post_rule` rejects in the body position after the two-conversion rule. `app.mojo`: `_slot`'s bare `FromBytes` branch raises `_Reject(413)` when `len(body) > A.max_bytes`, and its carrier branch does so with `A._max_bytes()` after the JSON steps and before the rebuild; `_rejected` answers it with the existing `_content_too_large()`, through the helper that answered the JSON 415 and 413, renamed from `_json_answer` to `_body_rejection_answer` now that a bytes body uses it too (external review; the raw and state spikes import it).
- **Not included.** A limit for text bodies, an `App`-wide or per-registration limit, a configurable `Json[T]` cap, a run-time limit, any receive-time or streaming behavior, a status other than 413.
- **Text, JSON, raw, `HEAD`, 404, 405.** Unchanged: a `FromBody` type's member of that name is not read; `Json[T]` keeps 415, then 413 at 1 MiB, then UTF-8 400, then JSON 400; a raw handler measures `req.body` itself; `GET` routes (and `HEAD` through them) take no body; 404 and 405 select no route.

**Muntin and the backend.** The check runs in `App.handle` after the backend has received and buffered the whole body: it bounds what reaches `from_bytes` and the handler, not the memory a request takes to receive, not a client that keeps sending, not streaming, and not a body sent before authentication. Over Flare a body over `max_body_size` never reaches the adapter (over HTTP/1.1 Flare's own 413, without the application's middleware fields); a body within Flare's limit and over the type's is Muntin's 413, through middleware. A Muntin limit above the backend's is never reached.

**M2 contract: amended, not reopened.** `FromBytes` is an M3 trait (M3-041); `FromBody`, text bodies, `Json[T]` and every M2 signature, binding rule and answer are unchanged. By kind:
- the accepted set shrinks for `FromBytes` types only: one without a valid `max_bytes` (missing, misspelled, another type, declared twice) does not conform, unless a refining trait it conforms through gives a default, which it then inherits for a missing or misspelled member, and one declaring it negative is rejected at registration; every type with a valid limit registers on every shape it did;
- the overload set is unchanged;
- diagnostics: one new `constraint failed:` message and the compiler's conformance error for a missing member; the comparison of every existing fixture's normalized output against the base is in the pull request;
- runtime: a route whose type declares `Int.MAX` answers as before; the Flare adapter is unchanged.

**Changes to existing APIs, classified.** Intentional:
- `FromBytes` gains the required `comptime` member `max_bytes: Int`. Impact: every existing `FromBytes` type stops conforming until it declares the member (in this repository: the M3-041 and M3-042 tests, fixtures, DX examples and the loopback suite's `Payload`: every one of the 33 `FromBytes` types on the base); a type that already had a member of that name now limits its bodies. Migration: `comptime max_bytes = Int.MAX` keeps a type's answers; the DX examples declare real limits (`Image` 1 MiB, `Upload` 8 MiB).
- Private: `_HeaderCarrier` gains `_max_bytes()`; `_kind` a kind and `_check` a message; `_content_too_large` and `_json_answer`, renamed `_body_rejection_answer`, answer the bytes 413 as well.
- `tests/from_bytes_api_fail/from_bytes_takes_text.mojo` and `from_bytes_takes_owned_bytes.mojo` expect the `from_bytes` signature note (`no 'from_bytes' candidates have type 'def(body: List[UInt8]) raises thin -> Payload'`) instead of the conformance error line, which a missing `max_bytes` now also produces: re-pinned to keep their cause, their compiler output otherwise unchanged.

Unintended regressions: none known; the suites' results and the normalized comparison are in the pull request.

**Invariants:**
- A `FromBytes` body longer than its type's `max_bytes`, bare or carried, is 413 with neither the carrier's rebuild, `from_bytes` nor the handler run; a body of at most `max_bytes` bytes reaches `from_bytes` exactly as before.
- The limit is measured on the body `_dispatch` hands the route, after middleware and after every route value is converted.
- Every `FromBytes` type states its limit, itself or through a refining trait's default; only `Int.MAX` means none. The compiler enforces the statement only for a type whose traits give `max_bytes` no default: under a family default, a misspelled override is not seen.
- The limit is Muntin's dispatch rule: `App.handle` enforces it on a typed route before `from_bytes`; a direct call to `from_bytes` is not limited.
- Muntin's limit never claims to bound what the backend receives.

**Cost.** Every `FromBytes` type carries one more line, and "no limit" is written out (`Int.MAX`). One type carries one limit: a route-specific limit needs a type parameter or a second type. The member on a text type is accepted silently and is not a limit (Mojo 1.1.0 does not reject members a trait does not require); the docs say so and a test pins it. For the same reason a misspelled override under a family default is accepted silently and inherits that default; two known-gap fixtures pin it, and DX advises a finite family default.

**Revisit when:**
- applications need a limit on text bodies, or a configurable `Json[T]` cap: read the same member from `FromBody` types or from `Json[T]`'s `T`, which reopens their "no Muntin cap" contract;
- applications need one type with different limits chosen at run time, an `App`-wide default, or a per-registration override: candidates A and R above;
- a backend configuration (body size) is decided ([M3-032](m3-032-serving-entrypoint-decision.md)): keep the two limits distinct in the docs and diagnostics;
- streaming bodies are decided: the limit then has to be enforced while receiving, not on a buffered body;
- the one-line cost per type proves a burden in practice (many types declaring `Int.MAX`): revisit a default in `FromBytes` itself, which reopens the fail-open trade-off above;
- a fixture in `tests/bytes_limit_known_gaps` stops building: if Mojo now rejects a misspelled member under a family default, the guarantee for such types can be widened; if Mojo stops inheriting a refining trait's default, the family-default contract (DX, `test_a_refining_trait_gives_a_family_default`) breaks and the family-default advice must be revisited.
