# Bodyless typed post, put and patch handlers decision (M3-048)

> **Current.** Now described in [routing reference, "Bodyless `post`, `put` and `patch`"](../../reference/routing.md#bodyless-post-put-and-patch), [state reference, "`post`, `put` and `patch`"](../../reference/state.md#post-put-and-patch) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-048, [pull request #86](https://github.com/sano-suguru/muntin/pull/86); `src/muntin` changes only in `_registration_rules.mojo` and docstrings). It decides whether a typed `post`, `put` or `patch` handler may take no request body, which M3-020 left a compile error "until M3-016's bodyless-`POST` condition is decided for all three", and with it M3-016's condition "`POST` without a body is decided: revisit whether a bodyless `post` takes a `Headers` slot as `get` does". The question, candidates, criteria and pass conditions below were written before any measurement; what precedes them was read from the records named above and from `src/muntin`.

**Why now.** M3-022 and M3-024 deferred it because an application `FromBody` that accepts any body (`def(V, Ignored)`) serves such a route, so it "unblocks no route". That stays true, but the workaround is the cost: every action endpoint that carries no representation (`POST /users/{id}/activate`, `POST /logout`, `PUT /users/{id}/follow`) needs an application type whose only purpose is to be ignored, a parameter the handler never reads, and, for one that reads a header field, `WithHeaders[Ignored]` and `input.headers`, where `get` and `delete` take `Headers` directly. The application code is less clear than the shape it means, and the diagnostics push a user who writes the obvious `def(id: Int)` toward the workaround. Of the remaining candidates in `docs/SPEC.md`, it is the one that changes ordinary handler code and needs no new public type, status or backend measurement.

**Read in code.** A typed `get` overload and the `post` overload of the same arity have identical bodies apart from the method string: `_check`, the `_admits` guard, `_route` (whose flags read the slot kinds: JSON, header fields, raw) and `_Erased` over the same `_call_N` adapter. A slot converts by its kind in `_slot`, and the body is read only by a body slot; `App.handle` hands the bytes beside the route values to every typed route, and a typed `get` or `delete` route never reads them. So a shape's run-time behavior depends on its slot kinds, not its method; the method family only selects `_get_rule` or `_post_rule` in `_rule`.

**Question.** Should `post`, `put` and `patch` accept typed handlers that take no body, and if so: which shapes (no parameter, route values, a `Headers` slot, each stateful); what a request's body does on such a route (unread, or refused with which status); which existing diagnostics change and to what, and whether a shape that most likely forgot its body conformance keeps a message that says so; whether the three methods stay one family; and what changes in the accepted set, the overload set, the diagnostics and the runtime, classified against M2-016.

**What it is not.** A typed `DELETE` body (M3-020's own condition), optional bodies (a body that may be absent), `TestClient.post` without a body argument, and a `Content-Length` rule are out of scope; so is any change to `get`, `delete`, raw handlers or body shapes.

**Candidates.**
- A, `get`'s shapes on the body family: a `post`, `put` or `patch` handler whose slots are only route values and at most one `Headers` last (`def()`, `def(V)`, `def(V, V)`, `def(Headers)`, `def(V, Headers)`, `def(V, V, Headers)`, each after a leading `State[S]`) takes `get`'s rules; the request's body is not read, as on a typed `get` or `delete` route. Every shape with a body slot, and the raw shape, keep `post`'s rules.
- A′, A without the `Headers` slot: bodyless shapes take route values only; a header field still comes through `WithHeaders[Ignored]`.
- B, a Muntin body type that means "no body" (`NoBody`, a `FromBody` and `FromBytes`-free marker or a `FromBytes` with `max_bytes = 0`): the handler declares `def(V, _: NoBody)`; the family's rule ("the body last") stays, and a non-empty body is refused (413 through `max_bytes = 0`, or 400).
- C, A with a refusal: as A, but `App.handle` answers a non-empty body on a bodyless route with a Muntin status (400 or 413) before the handler.
- D, decision only: the rule stays; the docs show the `Ignored` workaround.

**Comparison criteria**, per candidate: the application code for an action endpoint with and without a header field, beside the same endpoint on `get`/`delete`; the public API added; which existing shapes change from rejected to accepted and which diagnostics change; whether a handler whose body type forgot its conformance (a slot of no kind last) still gets `its type must conform to FromBody or FromBytes`; what a body sent to the route does, and whether Muntin then chooses a status (which RFC 9110 leaves to the resource for `POST`, section 9.3.3); whether `post`, `put` and `patch` stay one family; overload set, `where` clause, `_route`, `App.handle`, storage and the one rebind; accepted set, overload set, diagnostics and runtime by kind (M2-016). The smallest candidate that meets the pass conditions is chosen.

**Pass conditions** for an implementing candidate:
- each bodyless shape registers on `post`, `put` and `patch`, stateless and stateful, and answers through `App.handle` and `TestClient` exactly as the same handler on `get` answers the same target: route values decoded and converted with `get`'s 400s, header fields delivered in order, results, raises and `ToErrorResponse` as for every typed handler; a body sent to it (text, bytes that are not UTF-8, a JSON `Content-Type`) is not read and changes nothing;
- a `post`, `put` or `patch` route with a body slot answers exactly as before, and every existing test passes;
- a slot of no kind as the last parameter (a body type without its conformance) still gets the `FromBody or FromBytes` message, on all three methods;
- every diagnostic whose text changes is listed in this record with its old and new text, and each fixture that pinned a now-accepted shape is replaced by executable evidence that the shape is accepted;
- no overload, `where` clause, `_route` flag, `App.handle` step, storage change or second `rebind_var`; `check.sh` and `test.sh` pass;
- scratch mutations, each turning a listed test or fixture red: the bodyless branch removed, `Headers` excluded from it, a body-kind slot admitted into it, and the branch applied to `post` but not to `put` or `patch`.

If no candidate meets them, D.

**Selected: A.** `_post_rule` first asks whether every slot is absent, a route value or `Headers` (`_bodyless`); such a shape takes `_get_rule` with the same arguments, so its rules, their order and their messages (naming the registration's method) are `get`'s. Every other shape takes `post`'s rules as before. Contract: `docs/DX.md`, "Bodyless `post`, `put` and `patch`".
- **Shapes.** `def()`, `def(V)`, `def(V, V)`, `def(Headers)`, `def(V, Headers)`, `def(V, V, Headers)`, each after a leading `State[S]` with the state as the second argument; `V` an `Int`, a `String` or an `Optional` of either, with `get`'s placeholder rules. They are the shapes `get` and `delete` take minus the raw one, which `post` already has.
- **The body.** Not read and not refused: no slot reads it, and the route is neither a JSON route nor a carrier, so `App.handle` appends nothing for it and answers no 415, 413 or UTF-8 400 (measured: none, text, a JSON document under a JSON `Content-Type` and bytes that are not UTF-8 give the `GET` answer). A handler that must refuse a body takes a body type that refuses it, or is raw.
- **What stays a body shape.** A last slot of no kind (a body type without `FromBody` or `FromBytes`, `List[UInt8]`), a body anywhere, a `Request` or a second `State` keep `post`'s rules and messages: a slot of no kind is what a forgotten conformance looks like, so it is never read as bodyless.
- **One family.** `put` and `patch` keep exactly `post`'s shapes, now including the bodyless ones; nothing in `_rule` names a method beyond the family split.
- **Code.** `_bodyless` and one branch at the top of `_post_rule`, which replaces the `def()` rule; the codes and messages it makes unreachable (`a <method> handler takes the request body as its last parameter`, `Int is a route-value type, never the request body; the body parameter's type must conform to FromBody or FromBytes`) are removed. No overload, `where` clause, `_route` flag, `_slot` branch, `App.handle` step, storage change or `rebind_var` is added: an overload of `post` and the `get` overload of the same arity already had the same body (above).

**Diagnostics that change** (old text, then new; each fixture that pinned one):
- now accepted, the fixture removed and its shape added to `tests/test_bodyless.mojo`: `def()` on `post` (`body_fail/post_no_param`), `put` and `patch` and their stateful forms (`methods_api_fail/{,state_}{put,patch}_without_body`), all `a <method> handler takes the request body as its last parameter`; `def(State[S])` on `post` (`state_post_fail/state_without_body`, the same text); `def(Headers)` (`get_headers_api_fail/post_headers_alone`, `the handler's parameter is the request body; ...`); `def(Int, Headers)` (`get_headers_api_fail/post_route_value_then_headers`, `the handler's last parameter is the request body; ...`); `def(String)` on `/x/{a}` (`string_route_api_fail/post_string_alone_with_placeholder`, `handler takes only the request body; route must declare no path or query parameter`);
- `Int is a route-value type, never the request body; ...` becomes `handler takes one Int parameter; route must declare exactly one path or query parameter` for a lone `Int` without a placeholder (`compile_fail/post_int_body`, `typed_post_int_body`, `state_post_int_as_body`) and `handler takes two route values; route must declare exactly two path or query parameters` for `(Int, Int)` on one placeholder (`compile_fail/post_int_int`, `typed_post_int_int`);
- the body-type messages become `get`'s placeholder messages for a lone `String` without a placeholder (`compile_fail/post_string_body`: `handler takes one String parameter; ...`), `(String, String)` on one placeholder (`string_route_api_fail/post_string_then_string_body`: the two-value message) and a lone `Optional[Int]` without a placeholder (`optional_values_api_fail/post_optional_as_body`: `handler takes one Optional route value; route must declare exactly one query parameter and no path parameter`);
- four fixtures pinned rule order with an `Int` in the body position, which is now a bodyless shape; each keeps its intent with a type of no kind there instead (`route_values_api_fail/post_count_before_last_slot`, `optional_values_api_fail/post_optional_count_before_body_rule` and `put_optional_at_path_before_body_rule` keep their texts; `route_values_api_fail/put_query_key_twice_reported_last` is re-pinned from the `Int` message to `the handler's last parameter is the request body; ...`, still a body rule reported before the repeated key).
Shapes no fixture pins change the same way, by the same rule: every bodyless shape's rejection is now `get`'s message naming the method (read in `_rule`, for example `def(Int, Headers)` on the wrong placeholders, `handler takes one Int parameter; ...` where it was `... and the request body; ...`, and `def(Headers, Headers)`, `a post handler takes one Headers, as its last parameter` where it was the message for a slot before the body). Every other fixture keeps its text (`check.sh`, all fixtures). Only rule branches and messages change, so by `docs/DEVELOPMENT.md` section 3 no whole-output comparison applies.

**By kind (M2-016): not an M2 reopen.** The accepted set grows (bodyless shapes on three methods); no handler that registered is rejected or registers differently; the overload set and the result clause are unchanged; the diagnostics above change; the runtime of every route that registered before is unchanged (every existing test passes), and a bodyless route answers as `get` does.

**Cost.** A shape family is no longer one rule set: a change to `get`'s rules or messages changes bodyless `post`, `put` and `patch` handlers too, and a new slot kind must say whether it is bodyless. A handler that meant to take a body but declared none registers and answers without reading it; its own code shows that, and a body type that forgot its conformance is still rejected. `Int` and `String` in the body position lose their dedicated messages: they are route values, reported by the placeholder rules.

**Invariants:**
- On `post`, `put` and `patch`, a shape whose slots are all absent, route values or a `Headers` takes `get`'s rules and is dispatched as on `get`; its request body is never read and Muntin answers no status for it.
- Every other shape keeps `post`'s rules; a last slot of no kind gets the body-type message on all three methods.
- `get`, `delete`, the overload set, the `where` clause, `_route`, `App.handle`, `_slot`, the storage module and the one `rebind_var` are unchanged.

**Revisit when:**
- an application needs a bodyless route to refuse a body (candidate C), or optional bodies are decided: the refusal belongs to that decision;
- a typed `DELETE` body is decided (M3-020): `delete` would then take `post`'s shapes, bodyless ones included;
- a new slot kind is added: decide whether `_bodyless` admits it;
- a `FromHeaders` conversion trait is decided (M3-016's candidate 3): it would be a bodyless slot on these methods as on `get`.

**Verification.** `tests/test_bodyless.mojo` (5 tests) registers every bodyless shape, stateless and stateful, on `get`, `post`, `put` and `patch` with the same handler and compares each method's answer (status, body bytes and every header field in order) with `GET`'s for 40 targets (accepted ones and 400s), with and without header fields, under four bodies (none, text, a JSON document under a JSON `Content-Type`, bytes that are not UTF-8); spot-checks the answers themselves; and runs DX's example as written, a typed function value and generic forwarding. It does not build against `main`'s `src` (`the handler's last parameter is the request body; ...`). `tests/bodyless_api_fail` (8 fixtures), built against `main`'s `src`: the three that pin a last slot of no kind on `post`, `put` and `patch` fail there with the same text (regression pins: that message must not change); the other five fail there with the old texts (`handler takes two route values and the request body; ...`, `a post handler's parameter before the body is a route value: ...`, `a post handler takes the request body as its last parameter`, `handler takes only the request body; ...`, `Int is a route-value type, ...`), so each is evidence for the change. Scratch mutations of `_registration_rules.mojo`, each red: the bodyless branch removed (the test does not build; five fixtures lose their text); `Headers` excluded from `_bodyless` (the test does not build; `post_headers_before_value` loses its text); a slot of no kind admitted into it (the three body-type fixtures lose their text); the branch skipped for stateful handlers (the test does not build); and the branch applied to `post` only (the test does not build; the `put` and `patch` fixtures lose their text).

**Fresh-context review.** A review of the diff rebuilt the new and re-pinned fixtures and 95 existing `post`, `put` and `patch` fixtures against the change (all as expected) and the new ones against `main`'s `src` (as above), and confirmed that the deleted fixtures' shapes are covered by `tests/test_bodyless.mojo`. It found nothing blocking; each finding was acted on: DX's stateful `post` section did not list bodyless shapes or say a bodyless handler reads `Headers`; ARCHITECTURE's rule-order paragraph did not name the bodyless branch; `_post_rule`'s docstring still called a lone `String` a body; DX gave only the `Int` placeholder message; this record listed only the changes fixtures pin (the general rule and two unpinned examples are now named); the stateful three-slot shapes were untested (`def(State[S], V, V)` and `def(State[S], V, V, Headers)` are now in the comparison); three fixture comments had a doubled `#`.

**Owner review.** A second review on the pull request found no implementation defect and three gaps, each acted on: the comparison lacked `def(State[S], V)` and `def(State[S], Headers)` (both added, so every stateless and stateful bodyless shape is compared); it compared status, text and the count of `Content-Type` fields only (it now compares the status, the body bytes and every header field in order, and one handler sets a field; a scratch copy registering that route's `post` without the field turns two tests red); and DX's "any body" read as a network promise (it now says any body that reaches `App.handle`, and that a backend refuses some requests first, as Flare does over `max_body_bytes`).
