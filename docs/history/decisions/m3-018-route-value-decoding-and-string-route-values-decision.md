# Route-value decoding and String route values decision (M3-018)

> **Current.** Now described in [route-values reference, "Decoding"](../../reference/route-values.md#decoding), [route-values reference, "`String` values and decoding"](../../reference/route-values.md#string-values-and-decoding) and [route-values reference, "`String` rules"](../../reference/route-values.md#string-rules).

> - [M3-024](m3-024-optional-query-values-decision.md): an empty value is `None` for an Optional value (400 kept for required values).
> - [M3-048](m3-048-bodyless-typed-post-put-and-patch-handlers-decision.md): `def(String)` on `post` registers as a bodyless route value instead of keeping its body message.
> - [M3-054](m3-054-application-route-value-types-decision.md): added the conversion trait M3-018 rejected for now (`FromRouteValue`, additive).

Status: **decision** (M3-018, PR #49; `src/muntin`, `adapters/` and `tests/` are unchanged in it). It decides that percent-decoding belongs to the capture of a route value rather than to its type's conversion, reopens M2 so that `Int` values follow that rule, and decides what a `String` route value then receives, so that `/users/{name}` is routable. M2-016 named non-`Int` route values the most visible gap; M3-014 decided that raw `String` is a route-value type and never a body, and that adding it is one slot kind and converter, no overload.

**Why this candidate.** Of SPEC's remaining candidates:
- Route-value decoding and `String` route values: every route that names something other than a number (`/users/{name}`, `/tags/{slug}`, `/search?{q}`) is unreachable by a typed handler today, and raw literals declare no placeholder, so it is not reachable by a raw one either. Whether a route value is raw or decoded text is a semantic default that cannot change later without silently changing what an unchanged handler receives, and later route-value items (several values, path and query together, optional values, other value types) build on it.
- Middleware: more leverage overall, but `App.handle` is already the one seam and no handler shape depends on what wraps it, so postponing it builds nothing on a wrong seam; its design is also the largest and least settled on Mojo 1.1.0 (no captures, no existentials).
- `put`, `patch`, `delete`: M3-014 settled the structure (six arity overloads each over the shared rules); there is little design uncertainty left, so it is production work, not a decision.
- `POST` without a body and `FromHeaders`: both are M3-016 revisit conditions whose triggers have not fired.
- `app.run()`/lifecycle: serving belongs to the backend (SPEC, M2-016 item 1) and depends on Flare's server API more than on Muntin's.
- Several route values: a rule change that is cheaper after the value types are settled; `(Int, Int, B)` on `post` is slot arity 3, eight overloads.

**Question.** When Muntin captures a typed route value from a `{name}` path segment or a `{key}` query item, is percent-decoding part of the capture or of the destination type's conversion? If the capture owns it, should the existing `Int` semantics reopen accordingly? And what exact values, failures, shapes and diagnostics does adding `String` then produce?

**What settles it:**
- where decoding belongs: whether the alternatives make a handler's type decide how its URL is read, what each costs existing `Int` routes (which inputs change status, which proven DX statements and tests change), and what later value types would parse;
- the value's content: what clients can send (over Flare a request target carries only `!`..`~`, so any other byte reaches Muntin percent-encoded), the encodings in RFC 3986 section 2.1 and the `+` rule of the WHATWG URL Standard's `application/x-www-form-urlencoded` parser, and Mojo 1.1.0's behavior when a `String` is built from decoded bytes that are not UTF-8 (measured);
- shapes, statuses and messages: scratch copies of production with a `String` kind and each location of the decoding, built and run with `check.sh` (which expected texts change), `test.sh` (which existing tests change) and probes of each status, and a loopback probe through Flare for decoding exactly once;
- what the M2 contract says about each changed behavior, and whether a change follows M2-016's reopen conditions.

**Boundaries:**
- `Int` route values (conversion, the set of inputs answered 400, nothing decoded) change only through an explicit M2 reopen recorded here; query keys compared byte for byte; `Request.path` and `Request.query` raw; matching on the raw path; raw handlers;
- M3-014: `String` is a route value and never a body;
- the registration structure: six overloads per method, the `where` clause, the rule guard, one `rebind_var`, the storage module and unsafe confinement;
- every existing diagnostic, unless this record names the change and why;
- the M2 contract's 400/404/500 boundary (SPEC, "M2 completion contract"); a change to it reopens M2.

**Candidates to measure:** where decoding belongs (every route value at capture, reopening M2 for `Int`; `String` only; capture with `Int` kept raw; no decoding), and, under the chosen one, the empty value, the decoding rules (strict or WHATWG's, `+`, keys), control characters, where the decoder runs, a Muntin text type and a conversion trait for application route-value types, and deferral.

**Selected: a route value is percent-decoded once, when it is captured, and then converted; `String` becomes a route-value kind beside `Int`.** Decoding belongs to the capture, not to a type: the `Int` and `String` handlers on one route receive the same decoded text, and a later value type parses decoded text too. Because `Int` values were undecoded, this reopens M2 for one statement (below). It adds no overload, no public type and no injected kind.

```mojo
def profile(name: String) -> String:
    return "profile " + name

def search(q: String) -> String:
    return "results for " + q

app.get["/users/{name}"](profile)
# GET /users/alice        -> 200 "profile alice"
# GET /users/J%C3%B6rg    -> 200 "profile Jörg"
# GET /users/a+b          -> 200 "profile a+b"     (`+` is literal in a path)
# GET /users/%zz, /users/%FF -> 400 "Bad Request"  (bad escape; not UTF-8)
app.get["/search?{q}"](search)
# GET /search?q=mojo+lang -> 200 "results for mojo lang"
# GET /search?q=a%2Bb     -> 200 "results for a+b"
# GET /search, /search?q=, /search?q=1&q=2 -> 400 "Bad Request"
# and, for the existing `app.get["/items?{limit}"](list_items)`:
# GET /items?limit=%31%30 -> 200 "items 10"        (400 before this decision)
```

- **Shapes.** A `String` parameter goes wherever an `Int` route value goes, once: `get` `def(String)` and `def(String, Headers)`; `post` `def(String, B)` (`B` a `FromBody`, a `Json[T]` or a `WithHeaders[B2]`); each also after a leading `State[S]`. The route literal declares exactly one `{name}` segment or `{key}` item for it, as for `Int`; binding is positional. Results and errors are unchanged.
- **The kind** is decided by exact type equality, `A == String`, beside `Int`, `Request` and `Headers` (`String` is origin-free, so `_as[String, A]`, which `_respond` already uses for results, is exact). `StaticString`, `StringSlice` and application types are not route values. M3-014's rule stands: `String` is never a body, and `def(String)` on `post` keeps today's message.
- **A placeholder binds one non-empty value, whatever its type.** A path segment is never empty (an empty segment does not match, 404), and an empty query value (`?q=` or `?q`) is 400 for every route value, `String` included. Telling an empty value from an absent one belongs to the optional and default values item. 400 keeps today's M2 boundary; a later optional or default values decision can deliberately broaden the accepted set without invalidating any value accepted before, while a value now and 400 later would reject requests that work today.
- **Path capture:** the matched segment, percent-decoded (RFC 3986 section 2.1): each `%` followed by two hex digits (either case) becomes that byte, every other byte is kept, and `+` is literal. Matching runs first on the raw path, so `%2F` decodes to `/` inside one value and never splits a segment. Nothing is normalized (`..` and `%2E` are values like any other).
- **Query capture:** the value `App.handle` already finds by key, then `+` becomes a space, then the same percent-decoding. Keys are matched as before: undecoded, byte for byte, missing or duplicated 400.
- **Muntin's decoding, not a form parser.** Only the `+` rule comes from the `application/x-www-form-urlencoded` format, which is how `URLSearchParams` and HTML forms send a space. The WHATWG URL Standard's parser for that format decodes differently in three ways, each deliberate here (its binding also differs: `URLSearchParams` gives `""` for `?q=` and keeps duplicates, where Muntin's rules above answer 400): it keeps a `%` not followed by two hex digits (`?q=%zz` is `%zz` there, 400 here), it replaces bytes that are not UTF-8 with U+FFFD (`?q=%FF` is `"�"` there, 400 here, because a lossy value would give `%FE` and `%FF` the same name), and it decodes names too (`?%71=x` has the name `q` there; here it does not match `{q}`).
- **Invalid values, a closed set, each 400 before the handler:** an empty value, a `%` not followed by two hex digits, and decoded bytes that are not UTF-8 (Mojo 1.1.0's `String(from_utf8=)` raises on them, measured). Anything else that decodes to valid UTF-8 is a value, NUL and other control characters included (`%00`, `%0A`, `%09`): which text an application accepts is the application's to decide (RFC 3986 section 7.3), as a missing header field is. Decoding validates the encoding, not the application's safety: a handler that passes a route value to a filesystem, a C API, a database or another interpreter validates the characters that destination requires.
- **Conversion after decoding:** a `String` receives the decoded text; an `Int` parses it with M2's unchanged rule (optional `-`, ASCII digits, `Int` range), so `%34%32` is 42 and `%2D7` is -7, while `+1`, `%2B1`, `%20`, `%zz` and `%2534` are still 400.
- **Where it runs:** in `App.handle`, where the values are captured: after `_match` has filled the raw arguments with the path captures, each is replaced by its decoded text, and the `_query_value` result is decoded before it is appended; one `try` around both answers 400. `App.handle` knows whether a value came from the path or the query, so no flag reaches the adapters, and the adapters, the overloads' signatures and `_Erased` are unchanged. `_slot`'s `String` branch copies the decoded text into the handler's value; its `Int` branch parses as before.
- **Order:** 404 → query value missing or duplicated, then any value empty, a bad escape or not UTF-8, 400 (`App.handle`) → `Int` conversion 400 (adapter) → body steps (415, 413, field rebuild 500, body 400) or the `Headers` rebuild → handler → result. Each status and its position relative to the body steps are as for `Int` today.
- **Ownership:** a fresh `String` per request, moved into the handler, which declares `name: String` or `var name: String`; `mut name: String` selects no overload, as for `Int`. A typed function value spells it `var String` (`def(String) thin raises Never -> String` is the toolchain's `TODO: function type conversions between closures not supported yet`, as for `Int` and `Headers`), and a generic helper forwards a `String` handler through M3-015's edge 4 (measured).
- **Raw handlers and `Request`:** unchanged and undecoded. Raw literals declare no placeholder, so a raw route captures nothing; `req.path` and `req.query` stay the text received, and an application that must see the encoded form (`%2F` versus `/`) uses a raw handler.

**M2 reopen.** M2 says nothing is percent-decoded: `docs/DX.md` ("Proven vs. target status") states it for path values ("Percent-encoding is not decoded") and for query values ("`limit=%31%30` is not `10`", proven by `tests/test_app.mojo`, where `/items?limit=%31%30` is 400). Decoding `Int` values changes that M2 semantics rather than adding to it, which [M2 closure (M2-016)](m2-016-m2-closure.md) makes a reopen needing its own explicit decision; this record is that decision. M2-016's other condition, a proven DX statement that stops passing its test, does not arise as a defect: the slice changes both DX statements and the test together, to the decoded behavior. What changes for `Int`: a value that contains at least one valid escape and whose decoded text satisfies M2's `Int` rule (`%34%32`, `%2D7`, `-%37`, `?limit=%31%30`) is no longer 400; it gets what the same value written in plain digits gets (the body steps, then the handler's result or error, so a raising handler's 500 or a `Json[T]` body's 415 where those apply). Escaped text that decodes to something the `Int` rule rejects (`%2D%2D7`, `%2B1`, `%20`, a number out of range) is still 400. Measured: `/items?limit=%31%30` is the one existing test whose outcome changes; no other existing test showed a semantic change. No value that was accepted changes meaning (an accepted `Int` value has no `%` and no `+`), and nothing that was answered without a 400 now gets one. What stays: every invalid route value is still 400 before the handler, the "missing, duplicated, empty or invalid query value" rule, binding, results, the raw escape hatch, the backend seam and every M2 signature. The slice amends the M2 contract for this, as M3-015 did, and updates both DX statements in the same pull request.

**Measured premise: Flare passes the encoded target through.** Decoding in Muntin is correct only if the backend does not decode first, and no loopback case sends `%XX`. A raw-TCP probe through Flare v0.11.0 confirmed that the backend keeps the target encoded: `/users/%2541` reaches Muntin encoded and the one decoding in Muntin gives `%41`, and `/i/%2534` is 400 for an `Int`.

**Invariants:**
- A route value is decoded exactly once, in `App.handle`, from the raw capture, before any conversion; `+` is a space only in a query value. Query keys, `Request.path`, `Request.query` and raw handlers are never decoded.
- A placeholder binds one non-empty value. The invalid values are exactly: empty, a bad escape, not UTF-8; each is 400 before the handler. No new status.
- `String` is a request slot kind by exact type equality; a route value is an `Int` or a `String`, at most one per handler; `String` is never a body.
- No overload, adapter signature, `_Route` field, storage or unsafe change; one `rebind_var`.

**Cost.** M2 reopens: an `Int` value written with escapes is accepted (the M2 reopen paragraph has the exact scope). Query keys are matched undecoded while values are decoded. The decoding is Muntin's own and is not what `URLSearchParams` parses (three documented decoding differences). Three route-value messages exist in an `Int` and a `String` form so that every `Int` message stays byte-identical; two existing messages are reworded and one fixture is retired. Each route value costs one decoded copy per request, `Int` included, and a `String` value a second copy at the slot.

**Revisit when:**
- an application must tell `%2F` from `/` or see the encoded text in a typed handler (a raw handler can today): revisit a raw-text form;
- applications need lossy decoding, a `+` kept in a query value, or control characters rejected: revisit the closed invalid set and the `+` rule;
- a route literal needs a query key that clients encode (`{tags[]}` arrives from `URLSearchParams` as `tags%5B%5D`): revisit decoding keys;
- an application-defined route-value type is proposed: revisit the conversion trait with M2-005's disjointness condition; it parses decoded text;
- a backend delivers a decoded target: the seam must carry the raw target, or decoding moves;
- optional or default query values are decided: revisit whether an empty value stays 400;
- several route values are decided: the `at most one route value` messages and the `Int`/`String` message pairs are replaced by that item's rules.
