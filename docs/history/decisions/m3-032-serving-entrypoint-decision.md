# Serving entrypoint decision (M3-032)

> **Current.** Now described in [serving reference, "`Server.bind`"](../../reference/serving.md#serverbind), [serving reference, "`serve`"](../../reference/serving.md#serve) and [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter).
> Changed in part since:
> - [M3-044](m3-044-server-receive-body-limit-decision.md): Server.bind gained max_body_bytes, and serve refuses FLARE_BUFRING_HANDLER=1 (M3-032: no backend configuration, the variable neither set nor tested).
> - [M3-045](m3-045-graceful-shutdown-decision.md): serve turns SIGTERM and SIGINT into a graceful stop (M3-032: no stop, graceful shutdown or signal handling).
> - [M3-047](m3-047-server-idle-timeout-decision.md): Server.bind gained idle_timeout_ms.
> - [M3-049](m3-049-multi-worker-serving-decision.md): several serving threads through `serve[make](workers=n)`, one App per worker (M3-032: one reactor thread, no worker count); serve(app) stays single-threaded.
> - [M3-051](m3-051-server-tls-decision.md): HTTPS through a tls argument on Server.bind (M3-032: no TLS).
> - [M3-066](m3-066-request-header-conversion-decision.md): Server.bind gained max_header_fields, with a 431 past it.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-032, PR #69; `src/muntin`, `adapters/`, `compat/` and `tests/` are unchanged in it). It decides the first supported way for application code to serve an `App` over a real socket. Today there is none: the Flare integration is exercised only by tests, and a program that builds Flare's `HttpServer` around `MuntinHandler` itself is unsupported (`docs/ARCHITECTURE.md`, "Flare adapter").

**Why now.** No supported way to serve is the largest gap in reach ([M3-024](m3-024-optional-query-values-decision.md)). M3-024 deferred it because the pinned Flare v0.11.0 could not stop gracefully and would drop its server spellings in v0.12. The pin is now v0.12.0, whose spellings (`HttpServer.bind`, `serve`) this record measures. Graceful stopping is still out of reach from the serving thread (below), so this record decides a lifecycle that does not need it.

**Question.** What is the smallest supported entrypoint that serves an `App` without the application building backend objects or test code, and: its spelling and import path; whether it moves, borrows or copies the `App`; how the address is given, and with which defaults; whether it blocks or returns a handle; how a bind or start failure surfaces; whether it includes graceful shutdown, signal handling, several workers, backend configuration, TLS, HTTP/2 or HTTP/3; and whether it keeps Flare out of `src/muntin` (A2).

**What settles it:**
- the current serving path, traced in code, and the pinned Flare v0.12.0 server API (`flare/http/server.mojo`, `flare/http/handler.mojo`, `flare/net/address.mojo`, `flare/utils/posix_proc.mojo`);
- per candidate, scratch code (not retained) built with the pinned toolchain in the `flare` environment: a user program built with `--Werror`; a loopback server answering a fixed request set as `App.handle` does; a bind failure; a stop; the worker arity;
- whether `src/muntin` still precompiles in the default environment and `scripts/check_boundaries.sh` still passes.

**The serving path today.**
- `MuntinHandler(var app: App)` owns the `App` and implements Flare's `Handler` (`Deinitable & Movable`). Its `serve` converts the request (a field it cannot represent is answered 400), calls `App.handle`, converts the response back (an invalid outgoing field is answered 500), and applies the `HEAD` rule at every exit (M3-027).
- The only server lifecycle is `_serve_in_child` in `adapters/flare/test_localhost_roundtrip.mojo`: `HttpServer.bind(SocketAddr.localhost(0))` in the parent (`bind` already listens, so the port is known and readiness is `bind` returning), `fork`, `server.serve(MuntinHandler(app^))` in the child under a 30 s `alarm`, SIGKILL and `waitpid` in the parent. It is test code: it puts Flare's `HttpServer` and `SocketAddr` and the adapter's handler in the program, and no spelling of it is documented or pinned. `adapters/flare/serve_probe.mojo` type-checks the same shape without binding.
- Flare v0.12.0: `HttpServer.bind(addr: SocketAddr, config=ServerConfig()) raises` (`AddressInUse`, `NetworkError`). `serve[H: Handler](mut self, var handler: H) raises` runs one reactor on the calling thread, serving HTTP/1.1 and HTTP/2 with prior knowledge on one listener, and leaves its loop when `close()` or `drain(timeout_ms)` sets its stop flag, which their docs say is done from another thread, or when the reactor's poll raises, which the loop records as a crashed worker and answers by returning normally (`_unified_reactor_impl.mojo`); `serve` itself can also raise. `serve[H: Handler & Copyable](mut self, var handler: H, num_workers: Int, ...)` runs one reactor per thread, each on `H.copy()`. On the cleartext path Flare installs no signal handler (`flare.utils` names `SIGINT` and `SIGTERM` as constants only; its TLS wrapper ignores `SIGPIPE`). Its `serve` reads `FLARE_BUFRING_HANDLER` (an opt-in Linux io_uring path, HTTP/1.1 only) from the environment.
- Mojo 1.1.0: `App` is `Movable`, not `Copyable`.

**Measured premises.** Each candidate served this `App` over loopback on macOS arm64 with Mojo 1.1.0 and Flare v0.12.0:

```mojo
app.get["/hello"](hello)          # "hello"
app.get["/users/{id}"](get_user)  # id: Int, "user <id>"
```

and Flare's client sent `GET /hello`, `GET /users/7`, `GET /users/abc`, `GET /missing`, `POST /hello` and `HEAD /users/7`; each wire answer was compared with `App.handle` on the same request (status and body; `Allow` on the 405; for `HEAD`, no content and a `Content-Length` equal to the `GET` body's length).

- **Bind failure** (B2, parent process, while a child served): the child's port raised `AddressInUse: 127.0.0.1:<port>`; `"localhost"` and `"example.invalid"` raised `AddressParseError: invalid address '...'` (`IpAddr.parse` is `inet_pton`: IP literals only, no name resolution); `"::1"` and `"0.0.0.0"` bound. Flare's `SocketAddr` takes a `UInt16` port, so port 70000 needs a range check before the conversion; the scratch code's own check raised `port out of range: 70000`. After these raises the borrowed `App` still answered (`app.handle` gave `hello`).
- **Stop:** SIGTERM and SIGINT sent to a serving child each ended it; `waitpid`'s status reported termination by that signal, within the probe's millisecond resolution, with no exit code and nothing drained. The same held for B1 with a borrowed and with a moved `App`, A and C. No server process was left.
- **Workers:** `server.serve(MuntinHandler(App()), num_workers=2)` does not build: `argument type 'MuntinHandler' does not conform to trait 'Handler & Copyable'`. A handler holding a `Pointer[App, origin]` and declared `Copyable` does build with `num_workers=2` (its `serve` did not call `App.handle`); the same handler not declared `Copyable` fails with the text above. So `Handler & Copyable` is the first compile-time gate to Flare's multi-worker overload, and a handler that only holds an `App` pointer passes it. That does not show that a handler calling `App.handle` from several worker threads builds, or that doing so is safe; this record neither tests nor promises either.
- **Warnings:** the B1 and B2 user programs build with `--Werror`; only programs that reach Flare's `HttpClient` (the probes' clients) print the warning `check_flare.sh` already knows (`KNOWN_WARNING`).
- **Call shapes:** with `serve(mut self, ...)`, `Server.bind(...).serve(app)` does not build (`invalid use of mutating method on rvalue of type 'Server'`); with `serve(var self, ...)`, `server.serve(app)` does not build (`value of type 'S' cannot be implicitly copied ... consider transferring the value with '^'`), so each call would be `server^.serve(app)`.
- **A, observed:** a default-environment program that never calls `run` still built against A's core (the Flare import was local to `run`); this is observed behavior of Mojo 1.1.0, not something Muntin could rely on. Precompiling the package (`pixi run package`, `check.sh`'s package build) fails, and so does any default-environment program that calls `run`. A's core also imports the adapter module for the conversions, a cycle from core to adapter to core.
- **Spelling and drop** (B2 with the initializer below): `Server("127.0.0.1", 0)` and `Server(host="127.0.0.1", port=0)` each do not build (`no matching function in initialization`, noting `missing required argument: '_host'`); `Server(_host="127.0.0.1", _port=0)` builds. While a `Server` held a port, binding it again raised `AddressInUse`; after that `Server` was dropped, binding the same port succeeded. The revised B2 still answered the request set as `App.handle` does (6 of 6), and its user program still builds with `--Werror`.
- **The selected shape as a program:** B2's user program bound `127.0.0.1:8080`; `curl /` answered 200 `Hello, Mojo!`, `curl -X POST /` 405 with `Allow: GET, HEAD`, and SIGTERM ended it.

**Selected: B2. The Flare adapter module gains `Server`: `Server.bind(host, port)` binds and listens, `server.port()` reports the port, and `server.serve(app)` serves a borrowed `App` on the calling thread until the process ends or serving fails.** `src/muntin` and `App.handle` are unchanged, and no core API is added.

```mojo
from muntin import App
from muntin_flare import Server


def hello() -> String:
    return "Hello, Mojo!"


def main() raises:
    var app = App()
    app.get["/"](hello)
    var server = Server.bind("127.0.0.1", 8080)
    print("listening on http://127.0.0.1:" + String(server.port()))
    server.serve(app)
```

From a clone it runs as `pixi run -e flare mojo run -I src -I adapters/flare examples/hello_server.mojo`.

- **Spelling and import.** `Server` in `adapters/flare/muntin_flare.mojo`, the existing adapter module, imported as `muntin_flare` with `-I src -I adapters/flare` in the `flare` environment. Not `muntin.Server` or `muntin.flare`: `src/muntin` imports no backend (A2) and builds in the default environment, which has no Flare. The backend is chosen by one import in `main`; handlers, routes, `App` and tests stay backend-free, and no Flare type appears in `Server`'s signatures.
- **`Server.bind(host: String, port: Int) raises -> Server`.** No defaults: neither a port nor an exposure choice is right for every program. `host` is an IPv4 or IPv6 literal (`"127.0.0.1"`, `"0.0.0.0"`, `"::1"`), never a name. `port` is 0 to 65535; 0 lets the system choose. It binds and listens before returning, so a client may connect as soon as it returns. It raises an `Error` for a port out of range (Muntin's check, before anything is bound), a host that is not an IP literal, an address in use or any other OS error; the text of Flare's errors is not part of the contract. Dropping a `Server` closes its listener (measured above). `Server.bind` is the one public spelling, because it names the side effect. The work is done by the initializer `Server(*, _host: String, _port: Int) raises`, which `bind` calls: its arguments are keyword-only and `_`-prefixed, so `Server(host, port)` does not build, and `Server(_host=..., _port=...)` is callable but not API (`docs/ARCHITECTURE.md`, "Modules and public surface"), as `JsonValue`'s `_doc`/`_at` initializer is. No initializer takes a Flare value, so none appears in `Server`'s signatures; its one field, the `HttpServer`, is `_`-prefixed and, as every field on Mojo 1.1.0, reachable by name but not API.
- **`server.port() -> Int`.** The bound port, the system's choice for 0.
- **`server.serve(mut self, app: App) raises`.** Borrows the `App`, as `TestClient(app)` does, so a raise leaves it usable. It serves on the calling thread and does not return while serving. When Flare's `serve` raises, the raise propagates; when it returns, `serve` returns. Muntin adds no policy for a return: with nothing Muntin exposes setting Flare's stop flag, on v0.12.0 a return means the reactor stopped (a failed poll), and a program whose `serve` call ends has stopped serving. Each request that reaches the handler is answered as `MuntinHandler` answers it: `App.handle`'s answer, the adapter's 400 and 500, and the `HEAD` rule; a request Flare refuses first gets Flare's answer: a lowercase method and a target byte outside `!`..`~` (`docs/ARCHITECTURE.md`, "Other current limits"), and a body over Flare's 10 MiB `max_body_size`, which Flare answers 413 (backend configuration, below).
- **Protocols.** Cleartext HTTP/1.1, and HTTP/2 with prior knowledge on the same listener, as Flare's single-worker `serve` accepts them (with `FLARE_BUFRING_HANDLER=1` on Linux, HTTP/1.1 only; below). No TLS, no HTTP/3, no protocol settings.
- **Concurrency.** One reactor thread. `App.handle` is never called concurrently, as today. Whether it may be is undecided ([M3-001](m3-001-application-state-decision.md) interior mutability, [M3-008](m3-008-json-codec-decision.md) the JSON cap), so there is no worker count; the private handler that holds the borrowed `App` is not `Copyable`, which keeps Flare's multi-worker overload out of reach, but that is a guard, not the reason.
- **Stopping.** Muntin adds no stop call, graceful shutdown or signal handling. SIGINT (Ctrl-C) and SIGTERM end the process by their default action, unless the process inherited them ignored (`nohup`, a background job of a non-interactive shell): in-flight requests are cut, nothing is drained, and no destructor runs.
- **Backend configuration.** None is exposed: Flare's `ServerConfig` defaults apply (among them the 10 MiB `max_body_size`, keep-alive and its timeouts). Flare reads `FLARE_BUFRING_HANDLER` from the environment inside `serve`; Muntin neither sets nor tests it, and answers on that path are not covered. (This was the state when M3-032 was decided. [M3-044](m3-044-server-receive-body-limit-decision.md) later added `Server.bind`'s `max_body_bytes`, and measured the `FLARE_BUFRING_HANDLER` path, which Muntin does not support.)
- **`MuntinHandler`** stays the adapter's handler for its own tests and probes; a program that builds `HttpServer` around it is still unsupported.

**Candidates.**

| B1: one call, `serve(app, host, port)` | rejected for now: the caller cannot learn port 0 or when the listener is ready, so a test needs a fixed port and polling (as measured), the loopback suite could not run through it, and the tested path would again differ from the supported one. **Backend seam and M2: not reopened.** `App.handle(Request) -> Response` is unchanged and remains the only seam; the adapter gains a public type. A2 is unchanged and `check_boundaries.sh` keeps its rules. Nothing `App.handle` answers changes.

**Cost.** A public type in the adapter module, outside the package. A serving program runs in the `flare` environment with two `-I` paths, until Muntin is packaged. No graceful shutdown and one thread. If Flare's reactor fails, `serve` returns and a program that does nothing after it ends with status 0. The host is an IP literal. Error texts are Flare's. The adapter keeps two handlers, one owning the `App` and one borrowing it.

**Revisit when:**
- Flare offers a stop the serving thread can request, or the toolchain gives the process a thread or signal primitive Muntin would use: revisit whether `Server` gains graceful shutdown and signal handling;
- an application needs more than one serving thread: revisit whether `App.handle` may run concurrently ([M3-001](m3-001-application-state-decision.md) interior mutability, [M3-008](m3-008-json-codec-decision.md) the JSON cap) and whether `Server` takes a worker count;
- `compat/flare/serve/workers_need_copyable.mojo` or `compat/flare/serve/server_handler_not_copyable.mojo` builds (Flare drops the `Copyable` requirement, `App` becomes `Copyable`, or the private handler does): revisit the guard, not concurrency; serving from several threads still needs the decision in the previous item;
- `compat/flare/serve/server_positional_init.mojo` or `compat/flare/serve/server_keyword_init.mojo` builds (someone added a positional initializer, or gave the initializer's arguments public names): revisit whether `Server` has one public spelling;
- a second network backend exists: revisit whether its entrypoint and this one share a trait (C);
- applications need a backend limit or protocol setting changed (body size, timeouts, TLS): revisit whether `Server` takes a Muntin-owned configuration;
- Muntin is published as a package: revisit the import path `muntin_flare` and the run command;
- applications ask for one call that binds and serves: revisit B1 as a function over `Server`.

**Next production slice (M3-033): `Server` in the Flare adapter.**
- Code: `adapters/flare/muntin_flare.mojo` only. The body of `MuntinHandler.serve` and `_answer` moves into a module-level function of the `App` and the Flare request, unchanged, which `MuntinHandler.serve` calls. A private handler, generic over an immutable origin and not `Copyable`, holds a `Pointer` to the borrowed `App` and calls the same function. `struct Server(Movable)` holds one field, `_server: HttpServer`. `__init__(out self, *, _host: String, _port: Int) raises` raises `port out of range: <port>` outside 0 to 65535 before parsing the host, then binds `SocketAddr(IpAddr.parse(_host), UInt16(_port))` with Flare's default `ServerConfig`; no initializer takes a Flare value or positional arguments. `@staticmethod bind(host: String, port: Int) raises -> Server` returns `Server(_host=host, _port=port)`. `port() -> Int` reads `local_addr()`. `serve(mut self, app: App) raises` calls the single-worker `serve` with the private handler, and nothing else. The module docstring gains this record's contract. No change to `src/muntin`, `tests/` or the existing `compat` probes.
- Tests, in a new `adapters/flare/test_server.mojo`: `bind("127.0.0.1", 0)` reports a port above 0; a child serving a borrowed `App` answers a request sent right after `bind` returned, with no sleep or retry; binding a port a child serves raises; ports -1 and 65536 raise `port out of range` and `"localhost"` raises; `"::1"` and `"0.0.0.0"` bind (`"::1"` was measured on macOS only; the pull request reports it on both CI runners); a bound and dropped `Server` releases its port (binding the same port again succeeds); a serving child that first restores the default disposition of the signal it is sent (`signal(sig, SIG_DFL)` through `external_call`, so the test does not depend on what the runner's process inherited) is, when sent SIGTERM, reaped as terminated by SIGTERM, and, when sent SIGINT, as terminated by SIGINT, both read through `waitpid`'s status (Flare's `waitpid` discards it) and before the child's alarm.
- Loopback: `_serve_in_child` in `adapters/flare/test_localhost_roundtrip.mojo` binds with `Server.bind("127.0.0.1", 0)` in the parent and calls `server.serve(app)` in the child (keeping the alarm and SIGKILL), so every existing case, over HTTP/1.1 and h2c, runs through `Server`; its module docstring's lifecycle paragraph says so.
- Must not build, each with one error, checked by `check_flare.sh` as `headermap_in_request.mojo` is but built with `-I src -I adapters/flare`: `compat/flare/serve/workers_need_copyable.mojo` (`MuntinHandler` passed to `serve` with `num_workers=2`) and `compat/flare/serve/server_handler_not_copyable.mojo` (the private handler `Server` uses, built over a borrowed `App`, passed the same way), each expecting `does not conform to trait 'Handler & Copyable'`; `compat/flare/serve/server_positional_init.mojo` (`Server("127.0.0.1", 0)`) and `compat/flare/serve/server_keyword_init.mojo` (`Server(host="127.0.0.1", port=0)`), each expecting `no matching function in initialization`; the first catches a positional initializer, the second public keyword names. Nothing tests what `serve` does when Flare's `serve` returns: a failing reactor poll cannot be provoked from a test.
- Example: `examples/hello_server.mojo`, the program above as written; `check_flare.sh` checks its formatting, builds it with `--Werror` and does not run it (it binds port 8080).
- `scripts/check_flare.sh`: builds `test_server` (as a known-warning build if it reaches `HttpClient`) and the example, runs `test_server` with `NO_PROXY` and the leftover-process check the round trip has, runs the must-not-build steps, and adds the six new files to the default-environment exclusion loop.
