# Optional query values decision (M3-024)

> **Current.** Now described in [route-values reference, "Optional query values"](../../reference/route-values.md#optional-query-values) and [routing reference, "Order of checks"](../../reference/routing.md#order-of-checks).
> Changed in part since:
> - [M3-048](m3-048-bodyless-typed-post-put-and-patch-handlers-decision.md): a lone `Optional` on post is a bodyless route value, not a body with the `FromBody` messages.
> - [M3-054](m3-054-application-route-value-types-decision.md): the two reworded no-kind messages now also name `FromRouteValue`.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision** (M3-024, PR #56; `src/muntin`, `adapters/` and `tests/` are unchanged in it). It decides how a typed handler accepts a request in which a declared query key is absent. Today every `{key}` in a literal is required: a request without the key is 400 before the handler, so `GET /items` and `GET /items?limit=5` cannot reach one typed handler, and a raw handler that wants the same reads `req.query` and re-implements Muntin's pair splitting and percent-decoding, which are private.

**Why this candidate.** Of SPEC's remaining candidates, the strongest contenders:
- Optional or default query values: pagination, sorting and filters are optional by nature (`?limit=`, `?page=`, `?sort=`), and a client of an existing API omits them. No typed handler can serve such a URL scheme, because a matched route never falls through and a missing key is 400; a raw handler can, only by rebuilding query parsing and decoding by hand. DX section 3's design target is `def search(query: String, limit: Int = 20)`, and its status line says defaults and optional values are not implemented. M3-018 left the empty-versus-absent distinction to this item and M3-022 made it a revisit condition; both prerequisites (decoded capture, a second value beside the optional one) are now shipped. What is open is public and hard to change once applications depend on it: how absence reaches the handler, what an empty value (`?limit=`) means, which placeholders may be optional, and which diagnostics change. It is additive to the M2 contract and lives entirely in registration rules and `App.handle`'s capture.
- `HEAD` (with `OPTIONS` and 405 with `Allow`): the closest competitor. RFC 9110 section 9.1 says general-purpose servers MUST support `HEAD`, and today it is 404 even on a path a `get` route serves; no handler, typed or raw, can register for it. Answered automatically from `get` routes, it is not additive: every existing `get` route would start answering a method that is 404 today, which `tests/test_methods.mojo` and DX section 4 pin and which the M2 contract's 404 covers, so it reopens M2 under [M2-016](m2-016-m2-closure.md). Registered (`app.head`), it is additive, but it adds eight overloads and meets the MUST only for paths an application registers twice. Either way it decides a responsibility at the backend seam that has no owner yet: a `HEAD` response carries no content but a `Content-Length` it sends must equal the `GET` content's length (RFC 9110 section 8.6), so either `App.handle` or the backend suppresses the body, and how Flare v0.11.0 frames a `HEAD` response is unmeasured (M3-022). And choosing between the two is the resource-level method view M3-020 deferred together with 405 and `OPTIONS`. It is a decision of its own, with a reopen and a wire probe, compared again from SPEC's candidates when the next decision item is chosen.
- Lifecycle (a supported way to serve an `App`): application code has no supported way to serve today (M2-016, class 3), which is the largest gap in reach. But a serving API belongs to the backend, not to `src/muntin` (A2, SPEC product boundaries), so it is a decision about the Flare adapter's public surface and its packaging; and the pinned Flare v0.11.0 cannot shut down gracefully (`close()`/`drain()` need a second thread) or serve a move-only `App` on several workers, and its old server spellings are removed in v0.12. A supported serving API pinned to that version would fix a lifecycle contract the backend cannot keep yet.
- Observability (logging dropped handler errors), middleware: each needs a hook stored with the `App`, and on Mojo 1.1.0 handlers cannot capture and module-level variables do not compile, so each starts with its own injection or storage decision; no handler shape depends on them, so postponing them builds nothing on a wrong seam (M3-020, M3-022).
- Bodyless typed `post`, `put`, `patch`: a `FromBody` that accepts any body serves those routes today (M3-022). `FromHeaders` and compile-time header names: M3-016's revisit conditions have not fired. JSON follow-ups: an application `ToResponse` type answers with any status today, and the cap stays fixed until a concurrent backend (M3-008). Three route values or other value types: no current requirement names them, and the third value competes for slot arity 4 (M3-022). Schema/OpenAPI waits for a derived codec; parameter-name checking waits for function-parameter reflection.

**Question.** How does a typed handler accept a request in which a query key its literal declares is absent? Specifically: how absence (or a default) reaches the handler, through which parameter type or literal syntax, and whether Mojo 1.1.0 can express DX section 3's `limit: Int = 20`; which placeholders may be optional (query keys, path segments); what an absent key, an empty value (`?limit=`, `?limit`) and a repeated key each mean for an optional value; how an optional value counts against the two-value bound and the slot arities; how `App.handle` captures and transports an absent value; and which existing rules, diagnostics and M2 statements change.

**What settles it:**
- whether Mojo 1.1.0 can express each representation: a handler parameter with a default value (`limit: Int = 20`) registered through a generic slot, and whether the default is reachable from the registration (compile probe); `Optional[Int]` and `Optional[String]` through a generic `var A` slot, detected by exact type equality in `_kind` (M2-005's disjointness), converted through the one rebind site `_as` (compile and runtime probe on a scratch copy of `src/muntin`); a default written in the literal (`{limit=20}`), and whether its text can be checked against the slot's type at registration;
- whether a registration rule can tell, at compile time, whether the slot at a given position binds a path or a query placeholder (path placeholders bind first, so the position and `_path_params` decide it), so that an optional path value is a registration error, not a runtime surprise;
- what an empty value means, from M3-018's non-empty rule and its reasons, RFC 3986 section 3.4, and what HTML form submission sends for an empty field (the WHATWG URL standard's `application/x-www-form-urlencoded` serializer);
- every existing rule, diagnostic, fixture and test whose text or outcome a candidate changes (`_kind`, `_get_rule`, `_post_rule`, `_check` and `tests/`), and whether any statement of the M2 contract changes, as an addition or as a reopen under [M2-016](m2-016-m2-closure.md);
- that typed function values and generic forwarding reach the new parameter type through the existing overloads (M3-015's forwarding amendment names a new slot kind as its revisit condition).

**Boundaries that do not change silently:**
- every required route value: its rules, its capture (decoded once in `App.handle`, `Int` or `String` by exact type equality, non-empty, the closed invalid set, 400 before the handler), and every existing diagnostic, unless this record names the change and why;
- binding by position in the literal's order (path placeholders, then query placeholders), at most two route values, distinct query keys (M3-022);
- the registration structure: eight overloads per method name (slot arities 0 to 3, stateless and stateful), the `where` clause on the result, the rule guard, one `rebind_var`, the storage module and unsafe confinement; no overload is added;
- `State[S]` as the one injected slot, first; the body last on `post`, `put` and `patch`; `Headers` last on `get` and `delete`; the shape families of M3-020;
- query keys matched undecoded; `Request.path`, `Request.query` and raw handlers undecoded, raw literals declaring no placeholder;
- method matching, 404 on a method mismatch, first registered route wins, no fall-through;
- the M2 contract's 400/404/500 boundary for every request a registered route answers today; a change to it reopens M2;
- the backend seam at `App.handle`, with Flare out of the public API and of `src/muntin`.

**Candidates to measure:**
- the representation: an `Optional[Int]` or `Optional[String]` parameter, `None` when the key is absent; a default in the literal (`?{limit=20}`) with a plain `Int` or `String` parameter; a Mojo default parameter value (`limit: Int = 20`); an application conversion trait for optional text;
- which placeholders may be optional: query keys only, or path segments too;
- an empty value for an optional value: absent, 400 as for a required value, or `Some("")` for a `String`;
- a repeated key for an optional value: 400 as for a required value, or the first value;
- deferral.

**Selected: an `Optional[Int]` or `Optional[String]` parameter is an optional route value. It binds a query placeholder only; it is `None` when the key is absent or its value is empty, and the handler supplies any default (`limit.or_else(20)`).** A present value follows every rule of a required one. No public type is added (`Optional` is the standard library's), no overload is added, and nothing that registers or answers today changes; M2 does not reopen ("M2 contract" below).

```mojo
def list_items(limit: Optional[Int]) -> String:
    return "items " + String(limit.or_else(20))

def search(q: String, sort: Optional[String]) -> String: ...
def page(uid: Int, limit: Optional[Int], headers: Headers) -> String: ...
def tag_note(tag: Optional[String], note: Note) -> String: ...

app.get["/items?{limit}"](list_items)
app.get["/search?{q}&{sort}"](search)
app.get["/users/{uid}/posts?{limit}"](page)
app.post["/notes?{tag}"](tag_note)
# GET /items, /items?limit=, /items?limit -> 200 "items 20"  (limit is None)
# GET /items?limit=5, /items?limit=%35    -> 200 "items 5"
# GET /items?limit=x, /items?limit=1&limit=2 -> 400 "Bad Request" (handler not called)
# GET /search?sort=name                   -> 400 "Bad Request" (q is required)
```

- **Shapes.** An optional value is a route value wherever a required one is: `V` in every shape of M3-022's table may be `Int`, `String`, `Optional[Int]` or `Optional[String]`, in any combination, at most two per handler, with the body or `Headers` after them and `State[S]` before. No shape and no slot arity is added, so the eight overloads per method name and their candidate notes are unchanged.
- **Query placeholders only.** A path segment is never absent: a request without it has another path, which this route does not match (404), and an empty segment does not match either. So an optional value must bind a `{key}` placeholder. Binding is unchanged (path placeholders left to right, then query placeholders), so the value at position `j` binds a path placeholder exactly when `j` is less than the literal's path count, which the registration rule reads at compile time. An optional value at a path position is a registration error. This also catches one case of the positional swap M3-022 accepted: `def(limit: Optional[Int], uid: Int)` on `/users/{uid}?{limit}` is rejected instead of binding `uid`'s segment to `limit`.
- **Absent and empty are one case.** For an optional value, a key that does not appear in the query, a pair with an empty value (`limit=`) and a pair without `=` (`limit`) all give `None`. A placeholder never binds an empty value (M3-018), so the empty value's only choices were `None` or 400. Muntin deliberately treats an empty optional value as absence: it fits form-driven optional filters and defaults (an HTML form submits a named text control even when it is empty, as `name=`; the HTML Standard's "constructing the entry list" skips no control for an empty value, so a blank optional field arrives as `limit=`), and it keeps M3-018's non-empty invariant for every route value. What a blank field means is the application's semantics, not the standard's: the accepted cost is that `Some("")` is never produced, so an application cannot tell `?q=` from no `q` (an update API that reads an absent key as "unchanged" and `q=` as "set to empty" cannot be expressed with an optional value).
- **Present values keep every rule.** A non-empty value is decoded once at capture (M3-018) and converted as a required value is: an invalid escape, text that is not UTF-8, or an `Int` that does not parse is 400 before the handler, not `None`. A repeated key is 400, as for a required value, because a request that repeats it is ambiguous, not absent. Keys are matched undecoded. No new status and no new position: 404, then a required value missing, any key duplicated, a required value empty, or any present value a bad escape or not UTF-8, 400; then `Int` conversions, 400; then the body steps or the `Headers` rebuild; then the handler.
- **Defaults are the handler's.** DX section 3's `def search(query: String, limit: Int = 20)` is not expressible on Mojo 1.1.0 (measured premise below): the registration receives a function value, and the default does not travel with it. `Optional` with `or_else` is the closest type-safe form, and it also covers what a default cannot: a filter that is not applied when absent, and a default computed from `State`.
- **Kinds and rules.** `_kind` classifies `Optional[Int]` and `Optional[String]` by exact type equality, as `Int` and `String` are (M2-005's disjointness); `Optional` of any other type is a type of no kind, as today. Every existing rule treats an optional value as a route value; three rules are added, and the two no-kind messages, which list the route-value types, name the new ones:
  - `handler takes one Optional route value; route must declare exactly one query parameter and no path parameter` (`get`, `delete`; one optional value, alone or before `Headers`, on a literal with another placeholder count or with a path placeholder), checked where the one-value placeholder count is;
  - `handler takes one Optional route value and the request body; route must declare exactly one query parameter and no path parameter` (`post`, `put`, `patch`; `def(Optional[V], B)`), checked where the one-value placeholder count is;
  - `an Optional route value binds a query parameter; route values bind the path parameters first, then the query parameters` (both families; two values whose count matches, one of them optional at a path position), checked right after the two-value placeholder count;
  - reworded: `a get handler's parameter is an Int or String route value, an Optional of one, the request Headers or, for a raw handler, the Request` (and its `delete` form), and `a post handler's parameter before the body is a route value: an Int, a String or an Optional of either` (and its `put` and `patch` forms), as M3-019 reworded them to name `String`. Neither old text is a substring of its new one, so every fixture that quotes an old text fails until it is re-pinned;
  - unchanged: an optional value in `post`'s body position gets the `FromBody` messages it gets today (measured below), because only an `Int` there has its own message; every other message, the distinct-query-keys rule last.
- **Capture and transport.** `App.handle` gathers each query value in the literal's order, as today; for a key whose value binds an optional slot, an absent key or an empty value appends the empty string instead of answering 400, and anything else is decoded as today. A decoded value is never empty, so the empty string in the adapter's arguments means absent without a second channel. The adapter's optional slot gives `None` for it and otherwise converts the text as the required slot of its type does.
- **Typed function values and forwarding** reach an optional slot as they reach the others (measured): a typed value spells it `var Optional[Int]`, and a helper generic over its slots forwards it. That is the forwarding amendment's "a new slot kind" condition (M3-015), met without a change.

**Measured premises.** On Mojo 1.1.0, against `main`'s `src` and a scratch copy of `src/muntin` with the two kinds, the adapter conversion and a capture that passes absent or empty values on:
- A handler with a default parameter value (`def list_items(limit: Int = 20)`) registers on `/items?{limit}` as a required `Int`: `/items?limit=5` is 200 and `/items` is 400, the default never used. On `/items`, with no placeholder, it is `handler takes one Int parameter; route must declare exactly one path or query parameter`. A defaulted parameter cannot be detected at registration (Mojo 1.1.0 reflects no function parameters), so it stays a silent hazard; DX states it.
- `A == Optional[Int]` and `A == Optional[String]` classify a generic `var A` slot at compile time, the one rebind site converts to them under `comptime assert A == T`, and `get` (`def(Optional[Int])`, `def(String, Optional[String])`, `def(Int, Optional[Int], Headers)`, stateful `def(State[S], Optional[Int])`) and `post` (`def(Optional[String], B)`) register through the existing overloads. For optional values the answers are the examples' (absent, `limit=`, `limit`, a present and an escaped value give `None` or the value; `x` and a repeated key are 400), through a typed function value and a generic forwarding helper too. The scratch capture passed every absent or empty value on, so a required value beside an optional one, and the per-key capture the slice specifies, were not exercised; the slice's tests cover them.
- On `main`, `def(Optional[Int])` on `get` `/items?{limit}` is the no-kind message and on `post` `/x` the body message (`the handler's parameter is the request body; its type must conform to FromBody`); `Optional[Optional[Int]]` is the no-kind message with and without the kinds.
- A default in the literal (`?{limit=20}`, candidate B) can be checked against `Int` at registration: a compile-time function over the literal rejects `{limit=2x}` with its own `comptime assert` message.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A. `Optional[Int]`/`Optional[String]` route values, query placeholders only, absent or empty is `None`, repeated is 400 | **chosen** |
| B. a default in the literal (`?{limit=20}`) with a plain `Int` or `String` parameter | rejected: the handler's type matches DX's `limit: Int`, and the default can be checked at registration (measured), but it cannot express absence: "no `tag` filter" has no default value, since a value is never empty. Its default is a compile-time constant, never one computed from `State`. It puts a value of the handler's logic in the route text, which needs its own grammar (`=` inside an item, the encoding of the default) and a conversion of that text on every absent request. A covers each of its uses with `or_else`. A literal default is additive beside A, so it is a revisit condition (a schema that publishes defaults) |
| C. a Mojo default parameter value (`limit: Int = 20`) | not expressible on Mojo 1.1.0 (measured): the default does not travel with the function value, and reflection cannot read it |
| D. an application conversion trait for optional text | rejected: application route-value types are a separate candidate (M3-018 rejected a conversion trait for route values), and absence would still need A's capture rule |
| E. optional path values (`Optional` at a path position accepted, always `Some`) | rejected: the type would promise an absence that cannot occur, and the rule that rejects it also catches a required-optional swap. `/items` and `/items/{page}` are two routes today |
| F. empty value as 400 for an optional value (M3-018's rule kept) | rejected: a blank form field arrives as `name=` and means "not given"; 400 would make every optional field of a form-driven search fail when left blank |
| G. empty value as `Some("")` for `Optional[String]` | rejected: M3-018 made a value non-empty for every route value, and its reason holds (an empty segment never matches, an empty value is no value); it would also give `Optional[Int]` and `Optional[String]` different rules for one input. A revisit condition |
| H. a repeated key as the first value, or a list | rejected: a repeated key stays ambiguous (M2's rule); several values for one key are a multi-value candidate of their own |
| defer | rejected: a typed handler cannot serve any URL scheme with an optional query item, and the raw workaround re-implements Muntin's private query parsing and decoding |

**M2 contract: amended, not reopened.** The contract's "missing/duplicated/empty/invalid query value ... is 400 before the handler" stays true for every required value, and no route registered today has an optional one. By kind, as M3-022 classified:
- **Accepted set: expanded only.** Handlers with an `Optional[Int]` or `Optional[String]` parameter, rejected at compile time today, register; no handler that registers today is rejected or registers differently.
- **Overload set: unchanged.**
- **Rejected-call diagnostics: specific ones change.** The two no-kind messages are reworded to name `Optional` (every fixture that pins them is re-pinned); a call with an `Optional[Int]` or `Optional[String]` parameter that got the no-kind message now registers, gets one of the three new messages, or gets the existing message of the next rule it breaks, as a call with an `Int` or `String` there does (a `Headers` not last, three route values, a placeholder count, `Int` as the body, the last body type, a repeated query key). No existing fixture has such a parameter, and every other message is unchanged.
- **Runtime: unchanged** for every route registered today; for an optional value, an absent key or an empty value reaches the handler as `None` instead of 400, which is new behavior on new routes only.

**Invariants:**
- A route value is `Int`, `String`, `Optional[Int]` or `Optional[String]`, by exact type equality; at most two per handler, bound in the literal's order; an optional one binds a query placeholder.
- A value is never empty: for a required value an absent key or an empty value is 400, for an optional one `None`; a repeated key, an invalid escape, non-UTF-8 text or a non-integer `Int` is 400 for both.
- Eight overloads per method name, unchanged; every existing message other than the two reworded no-kind messages is unchanged.
- Capture stays in `App.handle`, decoding once; raw handlers and `Request` undecoded.

**Cost.** Two more slot kinds through `_kind`, both rule functions and `_slot`, and three more messages; the reworded no-kind messages re-pin every fixture that quotes them. `?q=` and no `q` are indistinguishable to an application, so a route that must tell "absent" from "empty" (an update that leaves a field unchanged when its key is absent) uses a raw handler. A defaulted handler parameter still registers as required, silently (no reflection). Two query values of one type swapped by the handler still bind silently (M3-022); only a required-optional swap across a path position is caught.

**Revisit when:**
- Mojo reflects function parameter defaults or names: revisit DX section 3's `limit: Int = 20` as a form beside `Optional`, and diagnose defaulted parameters;
- a schema or OpenAPI output is decided: revisit a literal default (B), which a schema can publish;
- applications need an empty value distinct from an absent one (an absent key meaning "unchanged" and `q=` meaning "empty"): revisit G for `Optional[String]`;
- applications need several values for one key (`?tag=a&tag=b`): a multi-value candidate, which also revisits H;
- application route-value types or a conversion trait are decided: `Optional` of such a type;
- a backend delivers a decoded target or drops empty query pairs: re-check the capture rule.
