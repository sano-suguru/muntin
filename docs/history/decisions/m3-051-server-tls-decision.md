# Server TLS decision (M3-051)

> **Current.** Now described in [serving reference, "HTTPS"](../../reference/serving.md#https) and [ARCHITECTURE, "Flare adapter"](../../ARCHITECTURE.md#flare-adapter).
> Changed in part since:
> - [M3-060](m3-060-tls-with-workers-decision.md): extended TLS to serve[make] workers, which this record left out of scope.
> Its pointers into documents that were split or renamed since (`docs/DX.md`, old `docs/ARCHITECTURE.md` headings) are mapped in [the list of records](../architecture-decisions.md#documents-older-records-cite).

Status: **decision and production** (M3-051, pull request to be linked on merge; `src/muntin` unchanged). Measurements, the mutations the tests catch and the review are in the pull request.

**Question and what settles it.** Can an application built with Muntin be served over HTTPS without changing its code, and if so how does it hand `Server` a certificate and key (M3-032's revisit condition "applications need a backend limit or protocol setting changed (body size, timeouts, TLS)")? It is settled by a public spelling that keeps Flare and OpenSSL types out of application code (A1, A2), and by real TLS connections on Linux and macOS showing: the same `App` answering over HTTP/1.1 and HTTP/2; a wrong certificate or key raising at `bind`, naming what is wrong; and `max_body_bytes`, `idle_timeout_ms` and the stop behaving as in cleartext. Out of scope: HTTP/3, obtaining or renewing certificates, mTLS, and TLS with several workers.

**Choice: a `Tls` value passed to `Server.bind`.** `Server.bind(host, port, *, ..., tls: Optional[Tls] = None)`, with `Tls(*, cert_file: String, key_file: String)` a value type of the adapter module; without `tls`, `bind` is unchanged. Flare v0.12.0 already serves TLS on its one reactor (`HttpServer.bind_tls(addr, cert, key, alpn, config)`), with the handshake on the reactor and ALPN choosing its HTTP/1.1 or HTTP/2 handle, so the same `ServerConfig`, `serve` and `drain` apply and nothing else in the adapter changes. The pair is one value because neither half means anything alone: a value with two required keyword-only fields cannot be given half, or swapped by position, which keyword arguments of `bind` would leave to a runtime check. The adapter offers `h2` then `http/1.1`, the protocols its cleartext listener serves. Flare's load failure carries no reason ("flare_ssl_ctx_new_server failed (see TLS error log)"; OpenSSL's reason is held only by Flare's private C helper `flare_ssl_last_error`), so before calling Flare `bind` reads both files (opened once with `O_NONBLOCK` and read no further than one byte past 1 MiB, so the common wrong paths, a device or a FIFO, do not stop or exhaust start-up, with no file type asked for; a slow disk can still delay it; both files' read buffers are wiped with volatile stores, which is not a guarantee that no copy of the key stays in process memory: OpenSSL's own copies and any temporary copy the compiler or runtime makes are outside it) and names the one that cannot be read, is empty, holds no PEM certificate, or whose first private key block is encrypted (Flare sets no passphrase callback, so OpenSSL's default would ask on the terminal) or missing; Flare takes paths, so OpenSSL reads the files again and a file replaced in between is loaded unchecked, a limit the contract states rather than works around: the checks are a best-effort diagnosis of common mistakes, not a guarantee; Flare's load failure becomes one message naming both files and no cause, since the cause is not known. With no ALPN protocol in common, Flare's selection callback returns `SSL_TLSEXT_ERR_NOACK` and the connection is served HTTP/1.1, where RFC 7301 section 3.2 requires a fatal `no_application_protocol` alert; Muntin cannot change it, so the contract states it as a deviation and the test pins it. Contract: `docs/DX.md` section 1, "HTTPS".

**Rejected.**
- `cert_file=` and `key_file=` keywords on `Server.bind`: no new type, but one half alone builds and fails only at run time, and a later TLS setting would add a third loose keyword.
- `Server.bind_tls(host, port, cert, key, ...)`, Flare's shape: a second spelling that repeats every setting `bind` takes, against M3-032's one spelling.
- A Muntin TLS configuration type with versions, ciphers, ALPN or mTLS: Flare's `HttpServer` exposes none of them (`TlsServerConfig` belongs to `TlsAcceptor`, which the reactor does not use), so the fields could not be honoured.
- Passing Flare's error through: it names neither file nor reason, which fails the start-up requirement.
- Reading the file's type with `fstat` to name a device or FIFO: the standard library has no `fstat`, and reading `struct stat` by offset ties the adapter to each platform's layout; reading without blocking up to the bound gives the same safety with none.
- Closing the gap between the check and OpenSSL's load by copying the files to a private path and handing Flare the copy: it writes the private key to a second place, for a race only a file replaced during `bind` can hit.
- Serving cleartext and TLS from one `Server`: Flare binds TLS per listener, and one `Server` serves per process (M3-045); two processes do it today.

**Revisit when:**
- Flare's Mojo API takes the certificate and key as bytes, or a passphrase callback: check and load the same bytes, and drop the documented gap;
- Flare refuses a client whose ALPN list shares no protocol (RFC 7301): the test that pins the HTTP/1.1 answer fails, and the deviation leaves the contract;
- Flare's Mojo API exposes OpenSSL's reason for a load failure, or a TLS configuration on `HttpServer` (versions, ALPN, client certificates, session tickets): revisit the combined message and whether `Tls` gains fields;
- applications need certificate reload without a restart, mTLS, or cleartext and TLS from one process;
- TLS with several workers is wanted ([M3-049](m3-049-multi-worker-serving-decision.md) shipped workers and refuses a TLS `Server`, `adapters/flare/test_tls.mojo`): a separate item, to be shown with the same tests;
- `adapters/flare/test_tls.mojo` changes an observation after a Flare or OpenSSL upgrade (the ALPN chosen, an error's text, a setting's effect over TLS, a cleartext request answered on the TLS port).

**Next production slice (M3-051, in this item).** The slice is implemented with this record:
- `Tls` and `Server.bind`'s `tls` in `adapters/flare/muntin_flare.mojo`, checked after `idle_timeout_ms` and the host; `examples/hello_https.mojo`, built by `scripts/check_flare.sh`.
- `adapters/flare/test_tls.mojo`, run by `scripts/check_flare.sh` against PEM files it writes with the `flare` environment's `openssl`: HTTP/1.1 (with and without ALPN) and HTTP/2 over verified TLS connections, the verification itself (an untrusted CA and a host the certificate does not name are refused); a certificate's intermediate sent from `cert_file`; no answer to cleartext on the TLS port; each start-up message, the file checks before anything is bound, a device, FIFO, empty file, directory or oversized file refused without waiting, files of 16384, 16385 and 1048576 bytes accepted and 1048577 refused, every opened file closed once whatever `bind` does, `std.io.FileDescriptor` leaving the descriptor it wraps open, and the first private key block deciding; `max_body_bytes` over HTTP/1.1 (413) and HTTP/2 (reset stream, next stream answered); `idle_timeout_ms` on a connection that never handshakes and on an idle handshaken one; a request in flight answered through a SIGTERM stop, new connections refused, exit 0; a body that is not UTF-8 echoed byte for byte and `HEAD` answered with no content, over both protocols; Flare's ALPN deviation pinned. `scripts/check_flare.sh` also asks a TLS `Server` (`adapters/flare/tls_probe.mojo`, on a port the system chooses) with `openssl s_client`: TLS 1.0, 1.1 and a CBC SHA-1 cipher refused, 1.2 and 1.3 accepted.
