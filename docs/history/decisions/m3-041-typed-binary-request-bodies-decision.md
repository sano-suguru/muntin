# Typed binary request bodies decision (M3-041)

> **Current.** Now described in [bodies reference, "Binary bodies (`FromBytes`)"](../../reference/bodies.md#binary-bodies-frombytes) and [ARCHITECTURE, "Registration surface"](../../ARCHITECTURE.md#registration-surface).
> Changed in part since:

> - [M3-043](m3-043-typed-binary-request-body-size-limits-decision.md): FromBytes gained a required `comptime max_bytes: Int`; a longer body is 413 between the route values and from_bytes (M3-041 had no size cap).
> - [M3-048](m3-048-bodyless-typed-post-put-and-patch-handlers-decision.md): removed one of the diagnostics M3-041 re-pinned (diagnostic only).

Status: **decision and production** (M3-041). It decides how a typed handler receives a request body of any bytes as an application-defined type, which M3-040 left to "its own decision item", and implements the choice in the same item. The question and what settles it were committed before the design was chosen; the only measurement before them was a scratch probe of how Mojo 1.1.0 checks a static trait method's argument convention.

**Why now.** Since M3-040 `Request.body` is `List[UInt8]` and a raw handler receives any body, but a typed body is text only: `FromBody.from_body(String)`, `Json[T]` and `WithHeaders[B]` read the bytes as strict UTF-8 and answer 400 otherwise. An application that takes an image, a protobuf message or a signed binary payload must write a raw handler and lose typed route values, `State[S]` beside the body and the pre-handler 400, which is the typed API's reason to exist.

**Question.** How does a typed `post`, `put` or `patch` handler take the request body's bytes, whatever they are, as an application type converted before the handler, with the conversion checked at registration? Specifically: which of the candidates below (a new public conversion trait over bytes; a Muntin wrapper type over the bytes; `List[UInt8]` itself as a body parameter) is the smallest design that passes every body byte for byte to the conversion with no text read, no lossy step and no second representation of the body; what the conversion's argument convention is (borrowed, owned, a `Span`) and what Mojo 1.1.0 then lets a conversion do with the bytes (keep them without a copy, change them); what a type that is both a text and a bytes conversion means; which handler shapes take it (body only, route values then body, `State[S]` first) and which do not (`get` and `delete`, `WithHeaders[B]`); at which step and with which status a failed conversion answers, and in which order relative to the route values, middleware, 404 and 405; and what changes in the accepted set, the overload set, the diagnostics and the runtime of routes that register today, classified against M2-016.

**What settles it:**
- the body slot's path traced in code: `_kind`, `_get_rule` and `_post_rule`, `_check`'s messages, `_slot`'s body branch, `_route`'s flags, `_Erased.invoke(args, bytes)`;
- Mojo 1.1.0 facts measured with the installed toolchain: `conforms_to` on the new trait in `_kind` and in `_slot` (and calling its static method after the check without a bound); which conforming signatures the compiler accepts for each argument convention and what it reports for the others; a conversion that keeps a borrowed `List[UInt8]` without `.copy()` or mutates it; a non-raising conversion; a move-only conforming type; a type conforming to both traits;
- per candidate: the public API added, what an application writes for the canonical example (an image upload), the copies of the body per request (read from the code, not timed), and what a test or fixture can pin;
- the bodies, through `App.handle`, `TestClient` and middleware, on every shape taken: ASCII, Japanese UTF-8, empty, NUL, `0x80`, `0xFF`, the PNG signature and every byte value, compared by length and byte by byte at the conversion;
- the wire: the same Flare loopback that M3-040 runs, over HTTP/1.1 and h2c, with bodies that are not UTF-8 reaching the typed handler;
- negative evidence: scratch mutations of the changed code (a lossy or text read before the conversion, a truncated body, a conversion failure answered other than 400 or reaching the handler), each turning a listed test red.

**Boundaries that do not change silently:** `FromBody.from_body(String)` and every text body type (`FromBody`, `Json[T]`, `WithHeaders[B]`) answering every body exactly as today, the JSON order (415, 413, UTF-8 400, JSON 400) and the carrier's field rebuild before the UTF-8 read included; routing, 404, 405 and `Allow`, `HEAD`, the raw escape hatch and middleware; `Request.body` as the one body representation (M3-040); the Flare adapter's byte rules; the registration overload set. A change to any of them is named here, with its classification against M2-016.

**The path at the base** (read from the code): `_kind` classifies a body slot as `_BODY` when its type conforms to `FromBody` or the private `_HeaderCarrier`; `_post_rule` accepts `_BODY` in the last slot only, and `_get_rule` rejects it. `_slot`'s body branch runs the JSON steps (`_JsonBody`), the carrier's field rebuild (`_HeaderCarrier`), then `_body_text(body)` (strict UTF-8, 400 otherwise) and `A.from_body(text)` (400 on a raise). `_Erased.invoke(args, bytes)` already hands every adapter the request's body bytes, borrowed (M3-040), so a bytes conversion needs no new transport: the body slot has the `List[UInt8]` in hand before it reads text.

**Measured premises** (Mojo 1.1.0 `8189361e`, Linux; scratch probes, then the fixtures named below):
- `conforms_to(A, FromBytes)` in `_kind` and in a `comptime if` branch of `_slot` selects the type, and `A.from_bytes(body)` compiles in that branch with no trait bound on `A`, as `A.from_body` does after its `comptime assert`.
- A trait method `@staticmethod def from_bytes(body: List[UInt8]) raises -> Self` takes the bytes borrowed and read-only. A conforming type that stores them without a copy (`Self(body)`) is `value of type 'List[UInt8]' cannot be implicitly copied, it does not conform to 'ImplicitlyCopyable'`; one that mutates them is `invalid use of mutating method on rvalue of type 'List[UInt8]'`; one that declares `var body`, `mut body`, `body: Span[UInt8, _]` or `body: String` does not conform (`'T' does not implement all requirements for 'FromBytes'`, with a note naming the required type). A non-raising `from_bytes` conforms. A move-only type (no `Copyable`) conforms.
- A type may conform to both `FromBody` and `FromBytes`; `conforms_to` reports both.
- `WithHeaders[B: FromBody]` around a `FromBytes` type is rejected where the handler is declared: `'WithHeaders' parameter 'B' has 'FromBody' type, but value has type 'AnyStruct[Payload]'`.
- Fixture diagnostics: every must-not-build fixture of the base (411) was built against the base's `src` and this item's, the whole output normalized (repository root and toolchain path removed, `src/muntin` and `tests` line and column numbers replaced): 389 identical, and 22 differing only in the `constraint failed:` line, `must conform to FromBody` becoming `must conform to FromBody or FromBytes`; those 22 are the production fixtures whose expected text is re-pinned. `tests/extraction_fail/body_without_conformance.mojo` keeps its text: it pins the M2-005 extraction spike's own message, not production's. Each new fixture in `tests/from_bytes_api_fail`, built against the base's `src`, fails differently (`package 'muntin' does not contain 'FromBytes'`, or for `neither_conversion.mojo` the base's shorter message); none is a regression pin. `both_conversions_in_with_headers.mojo` builds against this item's first implementation, before review added the carrier rule.

**Candidates.**

| Candidate | Verdict |
|---|---|
| A: a public trait `FromBytes` with `from_bytes(body: List[UInt8]) raises -> Self`, the bytes borrowed, accepted in the body slot beside `FromBody` | **chosen**: the application names its type and owns the format, as with `FromBody`; registration checks the conformance at compile time; Muntin passes `Request.body` itself, so there is no copy, no text read and no second representation; it adds one name and no shape |
| A': the same trait taking the bytes owned (`var body`) | rejected: `App.handle` holds the request borrowed, so Muntin would copy every body to hand it over, including for a conversion that only parses; with a borrow, a conversion that keeps the bytes copies them itself and the compiler enforces it (`cannot be implicitly copied`) |
| A'': the same trait taking `Span[UInt8, origin]` | rejected: a generic origin in a static trait requirement for no gain here (a `List` borrow already gives `Span(body)`), and a conformance must then spell the origin parameter |
| B: a Muntin wrapper type over the bytes (`Bytes`, a body that holds a `List[UInt8]`) | rejected for this item: it would be one fixed type with no conversion, so the application's format check would move into the handler and a malformed body could no longer be 400 before it; the same behavior is four lines of an application `FromBytes` type. A Muntin-provided bytes type stays possible later on top of A |
| C: `List[UInt8]` itself as a body parameter | rejected: `List[UInt8]` is the raw body representation; as a typed body it would be a third route-value-like kind by exact type equality with no conversion step (the format check moves into the handler, as in B), and Muntin would copy the body to give the handler its owned slot. `tests/body_bytes_api_fail/bytes_body_parameter.mojo` (M3-040) stays a must-not-build fixture, with its message re-pinned |

**Selected: A.**
- **Public API.** `muntin.FromBytes`, beside `FromBody` in `src/muntin/body.mojo`: `trait FromBytes(Deinitable, Movable)` with `@staticmethod def from_bytes(body: List[UInt8]) raises -> Self`. Nothing else is added or changed; `FromBody.from_body(String)` is unchanged.
- **Registration.** `_kind` gives a `FromBytes` type the body kind, so every shape that takes a `FromBody` body takes it, on `post`, `put` and `patch` (body only, one or two route values then body, stateless or with `State` first, either result policy), and `get` and `delete` reject it as a body. A type conforming to both traits is a kind of its own (`_TWO_BODIES`), and so is a `WithHeaders[B]` around one (the carrier converts with `from_body`, so accepting it would pick a conversion silently; the private `_HeaderCarrier._two_conversions` reports it to `_kind`): the rules treat it as a body everywhere, and in the body position report `the request body's type conforms to both FromBody and FromBytes; a body type conforms to one of them`, so Muntin never chooses a conversion silently. The three body-type messages name both traits (`must conform to FromBody or FromBytes`). The overload set is unchanged.
- **Conversion.** `_slot`'s `FromBytes` branch calls `A.from_bytes(body)` on the bytes `invoke` borrows from the request (after middleware, so a replaced body is what it receives), before any text step; a raise is `_Reject(400)`. A `FromBytes` type is never a JSON body or a carrier, so `App.handle` appends nothing for it and no `Content-Type` or size rule applies. Order: 404 or 405, the route values (400), `from_bytes` (400), the handler.
- **Not included.** `WithHeaders[B]` keeps `B: FromBody`: extending it to bytes would change its public parameter bound and `_HeaderCarrier._from_parts(String, Headers)`, a public-contract change of its own, so a typed bytes body with the header fields is not supported (pinned) and a raw handler reads both. No Muntin bytes type, no size cap, no `Content-Type` rule.
- **Copies of the body per request** (read from the code, not timed): a `FromBytes` route, none by Muntin (the conversion's own `body.copy()` if it keeps the bytes); every other route as in M3-040.

**M2 contract: amended, not reopened.** The contract's typed body is "an application-defined `B: FromBody`" converted "by `B.from_body`", and M2-016 reopens on a changed M2 signature or semantics, not an addition; this item adds a body trait beside `FromBody` and changes no M2 signature, binding rule or answer. By kind:
- the accepted set only grows: a `FromBytes` body registers on every body shape; no handler that registered is rejected or registers differently;
- the overload set is unchanged;
- specific rejected-call diagnostics change: `the handler's parameter is the request body; its type must conform to FromBody`, `the handler's last parameter is ...` and `Int is a route-value type, never the request body; the body parameter's type must conform to FromBody` end in `FromBody or FromBytes`, and the two-conversion message is new;
- runtime: every previously valid route answers as before, text bodies, `Json[T]`, `WithHeaders[B]`, raw handlers, middleware, 404, 405, `HEAD` and the Flare adapter included.

**Invariants:**
- A `FromBytes` conversion receives exactly the request's body bytes as `App.handle` holds them after middleware: no step reads them as text, replaces, drops or adds a byte, or copies them before `from_bytes`.
- A body type has exactly one conversion: registration rejects a type that conforms to both traits, alone or in a carrier.
- The bytes are borrowed and read-only in `from_bytes`: a converted value never aliases `Request.body`, and a conversion cannot change it.

**Cost.** One public trait; three diagnostics read differently (every fixture that pins them re-pinned to the full text) and one is new; a `FromBytes` type cannot be used with `WithHeaders`; an application that wants the raw bytes in the handler writes a small `FromBytes` type that copies them.

**Revisit when:**
- applications need a typed bytes body with the header fields (`WithHeaders[B]` over a `FromBytes`, which changes its bound and `_from_parts`), a Muntin-provided bytes body type, an owned or `Span` conversion input, or a size cap or `Content-Type` rule for bytes bodies;
- streaming bodies are taken up (M3-040's condition);
- Mojo changes how a borrowed argument of a static trait requirement may be kept or mutated (`tests/from_bytes_api_fail/from_bytes_keeps_borrowed_bytes.mojo` or `from_bytes_mutates_bytes.mojo` builds).
