# Deferrals

A decision to build nothing now, with no decision record (`docs/DEVELOPMENT.md` section 2), binds later items through its revisit condition, so that condition is kept here, versioned with the code it constrains. So are conditions a withdrawn design sets on its successor. Each entry is the choice, why, the revisit condition and its pull request; the discussion stays in the candidate's GitHub issue, which links the entry. The entries written before the candidates moved to issues keep the text `docs/SPEC.md`, "Remaining candidates", gave them.

## Linear request header conversion

Issue [#140](https://github.com/sano-suguru/muntin/issues/140); measured in [pull request #110](https://github.com/sano-suguru/muntin/pull/110).

The adapter's check of the fields it rebuilds costs fields × distinct names comparisons inside Flare, bounded since M3-067 by `Server.bind`'s `max_header_fields` (100 unless set; [M3-066](decisions/m3-066-request-header-conversion-decision.md)). A conversion through an ordered field accessor on Flare's `HeaderMap`, which would make raising the limit cheap, waits on Flare (pull request #119 drafts the proposal) and then a pin change.

## Spreading kept-open connections over workers (M3-069)

Issue [#155](https://github.com/sano-suguru/muntin/issues/155); [pull request #137](https://github.com/sano-suguru/muntin/pull/137), measured by [pull request #109](https://github.com/sano-suguru/muntin/pull/109).

[M3-068](decisions/m3-068-worker-connection-spread-decision.md) keeps the shared listener. M3-069 adopts none of its candidates, because re-registering the listener after each accept batch, Flare's `EPOLLEXCLUSIVE` fix (29550b6) alone and a `SO_REUSEPORT` listener per worker each raise how often a connection opened as a slow request is sent waits for it over the pin's, which M3-068's rules do not allow, and accept budgets changed nothing measured. Revisit when Flare rebalances its shared listener, or before the pin moves to a release carrying 29550b6, which that comparison measured as a regression (every connection opened in turn on one worker).

## Connection cap for `Server`

Issue [#156](https://github.com/sano-suguru/muntin/issues/156); [pull request #131](https://github.com/sano-suguru/muntin/pull/131).

A connection cap for `Server` (`max_connections`, counted for the whole `Server`) is deferred by pull request #131, which built it on Flare v0.12.0's per-reactor `max_connections` and measured that while a connection waits over the cap each full reactor spins a CPU core (its level-triggered poll keeps returning the readable listener), so the cap, a load control, would exhaust CPU in normal use; fixed per-worker shares also leave a free slot on one worker unusable by another. Revisit when Flare (a pin change, decided separately) stops polling the listener at its cap and accepts again once a slot frees, shown with no spin while connections wait, waiting connections accepted on several workers on Linux and macOS, and the graceful stop and TLS handshakes unchanged; fixed shares against a shared counter are compared then.

## Request context over a closed type (M3-065)

Issue [#151](https://github.com/sano-suguru/muntin/issues/151).

[M3-065](decisions/m3-065-request-context-storage-decision.md) found no sound storage for [M3-063](decisions/m3-063-request-context-decision.md)'s open `set(value^)` on Mojo 1.1.0 and withdrew it: a context value's type is a type parameter that its writer and its readers share. A decision item chooses the shape and decides the API again: `App[Ctx]` (reopens [M3-001](decisions/m3-001-application-state-decision.md)), or a typed group of routes and middleware moved into the `App` (with per-group middleware). The group is a candidate only if one of these holds, since otherwise the `App` erases it and a group type that borrows a local would read freed memory, as a `State` did before [M3-074](decisions/m3-074-state-borrowing-decision.md): the group's origins are part of the `App`'s type; the compiler keeps a group that borrows from being stored; or only group types that borrow nothing are accepted, enforced at compile time (M3-074's rule is one such check). Whichever shape is chosen, that its context is sound is a premise the decision verifies along the whole path, under AddressSanitizer: the `App` owning the context, a middleware writing it, `Next` passing it on, the handler reading it, and the drop order at the end. No `Context` ships before it.

## Closing `State`'s `AnyOrigin` hole

Issue [#173](https://github.com/sano-suguru/muntin/issues/173); [pull request #175](https://github.com/sano-suguru/muntin/pull/175).

[M3-074](decisions/m3-074-state-borrowing-decision.md)'s check reads `S`'s name, and a pointer built with `AnyOrigin` behind a trait's associated type stays out of it (`tests/state_known_gaps/state_any_origin_associated_type.mojo`); the same pointer registers inside an `Optional`, a `List` or a `Tuple` field of the application's own struct (`state_any_origin_in_optional.mojo`, `_in_list.mojo`, `_in_pack_field.mojo`), and each reads freed memory under `scripts/run_origin_gaps.sh`. No check is added, because on Mojo 1.1.0 none can refuse these and still admit owned states: walking the field types reaches the pointer, but it prints `{}` like the untracked pointers inside `List`, `String` and `ArcPointer`, and generic code cannot tell `AnyOrigin` from those (`tests/state_fail/state_any_origin_*.mojo`: `Origin.equals` only in a `where` clause, no overload selected by one, a type comparison that ignores origins); packs stay closed to reflection, so the `Optional` and `Tuple` forms would pass even then. Refusing application-defined generic structs and packs in fields stops the four reproductions, but refuses owned states such as `Cache[Item]` and M3-074's own migration (`struct Pair: var value: Tuple[...]`), without showing that nothing else gets through. Revisit when Mojo refuses a field whose type exposes `AnyOrigin` through an associated type (the four known gaps stop building or reporting: remove them and this entry), or when a `state_any_origin_*` fail fixture builds and generic code can also reach a pointer's pointee and a pack's elements: then weigh a check of the field types that refuses `AnyOrigin`.

## Extensions while Muntin's value is evaluated

The owner's request in pull request #166, after an outside review of `44ab303`.

The review found that what Muntin saves an application is shown only by one small comparison API that stores nothing, and asked that the benefit be shown before the surface grows. So no candidate in `docs/SPEC.md`, "Remaining candidates", starts, nor any other extension (OpenAPI, a second network backend, Muntin's own async execution), until four items have merged: the README states what Muntin is for and its serious limits (pull request #166); the AddressSanitizer check runs in CI; one application closer to real work (stored data, an authenticated user, a failing external call, start-up configuration, one change of requirements) is written with Muntin and with Flare alone, which takes up candidate 2's question; and what Muntin adds over Flare is measured again on the code of that time. Not frozen: fixing what that application gets stuck on, and every correctness or safety fix, listed as a candidate or not (candidate 1, `Host` value validation, is one). Revisit when the four have merged and a written evaluation records whose work Muntin made easier, the performance results, and for safety both what the checks cover and the known gaps they do not (such as those `scripts/run_origin_gaps.sh` expects to read freed memory); the owner then decides whether to resume the candidates or narrow Muntin's scope, and this entry and `docs/SPEC.md`'s note are replaced by that decision.
