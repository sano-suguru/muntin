## Easy to miss

- Each registration method (`get`, `post`, `put`, `patch`, `delete`) has eight overloads (slot arities 0 to 3). `put` and `patch` are copies of `post` and use `_post_rule`; `delete` is a copy of `get` and uses `_get_rule`. A rule or message change to a shape family therefore applies to every method in it, and `_check` builds each method-naming message from the method's lowercase name. A new shape is a slot kind or a rule in `_get_rule`/`_post_rule` plus its message in `_check` (where they live: `docs/ARCHITECTURE.md`, "Modules and public surface"), not an overload; keep the rule order that preserves existing messages. Route values are decoded once in `App.handle`, at capture (path captures, then `_Route.query_keys` in the literal's order); a slot converts decoded text and never decodes. For a key whose value binds an `Optional` slot (`_Route.query_optional`), an absent key or an empty value is passed on as `""`, which no decoded value is, and the slot reads it as `None`. The distinct-query-keys rule runs in `_rule` after the family rule accepts. Slot arity 4 would add two overloads to every method name and reach ten per method, Mojo 1.1.0's note cap.
- The route-literal grammar's structure is the primitives in `src/muntin/_registration_rules.mojo`: `_split_literal` decides the path/query boundary (the first `?`), `_path_part` and `_query_items` (split at `&`) read it, `_is_param` checks only a placeholder's outer shape (`{`, a non-empty interior, `}`; `{a}b}` passes), and validity is the parsers' and `_param_name` strips its braces. The rules' parsers (`_path_params`, `_query_params`, `_distinct_query_keys`), `_Route.__init__` and `_match` read the literal through them. Two pieces are still known twice: the brace shape (`_is_param` and `_param_name`) and the `/` separator (`_path_params` and `_match`, which splits the request path with it too); `tests/test_route_literal.mojo` checks that each pair agrees, that the three readers agree on a table of well-formed literals, and that the parsers reject the malformed forms. Validity (which bytes a name or key may hold, a leading `/`) is the parsers' alone.
- `HEAD` is answered by `GET` routes in `App.handle`, body included; the content is dropped and the length declared by the network backend (the adapter's `_serve_app`, at every exit, not `to_flare_response`, which takes no method). A change to what a `get` route answers changes its `HEAD` answer too, and a new backend inherits the framing duty (`docs/ARCHITECTURE.md`, "Backend seam"). `TestClient.head` is an in-memory caller of `App.handle`, not a network backend: it returns `App.handle`'s answer unchanged, body included, so a test of what goes on the wire for `HEAD` belongs to the adapter's tests.
- When the scan selects no route, `App.handle` scans again with `_allowed`, which reads only each route's method and path through `_match`: 405 with `Allow` if any route's path matches, else 404. A change to `_match`, to the method rule or to how routes are stored changes `Allow` too; `tests/test_method_not_allowed.mojo` checks, for each probed method, that a listed one selects a route and any other gets 405.
- `App.handle` is the middleware chain (`_run`) in front of `_dispatch`, which holds the route scan, the 400s, 404, 405 and the handler call. A change to Muntin's own answers goes in `_dispatch`; middleware sees and may change every one of them, so DX and ARCHITECTURE describe statuses as Muntin's own answers, and a 405's `Allow` as Muntin's. With middleware registered the request is copied once in `handle` and never again; a new copy per layer is a regression. A raise is caught around each middleware call, not around the whole chain (`tests/test_middleware.mojo`), and `tests/middleware_api_fail` pins `Next`'s once rule against production.
- `check_unsafe.sh` requires exactly one `rebind_var[` in `src/muntin`, comments included: write "the rebind" in prose.
- `check_flare.sh` builds the two binaries that reach Flare's `HttpClient` (the round trip and the JSON probe) without `--Werror`, because Flare v0.12.0 warns on one line of its own source (`KNOWN_WARNING`). Any other warning fails them, and so does that warning disappearing: then build them with `--Werror` again. Every other build in that parallel step is `--Werror`.
- The Flare adapter has two handlers, `MuntinHandler` (owns the `App`; the adapter's tests and probes) and the private `_BorrowedHandler` (`Server.serve`), and both answer only through `_serve_app`: an adapter answer change goes there, and the loopback suite, which serves through `Server`, then covers the borrowed path. `_BorrowedHandler` stays non-`Copyable` (`compat/flare/serve/server_handler_not_copyable.mojo`).
- `Request.body` and `Response.body` are `List[UInt8]`, the one representation of a body (M3-040): never add a `String` copy, cache or tag beside it. `text()` is strict UTF-8 and raises; a typed text body slot reads the bytes with `_body_text` (400 if not UTF-8) right before `from_body`, and a `FromBytes` body slot (M3-041) passes the borrowed bytes to `from_bytes` with no text step and no copy: keep it so (no `_body_text`, no copy before it). A body type conforms to one of `FromBody` and `FromBytes` (`_TWO_BODIES` is rejected), alone or in `WithHeaders[B]`, whose bound is their private parent `_FromBodyOrBytes` (M3-042): `_HeaderCarrier._from_parts` takes the borrowed bytes and converts them as a bare `B` does (`from_bytes` unread, or `_body_text` then `from_body`), and `_conversions` counts the two traits for `_kind`. Every `FromBytes` type must declare `comptime max_bytes` (no default; `Int.MAX` is no limit, M3-043), so a new bytes type in a test or fixture needs the line (or inherits it from a refining trait's default) or it fails with `required member 'max_bytes' is not specified`, which would also mask a fixture's intended diagnostic. It is checked in `_slot` with `len(body)` only, after the route values and, for a carrier (`_HeaderCarrier._max_bytes`), after the JSON steps and before the field rebuild: 413, nothing converted; a negative one is `_NEGATIVE_LIMIT` in `_kind`. The same member on a `FromBody` type is silently ignored, and the limit is never a receive limit (Flare buffers the body first). A bound or name change to it changes the compiler's text in three `tests/with_headers_api_fail` fixtures. The body never travels in the `List[String]` raw arguments: `_Erased.invoke(args, bytes)` passes it beside them, so a JSON route's verdict sits at the body's position and `_raw_request` rebuilds from method, path, query, header pairs and the bytes. The Flare adapter copies body bytes both ways unchecked. It builds the method and target with `String(from_utf8=)` from `as_bytes()` (M3-039): over h2c Flare builds them with `String(unsafe_from_utf8=)`, and on Mojo 1.1.0 a `String` slice that starts on a continuation byte aborts the process, so nothing may search, split or slice a Flare string before that check (`_serve_app`'s `==` with `HEAD` only compares bytes). Every `String` the adapter hands `App.handle` is UTF-8; keep it so for any new request part. No lossy conversion may decide what reaches `App.handle`: Flare's `Request.text()` replaces bytes with U+FFFD silently (`to_muntin_headers` decodes lossily only to parse, then checks every field against Flare's own view).
- `Server.bind`'s `max_body_bytes` (M3-044) must reach both of Flare's fields: `ServerConfig.max_body_size` is HTTP/1.1 only, and h2c reads `ServerConfig.h2.max_body_size`; `_server_config` sets both, and the loopback cases fail if either is left at Flare's default. Its range and the per-protocol refusals come from Flare v0.12.0's code (the record's "Revisit when" lists what to re-measure when the Flare pin moves). A refusal there happens inside Flare, before `_serve_app`: never call `App.handle`'s 413s (`FromBytes.max_bytes`, `Json[T]`) a receive limit, and tell the two apart in tests by middleware fields and counters, not the status. It is an upper bound, not a promise to accept every body within it (Flare's HTTP/1.1 buffered-bytes check, shown at its exact threshold by `h1_buffered_threshold`). The loopback wire helpers tolerate only `ConnectionReset`/`BrokenPipe` (`_is_reset`); a timeout is a failure. Flare's `FLARE_BUFRING_HANDLER=1` loop is unsupported and `Server.serve` refuses to start with it (`docs/DX.md` section 1); `test_receive_limit_on_flare_bufring_path` pins the loop's defect on Flare's own `HttpServer` and needs io_uring on Linux under `CI`. When the Flare pin moves, the refusal's message names the version.
- `Server.serve` owns the SIGTERM and SIGINT handlers while it runs (M3-045): `_StopWatch` installs a do-nothing handler with `SA_RESETHAND`, and a watcher thread (`_watch_for_stop`) reads the dispositions to see a signal, then calls Flare's `drain`. Nothing may be added to the handler (it runs in signal context, and Mojo 1.1.0 has no globals), and nothing in the watcher may touch the `App`. The `struct sigaction` values, the one-`serve`-per-process claim and the `_stage` test hook are described in `docs/ARCHITECTURE.md` ("Graceful shutdown"): a new supported system needs its values before the `comptime assert` admits it, a test that serves twice in one process must let the first `serve` end first, and the stop tests rely on the `_stage` calls staying where the `_STAGE_*` docstrings say. A test that sends a stop signal must reap the child with `_reap_within` (a bound, then SIGKILL), and the stop tests' timings assume Flare's 100 ms poll and 500 ms idle timeout.
- `adapters/flare/test_server.mojo`'s head-of-line blocking tests (M3-046) hold a handler for `HOLD_PROBE_MS` (1 s), longer than Flare's default `idle_timeout_ms` (500 ms) on purpose: the default-configuration cases assert that waiting keep-alive and h2c requests are dropped, the `_FLARE_PATIENT` cases (60 s idle timeout) that they are only serialized. Progress is asserted by the order pipe, read after the child has ended; a `Server` child must stop on SIGTERM with exit 0. If a Flare upgrade makes them fail, the observation changed: revisit the record and `docs/DX.md` section 1 rather than the test.
- `TestClient` adds no header field: a JSON body route answers `client.post(target, body)` (or `put`, `patch`) with 415 unless the test passes `headers=`. `post`, `put` and `patch` each have a text and a bytes (`List[UInt8]`, moved) overload, so a rejected call to them lists two candidates. `TestClient.head` and `.delete` send an empty body; a test that needs a `HEAD` or `DELETE` body builds the `Request` and calls `App.handle`.
